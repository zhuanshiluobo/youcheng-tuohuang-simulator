# 新架构任务共同执行约束

你正在 `G:\NoMadCity` Unity 项目中实施 Lua Effect 树与回合主链新架构。本文是所有 `NMC-xxx` 任务的强制共同约束；具体任务提示词在此基础上增加范围和验收条件。

## 一、权威文档与冲突处理

开始前完整阅读：

1. `AGENTS.md`
2. `docs/设计/Lua效果树与回合主链设计.md`
3. `docs/设计/Lua效果系统API初稿.md`
4. 当前任务提示词列出的代码和补充文档

`docs/设计/命令与效果系统准备规范.md` 已废弃，只能作为历史背景。与它冲突时始终采用两份 Lua 文档。若两份 Lua 文档彼此冲突，或实现需要新增未定义的规则语义，停止扩大修改并清楚报告冲突，不自行发明业务规则。

## 二、工作区与删除安全

- 先运行 `git status --short`，区分用户已有改动与本任务改动。保留所有无关修改和未跟踪文件。
- 禁止批量、递归或通配符删除。不得使用 `del /s`、`rd /s`、`rmdir /s`、`Remove-Item -Recurse`、`rm -rf`。
- 每次只能删除一个已经核对引用的明确文件；Unity `Assets` 下删除脚本或资源时，也要逐个检查和处理对应 `.meta`，不得批量清理。
- 不使用 `git reset --hard`、`git checkout --` 或其他会覆盖用户工作的命令。
- 不因为测试失败而删除测试。先判断是回归、过时合同还是环境问题。
- 不提交 Git commit，除非用户明确要求。

## 三、架构实施原则

- Host 是唯一权威规则执行者；Lua 不能直接修改 `GameState`、创建 Unity UI 或持有 C# 可写对象。
- `YC.Domain` 和 `YC.Application` 保持 `noEngineReferences = true`；不要为了方便把 UnityEngine、MoonSharp/xLua 等第三方运行时引用塞进 Domain。
- 新旧架构迁移期间，同一规则只能有一个推进或结算源。兼容投影可以保留读取能力，但不能让旧状态机与新执行器同时推进。
- 修改调用关系后立即检查旧入口、旧分支、旧 pending 状态、旧事件和旧测试是否仍有引用。使用 `rg` 给出零引用证据后再逐个删除明确文件。
- 不保留没有明确移除任务和期限的“双写”“双跑”“临时 fallback”。确需过渡适配器时，在代码和任务报告中记录唯一调用方、停用条件与计划删除的后续任务编号。
- 使用稳定 ID、显式 DTO 和可序列化列表；不要引入 `Dictionary`、`object`、接口实例、Lua table 或 Unity 对象作为权威持久化字段。
- 对规则失败、合法无变化、部分完成和内核故障分别建模，不能用异常或布尔值混在一起。

## 四、测试精简共同要求

当前 EditMode 约有一千项。所有任务不仅要增加新架构测试，也要同步压缩本任务触及范围的旧测试。

执行前：

1. 记录本范围测试文件、Unity 实际发现数、耗时和失败项。
2. 建立简短行为覆盖表：规则不变量、最低成本测试层、现有重复测试、新架构替代测试。
3. 优先识别以下冗余：同一条件仅换 ID/玩家/资源类型的复制测试；Domain 已覆盖而 Presenter/Controller 再逐项复述的测试；逐资源或逐 Prefab 的重复 EditorAsset 测试；只验证字段赋值而没有独特规则风险的测试；已经被新执行器切断调用的旧实现测试。

修改时：

- 用 `[TestCase]`、`TestCaseSource`、场景数据表和共享 builder 合并同构测试。
- 规则不变量尽量放在无 Unity 依赖的 Domain 测试；Application 保留编排、事务和跨服务合同；Presentation/EditorAsset 只保留可见性、绑定、资源存在性和少量代表性冒烟。
- 新旧测试覆盖同一行为时，保留新架构边界上的权威测试，删除或合并旧调用细节测试。
- 不追求一行生产代码对应一个测试；优先覆盖状态转换、事务边界、恢复幂等、权限和规则分支。
- 不用 `[Ignore]`、条件编译、重命名测试属性、移动目录等方式制造数量下降。
- 删除旧测试前在任务报告中写明替代测试；删除文件必须逐个明确执行并遵守 `AGENTS.md`。

任务完成时报告：测试文件数、Unity 实际发现用例数、通过/失败/跳过数、耗时，以及相对任务开始的净变化。若新增功能后用例数反而显著上升，解释为何不能通过参数化或上移到更低成本层解决。

## 五、Unity 测试命令

必须显式使用用户提供的 Unity，不使用测试脚本的默认版本：

```powershell
powershell -ExecutionPolicy Bypass -File .\tools\Run-EditModeTests.ps1 `
  -UnityPath "D:\2022.3.62f1c1\Editor\Unity.exe" `
  -ProjectPath "G:\NoMadCity" `
  -TestPlatform EditMode
```

开发中先用 `-TestFilter` 跑本任务相关测试，提交结果前再按任务要求运行完整 EditMode。不得同时启动多个 Unity 实例操作同一项目。遇到 `Temp\UnityLockfile` 时严格遵守 `AGENTS.md`，先核对是否存在命令行包含当前项目路径的 Unity 进程。

如果 Unity 返回非零但 XML 已生成，必须读取 XML 与 Editor 日志判断真实失败原因。不得仅凭进程退出码宣布测试结果。

## 六、每项任务的标准流程

1. 阅读权威文档、任务提示词和涉及代码。
2. 检查工作区与前置任务产物；发现冲突先停止。
3. 跑目标测试基线并记录发现数。
4. 用最小可回退增量实现生产代码和迁移适配。
5. 同步改写、合并或删除本范围旧测试，维护行为覆盖表。
6. 搜索旧符号和旧调用入口，清理已无用途的残留代码。
7. 跑目标测试；任务要求时跑完整 EditMode。
8. 运行 `git diff --check`，审查只修改了任务范围内文件。
9. 输出：完成内容、关键设计决定、修改文件、测试数字、测试净变化、已删除残留、尚存适配器与风险。

## 七、统一完成定义

任务只有同时满足以下条件才算完成：

- 生产路径实际使用新架构，不只是新增了未接线类型。
- 同一规则不存在新旧双推进或双结算。
- 对应状态、Event、日志或交互能够序列化并恢复。
- 目标测试通过，且测试数量经过合并审查。
- 所有已失去调用方的旧代码和旧测试已逐项清理，或明确登记到后续任务且仍有真实调用方。
- 没有掩盖失败、吞异常、静默回退或只为测试暴露的生产后门。
