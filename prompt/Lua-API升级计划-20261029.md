## 1. 目标与范围

面向隔离开发 DIY 内容，统一“文档允许调用、Lua 实际暴露、编译器接受、内核执行、存档恢复”五处的接口边界：

1. 禁用 `Effect.Repeat`，清理仍可执行的注册、编译、运行和表现残留。
2. 持续禁用已退役的 `Effect.LoadCardMarkers`，清理失效正向用法，防止通过旧名、旧类型或同义包装恢复。
3. 所有退役项均覆盖旧名、旧类型包装和间接入口，不能只删除公开名称。
4. 保留合法替代方式，更新 DIY Lua/JSON 文档、相关夹具和明确拒绝旧数据的证据。
5. 修复骰子哥（蒂亚戈）点数 4 的出售页面：出售过程必须与贸易街区、坎诺特策略一模一样，共用页面、提示文案、数量操作、价格、预计收益、累计成交提示和结束出售行为。
6. 退役 `Effect.SelectInfluence` 及 `effect.influence.select_action`。由 `RemoveInfluence`、`MoveInfluence`、`ReplaceInfluence` 各自承接相应目标选择与执行流程，内容作者只调用对应操作接口；复用必要内部逻辑，不要求 DIY 脚本先写选择效果再调用操作，也不因此改变玩家交互。
7. 保留 `RemoveInfluence` v2 已有的批次足量保护，修复严格分支未保留筛选参数的缺口；区分选择交互、批次移除保证和替换失败规则，不把三者混为一项保护。
8. 建设只保留一个公开 `Effect.Build` 入口，统一管理按需选牌、付款准备与确认、实际付款、选位置、取牌/补供应、放置、入场和完成结果。退役 `Effect.ChooseBuild` 及 `effect.facility.choose_build`，不再由两个公开建设流程分担同一次付款和续接。
9. 探索只保留一个公开 `Effect.Explore` 入口，统一管理按需选择目标、路线与路费接收者、确认复验、路费预留、事件及响应、路费交付和完成结果。退役 `Effect.ChooseExplore` 及 `effect.exploration.choose`；内部继续复用现有共用选路和探索结算模块，赠送探索不消耗主要行动但仍按规则支付路费。
10. 保留并明确区分 `Effect.GrantMainActions` 与 `Effect.ExecuteMainAction`：前者只增加本行动轮可用额度，后者只在当前效果链中即时选择并执行一次行动。退役 ExecuteMainAction 的 `executionMode='grant_budget'`，持续拒绝已撤下的 `facility_entry`，不通过两个入口重复提供额度发放。
11. 退役 `Effect.TransferCharacterCard` 及 `effect.character.transfer`，角色牌交给另一玩家手牌统一通过 `Effect.MoveCharacterCard` 的显式区域转移合同表达。迁移感染版刻俄柏计谋，复用并补齐权限、控制者更新、角色生命周期、转交事件与恢复处理，不新增同义公开包装。
12. 退役 `Effect.RetainCharacter` 及 `effect.character.content.retain`。感染版阿米娅计谋改为空效果正文，持续型声明、激活、订阅与常驻区去向仍由已有角色生命周期处理，不新增另一空操作接口。
13. 将 `Effect.MoveCharacterCardToZone` 合并进 `Effect.MoveCharacterCard`，退役旧 `effect.content.transaction.move_character`。采用用户提出的合并方案，统一支持同玩家区域移动与合法跨玩家转交；不再另起一个“在玩家自己区域内移动角色牌”的同义公开接口。
14. 扩展 `Effect.MoveItem` 的玩家标记操作范围，承接 `StorePlayerMarker`、`ReturnPlayerMarker` 并退役其公开名和旧类型。允许合法效果直接移动其他玩家的标记、操作企业与宣告标记，撤除仅因旧入口、来源卡身份或区域黑名单而存在的限制；主要业务约束收敛为企业/宣告逻辑区域内同玩家标记互斥、供应区归属和必要的状态一致性。同步调整显示、使用权限、轨道绑定和恢复，不能只放开底层搬运。
15. 将 `Effect.UpgradeEnterpriseForPlayer` 合并进 `Effect.UpgradeEnterprise`，用明确的目标玩家字段表达升级对象，保留逐级奖励与结算顺序，退役旧 `effect.content.transaction.upgrade_enterprise`；直接移动等级标记与执行企业升级分别表达，不能互相暗中替代。
16. 调整 DIY Lua 文档 5.2 节中实际操作区域物品的接口：MoveItem 提供完整共同能力，MoveFacilityCard、MoveCharacterCard、CoverCharacterCard、OperateToken、OperatePlayerMarker、ReturnCityStyleMarker 等专用入口只做物品类型/操作语义约束、参数补全和共同步骤组织，不能独占通用入口无法表达的选择、移动、生命周期、事件或结果能力。
17. 补牌纳入 MoveItem 的物品操作能力；**洗牌明确排除**，继续由 ShuffleDeck/ShuffleFacilityDeck 及 Host 随机服务处理。完整设施供应刷新组合 MoveItem 移回、独立洗牌、MoveItem 补牌，不给 MoveItem 增加洗牌模式。
18. 退役没有正式内容或生产创建调用的 `Effect.ReleaseFacilityBinding` 与 `Effect.DepartureBatch`，以及对应的 `effect.content.transaction.release_binding`、`effect.influence.departure_batch`；保留角色离场自动解绑、移除/替换自动批次及离场响应结算。
19. 退役 `CoverCharacterCard(apiVersion=2)` 旧额外盖放签名，迁移测试及恢复接受分支；保留正常主链盖牌、有效的额外盖放和统一物品操作能力，不退役整个 CoverCharacterCard 或 character.cover.task 类型。
20. MoveCharacterCard、MoveFacilityCard、ShuffleFacilityDeck 的无 apiVersion 旧公开写法仍有正式调用，须先迁移到最终有效合同再清理旧参数分支；保留接口本身。旧入口是否闲置必须结合内容绑定、系统生成 Lua、内部工厂及恢复检查，不能仅凭 .lua 文本调用数判断。

**本计划不包含 `Flow.UpgradeThenActivateEnterpriseSpecial`。** 用户已于本轮明确取消该项；不新增参数，不修改“综合企业办公室”（当前定义显示名为“综合企业办公区”）的脚本或规则，不安排该项专项测试。其他 `Flow` 接口也不因“属于业务特化接口”而自动被禁用或重构。

**设施供应接口保留名称与现有职责，内部纳入共同物品操作。** RefillFacilitySlot/RefreshFacilitySupply 不退役、不移入 Flow，补牌触发时机及完整刷新顺序保持；按本轮新要求，其取牌、移回和补入由 MoveItem 承接，洗牌仍调用独立接口。此前暂缓供应接口合并不再作为排除这次内部能力统一的理由。

出售部分仅处理骰子哥出售误入普通多选页及其重复提示，不扩大到全部无卡面多选显示链路或企业家文本清理。既有内容迁移保持玩法与收益；玩家标记部分按本轮要求扩大 DIY 操作空间，不以保留旧权限限制为由缩回仅能操作本人供应的合同。悬浮提示和界面资产改造继续归原清单管理；复用现有正式页面，不重建场景或预制体。

### 2.5 ChooseBuild 与 Build：两个建设流程存在职责重叠

当前 ChooseBuild 不仅选择设施，还管理付款准备/确认、调用 Build、等待实际建设和完成续接；Build 自己也负责费用校验、付款或检查已有付款记录，以及选位置、放置和入场。现有实现通过付款上下文避免重复扣费，但公开接口并不是“只选牌”和“只建设”的两个独立原语。升级目标是一个 Build 对外拥有完整建设流程，候选查询和付款准备继续作为内部模块复用。

## 4. 内容迁移方式

### 4.1 Repeat 的替代

固定次数直接声明多个独立效果，或在 Lua 中用有限循环生成普通列表；每次重新构造效果对象，不共享一个可变声明对象。

```lua
return function(ctx)
    local effects = {}
    for i = 1, 3 do
        effects[#effects + 1] = Effect.GainScore({
            player = ctx.playerId,
            amount = 1
        })
    end
    return effects
end
```

上例仅说明普通列表的生成方式，不要求修改任何现有卡牌规则。动态次数必须来自当前合法上下文并遵守既有脚本、节点和执行预算；不能借 Lua 循环绕过预算。

依赖上一步结果或玩家回答时，按现有完成回调合同续接；不能在一次 Lua 调用中假定前面声明的效果已经执行。保留原有条件、费用、数量、目标与后续效果，不为“去 Repeat”添加无语义的 Condition、Sequence 或另一种重复节点。

现行清单已记录正式调用迁移完成，本阶段先复核是否回流，不重复改写已完成的脚本，也不重建已有普通效果顺序机制。

### 4.2 LoadCardMarkers 的替代

沿现有真实实例转移合同处理：

1. 会影响供应库存的相关响应先结清，再在正确的 Lua 调用时点读取库存、计算合法数量选项。
2. 需要选择时使用既有选择合同；回答后按当前事实确定实际物品实例。
3. 生成若干独立的 `Effect.MoveItem`，每枚 `requiredCount=1`，明确源区、目标区、操作域及载体权限。
4. 某枚缺失或位置已经变化时，记录该枚的真实失败；合法兄弟效果的成功不回滚，不能把失败伪装成成功。
5. 保留真实费用、来源授权和原有角色/能力载体生命周期；零数量或无合法候选按原规则处理，不弹空选择页。

不得新增整批预留、供应屏障、足额装载专用执行器，也不得把上述旧功能换一个名字包装回来。普通预期失败与权限错误、非法状态故障须区分；不能为继续流程而全局吞掉失败。

### 4.3 骰子哥出售统一合同

#### 4.3.1 对照标准

以贸易街区和坎诺特策略当前正式出售入口为唯一对照，复用 [CharacterCardEffectChoiceDialog.cs](../Assets/YC/Presentation/CharacterCardEffectChoiceDialog.cs) 的 `ShowResourceSaleCandidates/ShowResourceSaleCore` 及现有资源数量控件。

- 四种资源的固定顺序、资源名称、当前库存、单价和数量加减/输入。
- 相同的预计金券计算、确认本批、放弃草稿及结束出售行为；具体按钮文案与样式取现有正式页面配置。
- 相同的公共提示 `core:interaction.sale.batch`，包含本次贸易已出售份数和累计金券；骰子哥不保留另一份出售说明。
- 相同的库存上限、非法输入、过期请求、重复提交、收起/展开和草稿处理规则。
- 不再出现按每个数量展开的普通候选列表，也不出现“最少 1／最多 4”的通用多选计数。

当前公共价格为源岩 3、源石碎片 3、异铁 4、至纯源石 15 金券；继续读取同一个 [ResourceSaleService](../Assets/YC/Domain/Economy/ResourceSaleService.cs)，不在蒂亚戈脚本或新 UI 中复制价格表。

#### 4.3.2 Lua 内容与完成续接

1. 蒂亚戈的出售使用与两个对照相同的 v2 批量出售参数、公共 `promptKey` 与 `Text.Ref('core:interaction.sale.batch', {soldCount=..., revenue=...})`；不复制整个坎诺特处理器覆盖蒂亚戈投资规则。

### 4.4 SelectInfluence 退役与基础操作承接

以下是拟实施合同，不表示当前三个基础操作已经支持全部选择参数。先在 API-08 固定唯一的参数、版本、结果和失败语义表，再实现和迁移；本计划不提供会被误当成当前可运行代码的新签名示例。

#### 4.4.1 单一操作入口

| 原调用 | 迁移后的公开入口 | 由该入口内部承担的流程 |
| --- | --- | --- |
| `SelectInfluence(operation='remove')` | `Effect.RemoveInfluence` | 按声明筛选并选择目标；严格模式选齐后执行同一个足量移除实现，普通模式保留原逐次执行规则 |
| `SelectInfluence(operation='move')` | `Effect.MoveInfluence` | 选择影响力及合法目的地，按原数量和去重要求推进，每次移动后更新合法候选 |
| `SelectInfluence(operation='replace')` | `Effect.ReplaceInfluence` | 选择目标并执行替换，保留替换来源、所有者、离场响应和 `keep_removal` 规则 |

1. 每个操作提供明确互斥的“显式目标”和“交互选择”合同。显式目标调用按已有规则执行，不新增无必要的选择页；交互模式由操作自身请求选择并续接，不要求作者手写 `Choice → 回调 → 操作`。
2. 保留现有合法显式目标调用，尤其是 `RemoveInfluence({apiVersion=2, targets=..., requiredCount=...})` 的数量不足失败语义。严格调用缺失 `targets` 仍应报参数错误；新增选择模式须显式声明，不能用缺键把错误调用静默降级为旧单目标操作。
3. 筛选、数量、去重、放弃与提示各有明确语义。统一执行玩家与主体字段；迁移旧 `player`、`ownerFilter`、`distinctPolicy='owner'` 时逐项映射，不能在新接口保留两套相互矛盾的定义。当前基础 Remove 的 `candidateScope` 是目标列表，旧 Select 的同名字段是范围字符串，禁止直接照搬或静默改义。
4. 新合同必须承接现有调用实际需要的 self/player/opponent/any、排除主体、资源点/航道、显式候选 ID、实例/主体去重、数量、是否允许放弃和提示上下文。未支持的组合明确拒绝，不接受后忽略。
5. 普通“最多执行若干次”和严格“完整移除指定数量”分别定义。旧选择器的迁移基线为 `count=1..16`（默认 1）、`requiredCount=0..count`（默认 0）；完整选择要求两者相等。不能把所有 `count` 调用自动改成严格付款，也不能根据效果位于 `Condition` 左式就暗中改变操作语义。
6. 复用内部候选和交互实现，不新增另一套公开 `SelectInfluence` 同义接口，也不恢复已禁用的 `Repeat` 作为迁移工具。

#### 4.4.2 足量保护与筛选修复

- 严格移除对整组目标一次校验、预演和提交；目标不足、重复、已经离场、类型/位置不符或不满足筛选时，本批移除数为零并失败。显式目标模式与交互选择模式共用同一实现，不能拆成若干次单枚移除后再检查总数。
- 足量保护的边界是本批移除提交。保留离场批次、响应、去向与条件右式的等待顺序；不把它描述成后续响应、整个 Condition 或整场操作的通用回滚。
- 将 `subjectFilter`、`excludedSubjectKeys` 从 Lua 规范化、编译、保存恢复完整传到执行校验。交互模式生成候选时检查，提交时再检查；显式目标也不能绕过声明的筛选。新内部严格调用不得丢失外层选择规则。
- 同步检查旧完整选择分支对排除主体、去重等字段的实际处理，迁移后的每个公开模式均须遵守已声明合同。其余允许字段一并核对：应支持的字段传递并生效，不适用的字段明确拒绝，不能继续静默丢弃。
- ReplaceInfluence 仍为移除旧影响力、结清必要离场响应、再放置新影响力；放置失败保留已发生的移除及 `removed_only` 结果。本次不新增“替换失败恢复旧影响力”或“多枚替换全组回滚”规则，也不把选择足量当成替换全成功保证。

#### 4.4.3 玩家交互与恢复

公开 API 名称收口不要求改变页面、点击次数或确认方式。需要交互的调用仍走正式候选和共享地图路由；严格两枚选择继续使用当前逐目标确认、选满提交的行为，不强加新的总确认弹窗。普通逐次操作继续每次选择后执行；显式目标模式不为获得足量保护额外弹出选择页。

保留请求归属、可见性、修订号、候选版本、过期/重复回答拒绝及输入防重入。UI 负责收集意图，规则执行器负责合法性与数量复验；不能靠按钮限制替代规则保护。恢复时区分本地选择草稿和已接受的正式答案，不扩大草稿持久化范围，不重复移动、移除、放置或触发响应。

### 4.5 统一 Build，退役 ChooseBuild

#### 4.5.1 唯一公开入口与两种目标模式

统一后的 Build 对一次建设从开始到完成负责：确定设施 → 付款准备/确认与提交 → 取牌及必要补供应 → 确定并复验建设位置 → 放置、计分及入场 → 交付完成结果。具体阶段顺序沿正式建设规则，不因接口合并改成先放置后付款，也不跳过既有响应。

| 模式 | 内容作者声明 | Build 的行为 |
| --- | --- | --- |
| 指定设施 | 具体实例及来源/费用/行动合同 | 跳过选牌，校验指定实例，继续付款与建设；位置未指定时仍可请求合法位置选择 |
| 按范围选择 | 明确选择模式、来源和筛选条件 | 内部生成正式候选并让玩家选择，再进入同一付款和建设流程，无须作者写前置 Choice 或拼接两个建设 API |

- 来源承接 supply/deck/reserve/authorized，以及 `sourceKey`、`expectedSourceZoneId` 的真实授权与来源复验。
- 选择范围承接现有 `effectId` 筛选、`includeStoredFacilities`、`excludeRainbow` 和 `maxGoldVoucherCost`。费用上限目前按卡面金券标价筛选，不在迁移中悄悄改成折扣后的实际付款额。

- `allowDecline` 明确适用阶段；保留原可选/必做区别，支付后不得新增放弃或退款路径。显式位置仍检查真实合法位置、叠建层与观察版本。

#### 4.10.2 调用迁移与禁用

迁移第 2.10 节的 5 个文件、7 处调用：赫拉格弃牌、缪尔赛思取得流形、涤火杰西卡自身弃置、两版罗德岛的收回/弃置及公开展示。以实施时重新核对的调用清单为准；检查已有卡牌移动测试和实际完成回调。与刻俄柏转交共用验证，不能以同玩家移动改造破坏已经承接的跨玩家转交。

新入口承接并验证后，禁用 MoveCharacterCardToZone 及 effect.content.transaction.move_character 的名称、别名、模块、编译、注册、内部构造和旧状态执行。旧节点明确拒绝，新等待/完成状态恢复不重复移动、清理或公开展示；其他 ContentTransaction API 按各自范围保留。

### 4.11 放宽 MoveItem 玩家标记操作，退役 StorePlayerMarker/ReturnPlayerMarker

#### 4.11.1 以状态约束替代旧入口限制

本节是用户对“尽可能放宽操作空间”的新要求，覆盖之前关于普通 MoveItem 不能操作企业/宣告标记、只能从本人供应装载的设计判断。完整能力统一归 MoveItem，不新增存入、返还或轨道操作专用 Effect。按第 4.13 节保留的 OperatePlayerMarker 只作为玩家标记类型的专用入口，不能形成另一套权限或执行实现。

允许真实效果直接指定玩家标记实例，在供应区、卡上存放区及企业/宣告等合法承载区域之间移动，包括其他玩家的标记、企业等级格位变更和宣告使用状态变更。普通标记移动不要求先成为 Store/Return、某张角色能力、UpgradeEnterprise 或正常宣告动作的子节点。执行玩家仍来自真实效果上下文；标记所有者与执行玩家可以不同，移动不自动改写标记所有者。

逐项撤除跨玩家源区一律拒绝、装载只能来自本人供应、必须带旧专用 carrier 许可、受保护区域一律拒绝、UsageTracks 执行器白名单等与新范围冲突的检查。原声明还用于支付等其他合同的部分按实际用途保留，不能把旧门槛换名后重新加回普通玩家标记移动。基本的实例存在、类型相容、实际源位置、目标/格位存在、数量及不重复选择属于有效状态要求，仍需复验。

#### 4.11.2 企业与宣告的互斥范围

1. **企业：同一企业实例的同一玩家合作轨道，所有等级格合计最多一枚该玩家标记。** 唯一键包含企业实例和标记所有者，不能只检查目标等级格空闲；不同企业互不冲突，不限制所有玩家合计只能一枚。
2. **宣告：同一个承担宣告状态/使用权限的逻辑区域内，同一玩家最多一枚标记。** declared、unused、used、次数格等属于该区域的不同状态，跨状态移动同一实例不算新增。实施时列明 declaration 子区、重复宣告计分记录与共用使用权限的映射；同一权限域不能通过拆子区、换 slot 或新建绑定绕过互斥，独立区域也不能被误合成全局唯一。
3. 同玩家已有一枚时，再放入另一枚必须明确失败，不覆盖旧实例、不自动退回旧标记、不悄悄改所有者。若统一合同支持显式整组调换，按整组最终状态校验并一次提交，不能先提交一半再发现冲突。
4. 玩家专属轨道中的标记所有者必须与该轨道玩家一致；允许执行者替其他玩家移动其标记。互斥按标记所有者计算，不能按发起效果的玩家计算。
5. 允许效果移出标记，因而“最多一枚”包含零枚。零枚不是自动补牌或复制标记的理由，相关查询与权限必须支持缺标记状态；显示和使用权限不能继续依赖不存在的实例。

唯一性必须在预检、提交和恢复入口共用，并被正常企业升级、宣告、回合重置等内部写入遵守，不能只约束 Lua。保留实际结构容量，不能把旧“轨道禁止通用操作”的规则伪装成容量限制。

#### 4.11.3 供应区与最小必要检查

供应区继续保存其所有者的标记：不能把玩家 A 的标记放入玩家 B 的供应区；original_supply 必须解析真实记录且与所有者相符。从对手供应取出对手标记进入合法目标允许执行，不再要求执行者就是供应区所有者。来源已变、库存不足或虚构实例仍失败，不生成替代标记。

卡上存放区按内容声明接受相应类型和容量，不再因为标记属于对手、来自对手供应或缺少旧 Store 节点而拒绝；返还按各标记原供应处理。保留真实依赖等待、卡上最后一枚离开后的生命周期和必要响应，不能因放宽权限跳过状态清理。

此次明确开放企业与宣告轨道；地图影响力离场、拓扑及计分一致性等确有业务意义的规则不因共用保护数组变动而被删除。剩余拒绝必须列出其保护的具体状态约束和必要性，不能只写“历史黑名单”“必须通过某旧 API”或以假设风险重新收紧已授权范围。

#### 4.11.4 轨道、显示与使用权限同步

- 扩展 MoveItem 参数以支持显式格位、同区换格及跨区转移；现有 v3 仅 unordered 的合同需明确升级。新能力只能通过正式版本生效，不能静默忽略 slot，或接受字段却仍报旧区域保护错误。
- 提交时同步物品位置与必要的轨道绑定/宣告状态，再发布结果。显示、候选、能力资格与实际可用次数读取同一权威状态；移出后旧资格失效，移回或换实例后按真实位置重建/调整绑定，不能沿用旧实例的悬空使用权。
- 改造企业 GetCooperationMarker/GetLevel 的“必须恰好一枚”假设。缺标记显示明确的未放置/未参与状态，相关操作按新合同给出可处理结果，不抛未捕获异常，也不把不存在的标记假装成可用的零级标记。
- 宣告历史计分、已用设施记录与当前标记带来的使用权分别处理：直接移动更新当前状态，不自动重发宣告奖励、重写历史计分或额外补充次数。正常宣告、发动与回合重置仍按其业务合同结算，移出的标记不得被旧重置流程拉回。
- 直接移动企业标记改变当前等级位置与相应可用资格，但不自动执行“逐级升级奖励”；需要升级收益的内容调用 UpgradeEnterprise。直接移动、升级和宣告的事件/收益边界须写清，不根据移动方向猜测作者想要哪种业务效果。
- 恢复校验、联机投影和内容版本同步改造：接受合法零枚/一枚状态，拒绝重复标记、错供应和悬空有效绑定；不在恢复时复制、补发、丢弃标记或悄悄修复非法存档。

#### 4.11.5 内容迁移与旧接口退役

诗怀雅从对手供应区收存、返还及林的返还统一改用 MoveItem。单枚操作明确 requiredCount=1，原交互、顺序和失败处理保持。originalOwner 等后续需要的信息由移动前真实实例记录与完成结果核对；诗怀雅后续给原所有者升级不能错误使用执行者或载体控制者。异客、林已有 MoveItem 装载及其他标记转移按新范围回归，不重新引入 LoadCardMarkers。

完成必要行为验证后，禁用 StorePlayerMarker/ReturnPlayerMarker 及旧 store_marker/return_marker 类型，移除仅识别这些节点的 AllowsMarkerTransfer 放行，归入统一转移和共同状态检查。旧名称、包装、内部工厂和旧恢复均不能执行；通用转移、角色生命周期和仍有效的系统收尾保留。DIY 文档明确新开放范围及三类关键边界：企业/宣告互斥、供应归属、状态同步；按第 4.13 节区分 MoveItem 共同能力、OperatePlayerMarker 类型约束与系统收尾，在实现完成前不提前宣称新能力可用。

### 4.12 UpgradeEnterprise 直接指定目标玩家

统一入口保留 player 表示真实发起者，增加 targetPlayer 表示实际升级对象，缺省为 player；明确版本和字段校验，不能把 targetPlayer 当成来源身份。目标玩家的合作标记、等级、逐级奖励与事件归属一致，发起者和目标玩家不同也等待完整升级子树。等级上限、无变化结果和已有奖励时序保持。

诗怀雅保持“返还标记 → 自己获得原收益并选择企业升级 → 标记原所有者在同一家企业升级一级”的顺序。显式同一 enterpriseItemId 交给目标玩家，不重新选择，不额外消耗其主行动，也不顺带发动企业特效。目标缺标记等新状态与第 4.11 节共同定义可处理结果；不能退回只接受执行玩家的旧限制。

迁移唯一正式调用、结果消费者及相关夹具后，禁用 UpgradeEnterpriseForPlayer 和 effect.content.transaction.upgrade_enterprise。实现直接复用升级服务，不创建旧包装节点；旧规格/恢复明确拒绝，新状态恢复不重复改变等级或发奖励。此项不调整 Flow.UpgradeThenActivateEnterpriseSpecial，也不把 MoveItem 的裸标记移动变成带奖励升级。

### 4.13 5.2 节区域物品操作统一由 MoveItem 提供，洗牌独立

#### 4.13.1 通用入口与专用入口的关系

MoveItem 是区域物品操作的完整入口。对同一合法操作，直接调用 MoveItem 与调用专用接口应有相同的候选、交互、状态变化、必要等待、事件、结果与恢复行为；不能出现“底层能移动，但只有换成角色/设施专用 API 才会处理生命周期或通过校验”的情况。专用接口仅限定适用类型和操作语义、提供默认区域/参数或展开有限的共同步骤，不维护另一份操作实现。

| 现有接口/职责 | MoveItem 必须承接的等价能力 | 专用接口保留的作用 |
| --- | --- | --- |
| MoveFacilityCard / MoveCharacterCard | 显式实例或合法候选选择、实际源区复验、同区换位/跨区移动、载物退出、控制者/原归属、完成结果及所需公开/转交事件；旧设施选择后补槽等完整步骤也须能表达 | 限定设施牌/角色牌类型，补全常用区域和操作参数；不能以专用节点类型获得额外权限 |
| RefillFacilitySlot | 执行时从指定真实牌堆顶取得所需实例，补入指定空槽；保留源牌顺序、空堆成功无变化、占用槽拒绝覆盖和完成结果 | 补全设施牌堆、设施供应槽和单槽数量；补牌是受约束的物品移动 |
| RefreshFacilitySupply | 当前供应牌移回、按既定次序补入各槽的物品操作；整次流程按原顺序等待必要子步骤 | 组织“MoveItem 移回 → ShuffleDeck/ShuffleFacilityDeck 洗牌 → MoveItem 补牌”，保留完整刷新语义，不私有实现搬运或洗牌 |
| CoverCharacterCard | 主/附加盖放所需的候选、选择、覆盖槽取得/创建、接受类型、可复用标记、阻塞期限、必要回收/等待、信息可见性及盖放完成事件 | 限定角色牌和明确的盖放操作，提供默认值；进入覆盖区所需元数据由共同策略校验并提交，不靠旧盖牌节点特权 |
| OperateToken | 地图位置到真实区域的解析、对应移动规则验证、必要等待、移动结果及 token.moved；允许通用入口正式声明同一操作规则 | 限定 Token 类型及所选地图操作语义，复用共同规则；不能只有该构造器能进入地图目标区 |
| OperatePlayerMarker | 第 4.11 节全部标记转移能力、企业/宣告互斥、供应归属、轨道显示/使用权限同步 | 限定 core.player_marker 类型并补全参数；旧 round_cleanup 不作为通用移物模式，必要系统收尾行为分离到已有收尾机制 |
| ReturnCityStyleMarker | 同等范围的合法候选选择、返还原供应、当前宣告/使用资格同步、完成结果；不重写历史分数、宣告和同回合使用记录 | 默认限定符合原规则的二级城市样式标记及返还操作；通用入口可使用同一选择/返还合同 |
| ShuffleDeck / ShuffleFacilityDeck | **不纳入 MoveItem；没有 MoveItem 洗牌模式或等价隐藏分支** | 继续作为独立牌堆随机重排接口，使用 Host 随机与既有顺序记录 |

“能力完整”包含必要的前后处理，不等于只暴露一次裸位置赋值。专用接口有多步行为时，允许展开为有限的通用操作及独立洗牌；每个物品操作步骤必须可由 DIY 内容通过正式 MoveItem 合同直接调用，不以“内部服务已经复用”代替公开能力对等。

#### 4.13.2 共同参数、执行与结果合同

1. 由 API-29 固定统一版本与参数表，覆盖显式实例、按合法区域/范围选择、源区和目标区、放置方式/格位、数量、物品类型约束、必要生命周期策略、公开展示及结果。按操作限定字段，非法组合明确拒绝，不能把现有 v1/v2/v3 字段简单拼成一张无约束大表。
2. 补牌需要正式的“执行时从区域取顶部若干物品”表达，由 Host 绑定真实实例及顺序记录；不能要求 Lua 先读取隐藏牌序或虚构未来抽到的 ID。执行与恢复使用已绑定实例，连续补槽按当前剩余牌堆逐步推进，不在刷新洗牌前冻结将来的补牌对象。
3. 有序区域支持合法顶/底插入、指定格位及当前所需顺序期望；这属于物品放置，不包含随机洗牌。洗牌输入、随机流和洗牌恢复仍由独立接口负责，MoveItem 不接受随机排列、随机种子或调用洗牌的同义操作。
4. 类型和生命周期逻辑放入共同操作策略；通用入口按所选操作执行全部必要清理和事件。普通移动不会因目标碰巧相同而猜测盖牌、升级、奖励或宣告意图；需要盖放等状态语义时明确声明同一共同策略，专用接口只是补全它。不得开放任意字段写入角色使用记录来冒充等价实现。
5. 所有共同检查以实际实例、区域、规则和状态约束为依据；保留专用入口的类型检查，不保留以专用 EffectTypeId、卡名或来源包装充当权限的分支。玩家标记仍遵守第 4.11 节的新开放范围，不能借这次统一恢复旧门槛。
6. 通用操作提供稳定的变化数量、真实物品、源/目标及该操作必要业务结果；专用接口可做确定的字段投影，不能重新推算另一套事实或吞掉失败。事件按真实变化只发一次；多步操作逐步/整组提交、取消和失败边界沿实际合同明确，不为了统一默认全回滚或全吞错。

复用现有生命周期、设施供应、地图规则和交互模块，消除仅专用接口能到达的分支；不要求把所有逻辑塞进一个方法，也不另建可绕过五层校验的任意效果脚本执行器。专用节点可以保留名称与可读表现，但执行事实必须来自同一共同能力。

#### 4.13.3 5.2 节中不属于区域物品移动的职责

- SetCharacterDoubleUseRule 管理角色使用规则，独立保留并从“区域物品操作”分组移出，不变成 MoveItem 的任意规则设置参数。
- ConsumeCharacterDoubleUseSource 的真实卡牌移动、载物退出由共同 MoveItem 能力承担；已证明来源的消费记录、使用窗口和单次消费仍属于角色使用规则。相关接口归入规则生命周期分组，普通移牌不会自动消费或授予双用资格。
- CreateCityInfluenceLock 的组件生成、城市绑定、影响力限制和到期规则独立保留；其中确需转移真实物品的部分复用共同转移能力，不把创建锁或设定期限伪装成移动现成 Item。
- OperatePlayerMarker 当前承担的 round_cleanup 从物品操作职责中分离，核对 CityStyleLuaCatalog 等系统调用并保留实际收尾行为；不能为完善该名称而让普通移动重置全回合状态。
- 已决定退役的 TransferCharacterCard、RetainCharacter 及第 3.1 节其他旧名/旧类型继续禁用，不以“现在专用接口允许包装”为由恢复。

实施后的 DIY 文档分别列“通用/专用物品操作”“独立洗牌”“角色使用与持续规则”，明确哪些接口共享 MoveItem，哪些本来就是其他职责；当前文档在实现完成前不宣称新功能已可用。

#### 4.13.4 迁移、等价验证与恢复

先完成逐接口能力和消费者清单，再实现共同合同，最后把专用入口改为类型约束/参数归一化/共同步骤组织。与第 4.8、4.10、4.11 节共享最终 MoveItem/MoveCharacterCard 版本，避免同一能力先补到角色专用入口、随后通用入口又漏掉。

为每个保留的物品操作入口给出可执行的 MoveItem 等价写法；完整供应刷新示例明确包含独立 ShuffleDeck。按相同合法初始状态和相同选择比较实际状态、事件、可见性、结果、等待和失败，不仅比较返回参数。包含牌堆空/不足、槽已占用、源变化、角色载物/盖放、Token 位置非法、标记互斥、跨玩家操作、重复提交和恢复；随机洗牌单独验证输入与随机记录，不要求 MoveItem 复制随机能力。

新通用路径不得在内部创建第 3.1 节已退役类型。保留的专用接口若调整参数、结果或内部保存结构，明确版本及旧状态支持边界；恢复不会重复抽牌、补槽、清理、发事件或洗牌。正常建设等调用补槽的内部消费者也必须接入相同能力，原补牌触发时机和玩法保持。

### 4.14 闲置公开入口退役与旧签名迁移

#### 4.14.1 ReleaseFacilityBinding 与 DepartureBatch

根据第 2.14 节审计，将这两个闲置公开入口纳入退役，不删除其名称相近但仍有效的内核能力。实施前再次确认正式内容、生成 Lua 和生产工厂仍无创建调用；出现新增消费者时，先查明语义并迁移，不覆盖或跳过新增内容。

ReleaseFacilityBinding 清理构造目录、字段接受、release_binding 分支及旧状态执行入口。CharacterLifecycleService 中只被该包装调用的手动方法可在引用复核后清理，但角色离开常驻区、设施离开城市时的自动解绑必须保留，BindCharacterToFacility 仍有效。验证涤火杰西卡实际绑定、后续结算及离场不受影响，不为清理闲置入口另造新的手动解绑 API。

DepartureBatch 清理公开构造、编译嵌套接受、旧包装执行器/工厂和旧节点恢复。保留 RemoveInfluence/ReplaceInfluence 自动建立的批次、InfluenceDepartureBatch 状态、生产步骤归属、封存、response.batch 聚合、子效果等待及相关存档协议。不要按 DepartureBatch 子串全删，也不把“删掉包装”误解成逐个离场响应无需结算。

原 [InfluenceDepartureContractTests.cs](../Assets/YC/Tests/EditMode/ExpansionRules/InfluenceDepartureContractTests.cs)、[InfluenceDepartureLuaTests.cs](../Assets/YC/Tests/EditMode/ExpansionRules/InfluenceDepartureLuaTests.cs) 和其他集成测试中显式构造旧包装的正向用例需逐项处置：有效离场保证改从真实基础操作及自动批次验证；只验证旧显式/嵌套包装能力的用例改为退役拒绝负例。不能把普通效果列表当成与旧手动分组完全等价，也不能删除批次测试后声称批次行为通过。

两类旧名称、类型、别名、模块、手写/嵌套规格及内部构造均不能继续执行；保存中的旧包装节点或待执行规格在恢复前明确拒绝，不修改原存档。正常基础操作产生的有效自动批次和自动解绑状态仍可恢复。

#### 4.14.2 只退役 CoverCharacterCard v2

将 v2 额外盖放正向夹具迁入第 4.13 节最终共同合同或有效专用盖放版本，补齐真实来源、目标、接受类型及阻塞期限；不能只把版本数字改成 3 后忽略不同字段和来源要求。正式赫拉格、缪尔赛思两处 v3 行为随统一物品操作验证，保留附加覆盖、可复用覆盖槽和既有选择流程。

之后在 Lua 归一化、编译、内核和恢复中明确拒绝 character.cover.task 的 apiVersion=2 合同；保存节点、嵌套待执行规格和别名均覆盖。正常主链创建的盖牌任务具有自身的内部参数形状，不能因没有 apiVersion 或共用同一类型而误禁。保留有效 v3/后续统一版本；不把这个版本退役扩成整个 CoverCharacterCard 退役，也不全局拒绝所有接口的 apiVersion=2。

#### 4.14.3 仍在使用的三个旧公开签名

按第 2.14.2 节先迁移当前 **5 处正式构造调用**及其 C# 内部生产者、测试和完成回调：铁皮人的弃牌回手、德克萨斯/马丁的供应牌回底与补槽，以及雷神工业/城建开拓区的独立洗牌。使用 API-29～API-31 的最终明确版本合同，实际参数和结果逐项对照，不能将当前使用中的旧写法标记为闲置后直接删除。

验证迁移成功后，禁止这三个接口原无版本公开参数、旧 sourceZone/destinationZone 兼容与相关旧保存规格继续执行；合法接口名和显式版本保留。明确限制适用的接口及版本形状，不对所有 Host 内部无版本子效果统一报错。ShuffleFacilityDeck 仍属于独立洗牌，不能以签名迁移为由接入 MoveItem 随机模式。

#### 4.14.4 审计记录与误删防护

审计清单逐项区分正式 JSON 绑定/模块调用、生成 Lua、生产工厂、仅注册/校验、仅恢复、正向测试、拒绝负例和历史材料。零直接 .lua 调用的六个现行消费者按第 2.14.3 节保留或沿原计划调整职责，不增加闲置退役项。新通用接口尚未被现有内容直接调用也不能据此删除。

## 6. 验收清单

### 6.1 接口禁用

- [ ] 当前公开构造器清单没有 Repeat、LoadCardMarkers、SelectInfluence、ChooseBuild、ChooseExplore、TransferCharacterCard、RetainCharacter、MoveCharacterCardToZone、StorePlayerMarker、ReturnPlayerMarker、UpgradeEnterpriseForPlayer、ReleaseFacilityBinding、DepartureBatch 十三项整体退役 API，也没有可执行别名。
- [ ] CoverCharacterCard v2、三个旧无版本公开签名和主要行动退役模式按各自合同拒绝；正常主链盖牌及这些接口的有效版本不被连带禁用。
- [ ] GrantMainActions 与 ExecuteMainAction 均保留且职责独立；ExecuteMainAction 的 grant_budget、facility_entry 明确拒绝，合法 immediate 不受误禁。
- [ ] 直接调用和模块转发不能生成旧效果；手写顶层/嵌套旧类型规格被拒绝。
- [ ] C# 工厂、执行注册、旧版本分支不能绕过禁用。
- [ ] 含旧节点、旧嵌套规格或专用旧状态的数据不能恢复执行；有明确拒绝原因，原存档保持原样。
- [ ] 正式内容与表现映射没有可执行旧入口；残留字符串均有“拒绝、负例、历史说明”等明确用途。
- [ ] `count=0/1`、换名、改类型包装不能规避 Repeat 禁用；旧装载专用字段不能被静默接受。

### 6.2 合法替代与回归

- [ ] 普通有限效果列表仍能按现有机制执行，已有费用与条件分支不被改义。
- [ ] `repeatPolicy = once/unbounded` 与原收尾来源机制不受影响。
- [ ] 相关旧装载正向夹具完成迁移，必要的“拒绝旧 API”负例仍然有效。
- [ ] 真实 MoveItem 校验实例、实际来源和必要状态约束；按第 4.11 节开放的跨玩家及轨道操作不再被旧权限拒绝。逐枚独立操作的预期失败不撤销成功兄弟，也不隐藏故障；明确要求整组提交的合同按其足量保证执行。
- [ ] 通用选择、数量、付款和表现不因专属分支清理失效。
- [ ] 受影响内容完成加载/编译与已有版本、哈希登记校验；无改动内容不无故全量升版。

优先复用既有测试，补充能够证明禁用边界和迁移语义的必要用例。源码字符串检索只能辅助定位，不能单独证明内核不可达或旧存档安全拒绝。不要为了这一清理重复建立普通效果列表执行顺序的全矩阵测试。

一致性通过共用现有页面和配置实现，不新增锁死坐标、尺寸、颜色或静态文案的测试。视觉验收依据实际使用的场景/预制体来源和当前显示，不以换皮后的通用多选页代替。
