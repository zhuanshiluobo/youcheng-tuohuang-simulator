## 1. 已确认的框架

固定顺序为：分发前流程 → 分发企业候选 → 中间流程 → 确认企业及必要初始化 → 确认后流程 → 原有入场流程。

- 两个固定节点由共同框架执行，模式通过 JSON 或 Lua 声明三段流程。
- 中间流程为空时，分发后直接显示确认企业 UI，仍需回答正式的企业选择请求。
- 中间流程及其嵌套步骤的所有卡牌选择页面，都提供查看本人已分发企业板的按钮，参照当前企业家的预览和返回行为。
- 企业扩使用空中间流程；企业家的现有专用准备逻辑迁为中间步骤；DIY 可声明其他步骤以及前、后置流程。
- 本方案将确认后入口放在最终企业公开、科室/组件、合作标记和初始升级等必要初始化完成之后。
- 企业与城市样式的固定名单、必选加随机补足、数量及人数差异继续纳入准备数据配置，不再以固定四家作为所有模式的通用限制。

- [ ] 固定企业及城市样式策略：指定完整名单、必选名单加随机补足、分发/保留数量和按人数配置；数量不足、重复、非法引用应定位到声明。

验收：只读装配可确定完整顺序、调用来源、所需能力和分发规则；空中间流程、企业家中间流程和 DIY 三段流程均能明确表达。

## F1 建立共同框架与分发记录

- [ ] 从现有企业准备流程提取分发与确认节点。分发只执行一次；每位玩家候选保存为真实实例记录，确认消费同一份记录。
- [ ] 框架按三段列表调用步骤，等待必要选择、子效果和完成续接；空列表立即推进。中间为空也必须打开确认企业页，不能把全部候选自动选中。
- [ ] 把企业公开、未选牌处理、合作标记、科室、关联组件、必要洗牌和初始升级作为确认后的共同初始化，完整结束后再调用后置流程。
- [ ] 统一准备状态及对各玩家的可见投影，解除企业分发信息对企业家专用状态的依赖。旁观者和其他玩家不获得私密候选。
- [ ] 明确批次完成边界：前置结束才分发，中间全部必要任务结束才确认，确认结果及初始化完成才后置，后置结束才继续原入场。
- [ ] 暂以原官方数量验证框架等价；F4 再开放不同名单与数量，保留正式合法性检查。

验收：普通企业扩不配置中间步骤即可完成原流程；空列表不新增确认前停留页，分发、确认与初始化各执行一次。

## F2 中间卡牌选择页统一提供企业板预览

- [ ] 框架把受验证的准备上下文关联到中间流程的交互请求，包括 Lua 产生的嵌套卡牌选择；不依赖固定交互名称或脚本自己添加按钮。
- [ ] 共同卡牌选择展示层按该上下文提供企业板查看入口；使用请求作答玩家有权查看的分发投影和现有企业详情页。
- [ ] 预览与返回保留已选候选、滚动位置和原待答请求；不提交选择、不触发 Lua 重跑、不重新随机或分发。
- [ ] 请求被更新、回答、切换或重连时重新核对上下文；不把旧预览绑定到新请求，不读取别人的候选补齐显示。
- [ ] 核对单选、多选、多页和嵌套卡牌选择，以及原企业家页面；普通非卡牌选择不强制附加入口，分发前不显示尚不存在的本次候选。
- [ ] 复用实际模板和文案配置，明确所用场景覆盖或预制体来源。此计划不授权自动生成或保存覆盖界面资产。

验收：每种受支持的中间卡牌页都能查看正确企业板并返回原选择，Lua 与 JSON 入口行为一致。

## F3 接入模式步骤与迁移企业家流程

- [ ] 企业扩使用空中间列表；企业家原预览、选人、所选内容初始化登记为中间步骤，引用外层已分发记录，删除同一路径的重复执行分支。
- [ ] Lua 步骤沿现有合法 API 返回效果并正式续接，JSON 步骤调用已注册处理器。校验两者都能等待多级选择并正确回到框架下一步骤。
- [ ] 为步骤加入来源包、版本、脚本及模块身份；加载和语法检查不提前执行步骤。
- [ ] 通过验证包分别覆盖前置、中间、后置及三者组合；同时核对前置仅运行一次、后置看到最终名单而非未确认候选。
- [ ] 不为每个 DIY 模式加代码分支；新增宿主能力集中登记，缺失能力不能通过填写 Lua 路径冒充已支持。

验收：企业家保留原规则与选择顺序，DIY 使用相同框架完成不同的中间选牌；前后置独立可用。

## F4 开放企业和城市样式名单与数量

- [ ] 企业候选池、每人分发数、保留数、公共必选企业与补足规则来自冻结配置，移除通用路径中“最终必须四家”及人数写死的假定。
- [ ] 固定企业明确初始归属及是否需要玩家选择；企业确认仍校验正式候选，不能靠移动到展示区绕过必要初始化。
- [ ] 城市样式支持明确名单和必选加补足，一级/二级按配置分别处理；将当前装配时随机抽取纳入统一准备数据策略，避免配置后又被旧逻辑裁减。
- [ ] 通用规则校验、企业后续操作、列表展示及恢复检查读取实际结果；官方四家规则保留在官方配置中，不取消其他完整性校验。
- [ ] 检查多于四家时的真实合作标记供给与各企业组件；确认数量合法且能完成准备，不能仅放开数量判断。

验收：至少覆盖不同企业数量、指定名单、固定加随机和城市样式不同数量；候选不足明确失败，恢复不重新补牌。

## F5 保存恢复、联机与正常流程验收

- [ ] 模式步骤、顺序、执行对象、分发规则与脚本身份进入活动内容指纹；保存窗口与步骤进度，恢复继续已有效果树。
- [ ] 覆盖分发前等待、分发完成、中间选牌、嵌套选择、企业待确认、初始化中及确认后流程等待；不重复分发、选人、初始化或发奖。
- [ ] 核对主客端相同确认结果、私密信息投影、重复提交处理以及全部玩家完成后才推进的边界。
- [ ] 从可见独立程序正常菜单进入：基础无企业、企业扩空中间流程、企业家原流程、DIY 三窗口、不同数量/固定名单分别验证。
- [ ] 按程序版本、活动哈希、GameId 记录真实证据；随机未出现不算覆盖。隔离、正常单机、本机多进程与真实 Steam 多账号分别报告。
- [ ] 能力完成后再更新 `内置DIY/文档` 中的作者文档和示例；本计划的未完成项保持待实施。

最终目标：模式作者以 JSON 或 Lua 配置三段准备流程，共用企业分发、确认和初始化；中间所有卡牌选择页能查看本人企业板；指定名单与数量、联机及恢复使用同一份已确认规则。
