# 事件牌迁移核对记录（静态源码基线）

核对日期：2026-11-10。提交：`6651983f728c05442d30b5d5a35207fd78daa5af`；core：`2.1.70`。这是一份静态核对和迁移输入，不代表新协议已实现或界面、对局、存档、联机验收通过。
工作区另有无关未提交文件，未作为迁移输入。以下图像信息仅来自正式 core 定义和切片登记；未读取受限原档案。

## 现行流程与待迁移边界

- 正式探索通过 `ExplorationEffectExecutor` 建立事件效果；移动完成观察者由 `EventCardLuaCatalog.RegisterCityMoveObserver` 产生 `RevealEventCard`；入场通过 `PlayerEntranceEffectExecutor` 和已注册的事件效果处理。抽牌、资源点、公开地点及选择由 `EventCardEffectExecutor` 持久化。
- 正式选择、候选和恢复目前使用数字索引；`EventCardEffectExecutor` 在触发 `EventCardResolved` 前依据 `ChoicePendingEffects` 预选影响力。不可仅删除数组而丢失合法范围、支付顺序或恢复状态。
- 基础牌当前由 `EventCardLuaCatalog` 按旧数据生成整牌脚本；两张企业替换牌由定义中的 `data.effectScript` 提供整牌脚本。两类脚本都包含基础影响力处理。迁移时须保留其执行顺序并保证恰好一次。
- `ActiveContentCatalogBuilder` 正式快照使用最终 `definitionId`；基础配方引用被替换目标的槽位，再解析到最终定义。企业替换的显示顺序必须按最终牌面单独核对，不能套基础牌特判。
- `EventCardDatabase`、`EventCharacterCardCatalog`、其编辑器序列化工具、`CardFlowService`、探索和移动的旧服务、日志、自动玩家、UI 工作流、状态克隆及存档恢复都消费旧结构。它们的正式/遗留用途尚须逐调用点核对，不能把遗留方法一概当作正式链。
- `EventChoiceDialog` 现在的横向范围和颜色等来自运行时已有逻辑；下表纵向边界只记录旧实现，需对实际切片单独核验后方可作为迁移数据，不能仅凭此表宣称视觉正确。
- 用户于 2026-11-11 明确批准新增 `ctx.payload.choiceId`；其余 Lua 接口仍按现行合同保留。新选择身份和脚本路由必须由宿主校验和冻结，不能由客户端指定脚本。
