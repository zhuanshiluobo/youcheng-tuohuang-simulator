# 准备阶段执行合同草案

日期：2026-11-14。用于实施计划 F0 的内部设计，尚未代表生产入口或作者 API 已支持；最终以实现和验证结果为准。原三阶段真实 Steam 四人验收由用户稍后安排，不因先实施新框架而标为通过。

## 模式编排

只从所选模式读取一个 `preparation` 对象；扩展或依赖包不得自行插入步骤。对象按版本冻结，三个有序数组依次为 `beforeDistribution`、`betweenDistributionAndConfirmation` 和 `afterConfirmation`，缺省数组表示空流程。每个条目有全局唯一的 `stepId`、来源包身份、处理器版本、参数和执行方式。条目保持声明顺序，依赖包中的处理器必须由模式显式引用，来源及版本在内容装配时核验并冻结。

执行方式明确为：`once`（整局一次，Lua 使用固定玩家顺序首位作为现有 `ctx.playerId`）、`eachInOrder`（按固定玩家顺序依次完成）、`eachIndependent`（各玩家独立任务完成后汇合）。共享候选选择必须采用有序方式，不能因为交互都属于玩家而并行。当前官方企业家的预览及选人作为一个已注册中间步骤，内部保持既有独立预览与反序选人逻辑。

步骤由已注册的 JSON 处理器或 Lua 文件提供。JSON 只允许调用正式登记的步骤处理器；Lua 使用现有普通入口、效果／选择和完成续接合同，沿现有只读玩家视角装配，不能增加构造器、`ctx` 字段或变更 Lua 沙箱。步骤完成意味着必要子效果与续接完成；空流程直接进入下一固定节点。脚本源包、实际版本、入口与源码哈希均参与内容身份。

前置步骤如需影响分发，使用框架读取该步骤正式完成的效果结果并通过模式声明的输出绑定映射到有限的分发参数；绑定必须限定步骤、执行玩家及允许的结果字段，并在分发前验证完整性和权限。不能直接修改全局配方、把脚本内任意数据当成可信分发结果，或增加 Lua 返回字段。无法由现有效果结果表达的情况不通过新增 Lua 接口掩盖。

## 分发和城市样式配置

企业候选池和每级城市样式分别使用以下策略：

| 策略 | 定义 |
| --- | --- |
| `all` | 使用所有实际符合类型和范围的定义；不额外指定抽取数 |
| `fixed` | 精确使用明确且无重复的定义名单；不存在或类型不符即失败 |
| `requiredRandom` | 先包含无重复的必选定义，再从允许的其他定义中随机补至声明数量；候选不足即失败 |

企业按人数声明每位玩家分发数、保留数、公共随机补足数和最终数量。固定企业另明确其定义、初始归属（无归属或固定玩家顺序中的席位）以及是否必须经该玩家确认；要求确认的固定企业计入本人分发和保留配额，自动固定企业计入最终数量。分发前核对总量、重复、席位、必要组件及所有玩家标记供给；官方二、三、四人结果通过官方配置继续保持四家。

城市样式一、二级各自独立配置名单与数量；最终实际供给只确定一次，之后不得再次套用旧随机裁减。样式和企业配置均在开局内容身份中冻结，实际随机结果及企业真实实例分发记录保存在对局状态。

## 保存、可见性和顺序

正式主链等待：前置步骤 → 一次分发 → 全部中间步骤 → 每位必要玩家确认 → 企业公开与必要初始化全部完成 → 后置步骤 → 原入场。每个步骤保存窗口、步骤身份、执行对象、子树与完成边界；分发记录区分真实实例 ID 与定义 ID，不能从实例 ID 推测卡面。

所有中间流程卡牌选择请求，包括嵌套子效果，通过受验证的当前准备树关联本人分发投影。本人只能查看自己的候选，其他玩家和旁观者不可查看；确认后使用正式公开结果。复用现有详情页和实际卡牌选择模板，浏览时不提交、不重跑 Lua，并保留选中项和滚动位置。静态文案、样式及资产来源遵循项目 UI 所有权要求。

旧存档及 R956 两份用户档的原执行合同必须显式区分；恢复时验证真实节点、脚本版本、分发记录与待答请求，不因新字段缺省就重分发或重复初始化。新合同尚未完整实现时，不向房间或作者文档声明能力可用。
