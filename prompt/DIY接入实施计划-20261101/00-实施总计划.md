# DIY 接入实施总计划

日期：2026-11-01。状态：全部待实施。

设计依据：[DIY 包体设计](../../docs/设计/DIY包体设计.md)。本目录仅存实施计划；本次不创建实现、迁移脚本、测试产物、安装包或实施完成记录。

## 1. 范围与顺序

| 阶段 | 目标 | 计划 |
| --- | --- | --- |
| A | 事件按钮直接绑定奖励 Lua，数量与卡面高度由 JSON 决定，迁移既有事件 | [01 事件牌改造](01-事件牌改造计划.md) |
| B | AppData Mods 发现、模式/扩展注册、机制与 Lua 装配、房间选择及精确恢复 | [02 DIY 读取与安装](02-DIY读取与安装计划.md) |
| C | 安装时选装、仅补装、独立 ZIP 导出及完整分发验收 | 同上，在 B 的格式与读取稳定后实施 |

依赖顺序：A0 → A1 → A2 → A3 → A4 → A5 → B0 → B1 → B2 → B3 → B4 → C1 → C2 → C3。阶段内可按依赖组织普通开发工作，本计划不要求多 agent 并行实施。

DIY 包可提供模式、扩展或同时提供两者。阶段 B 支持与基础、企业家平级的新模式，通过配置组合现有玩法机制，并用既有 Lua API 表达规则差异。房间沿用“单选模式＋选择扩展”，不新增包或包版本选择控件；所需包及精确版本在后台解析和核对。

事件牌是阶段 A 的先行改造对象，也是阶段 B 的内容样例，不限制 DIY 只能提供事件。新地图、创意工坊、自动下载、可视化编辑器、任意 C# 插件及对局中热更新不在本次范围。

## 3. 里程碑与完成条件

| 里程碑 | 必须满足 |
| --- | --- |
| M1 事件格式稳定 | 新选择条目直接带 Lua；无旧下标数组、双重奖励或硬编码卡牌布局；全部消费者与版本变化已登记 |
| M2 事件阶段完成 | 既有事件迁移；任意已支持数量按钮正确命中；正常流程、保存恢复和必要联机检查有真实证据，剩余随机覆盖明确列出 |
| M3 独立包可用 | 不改 core，将纯模式包、纯扩展包或混合包放入 Mods 后，内容进入房间对应选择；新模式复用机制与 Lua，事件按配方入堆；坏包和冲突可定位 |
| M4 分发闭环 | 可选安装、仅补装、导出产生一致包；重复安装和用户修改保护有效；联机与存档能解释精确内容差异 |

“仅生成 schema”“能反序列化”“Lua 隔离执行通过”“看到按钮”均不能替代对应里程碑的完整结果。未完成项保持待实施或未覆盖，不通过修改预期来消除真实失败。

## 4. 共用验证要求

1. 格式与规则检查验证真实边界：身份、路径、引用、脚本路由、重复结算、配方、版本和恢复，不编写只复述实现的测试。
2. 正常验收使用当前实际运行包与场景资产，从可见独立程序菜单和合法行动进入，不注入卡牌、不改随机、不热换包。
3. 按程序版本、内容哈希、GameId、包清单与实际证据累计覆盖。未抽到目标时继续本局，下一局优先在合法可见候选内补缺。
4. 夹具与实际文案、候选或收益不符但可合法推进时保留首次差异并继续；崩溃、不同步、无合法下一步或操作权限丢失时保留现场并停止受影响部分。
5. 测试验证按钮与正确选择、Lua、结果的对应，不把用户可调整的颜色、坐标、字号和装饰固化成不变合同。百分比合法范围及非重叠属于新数据合同。
6. 最终报告区分隔离检查、正常单机、多进程与真实 Steam 多账号。每局列明实际覆盖、缺口和下一局优先级。
