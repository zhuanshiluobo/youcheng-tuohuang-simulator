# 挂链时 Effect 替换：操作时序、保护边界与依赖清单

审查日期：2026-11-16。性质：基于当前工作区代码的静态复审及实施方案；未实现通用替换，也未修改运行时代码。

## 1. 结论

**挂链发生在执行之前，不代表此时仍能任意改换操作。**节点挂入时，调用方可能已经确认了某笔支付、封存了特定行动计划、转移了物品，或者承担了必须完成的义务。此时新节点是在履行已有操作，不能用任意 B 替换 A。

因此不能按“所有公开业务效果都可替换”“所有父流程子节点都不可替换”或“只有纯技术节点不可替换”划分。需要逐次挂链判断其业务用途、已经发生的事实、后续必须履行的合同。

主要行动建设的执行节点应受保护。移动城市产生的下子仍保留独立放置挂链入口。两者都可能是子节点，但承担的责任不同。保护一个父节点不应自动保护整棵子树；某个子节点保护与否也不能仅靠查看祖先是否曾支付费用决定。

本方案区分三种结论：

| 分类 | 含义 |
|---|---|
| 保护原操作 | 按现有业务合同不能开放任意效果替换；保留真实类型、目标、费用、收据和必要收尾。相关专用规则查询/候选修改/费用替代仍按原合同使用。 |
| 保留独立替换入口 | 此处有独立规则操作的含义，允许挂链替换；父流程、结果消费和存档校验需要适配实际执行结果。 |
| 需要先定义结果语义 | 没有证据证明必须保护，但现有调用方依赖特定数据或成功含义；不能仅删类型判断就开放，也不能为省改造而直接全禁。 |

除用户已明确的主要行动建设外，保护范围是本次依据当前实现提出的方案，不表示运行时已经存在这些通用保护标记。第4—7节保留代码依赖索引，不能把每一处类型校验都视为应删除的限制。

## 2. 建设和城市移动的实际时序

### 2.1 主要行动建设：确认支付时已经绑定特定 Build

正常预备付款路径：

1. 建设命令取得已选设施、支付方式、来源区域与付款准备 ID。[BuildFacilityCommandHandler.cs:146](/G:/NoMadCity/Assets/YC/Application/Gameplay/BuildFacilityCommandHandler.cs:146)
2. `TryCreatePreparedPlayerActionEffect` 核对准备记录的 `ActionKind`、`TargetId`、玩家、支付方式、来源与当前报价，不能把另一项操作接到这笔准备付款上。[ResourcePaymentPreparationService.cs:593](/G:/NoMadCity/Assets/YC/Domain/Effects/ResourcePaymentPreparationService.cs:593)
3. 给 Build 添加 `preparedPaymentOwnerEffectId`，然后 `AppendChildEffects` 挂入 Build；接着设置 `PromotedActionEffectId`、`IsPromoted=true`、`IsCommitRequested=true`，关闭原付款输入。这些属于同一次确认工作副本提交。[ResourcePaymentPreparationService.cs:622](/G:/NoMadCity/Assets/YC/Domain/Effects/ResourcePaymentPreparationService.cs:622)
4. 调度先完成付款节点；实际扣费在 `ResourcePaymentPlanService.Apply`，之后才设置 `IsCommitted=true` 并生成最终收据。[ResourcePaymentPlanService.cs:97](/G:/NoMadCity/Assets/YC/Domain/Effects/ResourcePaymentPlanService.cs:97)、[113](/G:/NoMadCity/Assets/YC/Domain/Effects/ResourcePaymentPlanService.cs:113)
5. Build 开始执行时强制要求付款已提交、付款准备指向自身、目标设施一致；已付款后的前置条件失效走故障处理，不另找同名牌。[FacilityEntryEffectExecutor.cs:581](/G:/NoMadCity/Assets/YC/Domain/Effects/FacilityEntryEffectExecutor.cs:581)

精确到代码，顺序是“**确认特定建设与付款 → 挂入 Build 并提交付款请求 → 前序付款完成 → 执行 Build**”，不是先扣完钱包才创建 Build 节点。用户所指出的业务结论成立：这个 Build 已是确认付款对应的执行节点，不能换成得分等任意效果。

由此得到两个实现要求：

- 保护须在 `AppendChildEffects` 之前确定，不能只判断 `Payment.IsCommitted`。当前 `IsCommitRequested`、`IsPromoted` 甚至在 Append 之后才赋值，仅查这些布尔值也来不及。
- 保护的是这一次“付款确认产生的 Build”，不是永久禁止所有 Build。独立 Lua Build 在自身尚未执行、没有承接外部支付或义务时，与此处不是同一操作阶段。

Lua Build 的选择/explicit-auto 付款确认路径也如此：构造实际建设子节点、带付款准备引用、挂链，再晋升付款与切换父阶段。[ResourcePaymentPreparationService.cs:486](/G:/NoMadCity/Assets/YC/Domain/Effects/ResourcePaymentPreparationService.cs:486)

### 2.2 建设已经开始后的内部履行链

Build 在完成自身付款后才挂取牌移动；取牌后补供应槽；之后选择/复验城市格并挂设施安放；安放完成再记录建设事实、消费行动额度、发入场事件及入场效果。[FacilityEntryEffectExecutor.cs:677](/G:/NoMadCity/Assets/YC/Domain/Effects/FacilityEntryEffectExecutor.cs:677)、[742](/G:/NoMadCity/Assets/YC/Domain/Effects/FacilityEntryEffectExecutor.cs:742)、[747](/G:/NoMadCity/Assets/YC/Domain/Effects/FacilityEntryEffectExecutor.cs:747)

已确认建设对应的取牌、补槽、安放、建设事实与额度收尾不能各自变成另一项无关操作；应保留建设日志与实际安放收据校验。免费建设也不等于执行中每一步都可随意改换：免费只是费用为零，已受理的设施转移和最终建设合同仍须成立。

保护这些履行步骤不代表屏蔽入场 Lua 正文。固定入场宿主负责记录“该设施入场”，其返回的独立业务效果仍按各自用途判断；带 `RequiredOutcome` 的必做义务另外保护。

### 2.3 城市移动：整体执行承诺与下子分开

带付款准备的主行动 MoveCity 复用同一晋升函数，绑定已确认的目标地点及付款；它开始执行时也要求付款已提交及前置业务事件已完成。[ResourcePaymentPreparationService.cs:597](/G:/NoMadCity/Assets/YC/Domain/Effects/ResourcePaymentPreparationService.cs:597)、[CityMoveEffectExecutor.cs:147](/G:/NoMadCity/Assets/YC/Domain/Effects/CityMoveEffectExecutor.cs:147)

但 MoveCity 生成子步骤时，位置提交和原位置下子是两个不同操作：[CityMoveEffectExecutor.cs:262](/G:/NoMadCity/Assets/YC/Domain/Effects/CityMoveEffectExecutor.cs:262)、[271](/G:/NoMadCity/Assets/YC/Domain/Effects/CityMoveEffectExecutor.cs:271)。

- 受理特定移动后的整体执行节点，以及落实目标地点的 `CityPositionCommit`，承担该次移动的固定履行责任，应保护。
- 原位置 `PlaceInfluence` 是移动带来的独立下子。保留它的挂链入口，传递 `influenceSource='city_move_source'`、`causeKind=MoveCity` 及父操作来源。不能因为移动已支付而自动屏蔽它。
- 未使用预备付款的 MoveCity 在一次 `AddChildren` 中组织付款、清路、位置提交、下子。**后面的孩子虽然稍后执行，但都在这次 AddChildren 中挂链**；不能把执行顺序当成挂链顺序，误称下子一定是在扣费后才创建。[CityMoveEffectExecutor.cs:224](/G:/NoMadCity/Assets/YC/Domain/Effects/CityMoveEffectExecutor.cs:224)、[279](/G:/NoMadCity/Assets/YC/Domain/Effects/CityMoveEffectExecutor.cs:279)

## 3. 按操作逻辑确定保护范围

### 3.1 按现有合同应保护的履行节点

### 3.2 保留的独立入口与不能自动推导的禁止项

| 场景 | 复审结论 |
|---|---|
| 移动城市中的下子、主要行动额度壳内的部署 | 保留独立 PlaceInfluence 挂链入口。保护已确认的城市移动不等于保护它产生的每个业务后果。 |
| 没有承接已确认操作/必做义务的独立 Lua Effect | 可在自身执行前考虑替换。不能按 Build、Pay、MoveItem 等类型永久归类；后续结果消费者仍须处理实际结果。 |
| InvokeAction 已扣次数后的 Lua 正文、设施入场正文、普通事件响应 | 不因祖先已付款/已消费次数自动禁用。替换后的执行也不能退款、恢复次数或撤销已经发生的发动事实。 |
| Condition 左右式、作者 Choice 分支、AllocateEffects 选项正文 | 它们是实际内容声明。仅选中选项、封存分配顺序，不等于有一笔绑定实体操作的付款/必做义务；不能据此全部禁止。行动专用入口费用门与普通 Condition 必须区分。 |
| ReplaceInfluence 移除后挂放置 | 已移除不自动推出后续放置不可替换。当前已有 `removed_only` 结局；可以在保持真实离场、去向和 RequiredOutcome 约束的前提下研究开放。需先改现有“必有Place叶子”的投影，不能把任意 B.changed 当成放置成功。[InfluenceDepartureExecutor.cs:66](/G:/NoMadCity/Assets/YC/Domain/Effects/InfluenceDepartureExecutor.cs:66) |
| 调度两次移动、批量企业升级、升级后发动特效 | 不能仅因父流程写死类型就认定全部不能替换，也不能仅因没有付款就直接放开。需明确替换后如何计移动次数、实际升级、额度与后续发动，详见索引 P01/P12—P14。 |
| 骰子、候选选择、设施面板选择、出售、分配完成的 Lua 回调 | 有明确数据依赖；是否保护产生数据的节点，或让调用方接收“原结果不可用”，需按该内容规则定义。不能把这31个文件统一改成忽略字段，也不能让替换体伪造原数据。 |

尤其不能采用以下捷径：只检查 `IsCommitted`；看到 `targetMode='explicit'` 就禁止；看到 `Sealed=true` 就禁止；看到祖先有付款就禁止所有后代；看到父节点固定结果就取消该结果校验。这些判断都没有充分表达当前操作的责任。

### 3.3 需要修改的内核合同

1. **在调用点、挂链前确定用途。**Host 对此次挂链明确给出“独立效果”“确认操作的履行”“费用/收据/保管收尾”“必做义务”“纯调度包装”等用途及来源引用。命名尚未定稿，不作为新的 Lua 内容调用许可名单。
2. **保护节点跳过通用任意替换。**它仍正常创建执行，原费用、次数、目标和收据校验保留。若“挂链事件”专指可返回 replace 的规则入口，就不向该入口分发受保护节点。正常业务事件和专用前置接口不受此标记影响。
3. **用途不递归继承。**付款后的 Build 是固定履行，Build 入场 Lua 正文可能是独立效果；受保护的 MoveCity 会产生可改写的 PlaceInfluence。必做义务则只覆盖履行该义务所必需的范围，不能污染无关响应。
4. **用途在冻结模板及运行态中保存。**必须覆盖 Spec复制、Lua编译、NestedEffects、延迟响应、分配执行、替换体创建和存档恢复。不能读档时根据父类型猜测，也不能接受替换体自行把受保护用途改成自由用途。
5. **原声明→实际执行映射只处理真正开放替换的节点。**保留原挂链身份、实际Spec/根ID、改写来源和版本，解决公开组合的恢复校验；无需给受保护履行链普遍放松类型或伪造结果。
6. **原回调与替换体自身回调分别定义。**现有放置实现递归清除替换回调再复制原回调，不宜推广。控制流续接、特定结果续接和真实业务观察者分开处理；不合成未发生的 A 业务事件。

## 7. 不应误判的反例

- `MainActionEffectExecutor.cs:37` 等待部署子状态并负责行动额度；它不要求孩子必须为 PlaceInfluence。部署下子的挂链入口应保留，额度仍按部署行动合同消费，无需伪造放置结果。
- 普通 `Condition`/作者逻辑 `Choice`/分配选项不是天然受保护的支付承诺。其分支可按实际效果结局推进，专用行动入口条件门则有固定费用合同。
- `ResourceCollectionEffectExecutor.cs:42` 及 `ExplorationActionEffectExecutor.cs:75` 的包装能直接转发子结果，不代表整条操作链可任意替换：探索子节点承接封存选路与托管义务。是否保护和是否碰巧没有类型 if 无关。
- 入场和能力正文可以在外部已经扣费、锁牌、消费次数后产生；这不等于正文必须保持原类型。保护外层发动事实，不自动保护每个后续独立收益。
- `ReplaceInfluence` 已有只移除结局；不可仅因前一步产生状态变化，就推导后一步绝不能替换。受必做数量约束的具体调用仍须单独保护。
- 同名 `changed=true` 不是跨效果通用的业务成功证明；得资源改变状态不等于退回标记。开放替换的结果消费者必须区分真实行为，受保护节点则继续核验原合同。

## 8. 实施顺序与验收

### 8.1 实施顺序

1. **先确定每次挂链的操作用途。**登记所有实际挂链入口以及直接 CreateNode 的宿主，区分固定履行、独立效果与尚待确定结果语义的调用。用途由 Host 的操作流程确定，不恢复内容调用许可名单。
2. **保护先于通用改写接入。**先完成 H01—H05 以及暂存/保管等已有责任的保护传递；两条付款晋升路径、覆盖建设义务包装都必须在 Append 前带用途。保留付款、类型、目标、足量、收据及失败处理校验。
3. **只为开放节点实现替换映射。**确定原挂链身份、实际根/Spec、改写来源、多个来源的顺序/冲突以及防循环规则。通用映射不要求存在 Place 叶子，不将 B 的结果覆写成 A。受保护节点不进入任意替换处理器；专用业务前置事件仍正常处理。
4. **执行、结果消费者与恢复一起修改。**P01/P02/P09/P10/P12—P14/P19/P28 等先明确替换后的实际计数、额度、后续执行规则，再适配恢复。第5节只迁移开放调用涉及的回调；保留真实业务观察者、被保护履行链与原费用证明。
5. **同步来源、存档与作者文档。**规格复制、Lua编译、延迟响应、分配执行及存档均保留用途与映射；原回调和替换体回调分别绑定，最多执行一次。最终 Lua API、Event、JSON 写清边界与结果合同，不能将本方案的拟议分类写成已经可用的参数。

本次仅完成静态审计和方案修订。下表是后续实现的验证要求，不是已执行或通过的测试。
