# API-29～32：移动与选择职责纠正

2026-11-01后续实施：core2.1.50；MoveItem4.15.0／item.move.v4.3保持，MoveFacilityCard执行6.0.0（cycle_supply显式apiVersion=4），补槽／刷新2.3.0，ReturnCityStyleMarker执行4.0.0（显式apiVersion=2），Choice执行2.0.0。三个移动接口均不自行或组织补选请求；马丁／德克萨斯在Lua中选择真实设施，街区管理通过独立Flow.ChooseCityStyleMarkerReturn组织真实返还分支。旧阶段包装内选择结论仅为历史。 本文较早复核和XML继续作为历史，当前进展见[显式包装与外部真实选择](API-31显式包装与外部真实选择-20261101.md)。

依据本轮用户明确纠正：`MoveItem`只是完整移动效果，不能发出选择。该要求覆盖此前4.13及API-29中错误的共同select设计。本轮仅修正原API-01～39范围，API-40～44仍待实施。

本阶段历史合同为core2.1.49、MoveItem执行4.15.0、item.move.v4.3。原39项暂按33完成／6部分（API-07、25、29～32）记录；相关合同、实现和等价验证重新打开，不能沿用旧37／2完成口径。

## 较早阶段实现（下列包装内选择已撤销）

2026-11-01 本轮用户进一步明确：无交互约束包括 MoveItem、MoveFacilityCard 和 ReturnCityStyleMarker。以下条目记录执行者目前的阶段实现；其中把选择移到设施／样式返还包装内的做法尚不满足最终要求，不能作为整改完成依据。三个移动接口之外的独立编排才是最终选择所有者，其他合法业务 API 的交互不在本次撤除范围。

- `MoveItem`接受explicit真实实例及源位置，或补牌的确定top取顶；不支持selector.select，不因为缺目标而自动打开选择。
- 设施v3回底由父业务节点从当前公开供应顶牌选择。确认前没有MoveItem子节点；确认后explicit回底，再按真实原槽是否为空决定top补牌。
- 正常主盖放任务处理已有盖牌、空手回收和character.cover.card选择；确认后才创建explicit共同盖放。槽、移动、生命周期及实际盖放事件仍由共同移动实现，不复制搬运。
- ReturnCityStyleMarker父业务节点持有本人二级样式标记选择，确认后explicit返还真实原供应；直接MoveItem必须给出明确目标。
- 旧MoveItem选择请求、旧执行定义及旧保存状态拒绝恢复，不改写旧档，不给错误请求新增UI路由。
