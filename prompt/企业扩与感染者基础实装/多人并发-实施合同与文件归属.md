## 客户端结果与草稿

UI统一新增表现层结果消费签名：`NotifyInteractionCommandResolved(string gameId, string commandId, bool accepted, CommandErrorCode errorCode)`。由正式Accepted/Rejected的准确已提交身份驱动，保留其他流程旧 `NotifyCommandSettled` 兼容入口；不能从当前新局随便补旧命令GameId。`Initial`、别人的确认、更高revision、纯诊断或超时不代表本人命令成功，不清未知pending或自动重发。

同局、本人、稳定request/owner、候选scope/版本、答案约束及真实依赖一致时，refresh只更新token，保留合法草稿和inFlight意图。采集新增业务方法 `TryRefreshOpenBinding(RouteSelectionSession session, RouteSelectionRequestBinding binding, IReadOnlyList<string> selectableLocationIds, out string diagnostic)`，调用原RefreshFromState复验，不能Clear/Begin清空同合同草稿。实际提交仍fresh检查准确revision。

仅准确同CommandId的正式StateRevisionMismatch拒绝，才可保留用户已确认的同一意图，等待更新的本人真实投影后以新CommandId/new revision重建原命令；只在上述合同未变且答案仍合法时执行，不替用户改目标/费用/收款方。每个已确认意图最多沿不同新revision自动重建3次，未变token不循环；未知结果/其他拒绝不重试。耗尽或真实合同变化沿原错误/草稿反馈，不加确认弹窗、按钮或其他新操作。

正常盖放资格来自本人当前normal cover open请求及原候选交集，不再用全局CurrentPlayerId挡住本人；行动轮和技能权限不扩大。企业现有合法选中项保持能力要保留，只补身份域和等待/一次确认逻辑。路由真实基类若不在上表，UI先报路径，避免改错共享层。

组合政策当前 `IsExactStaleRejection` 只认 `InvalidTarget + 原精确Reason`，本批必须消费新增typed码，同时保留原已记录旧格式的精确兼容。身份、同局、请求合同、候选、数量、有限重建及原超时不变；不得把全部InvalidTarget都算可重试。企业/盖放新增并发路径若需重建，沿相同精确原则且先报告业务文件增量，不编造成功。
