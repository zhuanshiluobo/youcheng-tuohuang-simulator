## 1. 建议收口的主路径

主机保留唯一编序入口，将每条已受理提案先纳入全局日志并转发；各端只按这份日志执行。主机自身也执行一次同样的规则提交，直接以这次提交的结果推进已核验前缀。编序与主机规则执行可以分时调度，不另建第二个会话重新跑完整业务校验。

首批建议发送者收到主机编序后才执行。发送者收到自己的回送也只按序消费一次。连续操作在本地应用前一条已编序命令后即可继续，不等待主机业务核验回包，也不等待其他进程逐条就绪。互不依赖的提案可以连续发送；依赖前一条结果的操作需等本地按序执行出真实结果。这里仍有编序转发的网络往返，但没有每条命令的全员屏障。若以后要求发送前就本地执行，必须增加预测分支与重排恢复，不能仅把回送当重复消息丢掉。

企业选择、正常盖放、正常采集的多个操作人使用同一个可并发窗口或规则定义的并行窗口，不把操作权轮流交给玩家。全局日志中命令有先后，不等于玩家逐个完成整轮。只有满足声明及异人条件的多萝西旁路窗口才与主窗口分别计数；同人或未声明的响应保持原窗口的必结子流程。所有回答仍进入同一全局日志。

主机规则执行尚未追上的命令属于已编序、未核验命令。仅主机编序成功不能触发旧接口中的最终接受回调。窗口封口时才核对全局连续前缀、窗口连续序号、命令数量和摘要。发生业务拒绝或确定性差异，首批统一停止当前模拟分支，恢复确认检查点；不假设已有跨命令任意回滚。

## 3. 唯一编序、窗口和前缀

### 3.1 身份及三个不同的进度

新协议身份复用已有 `GameId`、`RuleConfiguration.ContentPackHash` / `RuleContractVersion` 和当前连接 token；只增加新模拟能力/协议版本、`SimulationEpoch` 与同步副本 `MembershipVersion`。不另外产生 GameId/seed，也不重定义随机算法字段。当前连接的 `ConnectionToken` 只用于运输身份，不进入规则摘要。新能力与旧投影 schema 独立协商，不能碰巧数字相同就当兼容。

| 字段 | 建议定义 |
| --- | --- |
| `OperationWindowId` | 规则语义窗口 ID；保存窗口类型、开启原因、操作人集合、父窗口/事件引用及响应完成依赖。不能只拼 Round / Phase / CurrentPlayerId |
| `MainWindowPlayerId` / `RespondingPlayerId` | 响应创建时规则解析出的真实主操作窗口玩家与实际回答者，对应合同中的 `mainWindowPlayerId` / `respondingPlayerId`；与主窗口 ID/代次及来源全局号一起保存。没有明确单人归属时不能猜测为旁路 |
| `WindowGeneration` | 同一逻辑窗口恢复后的代次，用于拒绝迟到的旧封口、回答、就绪消息 |
| `ClientSubmissionSequence` | 每玩家、每模拟代次的提案连续号；跨本人主/旁路窗口保持顺序。由发起端分配，用于补取和去重，不作为规则执行顺序 |
| `WindowCommandSequence` | 主机为该窗口每条已编序业务命令分配的连续号，初次从 1 开始；多个操作人不各自分配窗口号 |
| `GlobalCommandSequence` | 主机单写者为全部业务命令分配的顺序，包含主机玩家、其他玩家和旁路回答；在当前模拟分支中连续 |
| `LastAppliedSequence` | 每个副本已按序执行完的全局连续前缀；不是最高收到的号 |
| `ValidatedThroughSequence` | 主机自身成功按序提交的全局连续前缀；不是最高转发号 |
| `LastSealedSequence` | 已完成规定副本就绪与摘要核对、已有恢复材料的窗口确认前缀；可落后于主机已核验前缀 |

`StateRevision`、规则 journal 的 `CommitSequence`、网络全局序号各自保留。不能假定一次命令只增加一次 revision 或一次规则 commit；也不能拿 `expectedRevision` 填全局序号。

恢复时需要序号分支命名，建议采用 `(GameId, SimulationEpoch, GlobalCommandSequence)` 身份：新代次导入旧代次的确认前缀到基线 V，后续从 V+1 继续，旧代次未核验的数字位置允许在新代次重新分配。数字单独不能跨代次比较。此建议需要根收口；若要求跨恢复数字永久不复用，需另定义废弃区间的占位日志及连续前缀语义，不能两种办法混用。

### 3.2 主机单写者

建议入口 `OrderedCommandSequencer.AdmitProposal`。主机自己的玩家也走这个入口，不能继续直接调用旧 `SubmitHostCommand` 绕过队列。

编序前仅核对当前连接绑定、同局/代次/协议、已公布窗口及操作/响应资格、所需转换许可、包大小和字段形状、提案连续号、命令 ID 与载荷摘要。窗口资格依据已经登记的规则窗口描述和许可，不在收包时再次执行整套业务。必结子流程的回答使用已公布交互请求的真实回答者授权，不因此扩大普通操作人集合。旧窗口不存在、成员不同、尚未取得必要转换许可或身份不符时不受理业务，不分配业务序号。

同一玩家提案缺号时暂存并请求缺项，不能让其后来的跨窗口命令越过缺项；其他玩家仍可编序。重复提案以同一个 `CommandId`、同一个原始载荷摘要返回原编序记录，不再次执行。同 ID 不同载荷必须报冲突。所有收到的有效提案由这一入口串行分配全局号及对应窗口号，并先写日志，再转发 `OrderedOperationCommandDto`。

首次迁移建议新窗口描述由主机自身规则执行产生后公布，各副本核对其开启全局号、真实主窗口归属、响应挂载结果和规范化窗口描述摘要。只有满足旁路条件且不存在真实依赖的主操作才可在新旁路等待公布/回答时继续；同人或未声明的 RequiredChild 仍保持父流程等待。不能把每条后续操作都变成等待主机重新授权。若以后允许主机尚未执行开启命令就受理子窗口，必须增加可核对的窗口开启证明，此处不假定已有。

主机收到控制封口请求时只暂停该窗口的新受理。规则合法性仍由随后按序执行确认；未核验封口不是正式完成。队列积压设有界容量和明确暂停原因，不通过清空未核验记录或静默丢包释放容量。

### 3.3 各端应用及自动流程

建议 `DeterministicCommandReplica.ApplyOrdered` 只消费 `LastAppliedSequence+1`。更高号缓冲，缺口补取；同号同摘要且已消费时不再提交；同号不同摘要立即记录差异并停止分支。窗口号与全局号的映射也须一致，不能仅全局序号相等就接受不同窗口。

使用该副本装配的 `GameSession.Submit` 执行业务和其自动后继，每条全局记录至多提交一次。各端不得按各自收包顺序执行，也不得额外把已由规则自动产生的内部流程再作为外部命令执行一遍。外部定时、UI刷新不能独立推进影响规则的自动流程；具体自动推进边界由共享状态方案收口。

普通 Event 仍由规则自动挂链，响应挂载种类只控制完成依赖，不把 Event 改为手动或可放弃。命令成功提交可以产生尚未完成的 RequiredChild；`LastAppliedSequence` / `ValidatedThroughSequence` 前进只说明命令提交成功，不说明该响应或父 Effect 已完成。只有准确答案结清、必结子流程完成后才允许执行父 Effect 后继；高序号、转发回包、输入解锁或 EndAction 都不能代替该条件。

主机的同一条 `ApplyOrdered` 成功结果直接写核验记录并推进 `ValidatedThroughSequence`，再发布 `CommandValidationPrefixDto`。不增加第二次完整 `session.Submit`。主机规则队列可以在既有允许的执行环境中逐批调度，与收包编序分离；“异步”不等于现在就把 Unity/Lua/会话对象放到任意线程并发修改。网络回调不得同时改正在提交的规则状态，真实线程约束仍需实现时核对。

其他副本可比主机先执行同一已编序前缀，属于未核验模拟进度。主机先核验而某副本尚缺号时，该副本仍先补齐，不能仅收到核验前缀就增加本地执行号。

### 3.4 复用已交 START 事实，初始化只补完整模拟检查点

开局权威来源已经确定：RoomState 协议 4 中的 GameId、EventDeckSeed、RandomReady、RandomAlgorithmVersion、RandomRuntime、LaunchPlayerOrder 与 Configuration。网络沿现有 START 传递，StartMenuController 转交现有 GameLaunchContext.Configure。后继不新增独立种子 DTO、InitializationId、另一算法字段或并行 GameSeed 真源，也不要求再次挑选随机算法/用途流方案。

实际算法为 `GameplayRandomRuntime.AlgorithmVersion = yc.splitmix64-fnv1a-utf16.v1`。已定义用途流：`launch.order.v1`、`setup.decks.v1`、`setup.styles.v1`、`enterprise.prepare.v1`、`effects.deck-shuffle.v1`、`effects.dice.v1`、`events.initialize.v1`。状态按 StreamId 有序保存 State、WordsConsumed、RequestsConsumed；种子仍取 EventDeckSeed。开局顺序已经消耗 launch.order.v1，冻结 RoomState.RandomRuntime 和 Context.InitialRandomState 保留该位置；后继直接继承，不重抽顺序或重播种。

第一批新模拟建议从主机已完成开局自动流程、停在合法操作边界的完整检查点开始，客户端不自行重跑开局配方。具体顺序：

1. 继续通过 RoomStateSerializer 的协议/字段/随机状态校验及现有 Configure 正式重载采用 START；联机 RandomReady 不成立时不进入规则模拟。本地新局保持 ConfigureNewLocal，复现保持显式 seed，均不另加协议入口。
2. 主机用现有 GameLaunchStateFactory 正式重载、Bootstrapper.Build 完成真实开局，到首个操作边界用 `HostRecoveryService.CreateArchive` / `SerializeArchive` 生成完整检查点，绑定新协议基线 0、窗口描述、成员版本和规则状态摘要。seed、算法及游标已在 Archive.Snapshot.State 中，不再复制成另一组权威字段。
3. 客户端等待完整检查点时只装配静态内容和同等 handler/registry；新模式在 `GameSessionBootstrapper.Build` 的 `StartEntrance` 调用点暂停，不能先在部分状态上执行入口流程再宣称已完成初始化。最小入口建议为 Build 增加缺省 false 的 `deferRuleInitialization`（或根统一的新模式选项），只由新模拟客户端采用；现有 Client factory 的未装配状态仅作装配基础，安装检查点后才执行规则，不改它为再次随机开局。
4. 接收端用 `HostRecoveryService.RecoverJson(archiveJson, effectRegistry)` 验证原 JSON、内容、handler 与随机状态，要求结果 Succeeded，并核对其 GameId、EventDeckSeed、算法及 LaunchPlayerOrder 与已接受 START 一致，再用 `GameSession.ReplaceState` 安装。初始完整检查点须有各流对 Context.InitialRandomState 的合法连续关系；此关系可以复用 IsContinuation，不另造游标验证器。
5. 复用既有 `OnInitialStateApplied` 的连接/玩家验证职责；新模式单独用 `SimulationStateAppliedMessage`，在这些身份之外只带模拟代次、checkpoint ID、基线序号、成员版本与该前缀状态摘要，不带第二份种子。主机核对全部规定副本后开放初始窗口；这是开局一次就绪，不是每条命令屏障。旧 `InitialStateAppliedMessage` 保持原 PlayerId/ConnectionToken 布局与处理语义，避免改变旧线格式；旧“投影已应用”不算“完整模拟已准备”。

Bootstrapper 的 effectRegistry 当前是 Build 局部对象；Result 尚未提供它。建议共享后继只补 `Result.EffectRegistry` 或等价的安装入口参数，供 RecoverJson 使用真实 registry，不在网络层重造 handler 装配。含 continuation 的 archive 不能省略 registry 后当恢复成功。

完整 State 安装/一次按序提交后，现有 `ProjectFor(viewer)` 可以生成本人投影，但它不更新会话 View；`ReplaceView` 会裁剪 State，不能用于新模拟刷新。建议共享补 `GameSession.RefreshLocalProjection(GameStateViewer viewer)`，只设置 `View = ProjectFor(viewer)` 并保留完整 State，再通知既有界面消费者。调用发生在提交/恢复边界，不逐帧推进规则；UI owner核对当前实际消费点使用本人投影，无新增布局。

同局重复 START 的幂等/冲突判断已由 Configure 处理。新完整检查点另按 GameId、SimulationEpoch、CheckpointId、基线及摘要去重：已安装的重复包只重发确认，不重新安装、重洗或把 LastAppliedSequence 退回 0；运行中的新恢复检查点必须经过明确恢复握手。其他局/旧代次/旧连接包不替换当前局。

重连直接采用当前确认 archive 中的真实 GameState.RandomRuntime，并补后续确认命令日志；不以 Context.InitialRandomState 覆盖当前游标。检查点恢复可以回到较早确认前缀，之后按序重放；IsContinuation 用于同向日志/批次验证，不能误用成禁止合法恢复到旧检查点的条件。旧档缺 RandomRuntime 的原兼容行为保留，但不能标成新模拟就绪，不猜游标或从初始 seed 跳到当前序号。

洗牌和骰子持久流、失败事务不提交随机游标已经落盘，本轮不将它们重复列为实现缺项或重跑检查。后继只验证这些既有状态随新完整检查点与命令日志正确续接；候选全放回仍按原规则洗牌，允许再次抽到同牌，不加“必须不同”断言或额外完整局批次。


## 4. 多人及多萝西交错

主窗口操作人集合与同步副本集合分开：前者决定谁能提交，后者决定窗口转换时哪些副本须就绪。多个操作人无需轮流完成整个窗口。窗口的关闭条件、是否每位操作人各自完成，由共享/规则 owner 定义，不能由网络层把“收到第一个 EndAction”解释成所有人完成。

### 4.1 可省略声明与创建时的真实归属

复用共享提案的 `EventResponseAttachmentKind`，不增加语义重复的必填布尔字段。现有直接返回 Effect 列表的 Lua 保持有效，未声明时按 `RequiredChild` 自动挂链。声明 `DeferredPlayerResponse` 只是允许进入条件判断，不是强制独立挂载，也不是允许自动跳过。

本轮补读的 [operator.dorothy.tactic.lua](<G:/NoMadCity/Assets/StreamingAssets/Content/core/lua/characters/operator.dorothy.tactic.lua>) 仍直接返回 Choice Effect 列表，没有上述挂载声明。以下异人交错例是声明与调度接口接入后的条件方案，不表示当前生产已允许旁路；旧脚本不因字段缺省而报错或被默认为旁路。

响应创建时，从规则操作窗口/因果上下文解析 `MainWindowId`、`MainWindowGeneration`、`MainWindowPlayerId` 与实际 `RespondingPlayerId`，保存来源全局号、父 Effect/完成依赖、触发 Event ID、准确离场影响力实例及角色牌实例。Host 身份、LocalPlayerId、旧 UI CurrentPlayerId、触发命令 PlayerId 或单纯 EventType 不能替代真实主窗口归属。

| Lua 声明与规则归属 | 实际挂载 | 完成依赖 |
| --- | --- | --- |
| 未声明；或明确 RequiredChild | RequiredChild | 原父流程等待响应完成 |
| 声明 DeferredPlayerResponse，但回答者与真实主窗口玩家相同 | RequiredChild | 本人必须回答并结清，父流程不能越过 |
| 声明 DeferredPlayerResponse，且两者明确不同、真实主窗口归属完整 | DeferredPlayerResponse | 独立响应段保留；仅放行与回答无关的主操作，真正依赖仍等待 |
| 声明允许，但没有明确单人窗口/身份不足；多人窗口未收口对应归属规则 | RequiredChild | 不猜测旁路，保留原完成依赖；若响应自身身份无效仍按原规则报错 |

多人并发窗口的操作人集合不能被临时挑出一人当主窗口玩家。若共享定义某命令具有准确单人主操作分支，须明确其权威分支 ID 与玩家来源后再采用；接口未收口时保留 RequiredChild，不因此把整个多人阶段改成轮流操作。

声明、创建时绑定和实际挂载结果是可规范化规则状态，各副本得到同一结果；主机发布的描述可核对，不允许客户端按当前界面重新分类。已合法形成旁路后，窗口切换不能仅因 UI 当前玩家变化就重新挂链；后续依赖仍由真实实例/资源/角色牌规则判断。恢复也应恢复这个绑定和父依赖，而非重新看 UI 判断。

### 4.2 异人且允许旁路的交错示例

本例限定：M 的真实主窗口玩家为 P，多萝西实际回答者为 Q，P≠Q，Lua 已声明允许，调度器据此实际挂 DeferredPlayerResponse。等待期间实例属于规则定义的保留状态，不回到可再次消费供应；收留回答不撤销原移除/替换事实。回答采用普通全局编序与一次性消费，不专设无序私有响应通道。

| 全局号 | 窗口与窗口号 | 操作 | 对状态/封口的要求 |
| --- | --- | --- | --- |
| 101 | 主窗口 M / 1 | P 操作移除实例，触发 Q 的多萝西响应 D | 验证允许声明与 P≠Q，为准确实例建立保留引用；D 由主机按规则公布 |
| 102 | M / 2 | P 的另一项与该归属无关的操作 | 不等待 D 回答，也不等待四端逐条确认 |
| 103 | D / 1 | 多萝西回答收留 | 只处理 D 绑定的实例，不重复执行 101 |
| 104 | M / 3 | 主窗口合法结束操作 | M 的最终窗口号 3、命令数 3；到全局 104 的规则状态包含 D 的回答 |

M 的命令有序摘要按 101、102、104 计算；D 按 103 计算。全局摘要按 101、102、103、104 计算。M 不是有四条窗口命令，也不能把 D 的序号 1 与 M 的序号 1 当成重复。

在这个已合法形成的异人旁路中，若 D 尚未回答而 M 请求结束，网络层保留 D，不能随 M 清空它。只在规则 owner 明确没有依赖时允许 M 转换并继续 D；若下一流程消费该实例归属、涉及角色牌离场或达到必答边界，按规则列明的依赖等待。旁路仍必须结清，不能因 M 结束就自动放弃。哪些后继依赖、最迟等待点、角色牌离场如何处理仍由多萝西方案确定，本方案不补造超时拒绝、自动收留或永久悬挂规则。

### 4.3 本人触发本人响应：保持必结子流程

若 M 的真实主窗口玩家就是多萝西 P，P 移除本人的影响力，即使 Lua 声明 DeferredPlayerResponse，实际仍为 RequiredChild。不会为这个 Choice 创建可绕过父依赖的独立响应窗口。示例：

| 全局号 | 窗口与窗口号 | 合法操作/状态 |
| --- | --- | --- |
| 201 | M / 1 | P 移除本人影响力，生成本人 RequiredChild，父 Effect 后继等待；提交成功不等于响应完成 |
| 202 | M / 2 | P 明确提交收留或拒绝答案，准确实例去向结清；子流程完成后才恢复父 Effect 后继 |
| 203 | M / 3 | 父流程满足原规则条件后，P 再执行下一合法操作或合法 EndAction |

本人回答按原窗口内交互请求绑定并计数，保留真实回答者和候选/revision 约束。未声明 Lua 的同人或异人响应同样保留 RequiredChild 完成依赖。等待、关闭控制消息或更大的全局/窗口序号不能替代答案；不能把拒绝选项解释成超时自动拒绝。非法越过提案即使已先编序，规则副本也不能因此执行后继或生成成功封口，仍按准确拒绝/恢复流程收敛。

契约已明确允许立方体与保罗帮派实例，不新增牌上四枚容量限制或空牌弃置。当前 Lua 默认分支的 `LoadCardMarkers(maxCount=4)` 不被本方案解释为新的收留容量规范；其具体含义与迁移由规则 owner 处理。无界面布局写入。

## 5. 窗口封口、数量及摘要

### 5.1 封口过程

1. 操作人发 `OperationWindowCloseProposalDto`，声明本窗口最后一项提案的客户端提交号及相应命令 ID。若规则要求真实 `EndAction`，它仍是一条业务命令并进入窗口计数；关闭提案不能代替这次规则提交，也不能替代尚未结清的 RequiredChild。已核验前缀和计数完整不代表原响应完成依赖已满足。
2. 主机先补齐并编序该声明之前的提案，结合窗口规定的其他操作人结束条件，关闭该窗口的新受理，固定 `FinalCommandSequence`、`CommandCount`、`GlobalFenceSequence`。最后一个窗口命令的全局号与全局封口前缀可不同，因为其他窗口可能已交错进入日志。
3. 主机自身按序执行至 `GlobalFenceSequence`，成功前缀覆盖它后才生成核验摘要和 `OperationWindowSealDto`。若业务拒绝，窗口中止，不发送成功封口。
4. 每个规定副本补齐到该全局前缀，核对窗口号连续、数量、命令摘要与规则状态摘要，然后回 `OperationWindowReadyDto`。主机自身也在规定副本集合中。
5. 主机收齐完全匹配的就绪并保留确认检查点/必要日志后，发布 `OperationWindowAdvancePermitDto`。每条窗口内命令没有这项全员屏障。

仅在 RequiredChild 已结清且原规则允许结束时，`EndAction` 本地提交才可能自动推进到下一操作窗口；这属于模拟结果，不自动授予下一依赖窗口的输入权限。共享状态模型须标明 `RequiredSealedWindowIds` 或等价的同步依赖边界，并保留独立的子流程完成条件；下一窗口在收到匹配转换许可后开放，不能为了等待而再次执行 EndAction。无此依赖的其他开放窗口及已满足异人条件的多萝西旁路仍可继续。自动流程在边界的暂停/恢复必须由规则调度统一，网络层不能靠临时修改 CurrentPlayerId 阻止或恢复推进。

允许无操作窗口时，最终窗口号及数量均为 0。普通窗口初始号为 1，正常成功封口要求窗口命令 1..F 完整，`CommandCount=F`。命令数只计算业务命令，不计算提案重传、就绪、日志补取、关闭控制消息。受理前拒绝不占号；已编序但业务拒绝会中止此模拟代次，不把这段窗口伪装成正常成功封口。若需要另报成功数/拒绝数，单独命名，不能用成功数覆盖命令数。

恢复导入的窗口保留已确认的窗口前缀 1..K，新代次从 K+1 继续，描述带 `BaseWindowSequence=K` 和该前缀摘要。最终数量包含导入的真实命令；未核验尾段作废。新窗口与恢复后的旧窗口不能含糊地都从 1 重置。

### 5.2 连续前缀与就绪身份

每条就绪必须匹配同一 `GameId`、`SimulationEpoch`、`OperationWindowId`、`WindowGeneration`、`MembershipVersion`、准确副本成员 ID、`GlobalFenceSequence`、F、数量和摘要。操作人全部点完不能代替全部规定模拟副本就绪；收到最高号不能代替缺失的连续前缀。

旁路或其他窗口可以继续编序，不强制全部停在某个窗口封口。此时副本可能已执行到更高全局号，必须保留或可重建“恰好在封口前缀”的规则状态摘要。不能拿后来已经变化的当前状态与较早封口摘要比较。需要实现按前缀保存摘要/检查点的生命周期，现有当前投影不足以提供这一能力。

断线不静默算就绪。成员变更须由明确的会话策略产生新成员版本，并完成恢复/重新封口；本方案不自行决定踢人、超时替答或转移操作权。晚到的旧成员、旧窗口、旧代次就绪直接隔离。

### 5.3 规范化摘要

建议定义明确版本的 `CanonicalCommandDigest` 与 `CanonicalRuleStateDigest`，均采用固定编码规则；具体算法和字段白名单由根与共享统一，不能各端直接序列化任意对象后各自哈希。

命令摘要覆盖局/代次及来源、全局号、窗口及代次、窗口号、操作玩家、CommandId、Kind、SourceId、TargetId、OptionIds、参数、观察前缀及依赖令牌。参数按 ordinal 键顺序规范化，拒绝重复键；保留有语义的列表顺序。数字、空值及 UTF-8 编码固定，禁止受本地文化影响。按窗口号组成有序窗口摘要，另保存全局连续日志摘要。原始提案和后述 revision 执行适配证明都能追溯，不能悄悄改掉原提案后只保留新摘要。

规则状态摘要必须覆盖影响未来规则的完整模拟信息：内容及规则版本、玩家/地图/卡牌/影响力等实体和稳定 ID、牌堆顺序、资源及区域归属、开放交互及候选合同、Effect/continuation/结算进度、响应声明/实际挂载/创建时主窗口归属及父完成依赖、旁路保留实例与依赖、操作窗口、本局初始化载荷/种子、随机算法与流版本、每局随机状态及调用位置、规则使用的 ID 生成状态。规则 revision 与 journal 元数据是否入摘要按其实际规则作用定版，不能一概抹除。无序容器须确定排序；有序容器保持规则顺序。

排除不影响规则的本地日志时间、UI对象/装饰/静态文案、连接 token、网络延迟、进程号、展示缓存。不得排除真正影响规则的时间或字段来掩盖差异；若存在进程本地时间参与规则，要先改为同步规则输入。`GameStateView` 缺少隐藏规则信息，不能作为完整模拟摘要；原始 `GameState` JSON 也未提供上述规范化合同。

## 6. 缺包、重传、去重和确认账本

建议补取 `OperationCommandRangeRequestDto` / `OperationCommandRangeDto`，按同局/代次请求从本地下一全局号起的连续区间，携带日志起点和校验摘要。这里重传已编序日志，不生成新 CommandId，不调用业务入口重新提交。

在编序前，用玩家提案号和 `CommandId + 原载荷摘要` 去重；在消费端，用 `代次 + 全局号 + 载荷摘要` 去重；在最终通知端，用真实局/玩家/CommandId 去重。这三个层次不能由一个“最近收到 ID”替代。恢复导入的已确认命令身份也保留，避免重连后把已经成功的业务当成新提案再次执行。

日志须保存到相关检查点可恢复且规定成员不再需要该范围。若缺项已超出可补区间，返回明确的检查点恢复指令；不凭 `Unknown` 推断拒绝、不补造空命令跨缺口。现有 512 条结果缓存是结果查询缓存，不是持久命令日志或全量重放保证。

建议 `OperationCommandTracker` 区分：待编序、已编序、已本地应用未核验、已核验、业务拒绝、因恢复中止。提案号、全局号、窗口号、真实 ID 和原始载荷保留到终态。客户端界面需要两个独立消费点：

- `SimulationCommandApplied`：真实命令已经本地按序执行，释放这一提交的本地输入占用；继续保存未核验记录。若产生 RequiredChild，仍受其既有交互门控约束，不能清空待选择或释放父流程完成依赖；不能借输入释放执行父后继或非法 EndAction。
- `CommandValidationPrefixAdvanced`：主机确认前缀覆盖该命令，才一次性形成最终接受；拒绝/恢复终态另行处理。

这些是建议新事件，不在本轮接入。现有 `commandSettled` / `interactionCommandResolved` / 覆盖确认的成功语义不能靠编序回包提前触发。新模式的 UI 投影由完整模拟调用 `ProjectFor(GameStateViewer.Player(...))` 得到，不直接把完整 State 填进他人手牌、秘密裁牌、游戏盒或日志展示入口。

分片继续保持有界、严格身份和完整组装后应用。新全量 checkpoint 若超过当前 8 MiB 限制，应报告实际大小并设计新限制/格式，不先放宽上限或称当前组装器已经支持。新传输类型应包含用途、局/代次、checkpoint/范围 ID、总长及载荷摘要，与旧 `initial` 布尔分支隔离；同一组装器不能混入不同用途的片段。

## 7. 主机拒绝、差异及确认前缀恢复

首批建议保守地停止整个共享全局分支。虽然错误来自一个窗口，但其他窗口的已编序尾段可能依赖其状态；尚无依赖隔离证明时，不只撤回一个玩家的命令并继续全局尾段。这是协议建议，需根确认后实施。

假设主机已成功到 V，在 V+1 首次业务拒绝，部分客户端已执行到 V+4：

1. 主机停止规则消费与该代次的新编序，保留 V+1 的原提案、准确拒绝结果、已转发尾段及摘要差异。客户端若先出现规则执行失败，也停止推进并上报差异；不能自行当作主机终态拒绝。
2. 发布 `SimulationRecoveryDirectiveDto`，绑定旧代次、失败号、已核验前缀 V、恢复目标、checkpoint ID、成员版本和新代次。V+1 为准确业务拒绝；后面的未核验命令标为因恢复中止，不伪造其业务拒绝或成功。
3. 选择确认检查点 C≤V，恢复完整规则状态、随机状态、稳定 ID 状态、窗口/响应任务、响应创建时真实归属与实际挂载/父完成依赖、实例保留关系及确认命令账本。C 不必等于 V；必须有 C+1..V 的完整、已核验日志和一致版本。
4. 按旧日志的唯一顺序重放 C+1..V，核对重放结果与目标摘要，再导入新代次基线 V。重放不得重新发送网络提案或重复触发外部一次性通知；本轮不假定现有 UI/日志消费已具备此隔离能力。
5. 新代次从 V+1 编序。保留仍有效的逻辑窗口及已确认窗口前缀，增加窗口代次，旧未核验封口与尾段全部作废。已确认响应保留创建来源、实际挂载和未结清父依赖，不因恢复后 UI 当前玩家变化改为独立窗口。旧代次回包不能推进新代次进度。
6. 规定副本回 `SimulationRecoveryReadyDto`，核对基线、摘要、窗口描述和成员集合后恢复输入。未核验尾段不自动换 ID 重发；按新真实交互状态重新处理意图，是否允许有限重建须有明确定义。

窗口/规则摘要不一致、同号载荷冲突、内容版本不一致、随机状态不可恢复，也进入停止与差异保全，不仅处理漏包。单纯网络等待或规则执行异常不自动翻译成业务拒绝。主机已核验前缀只表示其业务提交成功；规定副本发现确定性差异时仍须通过恢复握手核对目标状态，不能静默承认错误结果。

现有 `HostRecoveryService.Recover` / `RecoverJson` 已恢复并校验随机状态及其连续性，不再列为缺项。后继缺的是网络全局/窗口游标、窗口/响应绑定、确认命令日志及去重账本、跨副本摘要握手和 C+1..V 的按命令重放。必须检查 `HostRecoveryResult.Succeeded` 后才用 `GameSession.ReplaceState(result.State)` 安装；恢复失败即使携带 State 也不能当作成功检查点。旧档没有 RandomRuntime 的兼容恢复不等于可加入新模拟协议，不自动猜测或补建游标。

## 8. strict revision 与新序号兼容

旧路径保留原 `expectedRevision` 以及现有 pending / 真实结果恢复。新模式由完整能力协商选择，禁止半数副本走投影替换、半数副本走规则重放；恢复也不能通过换运输模式掩盖差异。

直接照搬旧全局 revision 会使合法并发操作互相过时。直接删掉 strict revision 则会放行已经改变的候选、费用或实例。因此建议两层兼容：

1. **默认精确模式**：未登记依赖兼容合同的命令继续按真实 `expectedRevision` 执行；不把新全局号替代 revision。发送前记录 `ObservedGlobalSequence`、`ObservedStateRevision` 及对应交互绑定。
2. **定向依赖模式**：仅共享/规则 owner 已定义依赖合同的企业选择、正常盖放、正常采集等交互允许适配。验证原提案确实绑定观察前缀下的请求/玩家/窗口，比较请求语义、候选版本、契约摘要和真正影响合法性的依赖。全部仍有效时，各副本在执行该全局号前，由同版本适配器导出独立执行命令，把其 `expectedRevision` 绑定到当前真实请求 revision，再调用现有严格处理器。

建议类型 `InteractionCommandPreconditionDto`，字段至少有请求 ID、类型/owner、窗口、候选合同版本、观察全局号/规则 revision、`ContractDigest`、`DependencyStamp` 和适配器版本。建议入口 `CommandRevisionCompatibilityAdapter.TryCreateExecutionCommand`。原 `GameCommandDto` 不修改，原始 revision 与派生执行 revision/适配证明都进入命令结果记录及重放摘要。编序器不负责计算业务依赖或派生 revision，主机同一次规则消费检验它。

仅候选 ID 不变或去掉 revision 后投影 JSON 相同，不足以证明依赖不变。费用、资源/供应、区域归属、实例存在、牌模式、响应因果及本次选择的合法性可能已经变化。`InteractionCommandIntent.Contract` 和 `dependencyKey` 提供了现有定向比较思路，但不代表上述命令已经具有完整依赖合同。具体依赖字段与支持种类必须由各规则 owner 确认，不能普遍把所有 `expectedRevision` 重写为最新值。

依赖改变、不认识的命令、缺少观察前缀证据或适配器版本不一致，保留准确的 revision/规则拒绝并进入上述恢复政策。旧 `TryRebuild` 只在明确拒绝和刷新后有限重建的边界继续成立；未知结果和未核验通知不触发自动重提。多人并发协议正式切换的条件包括这些并发种类的依赖合同，不能用只支持精确模式且频繁互相拒绝的结果宣称保持原并发体验。

## 10. 后继窄验收与仍缺的产品规则

本轮只有接口审查和文档修改，没有运行下列检查。后继在准确写权/接口落盘后，将这些机制合并检查；已交每局随机项与原确认两例不原样重跑，不为文档启动构建。

2. 四份隔离会话按同一日志推进；同人连续操作不等其他副本逐条就绪，主机每条业务仅执行一次；窗口末核对同一连续前缀、数量和摘要。

4. 乱序/重复/缺口/连接代次，确认范围过期走检查点恢复；同号载荷冲突停止，旧窗口/成员/代次就绪不能封口新窗口。
5. 业务拒绝或摘要差异时，恢复 C及确认日志到V，准确保留原拒绝与尾段恢复中止；不重复已确认实例/最终通知，不自动重提尾段，RequiredChild及旁路绑定正确恢复。
6. 定向 revision兼容放行真正无关的并发变化，费用/供应/候选/实例依赖变化仍拒绝；原始命令和派生证明可追溯。完整状态参与规则摘要，现有 UI保持原展示权限，摘要取准确封口前缀。

- 多人并发主窗口里，响应创建时准确的单人主操作分支归属。无定义时 RequiredChild，不能选Host/本机/首位操作人代替。
- 已合法形成异人旁路后，实例归属的真实后继依赖、最迟等待点及期间多萝西角色牌离场行为；旁路仍必结，不采用超时自动接受/拒绝、结束即放弃或永久悬挂。
- 多操作人窗口各自/共同完成的关闭条件；网络数量与全局核验前缀不能自行替代规则完成。
- 断线成员的参与集合变更、操作权或退出政策；未收口时停止等待，不静默算就绪、不自动踢人或代答。
