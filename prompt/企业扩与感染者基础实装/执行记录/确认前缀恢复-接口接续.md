# 确认前缀恢复：接口接续

2026-10-12。协议执行者只读核对当前源码后收口。本轮仅写本文，不修改生产、测试或工具，不编译、不运行 Unity/Player。UI 已通知释放源码与原生窗口；以下文件表供根执行者直接派代码，不在本文阶段执行。

## 1. 恢复基线与不可变捕获点

`S` 为 Host 已编序尾号，`R` 为 Host 实际连续执行成功并完成协议事实捕获的确认前缀。恢复保持原 GameId、内容、seed、随机游标、成员版本及冻结成员；新 epoch 为旧 epoch+1，全局号从 R+1 继续。不能以收到的最高号、客户端前缀、广播过的最高号或当前 State 替代 R。

健康 Host 先冻结新接纳，再按已有 Pump 上限处理已接纳的原队列，成功排空后取 R=S。已经失败的 Host 不再推进尾段；只导出原确认 R。缺少 R 的捕获点返回 `checkpoint_not_retained`，不反向重演整局、不把当前建档标成旧 R。

捕获采用两个槽位：最近两次成功事务的私有捕获点，并允许当前恢复任务钉住其中一份。初始基线在确定性模式 Begin 前捕获一次。仅 Host 启用；每条命令允许一次私有深拷贝，不逐条完整序列化或增加一轮完整规则摘要，也不缓存全部历史全量状态。

现有 `GameSession.Submit` 在 `PublishWorkState` 内完成 RuleCommit、并发请求 revision 更新和运行时校验，然后 `GameStateCloneService.CopyTo(State, workState)`。不能直接保留 `State`，也不能把工作态或 `nextPendingActionLog` 的可变引用当快照。共享侧按以下顺序补齐：

1. 成功处理器的最终工作态已完成上述提交整理、尚未 CopyTo 时，准备 `DeepClone(workState)` 和 `nextPendingActionLog` 的完整私有深拷贝。准备失败发生在发布前，不生成成功捕获点。
2. CopyTo 成功、会话 `pendingActionLog` 更新后，在 Submit 返回前将捕获点放入两槽缓存；绑定原 CommandId。其 State、命令参数、结果、Before 集合与定义/实例上下文均不向调用者暴露可写引用。CopyTo/处理失败不挤掉旧点。
3. 协议 Pump 在 `ApplyOrdered` 成功后，按原 CommandId 取得该点，建立同一 G 的窗口与账本基线。将事实捕获和 V 推进放在权限/业务回调及 Host 前缀发布之前；内部捕获成功后才令 `validatedThrough=G`。当前代码在窗口整理之前推进 V，需要调整此顺序。
4. 若 Submit 成功但协议整理失败，已应用号可以比 V 多一条；两槽中的前一份仍对应原 V。停止后不能继续 Submit。前缀广播延后到 Pump 批次尾不影响 R 的本地绑定；不能把“最后广播前缀”拿来索引两槽。

协议保留最新确认点的句柄与独立基线；共享缓存不得修改被钉住点。恢复建包时才通过现有 `HostRecoveryService.CreateArchive(point 的私有状态)` 生成完整档案并序列化。导出副本不能反向修改点。两槽及必要私有日志上下文、一个在途包均有界；超出原压缩/解压上限报错停住，不删减状态凑包。

## 2. 共用类型和必备字段

继续使用 `SimulationIdentityDto`、原 Proposal/Ordered/GameCommand DTO、窗口描述/事实、Outcome 与前缀 DTO，不另造身份或命令模型。新增类型放入现有协议 DTO 文件；除明确列出字段外，沿用已有类型字段。

| 新增类型 | 必备字段与约束 |
| --- | --- |
| `SimulationRecoveryBaselineDto : SimulationIdentityDto` | 身份为目标 epoch；`SourceSimulationEpoch`、`CheckpointId`、`ConfirmedGlobalSequence`、`CommandPrefixDigest`、`ContentPackHash`、`RuleDigestVersion`、`RuleStateDigest`、`FrozenPlayerIds`、`RequiredReplicaIds`、`Windows: List<SimulationWindowFactDto>`、`NextSubmissionSequences: Dictionary<int,long>`、`ConfirmedCommands: List<SimulationConfirmedCommandReceiptDto>`、`MetadataDigest`。每玩家计数、已消费 CommandId 和窗口账本均截到 R，不能导出 S 的未确认计数。 |
| `SimulationConfirmedCommandReceiptDto` | `SourceSimulationEpoch`、`ClientSubmissionSequence`、`ProposalDigest`、`OrderedDigest`、`Outcome: OperationCommandOutcomeDto`。Outcome 保留原 CommandId/PlayerId/G/窗号及准确原结果字段；这是已确认消费凭据，不是重建提案或伪造本地 CommandResult。 |
| `SimulationRecoveryCheckpointDto` | `Baseline`、`Archive: HostSessionArchiveDto`、`Continuation: GameSessionLogContinuationDto`。通过专用序列化写入已有档案序列化器产生的原 JSON 对象，不使用默认通用序列化器重写 Archive，也不把全量档案编码成转义字符串。 |
| `SimulationRecoveryNoticeDto : SimulationIdentityDto` | `SourceSimulationEpoch`、`CheckpointId`、`ConfirmedGlobalSequence`、`MetadataDigest`、`Phase: SimulationRecoveryPhase`、`ResumeAllowed`、`ErrorCode`、`Reason`。阶段为 Prepare/Prepared/Commit/Installed/Failed；来源和确认阶段用真实连接身份验证，不能信客户端自报角色。 |
| `SimulationRecoveryResultDto` | `Succeeded`、`CheckpointId`、`ErrorCode`、`Reason`；重复包返回同一结果，不重复安装或通知。 |

窗口基线保留所有已登记窗口的原 OpenedAtGlobalSequence、Generation、固定 Authorized/Required、是否关闭、准确 W/Count/窗口摘要；目标协议描述只切换 epoch，并以 R 时的 W/摘要设置 BaseWindowSequence/PrefixDigest。规则层窗口 ID、generation、绑定 revision、来源契约与随机状态原样恢复。Available 从恢复态真实服务复核；Ready/Permit 全部清空，不能沿用旧许可。

`Windows` 使用现有登记容量（当前上限 4096）；恢复边界另按现有边界事实上限构建，仅包括实际开放窗口及必要封口事实，不能把 4096 项塞入最大 256 项的 `SimulationBoundaryDto.Windows`。新 metadata 摘要按排序、显式长度及现有容量规范化；不复用限制 1MiB 的单命令编码器编码全量恢复包。

`ConfirmedCommands` 使用现有命令账本容量（当前 4096），跨恢复累计占用，不靠清空旧消费记录获得无限容量。新 epoch 的提交号恢复为“R 内已确认消费的下一号”；旧 epoch 未确认号退役，不成为新代次缺口。新代次显式提交若复用已确认 CommandId，返回已确认/冲突结果，不再次 Submit、不发成功事件。原 Ordered 的 epoch 和摘要不得改写；新命令摘要链以 R 的原全局摘要为基线。

共享新增 `GameSessionLogContinuationDto` 保存 `SchemaVersion=1`、`HasPendingActionLog`；有值时完整保存现有私有日志字段 PlayerId/Kind/Message/Command/InitialResult/SettlementResult/Before/Commands。Command 使用已有 GameCommandDto。Before 按 `PublicActionStateSnapshot` 和各子快照的实际字段保存集合、资源、设施/影响及 ContentState 定义/实例身份上下文，不能套用浅拷贝或假定它仅含文案。CommandResult 用专用字段转换及现有工厂还原，不依赖 private setter 的默认 JSON 行为。

该私有日志不在 HostSessionArchiveDto 内。丢失它会改变后续正式 Logs 的数量和原根 CommandId；规则摘要虽忽略 Message，仍包含这些日志结构事实。恢复时显式无待日志与缺失必要续接字段必须区分。

## 3. 可直接实现的入口

下列为目标签名，尚未存在；类型均在 `YC.Application.Sessions`。捕获点和 Prepared 类型封装内部状态，不公开可写 GameState。共享侧负责续接转换与投影；协议侧负责基线、运输和阶段机。

```csharp
// GameSession：仅确定性 Host 启用；返回初始捕获点。
GameSessionRecoveryPoint EnableConfirmedRecoveryCapture();
bool TryReadCommittedRecoveryPoint(string commandId,
    out GameSessionRecoveryPoint point);
GameSessionRecoveryExport ExportConfirmedRecoveryPoint(GameSessionRecoveryPoint point);
bool TryPrepareConfirmedRecoveryState(GameState restored,
    GameSessionLogContinuationDto continuation, GameStateViewer viewer,
    out PreparedGameSessionRecovery prepared, out string fault);
bool TryCommitPreparedRecovery(PreparedGameSessionRecovery prepared, out string fault);

// GameSessionRecoveryExport：Archive 和 Continuation 均为独立导出副本。
// Coordinator：冻结接纳；健康态有界排空原队列，故障态保持停止。
void BeginConfirmedRecovery();
bool TryCreateConfirmedRecoveryCheckpoint(long expectedConfirmedSequence,
    long targetEpoch, out SimulationRecoveryCheckpointDto checkpoint,
    out SimulationRecoveryResultDto result);
static DeterministicSimulationCoordinator FromConfirmedRecovery(
    GameSession session, DeterministicSimulationSessionOptions targetOptions,
    SimulationRecoveryBaselineDto baseline, GameState preparedState);

// Sequencer/Replica：专用基线工厂，旧初始构造函数保持。
static OrderedCommandSequencer FromConfirmedRecovery(
    DeterministicSimulationSessionOptions options, SimulationRecoveryBaselineDto baseline);
static DeterministicCommandReplica FromConfirmedRecovery(
    GameSession session, DeterministicSimulationSessionOptions options,
    SimulationRecoveryBaselineDto baseline, GameState preparedState);

// 新 installer 的构造参数绑定真实 session/registry/viewer/本机 options。
bool TryPrepare(SimulationRecoveryNoticeDto expected, string bundleJson,
    out PreparedSimulationRecovery prepared, out SimulationRecoveryResultDto result);
bool TryCommit(PreparedSimulationRecovery prepared, out SimulationRecoveryResultDto result);

// MirrorCommandTransport：客户端请求由真实 Host 决定 R 和目标 epoch。
void RequestConfirmedRecovery();
bool IsRecoveringConfirmedPrefix { get; }
event Action<SimulationRecoveryNoticeDto> SimulationRecoveryStarted;
event Action<DeterministicSimulationCoordinator> SimulationRecoveryCompleted;
```

`GameSessionRecoveryPoint` 的外部只读身份为原 CommandId；全局 G 绑定属于协议，不塞进规则状态。`GameSessionRecoveryExport` 含上述 Archive/Continuation。`PreparedSimulationRecovery` 持有准备好的共享安装对象和暂停的新 Coordinator；只有成功发布后的 Coordinator 可公开订阅。

复用现有 HostRecovery `CreateArchive`、`SerializeArchive`、`RecoverJson`，本批无需改 HostRecovery.cs。预检使用同一实际 EffectRegistry，必须检查 `HostRecoveryResult.Succeeded`；State 非空不代表成功。复用现有规则摘要、随机身份校验、窗口规则服务、可靠分片和压缩组装。

不能直接调用 GameSession 的 ReplaceState/RecoverHost/ReplaceView：前两者不能提供本批原子续接语义，并会清空私有待日志；投影视图也不能代替完整状态。不能调用 InitialSimulationCheckpointInstaller、旧 Initialize、START 建场或改 seed。

预检先完成完整档案恢复、身份/内容/随机/摘要/协议元数据/私有续接校验，以及同一 projection provider 生成的本人 View，再准备新 Replica/Sequencer/Coordinator。工厂验证的是准备态，不能读取损坏的当前 State，也不能调用普通 Begin 将窗口号清零。

共享 Prepared 对象绑定本会话的内部 mutation generation；提交前再检查没有新的 Submit/Replace 使它过期。提交在主线程暂停区内，以预备对象替换 State 根、View、私有日志，再无异常步骤地发布运输的 Coordinator 引用；不在两步之间触发回调。预检/代次检查失败不改任何活动对象。普通逐字段 CopyTo 不能宣称这一发布原子。

保留同一 GameSession 与 handlers/provider。共享控制器在恢复开始冻结提交、在发布后刷新实际新 State/View 引用；任何持有旧 PlayerState/State 的消费者必须失效缓存。若落地发现确需 UI 文件协作，根按精确文件另派，协议侧不跨写。恢复后重新启用捕获时，基点是安装的 R，不能重新标成全局 0。

## 4. 运输与旧代次隔离

沿用 `SimulationCheckpointPartMessage`、现有 Encode/Assembler 和可靠 `SimulationProtocolPartMessage`，不另写压缩或分片算法。现有 Initial v1 保持；在同一 `SimulationCheckpointEnvelope` 新增 `Purpose=ConfirmedSimulationRecovery` 的 v2 分支和 `SourceSimulationEpoch`，既有 SimulationEpoch 为目标代次、GlobalCommandSequence 为 R。新增原包摘要版本 `yc.confirmed-checkpoint.sha256-utf8.v1`，摘要覆盖 Archive+Continuation+Baseline 的完整 UTF-8 包；gzip 摘要和 8KiB 分片、8MiB 压缩、64MiB 解压限制复用。Core 不引用 Application。

CheckpointId 由原 GameId/source epoch/target epoch/R/命令前缀/metadata digest 稳定派生。Assembler 固定此次期望身份；每连接只保留一个当前恢复包。`SimulationCheckpointChannel` 继续初始安装专用，本批无需修改；Mirror 新阶段机直接调用现有 Transfer/Assembler。

最小流程：冻结源代次 → Host 宣告 Prepare 并传完整包 → 每冻结成员预检成功报 Prepared → Host 收齐后发 Commit → 各端暂停原子安装并报 Installed → 全员在同一 R/摘要下安装成功，再走目标代次现有 Boundary/Ready/Permit。缺席成员不补 ready、不缩集合；丢片按同一在途包有界重传，失败保留停止态。恢复消息必须在普通 `IsStopped` 拦截之前由专用阶段处理，否则已经停止的会话无法接收恢复。

源代次队列、已接纳未确认 Proposal/Ordered、原 FailureResult/LastFault 保留为只读隔离记录，不入新 epoch 执行队列，不重签、不重发、不修改 expectedRevision。读取原日志补片仍只读已经确认的连续区间；旧记录不能重新标成新 epoch 命令。没有对应已保留状态时不实现第二个权威回放器。

旧 coordinator 解除订阅；Mirror 回调核验捕获的 coordinator 引用、代次和连接绑定。现有 `SimulationCommandAppliedDto` 改为继承已有 SimulationIdentityDto，并由实际提交上下文填 epoch/member。共享 CommandSubmissionController 以订阅 generation+身份过滤旧 Applied/前缀/拒绝/许可，保存已交付 CommandId，不能让旧控制器、旧包或重复 Commit 污染新会话。

恢复完成只发一次 SimulationRecoveryCompleted 并刷新视图；不再次发初始 DeterministicSimulationReady，不伪造 SimulationCommandApplied、旧 Accepted、commandSettled。导入 Host 凭据不等于本机逐条执行；安装 R 只建立基线。草稿可留为草稿；玩家重新决定提交时才生成新命令，并仍按实际当前 revision 校验。

若 Host 原生产 Submit 在 F 失败，F>R，或原始失败原因尚未核清，`ResumeAllowed=false`。可导出/安装 R 作诊断，目标 coordinator 仍保持停止，不能发放许可，不能通过丢弃 F 改成继续。需在修复后的固定输入上实际复现原命令及失败原因、由技术接续明确解除；未复现就保留原失败与尾段停住，禁止跳过、替换答案或自动再提交玩家选择。

## 6. 仅需四类验证

1. 实际 GameSession/handlers 成功提交后，在 CopyTo 保留旧业务引用、后续提交及消费者修改原命令/结果的情况下，原捕获点 R 的完整状态、随机游标、私有待日志和后续日志根 CommandId 不变；协议整理失败取前一已确认点，延后广播不取错点。
2. 完整包往返并恢复实际窗口 W、个人提交序列及跨 epoch 去重；新 G=R+1。本人投影正确，重用已确认 CommandId 不 Submit；陈旧 revision 拒绝且无自动重签/重发。Host 原业务失败及隔离尾段保留，未复现时仍停止。
3. 篡改包、错误 registry/identity/digest/续接、容量超限或过期 prepared 任一预检失败均不改变 State/View/私有日志/当前 coordinator；重复 Prepare/Commit 不重复安装。两槽耗尽或指定旧 R 不保留时明确失败。
4. 真实恢复消息处理路径覆盖已停止端，缺一冻结成员不许可；旧 epoch 消息、旧 controller 回调、旧连接绑定被拒绝，全员安装完成才新 Ready/Permit，历史结果与成功通知不再重复。

只运行实现涉及的必要方法和实际 Unity 引用编译；这些检查不等于实际网络联机或完整局通过。本轮尚未执行上述验证。
