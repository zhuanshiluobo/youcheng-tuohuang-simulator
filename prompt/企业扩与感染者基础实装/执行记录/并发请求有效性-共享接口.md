新提案仅由正式共享提交门面在第一次 owned proposal 中附上述两个参数；原 CommandId、答案、expectedRevision、ObservedG/ObservedStateRevision不改。旧无参数命令、原checkpoint/baseline/receipt/JSON版本和摘要仍按旧语义验证；不回填历史记录，不提高协议主版本令旧存档失效。

Host `AdmitProposal` 可能返回 PendingValidation：保原提案、尚未分 G/W、尚未推进 C，也不是 Rejected。客户端收到该 proposal-result 后继续等原 CommandId，不 settle、不清 busy/草稿、不自动重签重发。同原提案重传幂等返回同一 Pending；冲突仍准确拒绝。

固定工作线程事实到来后，Host 主线程对原提案最终准入或拒绝，发 `SimulationProposalResultProduced`；这是**仅此前 Pending 的最终结果**。C 按其原 Proposal.Command.PlayerId 映射已验证连接转发；若该 actor 为 Host 本机，B 会同时走原本地 ReceiveProposalResult/Rejected 生命周期，C 不必再次制造本地结果。Accepted 最终结果仍不提前 settle，只有原 SimulationCommandApplied 解锁。原 OrderedCommandProduced 广播保持。

PendingValidation 不进入 SimulationProposalRejected。其他既有最终拒绝保持原含义。停止/恢复/故障会准确退役等待并给原结果，不伪装成功；C 的旧代次/离开保护仍需检查。Host 本机 Submit 分支也须把 Pending 当已经排队等待，不能返回立即失败。

原 `simulation.background-publication.v1` 启停/固定视图/保存接口不撤回。真正新规则接口由 B 内部接线，不需要 C 调用 Domain 或另建 DTO。C 只负责能力身份、结果运输和原 UI 提交生命周期，不对旧答案改 expectedRevision。
