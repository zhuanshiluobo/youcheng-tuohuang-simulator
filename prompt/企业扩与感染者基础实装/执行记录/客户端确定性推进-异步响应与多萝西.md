# 客户端确定性推进：异步响应与多萝西

2026-10-11。结算规则执行者的定向只读设计，按《客户端确定性推进-操作窗口与随机数迁移合同》第1.3条及第三、四节的最新限定修订。本轮仅维护本文，未修改生产源码、内容定义、场景或预制体，未运行编译、测试、Unity 或构建。以下新增接口、字段和归属均为协调者收口用的提案，不代表已实装，也不构成生产写权。

## 1. 已决定的行为与设计结论

用户已经决定：旁路只是一项有条件的流程优化。Lua/内容响应调度声明可以省略，缺省为 `RequiredChild`；声明 `DeferredPlayerResponse` 只表示允许旁路，不直接决定实际挂载。只有响应本人 `respondingPlayerId` 与真实当前单人主操作窗口的 `mainWindowPlayerId` 明确不同时，才可放行另一玩家不依赖该回答的操作。多萝西本人移除本人的影响力时，必须当场明确选择收留或拒绝，并结清实例去向后才能推进下一 Effect。这些限定不需要再次确认。普通 Event 仍自动挂链，旁路不表示可放弃；条件左侧、入场等必要响应也不因此改为非阻塞。

现有正式物品路径已经把实际离场实例放进 Effect 暂存区。需要改的是运行时条件判定、符合条件的响应挂载与保管责任转交，以及命令守卫。仅实际判定为异人旁路时，才登记有独立生命周期的响应根，由它保管同一立方体，原主操作窗口和响应窗口各自封口，回答统一进入 `GlobalCommandSequence`。未声明或同人分支继续由原父链保管并等待结清，不创建独立根，不转移原完成责任，也不再造标记。

已启用范围的旁路按最早真实因果依赖等待，并在最终封局前结清全部已登记义务，足以给出有限的终结边界。第5节已撤下人为设置的“下个窗口/下一收尾必须截止”二选一；不新增玩法，不设置超时默认答案，不把角色牌离场当成自动拒绝。未来多收留来源和未启用帮派扩展的边界单独记录，不作为本批基础/企业/感染者推进前置。

### 2.1 保罗帮派与公司标记必须区分

已经确认的卡面要求是：多萝西可收留保罗帮派的真实离场立方体，保留 `itemId`、本质类型、原所有者和原供应；存入牌上后不再是地图影响力，也不获得普通玩家标记资格。初始化的“最多4个玩家标记”不扩大为任意立方体，后续收留不设总容量4，牌空不自动弃置。

当前内置 `ItemTypeRegistry.cs:84` 注册了普通玩家立方体和 `infected.company_marker`，本次在定向的角色、物品、影响力源码及 Content 中未找到保罗/GangMarker 的生产定义或专用注册。`游城拓荒/企业家/卡面效果与Effect式.md:5、25` 明确帮派属于可选企业家模式，关闭时不装配能力、组件和计分；感染者基础规格也明确不与该可选模式混装。本批基础/企业/感染者基础组合没有因此增加企业家内容。只保留未来兼容要求，不补造类型、供应或实例，也不因缺少未启用的帮派入口阻塞本批热座或旁路设计。

`CharacterLifecycleService.CubeSupply:392` 已优先使用 `OriginalSupplyZoneId`，支付牌上标记和牌离场走此入口；而离场默认归还入口尚未统一。当前旁路登记仍须记录经现有类型合同验证的合法原供应，接受/拒绝/载体离场均移动同一实例。未来启用帮派时沿用其原供应，不能把帮派归入普通玩家供应；这不是本批扩充企业家生产内容的授权。

另一个现状是：`departed_owner` 和收留入口对 Player 主体核对本人，对非 Player 主体没有同样过滤。岩蹄公司没有玩家所有者，不能把当前对公司类型的放行当成“己方保罗帮派”的证明，也不能在本轮据此新增公司收留规则。

## 3. 最小状态与接口提案

### 3.1 共享内核的登记边界

保留 `RuleEvent.ResponseKind=Effects`。在 handler 登记上增加可省略的 `EventResponseAttachmentKind` 声明，缺省 `RequiredChild`；本批只有多萝西计谋的 Removed/Replaced 两个登记可声明 `DeferredPlayerResponse`。该声明是许可元数据，不能据 EventType 或登记值直接创建独立根。多萝西激活及 PlayerCleanupStarted 仍为原来的必要流程。原有返回 Effect 列表的 Lua 无须补字段，省略声明不能导致装配/校验失败，不增加另一套必填旁路布尔字段。

实际判定在 Event 自动分发的同一 Working 快照内完成，使用共享操作窗口模型标识的当前主窗口：核对 GameId、真实 OperationWindowId、窗口有效状态及准确参与玩家集合，确认它是单人主操作窗口，并从该权威窗口取得 `mainWindowPlayerId`；`respondingPlayerId` 来自本次响应 Choice 的实际回答者及源牌资格。当前 `EffectRuntimeState.MainNodes/ActiveMainNodeId` 与 `MainlineNodeRuntimeState.PlayerId/ExecutionEffectId` 可供共享入口核对实际链来源，但不能把旧主链 NodeId 冒充新协议的窗口身份，也不能取 `ActiveTaskPlayerId` 将多人窗口假装成单人。Host 身份、LocalPlayerId、旧 UI CurrentPlayerId、离场执行者、事件 PlayerId 或 EventType 都不能替代这两个身份的核验。

| 声明及身份 | 实际挂载 | 实例保管与原后继 |
| --- | --- | --- |
| 未声明，或声明 `RequiredChild` | `RequiredChild` | 原自动 Event 子树、Choice blocker 和父完成依赖保留；同人、异人都正常等待。 |
| 声明允许旁路，且 `respondingPlayerId == mainWindowPlayerId` | `RequiredChild` | 同人仍沿原链完成收留/拒绝及实例去向；没有交接记录、独立根或延期截止。下一 Effect、EndAction 和等待不能跳过它。 |
| 声明允许旁路，且已确认单人窗口中两者明确不同 | `DeferredPlayerResponse` | 才可原子创建响应根并转交同一实例；只放行无关主操作，响应本身仍是必须结清的义务。 |
| 没有明确单人窗口、窗口/身份不足，或处于多人并发窗口 | `RequiredChild` | 不猜测为旁路；多人窗口对应规则留给共同协议收口，不改变既有企业/盖放/采集并发机制。 |

以下名称为供共享 owner 收口的精确建议，最终只采用一套合同：

```csharp
enum EventResponseAttachmentKind { RequiredChild, DeferredPlayerResponse }

// EffectEventHandlerRegistration 的可选许可声明，缺省 RequiredChild。
// AttachmentKind 是声明，不是本次实际挂载结果。
EventResponseAttachmentKind AttachmentKind = EventResponseAttachmentKind.RequiredChild;
Func<EffectEventHandlerContext, EffectSpec, DeferredEventResponseDescriptor>
    DescribeDeferredResponse;

// 共享调度入口：从 Working 内真实当前主窗口解析身份；不足则 RequiredChild。
EventResponseAttachmentKind ResolveResponseAttachmentOnWorking(
    GameState work, RuleEvent sourceEvent,
    EventResponseAttachmentKind declaredKind, int respondingPlayerId,
    out string mainOperationWindowId, out int mainWindowPlayerId);

// 仅上述入口返回实际 DeferredPlayerResponse 后，才在同次提交中登记。
IList<string> AppendDeferredEventResponseOnWorking(
    GameState work, RuleEvent sourceEvent,
    EffectEventHandlerRegistration handler, EffectSpec body,
    DeferredEventResponseDescriptor descriptor,
    List<RuleJournalEntry> entries);
```

`ResolveResponseAttachmentOnWorking` 返回 RequiredChild 时，直接走现有 `AppendChildEffects`，不要求产生旁路描述符或补充旧 Lua 参数。返回实际 DeferredPlayerResponse 时，`DeferredEventResponseDescriptor` 至少携带 `StableResponseKey`、`SourceEventId`、`SourceDepartureEffectId`、`SourceCardInstanceId`、`AbilityId`、`AnsweringPlayerId`、`OriginMainOperationWindowId`、`MainWindowPlayerIdAtCreation`、`ReservedItemIds`、`ReservationHandoffHandlerId` 和 `CompletionHandlerId`。其中 AnsweringPlayerId 就是本次已核验的 respondingPlayerId，不另外保存一份可独立改变的响应者。handler ID 指向登记过的领域初始化/完成回调；内核不硬编码多萝西卡名或原供应规则。描述符不能由客户端直接提交，必须来自本次合法 Event、真实窗口及源牌资格。

只有实际异人旁路分支，内核才创建可持久化的独立响应根，`ParentEffectId` 为空，因果来源及创建时窗口身份由描述符和记录保存。这个根自己的 Choice、分支和保管责任仍是必要子树，只有它与原主操作树之间不建立完成 blocker。不能把 `Created` 子节点藏在已完成的父节点下，也不能用 `ResponseKind=None` 跳过真实响应。普通 Event 自动分发同时执行声明解析和实际分类，不改成 UI 手动创建或挂链。

根、记录和物品交接必须在上述 Working 分发提交内一起成立；不能从 handler 内另调用现有公开 `TryCreateRoot` 先独立提交一半状态。建议业务 ID 使用 `StableIdFactory.Create("deferred_response", GameId, DepartureOperationId, ReservedItemId, SourceCardInstanceId, AbilityId)`，响应根使用该 ID 派生的稳定语义键；同一离场的 Removed/Replaced 不因 EventType 不同建立两份保管义务。`SourceEventId` 仍保留实际触发事实。

### 3.2 同人原链结清；异人旁路才交接保管责任

未声明/同人分支沿用原顺序：原离场 Effect 暂存真实实例 → 自动挂载收留 Choice 并等待 → 本人提交 store/decline → Choice 分支完成 → 原父节点 `awaiting_destination` 结清去向 → 原父 Effect 完成 → 下一 Effect。store 移入本牌后原默认归还不重复移动；decline 必须是明确答案，随后原父按合法原供应归还。本人不回答时保留原 blocker 和实例；RunUntilQuiescent 的等待状态不等于回答、完成或放弃。此分支不得调用 `AdoptPendingDestination/CompleteDeferredDestination`，不得设置“去向责任已交接”，EndAction 也不能借声明的许可值放行。

仅实际异人旁路时，推荐为响应根沿用 `core.zone.effect_staging/removed_influence` 声明并创建其自己的暂存区，在同一原子提交中移动原实例，清空旧暂存区，再把原离场节点登记为“去向责任已交接”。这个过程不形成第二次地图离场 Event。

领域回调建议为：

```csharp
// 仅实际异人旁路可调用；接受真实离场事实及内核登记的响应根。
ItemTransferResult AdoptPendingDestination(
    EffectExecutionContext departureContext,
    EffectNodeRuntimeState responseRoot,
    DeferredEventResponseDescriptor descriptor);

// 响应根消费规范 store/decline；验证 reservation 和物品真实位置后提交。
EffectStepResult CompleteDeferredDestination(
    EffectExecutionContext responseContext,
    string deferredResponseId, string decisionId);
```

交接回调核对实际旁路判定及创建时窗口身份，再核对旧暂存 owner、`pendingItemId`、未处理去向、本次 Event、目标角色实例与本人资格。新根接管后，原 `awaiting_destination` 分支只有在存在合法旁路交接记录时才完成离场事实而不调用旧 `ReturnToSupply`。同人分支不能借相同 EventType 进入此完成捷径。直接将旧 `destinationResolved` 标成“已收留”不合适：交接完成不等于玩家已经回答，需独立的责任交接标识及响应引用。

原供应来自实例的有效 `OriginalSupplyZoneId`；缺省时只允许用现有正式类型/主体的供应合同推导并校验，随后固化该真实目标。不能为未知帮派回填普通玩家供应来使校验通过。

旧暂存区空后可随正常历史清理处理；响应暂存区必须一直归属于存活的响应根。暂存中的实例不计地图影响力、不计可消费供应、不计已经进入多萝西牌上的数量。普通放置、初始化投入、支付、其他收留都不能再次消费它。

`StoreRemovedCube` 和 `ItemTransferService.IsPendingDepartureCapture` 必须同时保留原链来源校验，并在实际旁路时识别新保管根的真实离场关联；不能要求所有响应都先转交独立根。对牌上入口的本人权限、物品类型和唯一去向检查仍保留。

### 3.3 持久化记录与回答

建议共享在 `EffectRuntimeState` 中增加 `DeferredResponseState` 集合，仅保存实际异人旁路；未声明/同人分支仍由原 `RuleEvents/DispatchReceipts/InteractionRequests` 和父链事实持久化，不制造旁路记录。共享还须在创建提交/分发收据中保留实际挂载分类，恢复不凭许可声明重新分类。实际旁路的必要字段如下，不另存一份可独立改变的答案。

| 字段 | 权威含义 |
| --- | --- |
| `DeferredResponseId`、`ResponseRootEffectId` | 稳定业务义务 ID 与实际保管/执行根。 |
| `SourceEventId`、`SourceDepartureEffectId`、`DepartureOperationId` | 离场因果；移除/替换去向选择只登记一次。 |
| `SourceCardInstanceId`、`AbilityId`、`AnsweringPlayerId` | 登记时的源牌与本人资格。不能从后续 CurrentPlayer 推导回答者。 |
| `OriginMainOperationWindowId`、`MainWindowPlayerIdAtCreation` | 创建时已核验的真实单人主窗口及其玩家，明确不同于 AnsweringPlayerId；不使用 Host/LocalPlayer/UI 旧 CurrentPlayerId。 |
| `ReservedItemId`、`ReservationZoneId`、`OriginalSupplyZoneId` | 唯一真实实例、当前保管区和经验证的归还目标。 |
| `ItemTypeIdAtDeparture`、`OwnerSubjectAtDeparture`、`PositionBeforeDeparture` | 帮派/普通标记区分及移除事实审计；位置变化不修改本质类型或所有者。 |
| `InteractionId`、`Version` | 本次交互及义务版本；Version 只因本义务资格/候选变化更新，不能随无关玩家每步提交变化。 |
| `OperationWindowId`、`CreatedAtGlobalCommandSequence`、`AnsweredAtGlobalCommandSequence` | 复用共同窗口/编序合同，记录触发与回答在全局顺序中的位置。 |
| `Status`、`ResolvedDestinationZoneId` | `Pending/Stored/Returned`；存入或归还的真实去向。没有“等待超时便释放”的状态。 |

实例只建立一份 reservation。未来存在多张合法收留牌或多个收留能力时不能逐订阅争抢、先回答先得，不能复制实例。本次定向范围未确认已启用的三组合存在这样的多去向竞争，不把未来仲裁列为当前必须新增的玩法或生产前置。若实际内容后来出现该情形，再保留准确源牌、同实例和冲突证据，按其正式卡面确定，不能静默挑第一张牌。

接受：从响应暂存移入指定真实角色牌的 `markers`，记录 Stored，完成响应自己的子树和窗口。拒绝：原 `decline` 空分支结束后由登记的完成回调移入合法原供应，记录 Returned。完成回调仅在本义务未处理且实例仍在指定保管区时执行；重复回送、重复回答、旧候选或其他玩家回答均不能再移动或产生奖励。

既有通用 `AnswerInteraction` 命令入口继续使用。待共享/命令 owner 收口后，旁路答案附带 `deferredResponseId/expectedResponseVersion`，引用已有 `interactionId/answerValue`；本人授权仍以请求和登记义务为准。旁路窗口拥有共同合同的 `WindowCommandSequence`，主窗口和旁路交错只按 `GlobalCommandSequence` 执行。客户端已经提前应用的自身命令不能回送再执行一次。

当前严格 `expectedRevision` 不能在本轮删除。共享必须先提供旁路版本校验与全局序号执行的新入口：无关操作后旧本人请求仍可回答；物品、源牌或 reservation 真正变化时拒绝陈旧答案。单纯持续重写请求全局版本仍会在网络交错时让本人答案反复过期，不能当成完整异步方案。

## 4. 主窗口、恢复与错误行为

`GameState.HasOpenActionableInteraction`、`GameSession.Submit` 和 `RoundExecutionService.HasPendingChoiceOutsideMainlineCompletion` 都要使用创建时确定的同一实际挂载分类。只有已合法形成的异人旁路没有资源冲突时不阻塞主窗口；未声明、同人和其他普通未决选择保持原 blocker 与命令守卫。不能按许可声明值直接放行，也不能仅按“回答者不是当前玩家”或 `lua.choice` 类型放行。同人响应未回答/未结清时，EndAction、等待和自动推进均不能跳至下一 Effect。

创建时判定及身份来源冻结到共同规则提交，后续主窗口切换不由 UI 重算、拆链或重新归并；已经形成的旁路按真实 item/card/supply 依赖及最终封局边界处理，不因当前窗口后来变成本人就伪造一份新的原链响应，也不单因窗口切换强迫结清。对新发生的响应则使用新创建时的真实当前主窗口重新作三分支判定。

建议共享提供第5.3节的一套 `GetDeferredResponseDependencies(GameState, DeferredDependencyQuery)` 查询，返回真实会影响该操作的有序义务及其响应根；领域后继指定自己的精确 item/card/supply 依赖，调度层只等待这些义务，不等待全部旁路。普通主窗口 EndAction 只封本窗口连续命令前缀和必要子树；不顺带完成、注销、归还或删除其他玩家的旁路。明确结束本次可选收尾段只按原合同跳过该段，不等于回答或放弃仍未结清的收留义务。

恢复检查点须保留实际挂载分类及其创建上下文。同人/未声明分支恢复原父链、原暂存实例和未决交互，不转换为旁路；实际异人旁路同时保留活着的响应根、暂存实例、义务记录、交互版本、分发收据、答案事实及共同命令序号。快照装载先检查 item→reservation→响应根→源 Event 的对应关系和创建时窗口身份，再恢复未回答的同一个请求；不能重新执行 Lua 重新登记一份 Choice。主窗口的 `FinalCommandSequence/CommandCount` 封口不代表旁路已回答，旁路在自己的窗口完成。

回答提交失败时回滚整个回答工作副本，保留未决实例与原请求，不把业务拒绝解释为玩家选择 decline。断线不自动回答；重新连线仍读取同一待办。原父节点结束不是失效理由。源牌不再满足资格、原供应找不到或多个去向发生冲突时，保留规则事实和诊断，不能无效释放或用新造标记补齐。

记录异常时仍须保持合法保管者：不能把装有物品的响应暂存 owner 直接标为 Faulted/Completed/Failed；应保留其存活状态及未决记录，按共同恢复合同暂停受影响推进并记录诊断，等待恢复或明确裁定。

发送端提前模拟的主操作与另一端旁路答案可能采用不同先后顺序。状态不一致时必须由共同协议停住受影响窗口，用最后确认检查点和确定前缀恢复；本设计没有宣称现有工程已经支持任意回滚。主机核验复用按序提交的规则结果，不再次消费同一随机流或再次移动实例。

## 5. 实际异人旁路的真实依赖收口

本节只处理已经合法形成的异人旁路。同人/未声明响应仍须在原父完成及下一 Effect 前明确回答、结清，不能借本节的等待优化延期。旁路没有独立的“下个窗口/下一收尾必须答完”玩法；在第5.2节最早真正消费因果结果的动作前等待相关义务，无相关动作时继续保管，到最终封局前必须结清。没有超时默认答案，也不把任何阶段结束解释为自动拒绝收留。

### 5.1 本次回查纠正：收尾登记不等于资格已经固定

多萝西规则正文 `lua/characters/operator.dorothy.tactic.lua:9` 是“支付本牌2枚，再放置1枚”的 Condition；卡面规格 `游城拓荒/企业扩/卡面效果与Effect式.md:329` 限制每个收尾阶段一次，没有要求所有未决收留一律在收尾开始前答完。资格声明 `lua/settlements/operator.dorothy.tactic.lua:17` 按当前 markerCount≥2 判断。

当前正式接线不是在 Started 时按数量筛掉整条收尾：`CharacterCardLuaCatalog.cs:73` 对 cleanup_order 调用 `SettlementLuaCatalog.CreateCleanupResponse:73`，只包装真实正文及源牌证明；`SettlementHost.RegisterAttachedSettlementSegments:252` 登记该段和一次性资格，不读取 markerCount 决定是否保留。`CharacterLifecycleService.RegisterPersistentObserver:443` 的 LastCleanupKey 防重复登记，不冻结牌上数量。旧 `WrapCleanupOffer/GetCleanupOptions` 是另一兼容分支，不能代替当前 JSON 声明的正式路径。

数量由 `SettlementHostCatalog.CreateFacts/Source:75、117` 读取真实卡区中的 Cube。`SettlementRegistry.QuerySettlementEntry:42` 和 `SettlementEntryService.GetOptions:169` 每次查询当前事实；`SettlementLuaCatalog.QueryAvailability:113` 的缓存按规则 StateRevision 失效。正式执行入口 `SettlementHost.TryInvokeSettlementEntry:329` 用 `forceRefresh=true` 再验资格。因此 Started 登记和可刷新的展示查询本身不必停主流程；暂时不足的展示结果不能固化成“本次没有该段”，也不能为晚到答案重新发 Started、重置 LastCleanupKey 或补一次收尾。

### 5.3 共享调度最小 API 与既有入口

沿用第3节的许可声明、创建时真实窗口判定和唯一旁路记录，不创第二套窗口、阶段状态或 UI。真实依赖只需共享增加一套纯查询及 Working 内挂 blocker 的入口；最终封局同样使用这套查询：

```csharp
IReadOnlyList<DeferredResponseDependency> GetDeferredResponseDependencies(
    GameState state, DeferredDependencyQuery query);

bool TryAttachDeferredResponseDependenciesOnWorking(
    GameState work, string ownerEffectId,
    IReadOnlyList<DeferredResponseDependency> dependencies,
    List<RuleJournalEntry> entries);
```

`DeferredDependencyQuery` 只描述当前既有动作的依赖：`OwnerEffectId`、语义 `DependencyKind`、实际 `SourceCardInstanceId/ItemIds/OriginalSupplyZoneId` 及该动作已有的数量/选取要求。语义覆盖 `CardMarkerConsumption/CarrierExit/ExactItemUse/SupplyRequirement/FinalizeGame`；FinalizeGame 查询本局全部 Pending，其余只返回会影响当前动作的义务。它不是窗口模型，也不是新的每回合截止配置。`DeferredResponseDependency` 返回既有 `DeferredResponseId/ResponseRootEffectId` 和业务原因，不生成另一份玩家答案。

共享内核沿用 `AddBlockerOnWorking/HasUnresolvedBlocker/ResolveTerminalTargetBlockersOnWorking`，将依赖挂到真实调用节点、目标为已有响应根；最后封局挂到现有末轮终结节点。同一依赖幂等复用稳定 blocker，不将响应重新变成普通 Event 子树。现有公开 `TryAddBlocker:1626` 会独立提交，不能从当前工作副本内调用它制造一半提交；应使用上述 Working 接口并与调用状态同次保存。等待结束后回到原动作重新验资格/位置，无新 UI、自动答案或手动挂链。

具体领域接入点是 `SettlementHost.TryInvokeSettlementEntry` 的正式资格消费、`PayCardMarkers` 的准确选取、`CharacterLifecycleService.MoveCard/MoveCardCore` 的载体修改、同 itemId 的真实转移/部署及 `RoundExecutionService` 末轮终结。只读 `GetOptions/QueryAvailability` 继续刷新，不新增模态确认，也不把可选收尾主动跳过接成收留拒绝。正常时期 GetDeferredResponseDependencies 不扫描或拦住整组并发企业/盖放/采集；仅真实调用节点消费其依赖。

### 5.4 当前规则缺口与未启用范围

在本批已启用的单一多萝西收留路径，规则正文、原载体政策、现有可选收尾合同及最终封局足以推出上述因果等待。没有需要用户补选“下一窗口/收尾截止”的游戏规则，不新增一次发动、自动拒绝或跨玩家确认步骤。

保罗帮派仅作未来企业家模式兼容：该模式关闭时不装配相关能力/组件（`游城拓荒/企业家/卡面效果与Effect式.md:5`，文档来源为感染者规则书印刷第2—6、8、10页）。区域设计第6.2节记录保罗1B后继继续使用原 itemId；未来真正启用并遇到“同一离场同时被收留又要求原位置放回”时，需依据该模式正式卡面确定后继是否还能取用，结果可能是立方体留在多萝西牌上或回地图，绝不能复制为两枚。本轮不扩充该模式、不替其裁定，也不把此未启用情形列为基础/企业/感染者的阻断项。

## 8. 待实施后的窄验收

以下直接纳入同一批机制窄检查，不额外重跑整套数值或完整局；本轮未编写或运行测试。使用同一真实离场/多萝西夹具，在创建时覆盖三个主分支：

| 分支 | 必须核对的结果 |
| --- | --- |
| 未声明 | 原 Lua 返回 Effect 列表正常装配，默认 RequiredChild；即使A窗口触发B响应，也不创建独立根、不交接实例，原后继及 EndAction 等待答案。 |
| 已声明，同人 | B的真实单人主窗口内移除B影响力，respondingPlayerId=mainWindowPlayerId=B；保留原 Event/Choice blocker、原暂存 owner，无独立根/交接记录；等待、自动推进、EndAction 不执行下一 Effect。分别明确提交 store/decline，实际实例去向结清后下一节点只执行一次。 |
| 已声明，异人 | A的真实单人主窗口触发B响应且A≠B；只此分支创建一次独立根并交接同一实例。B待办仍未结清时A可连续执行无关操作并结束主窗口；依赖该实例/源牌/受影响供应的后继仍正确等待，B明确回答才能结清旁路。 |

在上述分支中增补轻量反例：Host/LocalPlayerId/UI旧 CurrentPlayerId 与真实窗口玩家不一致时，结果只服从真实主窗口；无窗口、窗口过期、身份不足或多人窗口不猜测旁路；同人源 Event 与异人源 Event 使用同类 Removed/Replaced，也不能据 EventType 脱链。恢复及窗口切换保持创建时实际分类，不重挂已形成的旁路。

同批已有窄验收继续覆盖实际异人旁路的后继与实例完整性：

- A移除B的影响力后，只有声明允许且真实窗口身份满足异人条件时，B才保留旁路待办；普通必要响应仍阻塞其真实后继。
- B接受/拒绝均处理同一个 itemId；等待时地图、供应、卡上三者都不重复计入，按启用的真实类型回合法原供应；牌上超过4仍能收留，牌空仍在场。未启用企业家帮派只保留兼容要求，不追加本批检查内容。
- 替换成功只有相应 Replaced 响应，放置失败处理实际 Removed；多萝西回答不撤销替换、地图离场或公路奖励。
- 重复回送、重复回答、他人回答、旧义务版本、物品已转移、源牌资格变化不会重复移动或丢失预留实例。
- 收尾登记时牌上1枚仍保留同一 entry；store 后同一窗口查询刷新为2枚，不再发 Started 或额外发动。正式支付、准确实例重用及载体离场只等待自身受影响义务，再按真实状态验证，未受影响的其他收尾段继续。
- 明确跳过可选收尾段不回答/删除独立收留 Choice，预留实例保持；无关主窗口切换不制造截止。最后封局仍有 Pending 时不得提交已结清的最终结果，全部真实答复后只完成一次终结。
- 保存/恢复未决旁路与已答旁路，不再发一份 Choice；四端相同有序命令在旁路穿插、乱序/重复/缺包及恢复后仍保持相同实例、ID、规范状态与连续前缀。
- UI 在实际使用的场景/预制体来源上核查主操作与本人待办，不能用引用测试代替画面验收，也不能开放他人秘密信息。
