## 根因

用户理解成立：Lua应该限制企业升级的候选范围，选择和升级由通用企业Effect负责。两份[普通罗德岛脚本](G:/NoMadCity/Assets/StreamingAssets/Content/core/lua/enterprises/enterprise.rhodes_island.level_1.special.lua:1)与[感染者罗德岛脚本](G:/NoMadCity/Assets/StreamingAssets/Content/core/lua/enterprises/infected.enterprise.rhodes_island.level_1.special.lua:1)现在逐企业拼`Effect.Choice`分支，每个分支才调用确定目标的`UpgradeEnterprise`。因此真正挂起的请求来自通用Choice，`InteractionTypeId=lua.choice`、`PromptKey=enterprise.choose_other_enterprise`；角色能力协调器接管它，显示通用文字选项。

[EnterpriseEffectExecutor.AllowedFields/MissingFields](G:/NoMadCity/Assets/YC/Domain/Enterprises/EnterpriseEffectExecutor.cs:43)目前只允许并要求`enterpriseItemId`，升级Effect没有范围选择阶段。这是通用接口被收窄后内容用Choice绕开缺口的结果。[API初稿](G:/NoMadCity/docs/设计/Lua效果系统API初稿.md:882)原意为企业或候选企业；[EXP-006的落地合同](G:/NoMadCity/prompt/企业扩与感染者基础实装/06-Effect接口与提交合同.md:124)实际只定了确定目标签名。

[EnterpriseInteractionUiCoordinator](G:/NoMadCity/Assets/YC/Presentation/EnterpriseInteractionUiCoordinator.cs:31)只接开局企业、科室及特效请求，没有升级企业交互。已有`EnterpriseDistinctUpgradeFlow`也发布`lua.choice / enterprise.choose_distinct`，存在同类领域选择被通用菜单接管的问题。不能只让UI识别“罗德岛”或仅改Choice提示文字。

## 拟定通用接口与语义

保留现有`Effect.UpgradeEnterprise`和`effect.enterprise.upgrade`，在`apiVersion=1`追加范围入口：

```lua
Effect.UpgradeEnterprise({
    apiVersion = 1,
    player = ctx.playerId,
    enterpriseItemIds = allowedEnterpriseIds,
    levels = 1
})
```

`enterpriseItemId`与`enterpriseItemIds`必须且只能提供一种。旧的确定目标调用、`UpgradeSpec`、全员升级授权子节点及山的确定企业升级不变。两者都缺失继续按既有缺式合同记录并跳过，不能把漏字段自动解释为场上全部企业；两者同时提供、非字符串/重复ID/越权玩家明确拒绝。空数组是明确的空范围，不是缺式。

Lua的数组仅是范围上限；Host根据本局活动企业定义、真实公开企业实例及合作轨道重新确定合法候选，经`PrepareInteraction → CandidateSetResolver`登记。两份脚本改为收集其他企业真实实例ID后直接返回该Effect，删去Choice分支拼装和空范围`return {}`。卡面过滤仍放Lua，C#和UI不写罗德岛专用规则。`ResolveAbility`当前把空Effect列表当缺式；用明确空范围Effect还可避免“合法无目标”被误报为缺式。

范围选择使用`InteractionTypeId=enterprise.upgrade`、`PromptKey=enterprise.upgrade.choose`、`candidate_id`、本人可见、必选1且不可拒绝；候选只为真实企业ItemId，并携带已有`candidateDefinitionIds`投影。阶段为初始→`choose_enterprise`→既有`awaiting_arrival`→`finished`，选择的`selectedEnterpriseItemId`保存在ContinuationData，不能改写原NormalizedArguments。选定后由**同一升级节点**继续原逐级变更与到达收据逻辑，不创建卡名专用Effect，不增加第二份等级状态，不额外包一个同类型升级父子节点。

| 边界 | 拟定行为 |
| --- | --- |
| 多候选 | 正式企业选择页，提交真实ID并复验请求revision、候选版本与Host范围 |
| 单候选 | Host保存唯一目标后直接升级，不弹多余选择页 |
| 明确空范围或复验后无目标 | Completed、`changed=false/reasonCode=no_candidates`；无空框、无缺式日志，后续兄弟正常继续 |
| 满级目标 | 保留既有E-Q01：目标仍可在范围内，5→5成功，`changed=false/limit_reached`，无新到达收据或奖励；不擅自缩小卡面“其他企业”规则。单个满级候选同样自动成功无变化 |
| 4级升2 | 原内核只产生4→5一次真实到达并等待其奖励，后续封顶不重复奖励 |
| 候选失效/旧回复 | Host复验，不越出原范围；失效后重建剩余候选或自动结束，旧版本不能再次提交 |
| 恢复 | 保存范围、选择、请求版本、原等级和到达索引；恢复不能重选已选目标或重领到达奖励。缺失/伪造选择续接字段拒绝恢复 |

## 页面与兼容

`EnterpriseInteractionUiCoordinator`接新`enterprise.upgrade`请求，继续现成`EnterpriseSelectionMode.Company`、企业板预览、确认按钮和`AnswerInteraction`提交链。标题/确认/选择提示沿[现成预制体配置](G:/NoMadCity/Assets/YC/Presentation/Prefabs/Gameplay/Dialogs/Enterprise/EnterpriseSelectionDialog.prefab:2447)，不新增模式。升级请求的`Context`设为空，由现成通用选择提示提供说明，避免误用`InitialEnterpriseContext`写“开局企业”；不在控制器硬编码静态文案。没有必要改预制体、场景或GameplayExpansionUi文案资产。

`EnterpriseDistinctUpgradeFlow`仅将新生成请求改成`enterprise.upgrade`，保留原`enterprise.choose_distinct`提示键、不同企业排除、count及levels合同；不在本轮重写其批量升级规则。协调器兼容旧已挂起的`lua.choice + enterprise.choose_distinct`语义请求，使其也由正式企业页呈现，其他普通Choice仍走原渲染器。该别名需要核对渲染优先级，防止同一请求两页面竞争；现有地图影响力替换已有按`lua.choice + PromptKey`分派的先例。旧罗德岛Choice的已保存分支不改写或转成新节点，避免改变正在执行的效果树；新内容入口使用范围接口。
