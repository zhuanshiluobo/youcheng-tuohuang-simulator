### 根因与实施方案

`BasicRoomContentCapabilityProvider.TryValidate` 和 `GetContentPackHash` 原先各完整构建一次活动内容目录，包括定义复制、脚本检查和图片指纹。`StartMenuRoomPanelView.Render` 每次调用启动校验，`StartMenuController.ShowRoomPanel` 随后再次执行同一校验，请求待处理状态和回执又会触发多次 Render。原只读诊断的基础 328 ms / 企业 410 ms 是一次“校验＋取指纹”，多次刷新会叠加。

实施前确定的缓存键：已加载 `ExternalContentPack` 对象身份及其 `ContentHash`，加配置 `SchemaVersion`、`RuleContractVersion`、`RuleModeId`、`MapId`、`PlayerCount`、按序排列的 `EnabledExpansionIds`。先执行配置合法性检查，绝不通过去重把重复扩展洗成合法组合。

- 准备态、运输状态、房间修订和配置修订本身不影响内容目录，不放入内容缓存键；它们仍由每次启动检查验证。
- 有效人数、地图、扩展组合等变化使用不同条目；回到同一快照下已验证的组合可复用。即使当前部分组合的指纹相同，地图和人数仍各有独立校验条目。
- 内容源返回新快照，或快照摘要变化，清除该提供器全部成功与失败条目。内容包的定义、脚本、图片是已加载隔离快照；磁盘修改按现有加载流程形成新快照后生效，不逐帧扫描磁盘。
- 调用方声称的 `ContentPackHash` 不作为缓存键。构建时仅清空私有配置副本中的声称值，得到真实指纹；每次 `TryValidate` 都重新比较声称值，错误指纹不会污染成功结果。
- 仅缓存内容能力与真实指纹，不缓存 `canStart`。`RoomConfigurationService.TryFreezeForLaunch/TryValidateLaunch` 保持原样，最终检查配置修订、实际人数、规则、准备态、网络身份和各玩家内容版本。

| ChangeRoomConfigurationRequest / ChangeConfiguration / ChangeConfigurationAsync | MapId、RuleModeId、EnabledExpansionIds | 仅 Host；先完整验证后更新。相同值不加 revision、不清准备 |

| SetRoomSeatStatusRequest / SetSeatStatus / SetSeatStatusAsync | SeatIndex、Status | 仅 Host；只可开/关空位，不能关闭已占位槽 |
| RequestRoomSeatSwapRequest / RequestSeatSwap / RequestSeatSwapAsync | TargetSeatIndex | 玩家移动自己；空的 open 槽直接原子移动；occupied 槽建立请求，不能抢占 |
| ConfirmRoomSeatSwapRequest / ConfirmSeatSwap / ConfirmSeatSwapAsync | SwapRequestId、Accepted | 仅目标玩家确认；来源/目标/配置 revision 均仍一致才交换 |
| StartConfiguredGameRequest / TryFreezeForLaunch / StartConfiguredGameAsync | 无 | 仅 Host；复验人数、配置、准备、连接、身份、内容能力和版本，原子冻结 |

CommandId 在每个房间按玩家身份去重，保留最近256份收据。相同 CommandId 重发不重复产生配置变化；跨请求类型复用被拒绝。StateRevision 同步准备、运输和换座请求等变化；ConfigurationRevision 只在有效配置或座位变化时增加。人员和座位变化清除过期换座请求及人工准备。
