## 实例守恒检查方法

1. 冻结Recipe和PlayerIds，公共copyIndex为0—quantity-1；perPlayer按PlayerId升序用`playerOrdinal*quantity+localCopyIndex`。统计预期ItemId集合，重复EntryId或ItemId装配拒绝。
2. 每次工作副本变更后运行ItemZoneQuery.TryValidate：唯一ItemId/ZoneId、单父可达四根且无载体环、接受物理类型/子类型/政策、容量、合法槽占用、主体及每个Order成员集合精确一致。
3. 移动/转交前后比较ItemId集合与数量，OwnerSubject不变；Controller、ZoneId/SlotId与Orders作为同一提交变化；载体移动前后比较附属ZoneId不变。新创建只能增加源EffectId/业务键派生的确切ItemId，重复调用拒绝。
4. Clone/CopyTo后改变工作副本位置/顺序/ContinuationData，源状态不得变化；旧Values或旧标量影子写必须报错，不被克隆静默丢弃。
5. Host JSON往返及最新Journal.StateAfter恢复后再跑上述验证、比较实例集合和下一张牌的顺序；不得运行Recipe、不再次反转、不再次随机抽牌或支付。

### 给局内UI的发布与复用合同

以下事实来自本轮只读核验`GameSession.cs`、`RuleCommit.ApplyInternal`、CopyTo及View投影；未增加发布版本协议或扩大文件写权。

1. `GameSession.State`根对象在Submit成功发布、ReplaceState、ReplaceView及RecoverHost时均通过CopyTo就地更新。既有List及同类型嵌套DTO可保留对象身份；集合按位置复制，不能把旧元素引用当作稳定ItemId索引。根/列表对象身份不变不代表内容不变，不能据此保留跨事务缓存。
2. 每次成功RuleCommit均令EffectRuntime.StateRevision递增1，包含内部Effect提交；一次Submit内可能递增多次，外层追加命令/日志提交还可能再递增。StateRevision不是“每用户操作+1”的UI发布序号。内部Effect只更新该命令工作副本，GameSession在整个成功Submit末尾CopyTo后才发布；失败工作副本不发布。
3. UI应在Submit返回后开始一次同步读取事务，并在其间只读复用同一玩家投影；下一次同步事务默认失效。ReplaceState/ReplaceView/RecoverHost、网络快照接收、视角/玩家/会话切换都必须失效，即使GameId/StateRevision相同、回退或GameState对象引用不变。工作副本在相同revision下也可能已改变位置/候选，故查询本身仅建单次索引。
4. GameStateViewProjector每次创建独立可见性投影，但GameStateView是public字段/List可写DTO，类型不保证不可变。一次同步事务内可在消费者遵守只读的前提下复用；若消费者需修改，应先复制。GameSession.ReplaceView还直接保存传入View对象引用，不能把它当作自动冻结的长期缓存。禁止跨玩家复用私有牌、候选、答案或秘密身份的缓存。
