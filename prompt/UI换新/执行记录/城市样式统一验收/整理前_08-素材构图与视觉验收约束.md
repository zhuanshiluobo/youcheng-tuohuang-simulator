## 1. 先确定每个页面的视觉依据

开工必须列出“实际入口 → 显示模式 → 原说明段落／布局参数 → 原始预览 → 采用的贴图角色 → 当前实际资产 → 目标差异”。源包说明与预览一起读取，不能只看卡图索引、代码或旧 Unity 窗口。

不同入口即使用相同数据，也可能是不同视觉组件。城市样式就是明确例子：

- 主界面第三页：MainGameUI-v2.2 的紧凑状态表；Frontier 3.1 仍保留按行显示的构图。
- 独立查看／宣告页：CityPattern-UI-v1.0 的六张完整卡牌 3×2、卡下额外宣告带、固定纸底摘要和右侧城市。
- 原卡放大：玩家主动查看一个对象，返回原选择状态；按单页面规则处理显示与输入。

这三者不能仅用一个可复用卡牌网格替代。

## 2. 素材版本、结构与真实数据分别核对

| 项目 | 执行依据 |
| --- | --- |
| 外框、背景、按钮等视觉角色 | 仅对被新版明确替代的角色采用新版贴图和切片；写明旧→新依据 |
| 内容排布、信息密度、模式与入口 | 保留各专用素材的构图及用途；没有新版明确覆盖的部分继续按原说明 |
| 卡牌集合、版本、玩家与数量、资格和提交 | 读取正式规则及玩家可见投影；不复制源预览演示数据 |
| 层级、遮罩、窗口拖动、字体、页面数 | 用户最新规则优先；顶底栏最高、窗口不可拖动、单页面与指定字体继续成立 |
| 适配实现 | 原生布局复现上述构图，尺寸改变时按约束分配；禁止主列分页 |

Frontier 3.1 的明示换肤可改变边框纹理与底色，MainButtons 3.2 只覆盖其明确列出的按钮，3.5 只覆盖指定主框。不能据“统一主题”把状态表改成卡图网格、把 3×2 总览改成单卡轮播，或删除固定摘要等原设计区域。也不能因本次纠正把主界面整体回退到 v2.2 旧顶栏和旧层级。

## 3. 正确理解“保持 1920×1080 位置”

该要求保护已经完成且符合目标的主界面构图，布局重构不能顺便挪动它。对本来就待换新的旧窗口，旧 Prefab 的大小、左右比例和内容组织不是必须保留的设计标准。

执行时将对象分为：

1. 已正确完成、与本次目标无关：保持正常屏幕矩形与视觉。
2. 本项待替换、已被指出偏离素材：按目标素材修正，并记录旧／新差异。
3. 素材原矩形与最高顶底栏、安全区冲突：只作必要的边界、留白和尺寸分配调整，列出原因与调整量；保留信息结构和比例关系。

例如 CityPattern 原窗 1744×944 的下缘进入新版底栏，需要约束到实际 ContentRoot；这不支持把现有 1520×900 和原先左右占比直接当成最终目标，也不支持因此让六张卡在基准尺寸只能显示四张。

## 4. 原生布局服务于素材构图

先从源设计确定区域、顺序、行列数、固定内容与伸展内容，再选 VLG／HLG／GridLayoutGroup。状态表使用行与列；卡牌总览使用网格。两个都能滚动或都能用 Layout，不代表视觉用途相同。

布局参数在资产内管理。源坐标用于推导基准 padding、spacing、preferred size、比例和区域关系，不转成每分辨率坐标表。正文填充、单轴尺寸所有权、最小尺寸约束和内部滚动继续按 07 实现；不能以采用原生组件为由重新设计页面。

## 5. 视觉验收须有对应关系

顺序为：

1. 读取源说明、参数及实际预览，列逐区域检查表。
2. 在正确原生结构中放齐素材；先看 1920×1080。
3. 并排对照相同模式的源图与当前实际显示，逐项检查结构、可见数量、底图／边框、标题、摘要、按钮、状态与标记。
4. 区分合理数据差异、明示换肤、必要边界调整和未完成设计项。空局没有标记不是错误，但不能证明多玩家状态槽正确；需另用明确标为诊断的数据看实际资产。
5. 视觉偏差修正后核对层级、命中与保留的业务，最后做有限代表尺寸回归。

测试数、编译通过、图片无越界、Prefab 引用存在，只覆盖各自受测条件。视觉验收必须记录源预览路径、实际截图、所用数据／模式、具体差异及结论。没有源图对照表，不得把“已查看截图”记成“符合素材设计”。
