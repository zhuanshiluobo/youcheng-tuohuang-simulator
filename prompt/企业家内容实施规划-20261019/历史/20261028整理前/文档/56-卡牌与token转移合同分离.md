# 卡牌转移与 token 转移分离的最新纠正

2026-10-22，用户直接指出：“为什么会限制为设施牌，卡牌转移和token转移不要搞混了”。本文件纠正54/55中把设施批量分支视为 token 扩展入口的不准确建议；55的并行职责、单写边界和先交真实合同的安排保持。

## 当前唯一实施要求

1. 卡牌转移与 token 转移分别核对对象、合法来源去向、操作权限及生命周期。现有设施批量转移分支的设施限制不能外推为全部卡牌转移只准设施牌，也不能当成 token 必须借用的权限。
2. 禁止为了迁移指令、声望或角色标记，直接放宽 core.facility_card_transfer、冒充设施牌、套用设施层序/落位校验，或将卡牌与 token 混在同一含糊合同下。
3. Lua 使用真实存在并获授权的通用 token 转移能力表达标记费用；先核既有单来源多实例转移及 core.cube_storage / core.player_marker_storage 等配置的实际适用范围。确有缺项时，由005在 token 合同内补齐通用能力，不能让内容作者猜字段或注册名。是否复用底层原子事务由实现者依据代码决定，不等于合并业务合同。
4. 不新增或保留标记付款原语。Lua负责所需类型、数量、真实实例、本人/来源玩家及真实去向的规则组合；通用内核保障权限、足额原子转移、结果/收据和恢复。正规资源支付机制保持。
5. 卡牌转移仍按其真实牌类/区域/实例规则处理，设施落位/叠建特有约束保留；不能借本轮清理无依据限制其他牌类，也不扩张为无关的全转移系统重写。
6. 所有迁移保留既定费用、Condition左式成功后右式续接、原供应/回盒区别、响应与生命周期。等价 token 不因内部ID不同另弹多余支付选择；卡面有意义的目标、点数、收益选择继续保留。

## 本轮承接

- 005：核清 token 与卡牌现有操作链。先完成最小可用 token 合同和专用标记付款入口退役，交确切 API 版本、参数、允许的 token 操作配置、来源查询、原子失败/成功结果及恢复语义。解释既有卡牌/设施能力如何保持，不把“放开设施批量限制”当实现目标。独占范围仍按55，不写Lua或费用调用方。
- 008：费用、Condition、收尾及恢复消费通用 token 转移事实/收据；不消费设施层序结果来证明标记已付，不改005接口。
