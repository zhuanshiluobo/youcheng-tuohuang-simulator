# 玩家黑盒全流程测试方案

## 1. 结论与目标

本方案建立一套独立于 Domain、Command Handler、Effect 内核和旧自动跑局器的玩家黑盒验收。首要目标不是覆盖每条数值规则，而是证明一局游戏能够从开始菜单仅靠玩家可见、可执行的操作推进到最终计分，并且中途不存在无可用操作、无 UI 的阻塞、错误等待或必须由测试直接修改状态才能继续的情况。

主流程固定为：

```text
StartScene
  → 创建本地对局
  → 入场选点 / 入场事件
  → 第 1 回合盖放角色牌
  → 第一行动轮的各玩家窗口
  → 第二行动轮的各玩家窗口
  → 采集
  → 逐玩家收尾（无内容时自动通过）
  → 回合结束
  → 重复至第 8 回合
  → 最终计分
  → 返回开始菜单
```

当前已知的首个预期失败点是：最后一名玩家盖牌完成后，界面进入第一行动轮，但行动窗口的执行 Effect 尚未启动，导致玩家行动无法挂载。黑盒测试必须在这里失败，而不是调用 `RoundExecutionService.Advance` 帮游戏继续。

## 2. “只进行玩家操作”的硬边界

### 2.1 允许的操作

测试运行期间只允许：

1. 启动 Editor、Development Build 或多个客户端进程。
2. 在进程启动前固定随机种子、分辨率、日志目录和测试策略名称。
3. 通过实际 `EventSystem` 向当前可交互 UI 发送完整的点击、按下、抬起、拖动、放置、滚动和文本输入序列。
4. 点击当前玩家可见且启用的按钮、卡牌、地图热点、槽位或对话框选项。
5. 等待场景加载、动画、Host 回包、其他玩家操作或无需玩家参与的主链自动推进。
6. 读取玩家实际可见的信息：活动场景、按钮是否启用、提示文字、卡牌正面、合法目标高亮、弹窗、回合轨和最终计分面板。
7. 在失败时保存屏幕截图、玩家操作轨迹、Unity 日志和只读诊断快照。诊断快照不能参与测试决策，也不能被写回游戏。

固定随机种子属于启动环境，不属于局中作弊。种子只能在创建对局前注入；对局创建后禁止重排牌堆、替换市场或指定抽牌结果。

### 2.2 禁止的操作

玩家黑盒测试及其决策器禁止：

- 读取或修改 `GameState`、`PlayerState`、`EffectRuntimeState` 或任何 Pending 状态；
- 构造或提交 `GameCommand`；
- 调用 `GameSession.Submit`、`AuthoritativeCommandDispatcher`、任一 Command Handler；
- 调用 `RoundExecutionService.Advance`、`RoundAdvanceService`、`EffectTreeExecutor` 或回答内部主链 Interaction；
- 直接调用 Controller、Presenter、Dialog 的业务方法；
- 使用 `Button.onClick.Invoke()` 代替指针点击；
- 通过反射调用私有方法、读取私有状态或强行触发回调；
- 预置设施、资源、影响力、城市样式、已盖角色牌或行动完成标记；
- 因没有合法行动而直接写 `ActedMainActionThisTurn = true`、跳过阶段或强制进入下一回合；
- 在失败后修改状态并继续，将一次失败伪装成完整跑局成功。

现有 `LocalhostAutoplayRunner` 会预置设施与资源、重排设施供给，并存在直接补写行动完成标记的兼容逻辑，因此只保留为诊断工具，不得作为本方案的通过证据。

## 3. 测试架构

### 3.1 玩家输入驱动器

新增一个只在 `UNITY_EDITOR` 或 `DEVELOPMENT_BUILD` 中编译的玩家输入驱动器。驱动器只依赖 Unity UI、`EventSystem`、场景和轻量自动化标识，不依赖 Domain/Application/Effect 类型。

驱动器提供的公开动作限定为：

```text
Click(id)
Drag(sourceId, targetId)
Scroll(id, delta)
EnterText(id, text)
WaitUntilVisible(id, timeout)
WaitUntilHidden(id, timeout)
WaitForScene(sceneName, timeout)
CaptureEvidence(label)
```

`Click` 必须通过目标的屏幕坐标进行 EventSystem raycast，并发送完整的 pointer down/up/click 序列。`Drag` 必须发送 pointer down、initialize potential drag、begin drag、逐帧 drag、drop、end drag 和 pointer up。目标在 raycast 中不可达、被遮挡或不可交互时，动作必须失败，不得绕过遮罩直接调用组件。

### 3.2 稳定 UI 标识

为玩家能够交互或观察的对象添加稳定的 `PlayerAutomationId`，作用等同于网页的 `data-testid`。它只能帮助定位玩家可见元素，不能暴露隐藏候选或权威状态。

建议的最低标识集合：

| 区域 | 标识示例 |
|---|---|
| 开始菜单 | `start.local_game`、`start.create_room`、`start.join_room` |
| 入场 | `entrance.location.G-01`、`event.option.0` |
| 手牌与盖放 | `character.hand.{instanceId}`、`character.cover_slot` |
| 行动面板 | `action.character.strategy`、`action.character.tactic`、`action.deploy`、`action.dispatch`、`action.explore`、`action.move`、`action.build`、`action.end` |
| 地图 | `map.location.{id}`、`map.route.{id}`、`map.influence_slot.{id}` |
| 通用交互 | `dialog.option.{ordinal}`、`dialog.confirm`、`dialog.cancel`、`dialog.amount.plus`、`dialog.amount.minus` |
| 采集 | `collection.open`、`collection.location.{id}`、`collection.confirm` |
| 回合与终局 | `round.current`、`round.phase`、`final.winners`、`final.scores`、`final.return_to_start` |

动态元素的自动化标识只能挂在实际显示给该玩家的对象上。其他玩家的隐藏手牌、Host-only Effect、完整候选集和不可见答案不得生成可查询标识。

### 3.3 玩家观察器

观察器只生成以下玩家视角数据：

- 当前活动场景；
- 当前可见且可 raycast 的自动化标识；
- 可交互控件的 `interactable` 状态；
- 玩家可见文字和卡图标识；
- 地图上实际显示的合法目标高亮；
- 当前是否存在遮挡输入的模态弹窗；
- 最终计分面板中显示的玩家、分数和赢家。

测试策略只能根据观察器输出决定下一步。诊断代码可以在失败后额外导出内部状态，但决策器不得访问这份数据。

### 3.4 静态防作弊门禁

只保留一个轻量 EditMode 门禁，扫描玩家旅程测试程序集和运行时驱动器：

- 程序集不得引用 `YC.Domain`、`YC.Application`、`YC.Infrastructure.Lua` 或多人核心程序集；
- 源码不得出现上文禁止的状态、命令和执行器类型；
- 不允许反射、`SendMessage`、`BroadcastMessage`、`onClick.Invoke()` 或直接调用业务回调；
- 允许 Unity UI、EventSystem、场景、截图、日志、JSON 结果和自动化标识类型。

这个门禁是本方案唯一需要新增的 EditMode 测试，不按卡牌或流程复制测试项。

## 4. 测试套件

| 编号 | 场景 | 运行频率 | 通过目标 |
|---|---|---|---|
| `PJ-000` | 玩家边界静态门禁 | 每次提交 | 证明测试没有内部作弊入口 |
| `PJ-001` | Editor 本地单人完整 8 回合 | 每次主链、UI、Command、Effect 改动 | 从开始菜单推进到最终计分并返回开始菜单 |
| `PJ-002` | Editor 本地单人分支丰富种子 | 每日或相关内容改动 | 在完整跑局中自然覆盖事件、角色牌和多种主要行动 |
| `PJ-003` | Windows Development Build 本地单人 | 发布候选 | 证明构建产物而非 Editor 环境可以完成整局 |
| `PJ-004` | 四客户端真实房间完整 8 回合 | 夜间及发布候选 | Host 与四个玩家只通过各自 UI 完成整局 |
| `PJ-005` | 四客户端断线恢复后继续到终局 | 发布候选 | 在玩家等待点重启一个客户端，恢复后仍能完成整局且不重复结算 |

`PJ-001` 是最先实现、最重要的红线测试。它不负责证明正式四人平衡，但必须证明单人调试入口与新主链不存在结构性死锁。`PJ-004` 才是正式多人流程的最终证据。

## 5. PJ-001：本地单人完整跑局

### 5.1 启动条件

- 从 `StartScene` 开始，不直接加载 `SampleScene`；
- 使用正常本地游戏按钮创建对局；
- 使用四人地图的正常地图定义和一名本地玩家；
- 使用记录在结果中的固定随机种子；
- 不使用右卡冒烟状态、快速演示状态或任何 Fixture；
- 分辨率固定为 `1920x1080`，`timeScale = 1`；
- 全局上限 5 分钟，任何单次玩家操作或自动推进不得无限等待。

### 5.2 操作流程

| 步骤 | 玩家看到的状态 | 唯一允许的操作 | 通过条件 |
|---:|---|---|---|
| 1 | 开始菜单 | 点击“本地游戏” | 经过加载场景进入地图，未出现错误消息 |
| 2 | 入场地点高亮 | 点击策略选出的第一个合法入场地点 | 城市落位；若出现入场事件则进入步骤 3，否则进入盖牌 |
| 3 | 入场事件弹窗 | 点击第一个启用选项，并完成其后续目标/支付弹窗 | 弹窗关闭，进入盖牌阶段 |
| 4 | 玩家手牌与盖放区域 | 将策略选出的角色牌拖到盖放区域 | 牌从手牌消失；主链自动进入第一行动轮 |
| 5 | 第一行动轮 | 按 5.3 的策略完成可选快速行动和恰好一次主要行动 | 行动完成提示可见，所有派生弹窗已处理 |
| 6 | 行动面板 | 点击启用的“结束行动” | 自动进入第二行动轮，不出现未知选择或无 UI 阻塞 |
| 7 | 第二行动轮 | 重复步骤 5、6 | 自动进入采集阶段 |
| 8 | 采集 UI | 打开采集，选择 UI 显示的合法地点/路线/付费接收方并确认 | 采集结算完成，不再存在玩家可见待处理项 |
| 9 | 收尾 | 只处理实际出现的玩家选择；没有选择时不点击任何“内部继续”控件 | 空收尾必须自动推进；有收尾 Effect 时完成后自动推进 |
| 10 | 下一回合 | 等待回合轨更新，再从盖牌步骤继续 | 第 1 至第 7 回合都进入下一回合且只进入一次 |
| 11 | 第 8 回合结束 | 等待自动进入最终计分 | 最终计分面板显示玩家 1、分数和赢家 |
| 12 | 最终计分 | 点击“返回开始菜单” | 返回 `StartScene`，本次轨迹标记成功 |

### 5.3 行动决策策略

策略只从当前可见且启用的 UI 选择，不读取资源对象或规则服务。

每个行动窗口按以下优先级处理：

1. 若存在模态弹窗，先完成弹窗；不得点击被遮挡的行动面板。
2. 若本局尚未成功使用角色牌，且策略/战术按钮至少一个启用，则使用第一个启用效果并完成全部派生交互。
3. 从当前启用的主要行动中，优先选择本局尚未成功执行过的类型：探索、移动城市、部署影响力、调度影响力、建设设施。
4. 若上述未覆盖行动均不可用，则从任一启用的主要行动中选择第一个，并按 UI 高亮选择合法目标。
5. 若没有任何主要行动可用且“结束行动”也未启用，立即判定为 `PLAYER_DEADLOCK`，禁止补写完成标记。
6. 主要行动完成后，只有“结束行动”实际启用时才能点击。

通用交互策略：

- 单选：选第一个启用候选；
- 多选：按界面显示的最小必选数量，从左到右选择；
- 数量：选择 UI 允许的最小正数；
- 支付：选择第一个能够使确认按钮启用的组合；
- 可选效果：分支丰富测试优先接受，基础通关测试允许选择取消；
- 目标：只点击当前高亮且 raycast 可达的地图对象；
- 对话框提交后若仍显示，必须等待其内容变化，不能重复点击旧按钮。

### 5.4 自动推进要求

以下转换不得依赖测试点击内部确认或直接推进主链：

- 最后一名玩家完成盖牌 → 第一行动轮；
- 当前玩家完成空收尾 → 下一位玩家收尾或回合结束；
- 所有玩家完成采集 → 第一个收尾窗口；
- 最后一名玩家完成收尾 → 回合结束；
- 非最终回合结束 → 下一回合盖牌；
- 第 8 回合结束 → 最终计分。

每次自动转换默认超时 3 秒；场景加载默认超时 15 秒；Host/客户端网络等待默认超时 10 秒。超时必须记录最后可见提示和所有当前可交互标识。

## 6. PJ-002：分支丰富完整跑局

`PJ-002` 使用多个经过人工确认、但不修改局中状态的固定种子。每个种子仍必须从开始菜单跑到最终计分；不能只执行某张牌后退出。

种子集合共同至少自然覆盖：

- 一次入场事件选择；
- 一次移动或探索触发的事件牌选择；
- 一次需要地图目标的角色牌效果；
- 一次多步骤 Interaction；
- 部署、调度、探索、移动、建设五类主要行动；
- 至少一次有航道路费的采集；
- 至少一次城市样式宣告；
- 若正常资源积累能够达到，至少一次特殊行动；否则记录为独立内容覆盖缺口，不允许预置资源强行触发。

任何种子因规则变化不再能完成目标时，应更换为通过正常玩家操作发现的新种子，并在文档中记录原因；不得在局中补状态维持旧脚本。

## 7. PJ-004：四客户端完整跑局

### 7.1 进程模型

- 启动一个 Host Development Build 和三个 Client Development Build；
- 每个进程拥有独立日志、截图、结果和玩家输入驱动器；
- Host 玩家也必须通过自己的 UI 操作，不能由 Host 进程直接提交其他玩家命令；
- 四个客户端通过正常房间创建、加入、准备和开始按钮进入游戏；
- 测试编排器只负责启动/停止进程、分配窗口和等待结果，不接触游戏状态。

### 7.2 同步规则

- 当前玩家客户端根据自己的可见 UI 执行动作；
- 非当前玩家只允许等待、浏览公开信息或处理明确属于自己的并发采集任务；
- 任一客户端出现与 Host 不同的公开回合、当前玩家或最终分数时失败；
- 隐藏手牌不得在其他玩家的 UI 标识或日志中出现；
- 一个玩家完成操作后，其他客户端必须通过正常网络同步看到公开结果。

### 7.3 通过条件

四名玩家都完成入场、每回合盖牌、两轮行动、采集和收尾；Host 只生成一个第 8 回合终局；四个客户端都显示相同公开最终分数和赢家，并能正常返回开始菜单。

## 8. PJ-005：恢复后继续完成整局

恢复测试只在玩家等待点操作进程，不改变局中状态。至少覆盖三个检查点：

1. 已显示事件/角色交互，但玩家尚未回答；
2. 主要行动已完成，但玩家尚未点击结束行动；
3. 采集阶段中已有部分玩家提交，仍有玩家未提交。

在检查点关闭一个非 Host 客户端，使用正常重连入口恢复。恢复后只能通过 UI 继续当前选择，并最终完成第 8 回合。已经结算的 Effect、资源、事件和日志不得在 UI 中重复出现。

## 9. 全程不变量与失败分类

### 9.1 全程不变量

- 任一时刻最多只有一个遮挡玩家输入的模态弹窗；
- 当前玩家始终至少拥有一个合法的继续方式：可处理交互、可执行行动、可结束窗口或等待明确的自动推进；
- 玩家执行成功操作后，UI 必须出现可观察变化；
- 已提交操作在结果明确前不能被再次提交；
- 内部 `round.mainline.complete`、`collection.task` 等交互不得作为未知选择展示给玩家；
- 空收尾不显示“结束回合”要求；
- 场景、弹窗和地图目标之间不存在永久 Busy、透明遮罩或不可点击高亮；
- 到达最终计分时没有遗留玩家选择或仍可执行的行动按钮。

### 9.2 失败分类

| 代码 | 含义 |
|---|---|
| `PLAYER_DEADLOCK` | 当前玩家没有任何可见合法操作，也没有明确自动推进 |
| `MISSING_UI` | 规则等待玩家选择，但没有出现对应 UI |
| `PHANTOM_UI` | 出现玩家无法理解或不应看见的内部交互 |
| `INPUT_BLOCKED` | 目标可见并启用，但 raycast 被错误遮挡或拖放失败 |
| `NO_VISIBLE_PROGRESS` | 操作提交后 UI 在超时内没有变化 |
| `DUPLICATE_RESOLUTION` | 单次玩家操作导致重复奖励、重复弹窗或重复推进 |
| `WRONG_PLAYER_WINDOW` | 非当前玩家可行动，或当前玩家无法行动 |
| `ROUND_TRANSITION_TIMEOUT` | 采集/收尾/回合结束未自动推进 |
| `FINAL_SCORING_MISSING` | 第 8 回合完成后未显示最终计分 |
| `PROCESS_OR_LOG_FAILURE` | 崩溃、未处理异常、断言或错误日志导致流程终止 |

## 10. 证据与结果文件

每次运行创建独立目录：

```text
Logs/PlayerJourney/<timestamp>-<scenario>/
├─ result.json
├─ actions.jsonl
├─ player-visible.log
├─ unity.log
├─ failure.png
└─ clients/
   ├─ p1/...
   ├─ p2/...
   ├─ p3/...
   └─ p4/...
```

每条 `actions.jsonl` 至少记录：

- 单调步骤号与时间；
- 场景名；
- 玩家输入类型；
- 自动化标识；
- 操作前后可见提示摘要；
- 当前可见且启用的顶层操作；
- 成功、超时或失败代码。

`result.json` 至少记录：

- 场景编号、构建版本、随机种子、开始/结束时间；
- 是否到达最终计分并返回开始菜单；
- 观察到的回合数量；
- 各类玩家行动成功次数；
- 处理的玩家可见 Interaction 次数；
- 错误/异常数量；
- 失败代码、最后 50 步轨迹和截图路径。
