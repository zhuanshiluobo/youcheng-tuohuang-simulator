### 0.2 Effect 调度理解

以下是agent和txym对当前规则的理解，后续设计接口时继续核对：

1. 游戏规则中的 Effect 不并行执行。同一父节点下已经确定顺序的子 Effect 依次进入执行和结算；前一个兄弟节点完成后，下一个兄弟节点才能执行。
2. 一个 Effect 完成本身工作后，要么直接标记完成，要么创建子节点并等待阻塞型子节点完成。
3. “玩家可以选择先后顺序”不称为并发执行，而称为“无序候选集合”。玩家作出选择后，被选中的候选转化为当前有序执行节点。
4. 玩家行动窗口中的主要行动和快速行动可以作为无序候选挂在对应主链节点下，但玩家每次只选择并执行一个。
5. `指令姐`的“战术行动”可能同时出现在特殊行动入口和快速行动入口中；两个入口必须复用同一个挂在玩家身上的“是否已使用”状态。卡牌正式名称和具体入口仍待牌面核对。
6. 收尾阶段仍按本回合玩家顺序推进。某个玩家的原始收尾 Effect 直接挂在该玩家的收尾窗口节点下；同一玩家有多个收尾 Effect 时，它们先作为无序候选，由该玩家决定执行顺序。
7. 角色牌的永续、授勋卡的永续实际上只是ui表现，这些效果在被玩家选择使用的时候，不是挂上去，触发lua调用，永续退出的结算也可以在这里实现，比如从玩家可选行动池中移除。
8. 理想状态下，lua被触发都是因为玩家做了什么ui操作，常见event可能都是某一项效果结算前后产生的（玩家操作间接产生），非常见event都是玩家操作直接产生的。
9. 现在对角色双发状态的处理有点怪，主要是出现在阿米娅身上，因为阿米娅的永续是使用角色牌时再用的，严格按照规则书的话，顺序应该是使用角色牌、单发选择之前、使用阿米娅计谋、变双发、使用角色牌完成。但导致出现不一样的effect链扩展，正常来说，快速行动使用角色牌连在主链上的轮次节点，角色牌连接快速行动节点，它的子节点包含策略/计谋，在有了阿米娅时变成先挂阿米娅再挂策略和计谋。这里感觉最好把所有实际双发统一成同一个链结构。

#### 1.1.1 Effect式

`Effect式`不是条件式、选择式和次数式的统称，也不是一种独立的卡面最小 Effect。它特指“可以作为内容挂到 Effect 节点上的结构”。

当前关系为：

```text
一个或多个卡面最小 Effect
  → 组成可挂载的 Effect式
  → 作为 Effect 节点的内容

条件式 / 选择式 / 次数式
  → 本身属于卡面最小 Effect
  → 使用 Effect式作为参数或子内容
```

Effect式用于方便描述和挂载节点，本身不是一个可单独调用的 API，也不需要作为“第四类卡面最小 Effect”注册。挂载时，Effect式就是对应 Effect 节点承载的内容；其中引用的条件式、选择式、次数式或其他卡面最小 Effect，再按各自规则产生和阻塞子节点。Effect式的数据表示和内部固定顺序留到接口阶段定义。

#### 1.1.2 Lua 添加 Effect 的挂载位置

| 挂载位置 | 当前含义 | 顺序或阻塞 | 待确认项 |
| --- | --- | --- | --- |
| 当前父 Effect 节点 | 作为当前卡面处理产生的子 Effect | 默认阻塞父 Effect 完成 | Lua 的具体调用参数和允许的非阻塞选项 |
| 本回合该玩家的收尾窗口节点 | 延迟到该玩家本回合收尾时处理 | 同一玩家的多个收尾 Effect 先作为无序候选，由玩家决定顺序 | 何时停止允许追加、跨回合时如何处理 |
| 最终分数结算节点 | 在最终分数结算时处理追加 Effect | 按最终计分的规则顺序执行 | 追加时机、分项顺序和重复计分保护 |

这些挂载位置是内核提供的受控目标，不代表 Lua 可以用任意节点 ID 改写 Effect 树。具体权限和参数留到第 3、4 节定义。

## 2. Lua 卡面定义 API

### 2.1 定义阶段与运行阶段

C# 需要提供可校验的卡面定义结构、Lua 注册入口和内容目录。Lua 使用这些结构声明具体卡面，不要求 C# 硬编码每一张具体卡牌。

卡面定义加载不由 `RuleEvent` 触发，因为它属于对局开始前的内容注册阶段，不属于一次规则结算：

```text
内容加载阶段
  → C# 创建受限 Lua 定义环境
  → Lua 返回具体卡面定义
  → C# 校验并建立只读内容目录和 Event 订阅索引
  → 对局绑定本次内容版本

对局运行阶段
  → C# 形成 RuleEvent
  → EventBus 找到已注册的具体卡面 Lua
  → Lua 生成 Effect式或其他受支持请求
```

因此，“Event 是 Lua 的唯一规则入口”只约束对局运行阶段。定义阶段的 Lua 只能声明静态内容，不能读取或修改某局 `GameState`、创建实际 Effect 节点、请求 UI 或使用未受控随机数。

### 2.2 C# 需要提供的内容定义

这里的“定义类型”表示 C# 必须提供相应的数据契约、注册和校验能力；实现时可以使用共同基类加类型字段，不要求每种内容都必须成为完全独立的 C# 类。

| 内容类型 | C# 提供的逻辑定义 | Lua 负责填写的内容 | 玩家标记区 | 当前决定 |
| --- | --- | --- | --- | --- |
| 城市样式牌 | `CityStyleCardDefinition` | 具体牌面、标记区、能力和 Effect式 | 有 | 需要定义 |
| 企业板 | `EnterpriseBoardDefinition` | 合作等级、奖励、解锁内容、标记区和企业特效 | 有 | 需要定义 |
| 角色牌 | `CharacterCardDefinition` | 策略、计谋、标记区和对应处理器 | 有 | 需要定义 |
| 企业家能力牌 | `EntrepreneurAbilityCardDefinition` | 能力、标记区、触发条件和对应处理器 | 有 | 需要定义 |
| 企业家回合卡 | `EntrepreneurRoundCardDefinition` | 回合内容、标记区、触发条件和对应处理器 | 有 | 需要定义 |
| 设施卡 | `FacilityCardDefinition` | 费用、分数、标签、入场效果和其他牌面能力 | 当前未指定 | 需要定义 |
| 科室板 | `DepartmentBoardDefinition` | 科室板状态、区域和能力 | 待确认 | 可能不需要独立定义 |
| 牌堆 | `DeckDefinition` | 可包含内容、初始化和区域规则 | 不适用 | 可以考虑定义 |

“当前未指定”表示尚未确认这种内容是否普遍拥有玩家标记区，不等于禁止个别卡面将玩家标记作为目标。

### 2.3 内容共同定义

以下只作为待填写的数据壳子。字段是否放在 Lua 定义中，等实际卡面录入后再收敛：

```text
LuaContentDefinition
├─ definitionId
├─ contentType
├─ version
├─ displayNameKey
├─ artworkId
├─ tags
├─ playerMarkerZones[]
├─ abilities[]
├─ eventSubscriptions[]
├─ effectExpressions[]
└─ deckReferences[]
```

共同字段说明：

| 字段 | 用途 | 是否必须 | 待确认项 |
| --- | --- | --- | --- |
| `definitionId` | 内容包内稳定标识 | 是 | 命名和扩展命名空间 |
| `contentType` | 区分城市样式牌、企业板等定义类型 | 是 | 枚举范围 |
| `version` | 对局恢复时绑定相同规则版本 | 是 | 版本号与内容哈希关系 |
| `displayNameKey` | 引用本地化显示名称 | 待定 | 是否允许 Lua 直接提供默认名称 |
| `artworkId` | 引用 Unity 侧美术资源 | 待定 | 资源不存在时的处理 |
| `tags` | 提供受控分类和候选过滤 | 待定 | 标签注册表 |
| `playerMarkerZones` | 声明卡面上的玩家标记区 | 按内容类型 | 见第 2.4 节 |
| `abilities` | 声明卡面能力和稳定能力 ID | 按卡面 | 主动、被动和持续能力结构 |
| `eventSubscriptions` | 声明运行期监听的 Event | 按能力 | 实例何时启用或停用订阅 |
| `effectExpressions` | 声明可以生成的 Effect式 | 按能力 | 引用、内联和复用方式 |
| `deckReferences` | 声明所属或关联牌堆 | 待定 | 是否改由牌堆单向引用卡牌 |

具体卡面实例的所属玩家、所在区域、玩家标记占用、是否已使用等动态状态属于 `GameState`，不能写回 Lua 卡面定义。

### 2.4 玩家标记区

城市样式牌、企业板、角色牌、企业家能力牌和企业家回合卡都可以声明玩家标记区。C# 至少需要提供一种通用的玩家标记区定义：

```text
PlayerMarkerZoneDefinition
├─ zoneId
├─ zoneKind
├─ capacity
├─ allowedMarkerOwners
├─ selectionTags[]
├─ initialState
└─ displayAnchorId
```

字段的准确含义留到录入具体卡面时确认。最低要求是：同一卡面定义内的 `zoneId` 唯一，容量和允许进入的玩家标记必须可以由 C# 校验。

玩家标记区需要成为最小 UI 交互可以返回的一类卡面选项。运行期选择的不是静态 `PlayerMarkerZoneDefinition`，而是本局具体卡牌或板块实例上的区域引用：

```text
PlayerMarkerZoneRef
├─ contentInstanceId
├─ contentDefinitionId
├─ zoneId
└─ currentMarkerState
```

选择流程暂定为：

```text
Lua 或固有效果链提出玩家标记区选择请求
  → C# 根据定义目录和当前 GameState 生成候选 PlayerMarkerZoneRef
  → UI 显示卡面或板块及其可选玩家标记区
  → 玩家选择一个或多个区域引用
  → C# 复验内容实例、zoneId、容量、所有权和当前状态
  → 记录答案并形成后续 Event
```

Lua 只能使用稳定的内容实例 ID 和 `zoneId` 指定或过滤区域，不能保存 Unity 场景对象、坐标或 UI 控件引用。实际放置、移动和移除玩家标记仍需调用对应的卡面最小 Effect。

以下细节待填写具体卡面后确认：

- 玩家标记区是否包含单个槽位和多槽位两种结构；
- 区域是否区分可放置、计数、次数、锁定和已使用等用途；
- 某些区域能否只接受卡牌所有者或指定玩家的标记；
- UI 选择结果返回整个区域，还是必须返回区域内具体槽位；
- 企业合作等级轨道是否复用该结构，还是使用独立的等级轨道定义。

### 2.6 科室板与牌堆

科室板是否需要独立的 `DepartmentBoardDefinition` 暂不决定。若科室板只作为某家企业特效的内部状态和选项，可以先由对应企业定义引用；只有当它具有可复用区域、独立能力、独立订阅或需要作为通用 UI 目标时，再提升为独立内容定义。

牌堆可以考虑使用通用 `DeckDefinition`。它描述的是内容容器和区域规则，不是某张卡面：

```text
DeckDefinition
├─ deckId
├─ acceptedContentTypes[]
├─ setupComposition
├─ drawZone
├─ discardZone
├─ candidateZone
├─ visibility
└─ shufflePolicy
```

牌堆定义不能保存某局的实际顺序。实际卡牌实例、当前顺序、抽取结果和洗混结果属于 `GameState` 与 Effect 链。

### 2.7 内容加载校验

C# 加载 Lua 卡面定义时至少检查：

- `definitionId` 在当前内容集合中唯一；
- 内容类型、版本和引用字段合法；
- 同一卡面内的能力 ID 和玩家标记区 `zoneId` 唯一；
- 玩家标记区容量、允许所有者和标签格式合法；
- 引用的 Effect、Effect式、Event、Lua 模块和处理函数存在；
- 牌堆引用的内容类型符合约束；
- 扩展替换既有定义时具有显式替换关系，不依赖加载顺序覆盖；
- 对局记录本次内容目录的版本或哈希，恢复时不能静默换用不同卡面定义。
