# DIY 包体设计

日期：2026-11-01。本文保留设计基线；当前实现、验证与未覆盖项见 [DIY 接入进展](../../prompt/DIY接入实施计划-20261101/05-DIY接入进展-20261111.md)。

2026-11-18 更新：第 5.3 节的准备阶段框架已接入当前源码，官方模式通过显式合同启用，DIY 模式可以声明或继承准备流程。具体验证范围与尚未覆盖项见[准备阶段实施记录](../../prompt/DIY接入实施计划-20261101/18-准备阶段框架实施计划-20261114.md)；第 2 节保留原设计时的源码基线。

本设计规定事件牌按钮与奖励 Lua 的直接绑定，以及提供模式和扩展的 DIY 包的目录、装配、安装、联机和存档合同。实施顺序为：先完成事件牌改造，再完成 DIY 读取与安装分发。本文中的新字段和能力名是目标合同，不能当作当前版本已经支持的接口。

## 1. 已确定的方向

- 事件牌每个选项条目同时声明按钮、稳定选择 ID 和奖励 Lua，按钮数量取自该列表。取消另一个按钮列表通过数字下标寻找奖励的设计。
- 每个按钮的上下边界用单张卡面高度百分比配置；外观和默认横向范围继续来自现有场景或预制体。
- 界面提交选择 ID；正式规则执行链校验后调用该条目绑定的 Lua。按钮点击回调不直接运行 Lua，不直接改变资源或对局状态。
- DIY 安装到当前用户的游戏数据目录下的 `Mods`。已安装与本局启用分别管理。
- DIY 包是安装和分发单位，可以提供模式、扩展，或同时提供两者。房间的玩法选择只有“模式”和“扩展”，不增加 DIY 包或包版本选择控件。
- 一局至少选择一个模式，也可以组合不冲突的多个模式，并选择与启用模式兼容的扩展。DIY 模式与基础模式、企业家模式平级；模式组合现有玩法机制，配置不能表达的规则差异通过现有 Lua API 实现。
- 安装器支持安装游戏时选装 DIY、之后仅补装 DIY，以及将随包内容导出为 ZIP。
- 开发者协助制作的 DIY 与其他作者的 DIY 使用同一格式和读取流程。
- 单局使用冻结内容快照，进行中的对局不热换内容；旧版本保留给匹配的存档使用。

## 3. 事件牌选择合同

### 3.1 单一选择列表

在事件 `data` 中引入 `eventChoiceSchemaVersion: 1` 和 `choices`。每一项是一个可选择的规则分支及其卡面按钮，不再需要 `optionIndex`、`buttonCount` 或独立的布局到奖励映射表。

以下是拟议格式的定义示例，配套图片和 Lua 文件需由真实包提供：

```json
{
  "definitionId": "demo.events.ruins",
  "contentType": "event",
  "version": "1.0.0",
  "displayName": "荒原遗迹",
  "expansionId": "demo.events.standard",
  "replaces": null,
  "enabled": true,
  "applicableModes": ["standard"],
  "requiredCapabilities": ["event.choices.v1", "event.artwork_buttons.v1"],
  "artwork": "artwork/ruins.png",
  "tags": [],
  "playerMarkerZones": [],
  "abilities": [],
  "data": {
    "eventChoiceSchemaVersion": 1,
    "description": "队伍在荒原上发现了一处遗迹。",
    "color": 0,
    "resourceType": 0,
    "resourceAmount": 1,
    "representativeResourceType": 0,
    "representativeResourceAmount": 1,
    "choices": [
      {
        "choiceId": "collect",
        "description": "采集源岩",
        "button": { "topPercent": 56, "bottomPercent": 68 },
        "script": "lua/events/ruins.collect.lua",
        "version": "1.0.0"
      },
      {
        "choiceId": "trade",
        "description": "联系商队",
        "button": { "topPercent": 73, "bottomPercent": 89 },
        "script": "lua/events/ruins.trade.lua",
        "version": "1.0.0"
      }
    ]
  }
}
```

| 字段 | 合同 |
| --- | --- |
| `choiceId` | 卡内唯一、非空的稳定 ID；建议小写英文、数字、下划线或短横线。改位置、文案和数组顺序不改变 ID |
| `description` | 本选项的内容文案，用于文字展示、无障碍名称和诊断；不用于识别规则分支 |
| `button` | 本按钮的卡面位置，不含奖励逻辑 |
| `script` | 所属包内的 Lua 相对路径，直接绑定此选项的效果入口 |
| `version` | 该入口的版本；规则合同改变时更新，实际源码另计算哈希 |
| `completionHandlerId` | 可选，引用本定义正式登记的完成处理器；缺省为空，不允许任意函数名调用 |

一个事件可以复用同一个脚本文件给多个选择，但它们仍有不同 `choiceId`。跨包复用脚本只通过明确的共享模块依赖实现，不用 `../` 指向其他包。按钮数量由 `choices` 长度确定，v1 暂定每牌最多 16 项，作为有明确诊断的资源限制；至少验证 1、2、3、4、6 项，不得继续在消费者中写死三项。

零选项事件保留显式表达：`choices: []`，并声明 `immediateResolve: { "script": "lua/events/ruins.immediate.lua", "version": "1.0.0" }`。零选项时必须声明该入口，无额外效果可返回空数组；有按钮时禁止同时声明 `immediateResolve`，避免两套奖励一起运行。

### 3.2 高度百分比

- 单张卡面顶部为 `0`，底部为 `100`；数值表示百分数，不是 0～1 比例。
- 点击区域为 `[topPercent, bottomPercent)`，要求有限数值且 `0 ≤ topPercent < bottomPercent ≤ 100`；接壤边界只属于一个按钮，避免双重命中。
- 百分比基于切片后的实际单张图像显示矩形，不基于整张图集、弹窗、屏幕或包含留白的外层容器。
- 横向范围、颜色、反馈、字体、模板组件继续由实际使用的场景或预制体决定。v1 不开放任意 UI 树、任意 Prefab 路径或脚本式布局。
- 同卡按钮区域不得重叠；加载时报告冲突的 `choiceId`，不通过自动移动或缩小掩盖配置错误。
- 缩放与宽高比变化后，按钮跟随实际卡面；不能再用固定 850×600 假定所有图片。
- 渲染顺序取自 `choices`，结算身份取自 `choiceId`。移动按钮或调整顺序不能改变其绑定 Lua。
- 替换事件使用最终生效定义的图像、按钮和脚本，不能按基础运行时槽位套回旧布局。

### 3.3 执行链与权限

执行顺序为：正式抽牌并形成事件请求 → 展示可见候选对应的按钮 → 玩家提交选择 ID → 正式命令链校验 → 从本局快照解析绑定脚本 → Lua 返回 Effect → 按正式效果树结算并保存续接状态。

候选身份由正式候选 ID 工厂根据事件身份和 `choiceId` 生成，不能简单拼接未校验的用户字符串。命令继续携带当前请求身份、修订和候选集版本；服务端/各确定性副本校验玩家权限、候选成员和内容身份。客户端不得提交脚本路径、源码或自选奖励作为命令参数。

奖励脚本沿用 `return function(ctx) ... end` 和 Effect 数组返回合同。新增 `ctx.payload.choiceId`，其值来自已确认选择；卡牌、实际实例、目标位置及玩家字段来自受校验的正式事件上下文。新脚本不再通过数字 `optionIndex` 查奖励表。实例字段仅在该入口确实提供时可用，不能用定义 ID 冒充实例 ID。

公共事件流程与选项奖励分别归属：抽牌、资源点建立、公开事件和基础影响力处理属于事件流程；按钮 Lua 负责该选项的收益、支付与后续选择。旧脚本内重复的基础影响力处理迁入共同事件结算步骤时，必须逐项保持原有顺序、可见性和恰好一次语义，不能因拆脚本而重复放置或提前授予收益。

旧 `ChoicePendingEffects` 驱动的影响力预选必须一起迁移。需要玩家选择时，由奖励 Lua 或已有专门流程生成合法请求；移动、支付、放置等操作继续使用当前 API 合同。不得仅移除旧数组，却遗留依赖旧数组的候选预计算。

只有选中的 Lua 会被执行；未选脚本可以在加载时做语法检查，但不能预执行来估算奖励。支付后给收益必须使用现行支付条件组合。重复点击、网络重发及恢复都不能重复生成奖励子树。

### 3.4 旧内容与旧存档

所有正式事件迁入新合同，包括企业替换事件。迁移清单逐项记录旧规则下标、旧卡面顺序、新 `choiceId`、脚本和按钮区域。现有“险中净土”“采集平台残骸”前两项顺序修正也迁入真实条目，不保留按卡牌 ID 的特判。

新合同拒绝混写 `choiceDescriptions`、`choiceRewards`、`choicePendingEffects` 和整卡 `data.effectScript`，以免产生两个奖励来源。旧格式只允许由单独的迁移工具读取并生成待审查的新包，不在正式运行时自动猜测转换；旧安装版和原内容保留用于旧存档。

事件执行器、候选身份、序列化、恢复校验及内容能力版本需一起升级。未完成的旧事件节点不能自动把数字下标映射到新顺序。恢复要求原执行版本与精确内容匹配，不匹配时说明原因并保留原件。

## 4. DIY 包文件结构和身份

用户数据根以目标构建真实身份和 Windows 已知文件夹解析结果为准。当前项目配置下的预期位置为 `AppData/LocalLow/zhuanshiluobo/NoMadCity`；安装器依据目标构建 `app.info` 核对，不能写死用户名、盘符或只读项目 YAML。旧中文目录迁移由统一数据路径策略处理，不让两个 Mods 根同时被隐式扫描。

```text
<游戏用户数据根>/
  MatchSaves/
  ModProfiles/
  ModInstallReceipts/
  ModStaging/
  Mods/
    demo.events/
      1.0.0/
        pack.json
        event/ruins.json
        recipes/demo.events.standard.json
        lua/events/ruins.collect.lua
        lua/events/ruins.trade.lua
        artwork/ruins.png
        README.md
```

ZIP 根直接包含 `pack.json` 及其相对文件树，不要求作者外包一层同名文件夹。安装工具根据验证后的 `packId/version` 放置目录。手动安装遵循相同布局。

- `packId`：物理包身份，升级时不变。
- `version`：包发布版本，v1 使用三段非负整数版本；同包不同版本可以并存，本局依赖闭包只解析一个版本，房间不提供版本选择器。
- `modeId`：模式身份；包可以声明多个模式，每局至少启用一个模式，也可同时启用不冲突的多个模式。配置中的 `RuleModeId` 是基础模式，`AdditionalRuleModeIds` 记录其余启用模式；各模式使用相同注册合同。
- `expansionId`：玩家启用的规则内容分组，与物理包身份分开；包可声明多个扩展，定义必须属于本包声明的扩展。模式自带的内容可以放在其必需扩展中，在扩展区域显示为已启用且不可取消。
- `definitionId`：内容定义身份；DIY 新定义、处理器、配方与文案键使用包命名空间，不抢占官方身份。
- `contentHash`：按实际文件计算的内容身份，不能信任作者自行填的哈希冒充验证结果。

作者改动同版本文件会形成不同内容哈希。发布时应提升版本；联机仍以真实哈希判断一致性。

模式、扩展均记录来源包和发布版本。同一包的多个版本通过本地 `ModProfiles` 的版本绑定生成可用目录，不将每个版本重复列为房间选项。首次安装的唯一可用版本可建立默认绑定；升级并存不自动改变绑定。版本切换属于房间外的本地内容配置，房间和存档的精确锁定清单优先。不同包声明同一模式或扩展 ID 属于冲突，不能按扫描顺序覆盖。

## 5. DIY 清单目标格式

DIY 使用独立封装 `format: "nomadcity.diy"`、`schemaVersion: 1`。它与现有核心包 schema 3 是两个明确分支，不能把一个缩减的 DIY 清单伪装成完整核心包。核心包仍由现有读取适配器接入共同目录。

```json
{
  "format": "nomadcity.diy",
  "schemaVersion": 1,
  "packId": "demo.events",
  "version": "1.0.0",
  "displayName": "荒原事件包",
  "author": "示例作者",
  "description": "为标准模式添加事件牌。",
  "contentApiVersion": 1,
  "requiredCapabilities": [
    "diy.pack.v1",
    "event.choices.v1",
    "event.artwork_buttons.v1"
  ],
  "dependencies": [
    { "packId": "core", "versionRange": ">=2.1.50 <3.0.0" }
  ],
  "expansions": [
    {
      "expansionId": "demo.events.standard",
      "displayName": "荒原事件",
      "description": "为基础模式添加荒原遗迹事件。",
      "applicableModes": ["standard"],
      "requires": ["core"],
      "conflicts": []
    }
  ],
  "definitions": ["event/ruins.json"],
  "setupRecipes": ["recipes/demo.events.standard.json"]
}
```

示例的版本范围只演示语法，不能代替测试结果。即使核心包版本满足，宿主未实现 `event.choices.v1` 等能力仍拒绝启用。包版本、封装格式、宿主内容 API、所需能力和内容哈希分别检查，不把安装包 R 编号当作唯一合同。

v1 的 `versionRange` 仅接受 `=x.y.z` 或示例这种 `>=x.y.z <a.b.c` 半开区间；不猜测通配符、预发布版本和其他范围语法。当前核心包须发布相应能力后才可满足新格式。

基础字段之外，表现文案、图标、切片和冻结 Lua 模块沿用既有合同，按所属包读取；确有需要时声明 `presentation`、`artworkSlices`、`luaModules`、`scriptDependencies`。实现必须同步完善 Schema，未知字段报定位明确的错误。不得因现有 Schema 未覆盖运行时字段而放弃正式校验。

### 5.1 模式和扩展的职责

| 对象 | 声明与作用 | 房间中的表现 |
| --- | --- | --- |
| 包 | 提供模式、扩展及其定义、Lua 和资源；声明包级依赖与兼容要求 | 不作为玩法选择项，来源和版本可用于详情与错误诊断 |
| 模式 | 定义一局的玩法组合：现有机制与参数、开局配方、必需扩展、适用地图及正式 Lua 规则入口 | 可多选；模式互斥或准备阶段序号相同时不能组合 |
| 扩展 | 在适用模式中增加或替换内容，也可通过已支持的规则入口提供附加规则；声明依赖与冲突 | 多选；任一启用模式的必需项显示为锁定启用，不兼容项说明原因 |

模式使用统一目录注册，不要求为每个 DIY 模式增加 C# 分支。基础模式与企业家模式也通过适配进入该目录；企业家专属能力和配方只由其声明要求，不附加给所有非基础模式。

模式优先引用现有机制、配方和规则内容。参数不能表达的差异，使用既有能力声明、规则查询、事件订阅、效果与完成续接合同绑定 Lua，沿正式执行链运行。阶段 B 必须梳理这些入口的注册与调用来源，将可复用部分从固定模式 ID 判断中分离；模式生效、退出和恢复时统一装配与撤销绑定。Lua 效果入口、只读查询入口及完成入口分别遵守各自合同，不能一律当作返回 Effect 的函数。

Lua API 提供规则表达能力，模式定义还需声明脚本何时、以何种正式上下文调用。实施时按实际入口固定字段、执行顺序和恢复身份，不把仅存在一个 Lua 文件当作已经挂接模式规则。确需尚无宿主入口或 API 的机制时，单独补充对应能力；普通 DIY 模式的组合与脚本实现属于本次范围。

### 5.2 模式登记示例

清单新增 `ruleModes`，沿用现有模式声明中的 `modeId`、`requires`、`requiredCapabilities`，补充展示与配方引用。以下包只提供一个复用基础开局配方的模式，用于验证“没有自有卡牌也能注册模式”；进一步的玩法差异通过上述机制配置和 Lua 绑定声明补充，不由名称推断。

```json
{
  "format": "nomadcity.diy",
  "schemaVersion": 1,
  "packId": "demo.modes",
  "version": "1.0.0",
  "displayName": "荒原模式包",
  "author": "示例作者",
  "description": "演示复用现有玩法的独立模式登记。",
  "contentApiVersion": 1,
  "requiredCapabilities": ["diy.pack.v1", "diy.rule_modes.v1"],
  "dependencies": [
    { "packId": "core", "versionRange": ">=2.1.50 <3.0.0" }
  ],
  "ruleModes": [
    {
      "modeId": "demo.modes.expedition",
      "displayName": "荒原探索",
      "description": "复用基础玩法和开局内容的示例模式。",
      "requires": ["core"],
      "requiredCapabilities": [],
      "applicableMapIds": ["map-three-players", "map-four-players"],
      "setupRecipeRefs": [
        { "packId": "core", "recipeId": "standard" }
      ]
    }
  ],
  "expansions": [],
  "definitions": [],
  "setupRecipes": []
}
```

`dependencies` 的 `packId` 指包依赖，模式和扩展的 `requires` 指扩展依赖；两者即使都写 `core`，也不得混成同一个身份。`setupRecipeRefs` 明确配方来源包，来源须在依赖闭包中。没有新配方时可引用现有配方，有新组合时由本包声明并引用；不通过修改 core 落地新模式。宿主适配须先将共享基础配方开放给满足机制要求的模式，引用不能绕过配方适用性校验。

清单可以只含 `ruleModes`、只含 `expansions`，或同时提供两者；未提供的一类按空列表处理。至少提供一个模式或扩展，不要求每个包必须自带卡牌定义。扩展的贡献可为内容、配方或规则绑定，不通过“必须找到一张自有卡牌”判断扩展有效性。

扩展、定义和追加配方的 `applicableModes` 都按统一目录校验。未声明或空列表沿用现有“不限制模式”的语义，仍须满足其他机制与依赖约束；非空列表只适用所列模式。未知模式不是合法通配符，其来源包必须在依赖闭包中。官方内容迁入时逐项确认适用范围，不能因开放新模式而无意改变原组合。

第一期接入模式与扩展，以新增事件、事件替换、现有机制组合和 Lua 规则差异作为验收样例。新地图、任意 C# DLL、任意执行器注册和自定义 UI 页面另立范围；既有内容类型复用现有合同，未验证类型不宣称已完成验收。

### 5.3 准备阶段：固定节点与三段模式流程

2026-11-14 用户确认的方向：以“分发企业候选”和“确认企业”为两个固定节点，每个模式可通过 JSON 或 Lua 定义分发前、两节点之间、确认后三段流程。中间流程为空时，分发完成后直接显示确认企业 UI；中间流程中的所有卡牌选择页面都带有查看本人已分发企业板的入口，行为参照现有企业家选择页。

```text
分发前模式流程（可空）
  → 分发企业候选并保存分发结果
  → 中间模式流程（可空；所有卡牌选择页可查看本人企业板）
  → 确认企业 UI 与正式结果提交
  → 企业公开及必要初始化
  → 确认后模式流程（可空）
  → 继续原有入场流程
```

固定节点由共同准备流程负责，模式配置三段流程的内容与执行顺序。中间为空只省略中间步骤，不省略企业确认，不把分发到手的全部候选自动当作最终选中企业。是否启用企业准备框架由模式的机制配置确定；不启用企业的基础玩法不出现空的企业确认页。

| 部分 | 输入、完成条件与后续 |
| --- | --- |
| 分发前流程 | 运行模式声明的准备步骤；此时没有本次分发结果，不能展示尚未分发的候选 |
| 分发节点 | 按本局已确定的名单、候选池与数量规则分发，生成真实实例的分发记录；完成后才进入中间流程 |
| 中间流程 | 可引用本人已分发的企业候选进行选牌等操作；全部必要步骤及其子效果完成后进入企业确认 |
| 确认节点 | 使用同一批已分发候选，按本局规则校验选择；收齐必要答案后确定最终名单和初始归属 |
| 必要初始化 | 公开最终企业，处理未选牌、合作标记、科室、关联组件、必要洗牌和初始升级；保持既有合法顺序 |
| 确认后流程 | 本方案将入口放在上述必要初始化完成后，使用最终企业结果；全部子流程完成后继续入场 |

三个窗口各有一份有序步骤列表，空列表立即完成。JSON 用于声明步骤顺序、已注册处理器和参数；Lua 用于表达步骤中的条件、选择和效果。两种入口都接入现有效果树和正式交互请求，子选择及完成续接结束后才推进下一步。数据字段名、处理器参数和版本在实施计划 F0 中统一固定，不把本节描述当作已经可用的新 API。

启用模式可各自声明三段准备流程和非负整数 `preparationOrder`。同一窗口内按模式序号从小到大依次执行，每个模式内部仍按其步骤数组顺序执行；企业分发、确认和必要初始化保持固定位置。两个已启用模式的序号相同，或者任一模式声明与另一模式 `conflicts`，均不能同时启用。没有准备步骤且没有显式序号的模式不占序号；旧包有准备步骤或继承企业家准备步骤但未声明序号时按 0 处理。多个模式共用企业家机制时，其官方准备步骤只提供一次。模式可显式引用其依赖包提供的步骤，扩展仍不按扫描顺序隐式插入准备步骤。多模式声明的企业分发或城市样式配置不一致时拒绝组合；共同分发输出目标冲突也必须拒绝。同一准备过程不得同时运行旧企业家专用分支和新框架步骤。

企业扩使用空的中间流程，分发后直接进入确认企业页。企业家模式把现有预览、按既有顺序选择企业家及其必要准备子流程登记为中间步骤，共用外层分发记录，完成后回到共同的企业确认节点。其他 DIY 模式可以使用不同的选牌步骤，也可以只设置前置或后置流程。

#### 中间流程的统一企业板预览

- 预览属于框架提供的选择页能力。中间流程及其嵌套子效果产生的每个卡牌选择页，都自动带上企业板查看入口；无需各个 Lua 脚本重复声明按钮。
- 预览读取该请求作答玩家有权查看的正式分发记录，展示真实候选实例及对应企业板详情。把记录从企业家专属状态中分离，供企业家和 DIY 共用；不读取其他玩家的私密候选，也不从实例 ID 猜测定义。
- 查看、关闭和返回属于只读浏览，保留当前已选卡牌、滚动位置与待答请求；不提交答案、不重新分发、不重跑当前 Lua 步骤。
- 公布最终企业前，“本人已分发候选”与“本局最终企业”分别表达。进入确认后流程时，使用已确认结果，不能把未选候选继续当作可用企业。
- 单项、多项、JSON 步骤、Lua 步骤和嵌套卡牌选择使用相同规则；普通非卡牌选择页不因此强制增加按钮。新增模式的卡牌页须接入共同展示能力，不能只按企业家交互类型识别。
- 复用现有企业板详情页和实际选择页模板。静态文案、样式与布局继续来自场景、预制体或现有文案配置，测试与运行不重建或覆盖资产。

#### 分发规则、数量与保存恢复

企业和城市样式的固定名单、必选名单加随机补足、数量及按人数变化属于准备数据配置；三段模式流程负责组织操作。保留上一轮讨论的这些需求，实施时同时校验候选池、分发数量、保留数量、固定企业的初始归属和重复项。企业最终数量按本局配置校验，官方企业扩仍通过自己的配置保持四家规则。城市样式按指定名单及各等级规则确定供给，不在进入后置流程后再套一遍原随机抽取。

分发结果一旦形成，预览、选择与企业确认复用同一记录。普通中间步骤不隐式重分发；如玩法确需换候选，应另行定义明确的正式操作及候选版本变化。前置流程若要根据选择结果影响本次分发，应通过经校验的步骤输出交给分发节点，在分发前确定规则，不直接改运行中已冻结的全局配方。

准备流程与模式身份、步骤 ID、处理器版本/脚本哈希、执行顺序、作答对象和分发规则一起纳入本局内容身份。运行状态保存当前窗口、步骤进度、真实分发记录、待答请求和确认结果；读档或重连继续原步骤，不重复随机、授予收益或初始化企业。多人独立步骤在框架要求的完成边界汇合，企业家共享候选的顺序选择继续按原规则执行。

详细实施任务与验证范围见[准备阶段框架实施计划](../../prompt/DIY接入实施计划-20261101/18-准备阶段框架实施计划-20261114.md)。

## 6. 新增、替换与开局配方

模式通过 `setupRecipeRefs` 确定基础开局配方与机制组合，再按实际启用扩展合并追加项。保留现有基础与企业家开局行为，将硬编码配方选择迁入对应模式/扩展声明，不能继续让所有模式固定从 `standard` 并按指定 ID 拼接。相同配方身份只装配一次；参数冲突须明确报错，不按加载先后覆盖。

新增事件必须同时登记定义和入堆规则。DIY 追加配方采用独立格式，转为现有 `GameSetupRecipe` 的追加项，不允许悄悄覆盖所选模式的基础配方字段：

```json
{
  "schemaVersion": 1,
  "recipeId": "demo.events.standard",
  "expansionId": "demo.events.standard",
  "applicableModes": ["standard"],
  "entries": [
    {
      "entryId": "demo.events.ruins.main",
      "definitionId": "demo.events.ruins",
      "quantity": 1,
      "initialZoneRole": "event_green",
      "applicableMapIds": ["map-three-players", "map-four-players"]
    }
  ]
}
```

数量是牌堆实例数量；地图、模式、扩展、颜色与目标牌堆必须一致。通过实际地图 ID 判断适用范围，不拿玩家人数代替地图。现有四人图专用事件的固定 ID 筛选，应迁成基础配方的等价地图限制，再应用 DIY 追加项。不得因牌进入目录就默认加入所有牌堆。

替换继续使用顶层 `replaces: { expansionId, contentType, definitionId }`。目标包须声明依赖，目标扩展须同时启用，类型须相同。替换者有自己的 ID，基础运行时槽位保留；原配方引用沿替换链解析到最终定义。默认不额外追加被替换牌的份数，否则会重复入堆；v1 拒绝对替换事件再声明独立追加项。

同一目标被两个启用定义替换时失败；循环、自替换、缺失或未启用目标均失败，不按磁盘遍历顺序覆盖。链式替换在完整选择集合中一次解析。两个同名牌不自动视为替换。

当前企业扩展必须替换两个事件的检查作为官方内容完整性约束保留并明确归属，不能阻挡其他合法新增事件。对全量目录数量的固定判断须改成基础内容完整性与新增内容合法性的分别校验，不能简单删除所有规则校验。

## 7. 读取、装配与冻结

### 7.1 已安装目录

仅扫描既定 `Mods/<packId>/<version>/pack.json` 层级，不递归搜索整盘。发现阶段读取元信息并列出状态；坏包、缺依赖和不兼容包有独立诊断，未选包不得拖垮基础模式。运行时不执行安装包、外部程序或 Lua 顶层逻辑来发现内容。

每个资源以“来源包身份＋包内路径”寻址，同名 `lua/main.lua` 或 `artwork/card.png` 可以在不同包中共存。缓存、切片、文案、脚本续接及诊断都必须保留来源，不能仅按相对路径合并字典。

### 7.2 本局装配

1. 从房间启用的模式集合和勾选的扩展推导必需扩展及包依赖闭包，按本地版本绑定或既有房间锁定清单解析具体版本；依赖、冲突和能力不满足时停止该组合。无需房主另选包。
2. 读取所选包声明的定义、配方、Lua、文案和资源，形成不可变的原始快照。
3. 做包内字段和路径校验，再汇总跨包身份、引用及依赖。跨包替换不能在只读到一个包时判定目标缺失。
4. 按模式和扩展筛选，解析替换链，装配模式配方、扩展追加项和正式 Lua 规则绑定。
5. 冻结脚本及明确依赖的共享模块，加载文本、图像等所需资源，构建统一活动目录。
6. 计算活动内容指纹，将同一份活动目录交给规则、UI、房间、联机和存档消费者。

依赖按拓扑排序，同级包按稳定 ID 排序；包内有意义的数组顺序保留。不能让文件系统遍历顺序决定牌堆构成、替换结果或哈希。新组合构建失败时保留旧快照，不出现半更新的目录；玩家仍可回到菜单修改选择。

现有 Bootstrap、全局 `ExternalContentPack.Current`、目录单例和贴图缓存必须纳入生命周期收敛。房间切换配置、离局或加载新局时只在安全边界替换，不能令另一局继续引用已释放资源。首次可规定修改文件后重启程序；支持菜单刷新时，仍须保证不影响进行中的房间或对局。

### 7.3 文件与执行边界

路径限包内相对路径，拒绝绝对路径、`..`、盘符、目录联接和符号链接越界、重复规范化路径及大小写碰撞。ZIP 提取执行相同规则，限制条目数、单文件/解压总大小、图片解码尺寸和脚本预算；具体上限在实施时作为统一宿主配置与作者文档公布。

Lua 保持现有沙箱和预算，不提供 IO、网络、Unity、CLR 或自由 `require`。公共函数通过正式冻结模块合同接入，不能扩大脚本权限以解决包间寻址。

## 8. 联机、存档与诊断

安装目录的完整清单与本局内容身份分开。未启用且不被依赖的额外 DIY，不得改变本局指纹或阻止联机。活动指纹涵盖所选依赖版本、相关定义、配方、选项与脚本绑定、原始及装配脚本、切片、图片、按钮布局和文案等实际使用内容。v1 采用严格一致，不承诺仅布局不同也能联机。

房间发布锁定清单：模式 ID、包 ID、版本、实际哈希、启用扩展及规则合同；各玩家本地装配并核对，精确锁定优先于客端本地默认版本。第一期自行安装相同包，不实现自动下载。切换模式、增减扩展或重新建立不同内容身份的房间配置时，使原准备状态失效，所有玩家核对新清单后重新准备。包版本通过锁定清单核对，不在房间提供版本选择控件。

存档记录相同锁定清单及稳定选择 ID、实际处理器版本和已提交续接状态。恢复必须找到精确匹配内容，不自动选最新版本、不按数字位置猜选择、不重复执行已经挂接的奖励子树。保留旧包不意味着新宿主一定能恢复旧执行合同，缺少支持时仍明确拒绝并保留存档。

错误至少包含阶段、包 ID/版本、文件相对路径、JSON 字段或 Lua 入口、错误原因。区分缺包、版本不兼容、内容被修改、重复 ID、替换冲突、缺资源、脚本错误、按钮越界、配方错误及执行预算超限。被选包失败不能静默跳过后开一个不同规则的对局。

## 9. 安装和独立补装

| 安装器模式 | 行为 |
| --- | --- |
| 安装或更新游戏 | 保持游戏安装位置选择，另列可勾选的开发者协助制作 DIY 包，显示名称、版本、简介和兼容范围 |
| 仅安装 DIY 内容 | 识别已安装游戏的真实身份与内容能力，仅写入当前用户 Mods 和安装回执；不重装游戏、不改快捷方式或卸载注册信息 |
| 导出 DIY 内容包 | 将内置的原始 ZIP 输出到用户选择的目录；允许未安装游戏，不宣称已经可以启用 |

安装器不依赖游戏先运行才能创建数据目录；游戏与安装器共用数据路径合同。仅补装时无法确认目标版本或数据路径，应要求选择游戏目录或使用导出模式，不能随意落到另一个用户/产品的数据根。

独立 ZIP 与安装器内置 ZIP 来自同一份经过校验的发布产物，记录文件清单与哈希。更新 DIY 可单独分发 ZIP，随后再收录进完整安装包。第一期手动放置和安装器提取必须产生相同包身份。

写入流程：进入 Mods 之外的同卷暂存目录 → 校验归档和文件 → 检查已存在版本 → 完整发布到正式目录 → 记录安装回执。只在全部成功后显示安装成功，失败不改变已安装版本；共享同包安装须串行，发现阶段忽略暂存内容。

| 已有内容 | 处理规则 |
| --- | --- |
| 同包同版本同哈希 | 跳过并说明已安装 |
| 同包同版本不同哈希 | 标记本地修改或发布冲突，默认保留；修复需明确确认并先完整备份 |
| 已有旧版，安装新版 | 并存，保留当前本地版本绑定；玩家可在房间外调整内容配置，旧存档仍锁定旧版 |
| 已有新版，运行旧安装包补装旧版 | 明示版本情况，仅并存，不替换当前选择或自动降级 |

安装中不触发运行中的对局重载。卸载游戏默认保留用户数据；若用户选择删除应用数据，界面必须明确包含存档、DIY、作者修改和备份的范围。若提供单独移除开发者附带包，只能依据安装回执删除该包版本，修改过的文件须保留或另行确认，不能把整个 Mods 当作安装器私有目录。

## 10. 分阶段交付与验收

第一阶段只改事件合同和既有事件：选择条目直接绑定 Lua、JSON 百分比按钮、完整内容迁移、稳定候选与存档/联机版本处理。在第一阶段通过前，不依靠修改正式包、临时下注入状态来提前宣称独立 DIY 已可用。

第二阶段接入独立包：建立读取、校验、统一模式/扩展目录、配方与 Lua 绑定装配，将 DIY 模式和扩展接入房间已有两类选择，再制作安装、补装和导出流程。样例覆盖纯模式包、纯扩展包和同时提供两者的包，验证现有机制组合、Lua 规则差异及事件新增/替换；完成安装到正式对局的完整链路。

验证分为格式/规则隔离检查、运行包检查和正常玩家流程。界面与功能验收须从可见独立程序的菜单、建房、开局与合法行动进入，随机未抽到的事件记为未覆盖，通过正常多局累积。记录程序版本/内容哈希、GameId、选择 ID、图片与按钮对应证据、结算结果和恢复证据。隔离测试不能代替正常 UI 或真实 Steam 联机验收。

设计形成时只交付设计与实施计划；现行实现和验收结果以[实施进展](../../prompt/DIY接入实施计划-20261101/05-DIY接入进展-20261111.md)为准，详细任务和依赖见[实施计划](../../prompt/DIY接入实施计划-20261101/00-实施总计划.md)。
