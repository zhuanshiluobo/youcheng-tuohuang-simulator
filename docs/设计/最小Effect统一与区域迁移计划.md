## 2. 洗混干员牌堆目前在哪里

[API初稿](Lua效果系统API初稿.md)本轮修改前的1.1/1.4列“洗混设施牌堆”，3.6原先规划`Effect.ShuffleFacilityDeck`；1.3的“洗混牌堆”是**结算与表现目录**，不是已经公开的非卡面规则Effect。2.7的DeckDefinition描述容器及洗混策略，也不是执行器。未核实到独立、已公开的“洗混干员牌堆”构造器。本轮已将规划目录同步为通用ShuffleDeck，代码不变。

当前[宿主公开构造器](../../Assets/YC/Infrastructure/Lua/MoonSharpLuaRuntimeHost.cs)未安装ShuffleFacilityDeck或通用ShuffleDeck。存在规划typeId及内部洗牌调用，不表示Lua已经能调用它。特派规格要求未选干员洗回，但这目前是后续组合能力要求，不能拿表现表中的名字充当已完成实现。

建议将洗混定义为一个**牌种无关的卡面最小Effect**。卡面能力、特派、准备阶段和系统流程都能调用同一可信洗混合同。归入“卡面最小”不限制调用来源；执行权始终属于Host。

## 3. 合并到什么程度

**统一物品转移与洗混底层，保留业务语义链和必要的类型过滤。**不是把所有“动一下东西”的操作合成一个万能Effect。

| 原目录项 | 目标 | 必须保留的边界 |
| --- | --- | --- |
| 洗混设施牌堆、未来洗混干员/事件牌堆 | 通用`ShuffleDeck`，目标是已许可的有序卡牌区 | 不抽牌、不从别区收集卡、不补供应，不暴露隐藏牌序 |
| 移动设施牌、移动角色牌 | 共享`MoveItem`的转移提交与区域校验；可保留类型化构造别名，或以新`MoveCard`入口限定Card | 设施/角色各自来源、去向、生命周期与权限；旧设施移牌自动补牌语义不能悄悄消失 |
| 操作玩家标记 | 共享Cube区域转移；PlayerMarker是其中受限子域 | 不把帮派改为玩家标记；多萝西区可收Cube，诗怀雅仍限定玩家标记 |
| 普通存放、回盒、牌堆底、牌下区、图纸 | 使用已许可的转移操作模式和插入位置 | “放入城市”不等于Build，“放入盖牌区”不等于完成盖放流程 |
| 放置/移除/移动/替换影响力 | 复用内部转移内核，保留四类注册语义操作与Event | MoveInfluence不触发离场收留；Replace保留Removed/Placed/Replaced及removed_only合同 |
| 移动城市、嘉维尔token移动 | 共享拓扑查询/目标选择/位置提交技术；各自注册移动域 | 嘉维尔不继承城市停靠占位、费用、清除、留影响力或CityMoveCompleted |
| 角色盖放/使用、建设/探索/特派、资源交易 | 保留固有效果链，内部组合最小提交与选择 | 收费、奖励、实例去向、响应和最终等待不能压缩成一次裸转移 |
| UI洗牌/移牌表现 | 消费提交结果的表现能力 | 没有权威状态修改，也不能凭动画结束判定规则完成 |

`MoveItem`、`MoveCard`、`ShuffleDeck`等是**本轮建议名称**，尚无已实现的effectTypeId。建议正式规范选定一个通用转移typeId，类型别名只加过滤，不各自建立一套独立转移状态或服务。

### 3.1 现有两个移牌API不能直接改名合并

[ContentPrimitiveEffectExecutor](../../Assets/YC/Domain/Effects/ContentPrimitiveEffectExecutor.cs)当前真实范围：

- MoveFacilityCard只支持供应→设施牌堆底，包含选择，并调用ReturnSupplyCardToDeck处理补牌。
- MoveCharacterCard只支持本人全部弃牌→手牌，排除当前盖牌，返回实际回收数量。

它们尚不是任意源区/目标区移动。未来统一时先提取共同转移合同，再让现有Lua参数按版本适配；德克萨斯仍需移牌后补槽，锡人仍按回收数量生成奖励。保留同名函数可以降低内容迁移成本，但不能把旧节点静默解释成新的“只移动不补牌”。

建议新内容显式写“选/移动/补槽”，旧内容迁移后升版本及有效内容指纹。旧存档按已有版本校验恢复或明确拒绝；不要长期维持两份可写卡区，也不要在新执行器失败时fallback到旧服务。

## 4. 通用最小Effect合同草案

以下合同待实现；Lua只返回Spec，Host按已有Event、Candidate、Interaction、RuleCommit和完成响应窗口执行。

### 4.1 MoveItem：简单转移

| 输入/输出 | 合同 |
| --- | --- |
| `itemRefs`或选择范围 | 明确实例，或由Host生成当前域内候选；最终提交必须确定真实实例ID |
| `expectedSource` | 预期源ZoneRef及必要槽位，防止选择后被别的响应转移还继续拿旧目标 |
| `destination`、`insertion` | 目标ZoneRef；无序、牌堆顶/底、固定槽、层叠上/下等模式必须由目标模板支持 |
| `operationProfileId` | 已注册简单转移域；Lua不能自造权限、语义事件或调用任意C#方法 |
| `quantityPolicy` | 默认本次确定集合完整提交；尽量执行用上层逐项链明确表达，不凭空补不足数量 |
| `requiredCount`（按业务需要） | 支付/条件左项需要的真实数量，由来源操作合同设置并复验，不用空集合成功替代实际支付 |
| `carrierPolicy` | 仅选已登记载体随行/清空策略，不任意删除卡上/牌下内容 |
| 结果 | 实际移动实例、前后位置、原顺序/新顺序必要信息、是否有变化、提交ID；批量回收可派生实际数量 |

提交前对整组去重并复验源区成员、身份、许可、容量及有序结构。失败不移任何一件；合法空集合完成无变化，不能用它冒充已完成条件要求的数量。费用、卡上需要实际消耗的2/3枚、实例已离场等须由其条件/操作合同判断真实完成量。

Condition仍沿用已有“左子节点成功才建右侧”合同，不增加隐式数量推断。需要支付2枚的左项使用注册支付操作或带requiredCount的转移合同；不足时该左项Failed且无支付，不能返回Completed(no_change)让Condition误判成立。普通无候选操作的成功无效果规则保持独立。

最小提交使用内部`RelocateItems`或同等机制；公开MoveItem不能对地图影响力/城市/建成设施等受保护区域任意操作。存在不可拆业务语义时，要求走对应注册业务Effect，由其调用内部提交。

### 4.2 ShuffleDeck：只洗当前目标区序列

| 输入/输出 | 合同 |
| --- | --- |
| `deckZone` | 已存在且具洗混许可的有序Card区域；不能传根区、结构子树或任意Cube区 |
| 候选限制 | 不需要玩家选牌；必要牌种限制从区域定义与操作域确定 |
| 随机结果 | Host对本区实际全部卡实例产生排列；记录输入集合及最终序列，不能仅存一个可能跨版本变化的随机种子 |
| 不变事实 | 实例数量、所有者和所在区域不变；只改变顺序，不移动其他区域卡牌 |
| 空区/单牌 | 成功无变化，不报错、不虚构随机步骤；结果说明未改顺序 |
| 事件与恢复 | 一次洗混提交及收据，已提交节点恢复沿用牌序；公开投影仅给允许的信息 |

洗混选定集合“形成牌堆”拆为`MoveItem(指定集合→目标牌堆)`后`ShuffleDeck(目标牌堆)`。是否移回后补供应、是否应洗整个牌堆，属于调用者上层链。混合角色牌堆必须由区域的acceptedTypeIds许可，不因通用洗混而把基础角色和干员池自动混在一起。

### 4.3 其他底座操作

抽牌可共享“牌堆顶N个→候选/手牌”的转移提交，但抽取数量、展示、私密选择及剩余牌去向保留在抽牌/特派流程。旋转/翻面可共用受限状态更新内核，保留各自业务入口；区域位置不负责伪造这些状态。

设施供应补牌应是显式维护流程，只对规定空槽或揭露条件执行。交换图纸与供应牌可以使用受保护的同时转移组，不以两次可见的普通移牌暴露“移出成功、换入失败”中间状态；交换不等于Condition一般回滚，需单独固定交换合同。

立方体消耗不能全部改成map.RemoveInfluence。按所处区和操作域处理，普通玩家标记、帮派、公司分别返还合法供应；明确回盒才进游戏盒。角色结束后的弃置/回盒先执行实例生命周期，再调用转移提交。

## 5. 典型组合如何表达

以下是规格步骤，不是可直接粘贴运行的Lua。

| 场景 | 应组织的步骤 |
| --- | --- |
| 海德整批刷新 | 冻结设施供应全部层实例→全部移回设施牌堆→洗混同牌堆→按规定补6个供应槽；等待整批响应，不逐张洗 |
| 德克萨斯移牌堆底 | 选合法顶牌→移该实例到设施牌堆底→按已核定规则揭露/补原槽；不多洗一次 |
| 干员特派 | 从干员堆顶抽入候选区→私密选1或放弃→真实转入手牌并展示回盒自己角色，或给放弃分→未选卡移回干员牌堆→洗混；数量按企业/感染者规则 |
| 锡人回收 | 冻结本人弃牌实例，排除本次尚未弃置角色→完整移到手牌→以实际移动数建立奖励选择；不从手牌数差推断 |
| 多萝西收留帮派 | 真正移除G1地图影响力→暂存离场实例并组织去向→同一G1进多萝西Cube区；角色由影响力变为卡上存放标记，本质仍GangMarker |
| 多萝西收尾支付 | 在卡载区实际选/移出2个符合卡面消耗的Cube→完成真实支付后PlaceInfluence；不形成地图InfluenceRemoved以重复收留 |
| 保罗替换已有帮派且供应空 | 保存目标及实例→移除并完整结算非帮派响应→把同一帮派放回原位置→后续移动；不复制、不要求供应中另有帮派 |
| 马丁M1B/M5A | 明确选供应顶牌与图纸同色实例→分别插入所选顶牌下/上→后续移牌堆底及揭露/补槽按J-Q04核定合同 |
| 嘉维尔移动 | 从token当前资源点经注册相邻路径选点→移动Token并发布TokenMoved→根据到达点选择并移动其影响力；原所有者限制仍有效。token按用户裁定不会离场，保存同一实例，不因角色牌移动自动回收 |

准备阶段也调用同一模型：先建立四根和宿主容器，按启用扩展/模式配方创建有限实体，分配到公共池、玩家供应或盒内储备，再以设置子树选择企业/企业家、发牌、移动标记和入场。准备完成时每个本局实例都有合法位置；对局中没有创建第二份同卡来表示领取。

## 6. 从旧状态到新状态

| 现有状态/服务 | 目标事实源及应处理的差异 |
| --- | --- |
| `Player.InfluenceSupply`及计分标记布尔 | 实际PlayerMarker实例所在区域；供应计数与“已有分数轨道标记”变投影，不继续独立加减 |
| `Map.Influences` | 由合法地图影响力区中的物品形成查询视图；保留稳定身份、归属主体、来源及必要操作历史 |
| `DeclaredCityStyles.MarkerArea/RemainingSpecialActionUses` | 样式卡实例上的具体区域与标记位置为权威；I级2区、II级5区、一次性1区沿用既有用户方向 |
| 企业合作等级 | 企业板实例上的己方标记轨道；移动提交触发奖励，读取等级不再次发奖 |
| 手牌/弃牌ID列表及单盖牌字段 | CharacterCard实例所在区及盖牌槽；流形额外槽、持有者与原所有者分开 |
| 设施Deck/Supply/BuiltFacilityIds/Placement | FacilityCard实体＋唯一区域＋有序牌堆/供应层/城市层；建造得分、历史匹配与入场记录不能只靠位置推导 |
| 标记返还服务 | 按物品本质类型和离场操作域返回原合法供应，不能无条件普通InfluenceSupply++ |
| 内容`playerMarkerZones` | 迁到通用`zones`声明与宿主模板；旧字段转成只接受PlayerMarker的显式受限区域，不全局改成Cube |
| Lua查询及GameStateView | 同revision和同位置模型投影；隐藏区数量/身份/顺序分别过滤，直接成员与后代查询分开 |

旧存档需要版本方案。能够确定所有标记去向、颜色、类型和已使用轨道时可做一次迁移；不能确定实例守恒或历史奖励时明确不支持该版本，不能凭一个供应数补造标记。迁移过程也不得作为正式局中的放置/移除触发卡面奖励。

新快照生效后旧列表只能作为只读兼容投影。过渡期双向写入会形成两份权威位置，禁止以“暂时方便”长期保留。各字段删改前遵循NMC-015引用、序列化、测试覆盖及GUID核对要求；本轮不执行删除。

## 7. 建议实施顺序与边界

| 阶段 | 交付 | 进入下一步的条件 |
| --- | --- | --- |
| A 区域与类型合同 | 四根、Host模板、物理种类/子类/操作域、实例与顺序不变量、版本方案 | 能验证全部实体唯一归属，外部不能创建可装区域的区域或越过操作域 |
| B 查询和简单转移 | 只读区域门面、类型候选、MoveItem内核、Card别名及暂存区 | 所有源目标复验，原子组与逐项链分开；旧德克萨斯/锡人行为与版本差异有证据 |
| C 通用洗混与公共池 | ShuffleDeck、设施和干员同合同、明确抽取/洗回/补牌组合 | Host实际序列持久化，隐藏牌序不泄露，恢复不重洗 |
| D Cube与影响力 | 统一玩家/帮派/公司实例，卡载区、影响力角色、离场去向及事件去重 | 多萝西存帮派成立；MoveInfluence不触发收留，Replace保持原三个事件合同 |
| E 轨道与角色区域 | 样式位置资格、企业等级、持续/一次性角色、多盖牌与公开投影 | 撤下重复可写次数/等级，查询不发奖，离场清理不丢失区域内物品 |
| F 设施与移动复用 | 图纸、公共供应/城市两类层叠、载体退出策略、城市/token移动配置 | 马丁及嘉维尔各自语义不被通用接口覆盖；已有规则余项完成核定 |
| G 收口 | 各配置设置配方、内容迁移、旧路径清理与联机/恢复/视觉验收 | 完成覆盖矩阵后重新判断NMC-015，按范围交付基础/企业/感染者基础/企业家模式 |

区域框架先用基础内容验证，不以一次大改同时重写所有卡面。企业家模式不开启时不创建其有效能力及组件；配置、依赖、有效定义和指纹仍按[扩展总体规格](../../游城拓荒/可选扩展包实装改动清单.md)处理。
