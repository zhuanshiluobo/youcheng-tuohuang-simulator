# 通用抽卡流程模块接口说明

## 1. 目标

本模块把“按牌池抽一张事件牌、执行翻牌副作用、打开待选项、按选项结算奖励”抽成统一流程，供多个业务模块复用。

当前已经接入的场景：

- 探索事件
- 移动城市进入未开发资源点事件
- 入场事件

设计目标：

- 抽卡流程只保留一套状态结构和一套服务入口
- 各业务模块只实现自己的校验、翻牌副作用和选项结算
- 保留旧 `PendingChoiceState` 兼容出口，但新增 UI 与结算逻辑应优先使用 `PendingCardSessionState`
- 后续建设模块如需接入，只新增场景类，不再复制抽牌与待选逻辑

## 2. 核心组成

### 2.1 牌池服务

- `Assets/YC/Domain/Cards/CardPoolService.cs`
- `Assets/YC/Domain/Cards/ICardPoolService.cs`

```csharp
    string Peek(DeckRuntimeState decks, string poolId);
    int RemainingCount(DeckRuntimeState decks, string poolId);

```

### 2.2 抽卡流程服务

文件：

- `Assets/YC/Domain/Cards/CardFlowService.cs`

职责：

- 驱动完整抽卡流程
- 统一处理开始待选、即时结算、待选结算三种模式
- 统一写入 `PendingCardSessionState`
- 通过适配器同步旧 `PendingChoiceState`

核心接口：

```csharp
public sealed class CardFlowService
{
    public CardFlowStartResult StartPendingChoice(
        GameState state,
        CardFlowStartRequest request,
        IEventCardScenario scenario);

    public CardFlowResolveResult ExecuteImmediate(
        GameState state,
        CardFlowExecuteRequest request,
        IEventCardScenario scenario);

    public CardFlowResolveResult ResolvePendingChoice(
        GameState state,
        CardFlowResolveRequest request,
        IEventCardScenario scenario);
}
```

### 2.3 场景扩展接口

文件：

- `Assets/YC/Domain/Cards/IEventCardScenario.cs`

职责：

- 让具体业务只描述自己的规则差异
- 把公共流程与业务结算解耦

接口：

```csharp
public interface IEventCardScenario
{
    string ScenarioId { get; }
    string ChoiceType { get; }

    string ResolvePoolId(GameState state, CardFlowStartRequest request);

        EventCardDefinition previewCard);

    ValidationResult OnCardRevealed(
        GameState state,
        CardFlowContext context,
        EventCardDefinition card);

    ValidationResult ValidateOption(
        GameState state,
        CardFlowContext context,
        EventCardDefinition card,
        int optionIndex,
        IReadOnlyList<StringKeyValuePair> arguments);

    CardFlowApplyResult ApplyOption(
        GameState state,
        CardFlowContext context,
        EventCardDefinition card,
        int optionIndex,
        IReadOnlyList<StringKeyValuePair> arguments);
}
```

## 3. 状态模型

文件：

- `Assets/YC/Domain/State/GameState.cs`
- `Assets/YC/Domain/Cards/CardFlowStateAdapter.cs`

新增状态：

```csharp
public sealed class PendingCardSessionState
{
    public string SessionId;
    public string ScenarioId;
    public string ChoiceType;
    public string PoolId;
    public string CardId;
    public int PlayerId;
    public string TargetId;
    public List<string> OptionIds;
    public string SourceCommandId;
    public List<StringKeyValuePair> ContextData;
}
```

兼容策略：

- `CardFlowStateAdapter.OpenPendingSession()` 会同时写入 `PendingCardSessionState` 和旧 `PendingChoiceState`
- `GameState.HasPendingChoice()` 同时检查两种待选状态
- 表现层和三条事件结算链路通过 `CardFlowStateAdapter.GetPendingChoiceView()` 优先读取 `PendingCardSessionState`
- 旧 `PendingChoiceState` 只作为兼容 fallback，仍服务存量快照、旧 UI 或过渡期诊断

这样可以让新状态成为事件选择主事实源，同时保留旧待选状态的兼容出口。

## 5. 通用流程约定

### 5.1 `StartPendingChoice`

执行顺序：

1. 用 `scenario.ResolvePoolId()` 决定牌池
2. 用 `Peek()` 预览顶部牌做前置校验
3. 调用 `scenario.ValidateStart()`
4. 正式 `Draw()` 抽牌
5. 调用 `scenario.OnCardRevealed()` 执行翻牌副作用
6. 调用 `CardFlowStateAdapter.OpenPendingSession()` 写入待选状态

适合“先翻牌，后选择”的事件。

### 5.2 `ExecuteImmediate`

执行顺序：

1. 预览顶部牌
2. 校验开始条件和选项合法性
3. 正式抽牌
4. 执行翻牌副作用
5. 执行 `scenario.ApplyOption()`

适合“已经确定选项，直接一口气结算”的事件。

### 5.3 `ResolvePendingChoice`

执行顺序：

1. 读取 `PendingCardSessionState`
2. 校验 `ScenarioId`、`PlayerId`、`SessionId`
3. 恢复 `CardFlowContext`
4. 校验选项
5. 执行 `scenario.ApplyOption()`
6. 清除待选状态

## 6. 参数传递约定

文件：

- `Assets/YC/Domain/Cards/CardFlowArgumentUtility.cs`

当前统一使用字符串键值对列表传递扩展参数：

```csharp
List<StringKeyValuePair>
```

原因：

- 可序列化
- 可挂到 `PendingCardSessionState`
- 不强依赖某个具体业务模型
- 兼容未来网络同步或存档

当前典型参数：

- 探索：路径地块、路径航道、主影响力槽位、事件影响力槽位、路费接收者
- 移动城市：事件影响力槽位
- 入场事件：当前无额外参数

建议：

- 参数 key 使用场景类常量统一定义
- 复杂集合统一编码成逗号分隔或键值对字符串
- 解码逻辑只放在具体场景类中

## 8. 后续建设模块如何接入

如果建设模块以后需要复用抽卡流程，建议按下面步骤接入：

1. 新建一个 `BuildFacilityEventCardScenario`，实现 `IEventCardScenario`
2. 在 `ResolvePoolId()` 中决定建设要用的牌池
3. 在 `ValidateStart()` 中调用建设模块自己的前置校验
4. 在 `OnCardRevealed()` 中处理翻牌即时副作用
5. 在 `ValidateOption()` 和 `ApplyOption()` 中处理建设事件的选项与奖励
6. 在建设命令处理器里根据交互形态选择：
   - 需要待选：`StartPendingChoice()`
   - 直接结算：`ExecuteImmediate()`
   - 提交待选：`ResolvePendingChoice()`

这样建设模块只扩业务规则，不复制抽卡与待选基础设施。

## 9. 当前边界

- 事件选择表现层已优先读取 `PendingCardSessionState`；旧 `PendingChoiceState` 仍由适配器双写并可 fallback，但不应再作为新增 UI 或结算逻辑的主事实源
- 扩展参数仍是字符串键值对，适合当前范围，但更复杂的多段事件以后可能要补更强类型的编解码封装
- 通用流程目前聚焦事件牌抽取；若以后建设模块出现非事件牌、非固定 option 的复杂卡流，需要再评估是否继续沿用同一接口
