# 对局界面控制器职责拆分说明

## 背景

`MobileCityInteractionController` 原本同时承担会话构建、命令提交、地图热点、事件选择 UI、网络回调、规则查询和显示刷新等职责。该类长期膨胀后会带来两个直接风险：

- 对任一 UI 或规则入口做局部修改时，容易影响其他流程。
- 单个 `MonoBehaviour` 过大，测试覆盖和问题定位都更困难。

本次拆分采用低风险边界：保留 `MobileCityInteractionController` 作为对局界面的流程编排者，先把可独立迁出的 UI 构建、会话装配、点击目标类型、地图表现刷新、命令提交入口和顶部提示呈现移出，避免一次性重排规则判断。

## 当前拆分结果

### `MobileCityInteractionController`

保留职责：

- 接收地图热点、移动城市、影响力槽位点击事件。
- 根据当前 `GameState`、本机玩家和行动阶段决定下一步流程。
- 根据命令结果决定后续 UI 流程，例如刷新状态、打开事件选项、完成主要行动提示等。
- 调度地图表现层刷新，但不直接维护地图热点、资源图标、影响力槽位和城市对象的渲染缓存。
- 调度行动面板和事件弹窗，但不直接创建其内部 UI 结构。
- 保留二次确认状态机和地图点击流程编排。

当前该文件仍保留流程编排、状态刷新、点击状态机和二次确认逻辑；命令提交细节已转交 `CommandSubmissionController`，顶部提示 UI 和动画已转交 `PromptPresenter`。

### `CommandSubmissionController`

职责：

- 初始化本地或联网命令提交通道。
- 在本地模式下调用 `GameSession.Submit()`。
- 在 Host/Client 联网模式下只依赖中性的 `INetworkCommandTransport`，通过 Infrastructure 的 provider 获取当前 `MirrorCommandTransport` 实现并调用 `SubmitOrSend()`。
- 订阅联网初始快照、确认命令和拒绝命令回调。
- 确认命令或初始快照到达后调用主控制器提供的状态刷新回调。
- 联网拒绝命令时使用 `NetworkCommandPromptFormatter` 生成拒绝提示，并调用主控制器提供的提示回调。

该类只处理命令提交与联网反馈桥接，不决定具体行动规则，也不执行移动、探索、影响力等结算。

Steamworks、Mirror `NetworkServer/NetworkClient` 和 FizzySteamworks 都只出现在 Infrastructure/Bootstrap；`CommandSubmissionController` 不直接调用这些平台或传输 API。

### `PromptPresenter`

职责：

- 创建顶部提示所在的 Screen Space Overlay Canvas。
- 创建提示面板、描边、文本和 `CanvasGroup`。
- 统一执行 `SetPrompt()` 的文本更新、淡入、停留和淡出。
- 在主控制器存在二次确认时保持提示显示，不自动渐出。

该类只负责提示呈现，不读取或修改 `GameState`。

### `MapViewPresenter`

职责：

- 创建地图热点、资源图标显示对象、资源点影响力槽位、路线影响力槽位和移动城市显示对象。
- 刷新资源图标、影响力占用状态、影响力高亮边框、移动城市位置和地图热点高亮。
- 维护地图显示所需的 `SpriteRenderer`、热点和城市对象缓存。
- 提供地图坐标换算和调试热点高亮显示。

`MapViewPresenter` 只负责表现层刷新，不提交 `GameCommand`，不修改 Domain/Application 规则逻辑，也不接管地图点击后的目标选择状态机。

### `GameSessionBootstrapper`

职责：

- 创建 `MapQueryService`、`InfluenceService`、`ExplorationService`、`EventDeckService`。
- 根据 `GameLaunchContext` 构造初始 `GameState`。
- 注册 `SetupCommandHandler`、`EndActionCommandHandler`、`DeployInfluenceCommandHandler`、`DispatchInfluenceCommandHandler`、`MoveCityCommandHandler`、`ExploreLocationCommandHandler`。
- 解析联网启动时的本机玩家 id。

主控制器只接收构建结果，不再直接装配整条应用服务链。

### `ActionPanelController`

职责：

- 创建右下角行动面板。
- 创建快速行动和主要行动按钮。
- 刷新玩家/阶段标题、按钮可用状态和底部状态文案。

主控制器仍负责判断按钮是否可用，`ActionPanelController` 只负责呈现这些状态。

### `EventChoiceDialog`

职责：

- 创建事件牌选择遮罩和按钮。
- 创建探索路线选择遮罩。
- 创建探索过路费接收者选择遮罩。
- 维护当前展示的事件牌引用，供主控制器提交选择命令前校验。

事件选择、路线选择和过路费选择的命令提交仍由主控制器执行。

### `ExploreChoiceModels`

职责：

- 提供 `ExplorePathChoice`。
- 提供 `ExplorePaymentChoice`。

这些类型原本嵌套在主控制器内部，迁出后可被弹窗和主控制器共同使用。

### `MapInteractionClickTargets`

职责：

- 提供 `MapHotspot`。
- 提供 `MobileCityClickTarget`。
- 提供 `InfluenceSlotClickTarget`。

这些 `MonoBehaviour` 只负责把 Unity 鼠标点击转发给主控制器，不包含规则判断。

## 设计约束

- 拆分不修改命令模型。
- 拆分不修改移动、探索、影响力等领域规则。
- 拆分不改变地图热点和 UI 的 public 点击入口。
- `MapViewPresenter` 不直接提交 `GameCommand`，只接收主控制器提供的状态和高亮信息来刷新显示。
- `CommandSubmissionController` 不接管命令构造和成功后的流程编排；主控制器仍决定成功后刷新哪些 UI。
- `PromptPresenter` 不读取规则状态，不决定提示文案，只呈现主控制器传入的文本。
- 后续继续拆分时仍应小步推进，避免同时重构地图点击状态机和命令提交。

## 后续拆分建议

建议后续按以下顺序继续拆分：

1. `MapInteractionController`：迁出点击命中后的目标选择流程。
2. 可继续细化 `MapInteractionController` 边界，把地图点击后的目标选择状态机从主控制器移出。
3. 可继续细化 `MapViewPresenter` 内部的资源图标加载、城市对象显示和影响力槽位显示，但应保持其不提交命令。
4. 补充人工场景回归后，再决定是否为 `PromptPresenter` 或命令提交流程增加更细的 EditMode/PlayMode 覆盖。

每一步都应保持主控制器 public 点击入口稳定，并先跑 EditMode 测试确认编译。
