# 多人房间与联机入口方案

## 当前方案（2026-07-13）

当前联网主链路已替换为 `Steamworks.NET + Steam Matchmaking Lobby + Mirror + FizzySteamworks`，固定使用开发测试 AppID `480`，只面向本地开发和朋友联机测试，不包含 Steamworks 后台、Depot、上架或专用服务器。

实际创建、加入、构建与排障步骤见 `docs/联机手册.md`。

```text
StartMenuController
-> SteamRoomService（Steam Lobby、邀请、席位元数据）
-> MirrorNetworkRuntime（NetworkManager + FizzySteamworks）
-> SteamNetworkingSockets / Steam Relay
-> MirrorCommandTransport
-> AuthoritativeCommandDispatcher
-> GameSession / Domain
```

当前边界：

- `SteamBootstrap` 负责 `SteamAPI.Init/RunCallbacks/Shutdown`，回调只在初始化成功后注册。
- `SteamRoomService` 创建或加入 3/4 人 Lobby，以十进制 Lobby ID 作为房间号，并写入 `gameKey=yc_nomad_city`、`protocolVersion=2`、`roomStatus`、`playerCount`、`hostSteamId`、`seat.1..4` 和 Host 权威就绪 metadata。
- AppID 480 是共享环境，加入时必须校验上述命名空间、协议、人数、等待状态和房主 SteamID。
- 房主固定 `PlayerId=1`；房主把 Lobby 中的真实 SteamID 稳定分配到席位，不能使用成员枚举顺序。
- `MirrorNetworkRuntime` 禁止自动创建 Network Player；本项目不把 Domain 状态改造成 `NetworkBehaviour/SyncVar`。
- `PlayerSeat` 显式区分 Lobby 成员存在、Mirror 传输连接、连接身份验证和游戏初始状态同步；开局只要求前三项，第四项在进入游戏场景并应用初始快照后完成。
- `SteamRoomService` 只接受 Mirror Server 连接事件提供的地址，解析 FizzySteamworks 返回的远端 SteamID，并校验它属于当前 Lobby、对应稳定席位且没有第二条连接。Client 只读取 Host 发布的就绪 metadata。
- `MirrorCommandTransport` 以 FizzySteamworks 提供的真实远端 SteamID 绑定 `Mirror connectionId -> PlayerId`，非 Lobby 成员、未绑定连接和冒用 PlayerId 的命令均被拒绝。
- Client 连接后持续请求初始快照，收到后才能提交命令；确认序号断档时重新请求快照。
- Host 只向远端 Client 广播确认快照，不把已本地应用的确认消息再发给 Host 本地连接。
- 只有原始房主、等待状态、全部目标席位存在且都有唯一存活的已验证 Mirror 连接时才能开始；房主开始后 Lobby 不可加入。第一版不迁移房主，房主断线时 Client 返回 `StartScene`。
- 根目录 `steam_appid.txt` 内容为 `480`；Windows 本地构建完成后由 `SteamAppIdBuildPostprocessor` 复制到可执行文件旁。

依赖锁定在 `Packages/manifest.json`：Mirror `96.6.4`、FizzySteamworks `6.0.1`、Steamworks.NET `2025.163.0`。Fizzy 包不内置 Steamworks.NET，因此工程只保留一份独立 Steamworks.NET 包和原生库。

旧 `UnityOfficialRoomService`、`UnityNetcodeCommandTransport` 以及 Unity Authentication/Lobby/Relay/NGO/Unity Transport 包已经从主线移除；`NetworkRoomService` 不进入正式 Steam 路径，只作为下述本地测试模式的房间协调服务。

## Mirror 本地测试模式

为了在没有多个 Steam 账号时验证当前 Mirror 命令同步链路，开发环境增加了显式本地测试模式。该模式不会恢复 UGS/NGO，也不会修改正式 Steam 路径：

```text
StartMenuController
-> OnlineRoomServiceProvider
-> LocalMirrorRoomService
-> NetworkRoomService（仅负责本地房间和席位协调，端口 7780-7799）
-> MirrorNetworkRuntime + TelepathyTransport（端口 7777）
-> MirrorCommandTransport + Host 信令凭据身份握手
-> AuthoritativeCommandDispatcher
```

使用步骤：

1. 停止 Play Mode，在 Unity 菜单选择 `YC/联机测试/启用 Mirror 本地测试模式`。
2. Editor 进入 Play Mode，创建 3 人或 4 人房间，复制界面显示的 `IP:端口` 房间号。
3. 用 Development Build 启动其余实例，并添加参数：`--yc-local-multiplayer-test --yc-local-player-name=Client2`。
4. Client 在“加入房间”中粘贴房间号；所有席位加入后由 Editor 房主开始。
5. 关闭菜单勾选或不给 Development Build 传参数时，入口仍使用 Steam Lobby + FizzySteamworks。

本地模式边界：

- `LocalMirrorIdentity` 为玩家 1-4 生成稳定且互不重复的模拟身份，只用于开发环境。
- TCP 房间信令为每条已分配席位的 Client 连接签发随机凭据；Client 经 Mirror 呈递凭据，Host 解析为稳定席位后才绑定 `connectionId -> 模拟身份 -> PlayerId`。Client 不能用裸 `PlayerId` 声明自己或其他席位就绪。
- 本地模式与 Steam 模式复用同一开局门禁：所有目标席位都必须达到传输连接与身份验证；断线立即清除，重连恢复原稳定席位。
- 本地模式覆盖 Mirror Host/Client、命令权威、快照、序号重同步、断线和返回菜单，不代表 Steam Lobby、真实 SteamID、Steam P2P/Relay 已通过验收。
- 同机测试需允许 TCP `7777` 与房间协调端口 `7780-7799`；一次只运行一个房主。

## 历史方案（2026-06-13，已失效）

本文记录“开房间”和“多人游戏入口”的推荐实现方案。联网层统一采用 Unity 官方联网栈：

- Netcode for GameObjects：Host / Client 生命周期、RPC、连接状态和游戏内命令传输。
- Unity Transport：Netcode 的底层传输。
- Unity Relay：无专用服务器时提供公网连接转发。
- Unity Lobby：创建房间、加入房间、房间码、玩家列表和房间元数据。
- Unity Authentication：为 Lobby / Relay 提供匿名玩家身份。

目标是在不破坏现有规则分层的前提下，把“多人房间、玩家席位、开始游戏、游戏内命令同步”都收口到 Unity 官方联网栈上，而不是继续维护自定义 TCP 协议。

## 官方联网栈职责划分

本项目采用 Host 权威模型。Host 既是 Netcode Server，也是规则权威端。

```text
Unity Authentication
-> Unity Lobby 创建或加入房间
-> Unity Relay 分配公网转发连接
-> Unity Transport 使用 Relay 连接数据
-> Netcode for GameObjects 启动 Host / Client
-> Host 统一校验并提交 GameCommand
```

各组件职责：

- Authentication：启动游戏时匿名登录，获得 Unity Services 玩家身份。
- Lobby：保存房间列表、房间码、玩家席位、昵称、颜色、准备状态和 Relay join code。
- Relay：为 Host 创建 allocation，为 Client 提供 join allocation，解决 NAT / 公网连接问题。
- Unity Transport：配置 Relay Server Data，作为 Netcode 的传输层。
- Netcode for GameObjects：管理 Host / Client 连接、RPC、自定义消息、断线事件和场景同步入口。
- 项目内 `GameSession`：唯一规则提交入口，网络层不得绕过它直接修改 `GameState`。

## 入口设计

开始页保留三个入口：

```text
单机开始
创建房间
加入房间
```

### 单机开始

保持当前逻辑，直接进入 `SampleScene`。进入前创建本地启动配置：

- `LaunchMode.Local`
- 本地玩家数量
- 玩家名称、颜色、席位

单机模式不启动 Unity Services、Lobby、Relay 或 Netcode。

### 创建房间

点击后执行官方联网栈流程：

1. 初始化 Unity Services。
2. 使用 Unity Authentication 匿名登录。
3. 通过 Relay 创建 allocation，并获取 Relay join code。
4. 通过 Lobby 创建房间，并把 Relay join code 写入 Lobby data。
5. 配置 Unity Transport 的 Relay Server Data。
6. 调用 `NetworkManager.StartHost()`。
7. 创建房主席位并进入房间面板。

房间面板显示：

- Lobby 房间码。
- 玩家席位列表。
- 玩家名称、颜色和准备状态。
- 房主“开始游戏”按钮。

### 加入房间

点击后显示输入框：

1. 输入 Lobby 房间码。
2. 通过 Lobby 加入目标房间。
3. 从 Lobby data 读取 Relay join code。
4. 通过 Relay 加入 allocation。
5. 配置 Unity Transport 的 Relay Server Data。
6. 调用 `NetworkManager.StartClient()`。
7. 等待 Host 下发房间席位和开始信号。

Client 不直接决定席位和游戏开始，只提交昵称、颜色、准备状态等房间意图，由 Host 或 Lobby 状态确认。

## 跨场景启动配置

保留 `GameLaunchContext`，通过 `DontDestroyOnLoad` 在开始页和游戏场景之间传递启动参数。

```csharp
public enum LaunchMode
{
    Local,
    Host,
    Client
}

public sealed class GameLaunchContext : MonoBehaviour
{
    public static GameLaunchContext Instance { get; private set; }

    public LaunchMode Mode;
    public int LocalPlayerId;
    public string RoomId;
    public List<PlayerSeat> Players = new List<PlayerSeat>();

    private void Awake()
    {
        if (Instance != null)
        {
            Destroy(gameObject);
            return;
        }

        Instance = this;
        DontDestroyOnLoad(gameObject);
    }
}
```

`RoomId` 在官方联网栈中应保存 Lobby 房间码或 Lobby Id，不再保存 `ip:port`。

`MobileCityInteractionController.BuildSession()` 不应继续写死单人 `PlayerId = 1`。它应该从 `GameLaunchContext.Players` 生成 `GameState.Players`，并从 `GameLaunchContext.LocalPlayerId` 判断本机可操作玩家。

## 游戏内同步模型

多人对局采用 Host 权威模型：

```text
客户端点击地图
-> 生成 GameCommandDto
-> 通过 Netcode 发送给 Host
-> Host 还原 GameCommand
-> Host 调用 GameSession.Submit(command)
-> Host 广播成功命令或 GameState 快照
-> 所有客户端刷新 UI
```

规则层只接受命令，不关心命令来自本地、AI、回放还是网络。

推荐同步策略：

- 高频位置同步：不需要。
- 玩家输入：ClientRpc / ServerRpc 或 Netcode 自定义消息提交 `GameCommandDto`。
- 权威结果：Host 广播已接受命令、命令序号和必要状态快照。
- 新加入或重连：Host 发送完整 `GameState` 快照。
- 随机事件：Host 生成结果并广播，Client 不本地结算随机结果。

需要同步的数据：

- Lobby 房间码或 Lobby Id。
- Relay join code。
- 玩家席位列表。
- Netcode client id 与项目内 `PlayerId` 的映射。
- 本地玩家 id。
- 当前 `GameState`。
- 成功执行的 `GameCommand`。
- 随机种子、牌堆顺序或抽牌结果。
- 命令日志序号。

不建议同步的数据：

- UI 展开状态。
- 按钮高亮状态。
- 场景中每个棋子的 Transform。
- 临时提示文字。

## 联网技术路线

第一阶段：替换房间传输层。

1. 引入 Unity Services、Authentication、Lobby、Relay、Netcode for GameObjects、Unity Transport。
2. 新增 `NetworkManager` 与 `UnityTransport` 场景对象或启动预制体。
3. 新增 `UnityRelayConnectionService`，负责 Relay allocation / join allocation。
4. 新增 `UnityLobbyRoomService`，负责创建 Lobby、加入 Lobby、Lobby 心跳和 Lobby data。
5. 把“创建房间”从直接 TCP 改为 Lobby + Relay + `StartHost()`。
6. 把“加入房间”从 `ip:port` 改为 Lobby room code + Relay + `StartClient()`。

第二阶段：同步房间状态。

1. Lobby data 保存房间公开信息，例如最大人数、游戏状态、Relay join code。
2. Player data 保存昵称、颜色、准备状态和席位意图。
3. Host 维护最终席位分配，并通过 Netcode 下发给 Client。
4. Host 点击“开始游戏”后锁定 Lobby，写入 `GameLaunchContext`，通过 Netcode 通知所有端加载 `SampleScene`。

第三阶段：同步游戏命令。

1. 引入 `GameCommandDto`，避免直接序列化 `Dictionary<string, string>`。
2. Client 通过 Netcode 向 Host 提交 `GameCommandDto`。
3. Host 调用 `GameSession.Submit(GameCommand)` 校验和结算。
4. Host 广播成功命令和命令序号。
5. Client 按相同命令顺序刷新本地状态；必要时接收 Host 快照纠偏。

第四阶段：完善线上体验。

1. 断线检测和 Host 解散房间。
2. Lobby 心跳失效处理。
3. Client 重连和状态快照恢复。
4. 非法命令拒绝和错误提示。
5. 房间列表、昵称输入、颜色选择和准备状态。

- 当前玩家席位。
- 当前玩家是否为 Host。
- 当前玩家是否准备。
- 房间是否可开始。

Host 点击“开始游戏”时，由房间服务触发 Netcode 开始流程；Client 只等待 Host 广播。

### `MobileCityInteractionController`

需要移除写死的：

```csharp
private const int PlayerId = 1;
```

改为运行时字段：

```csharp
private int localPlayerId = 1;
```

初始化时从 `GameLaunchContext.Instance.LocalPlayerId` 读取。创建 `GameState` 时根据房间玩家列表创建所有 `PlayerState`。

### `GameCommand` 序列化

`GameCommand.Parameters` 当前是 `Dictionary<string, string>`，Unity `JsonUtility` 不支持直接序列化字典。

联网或回放落地前，建议新增 DTO：

```csharp
public sealed class GameCommandDto
{
    public string CommandId;
    public GameCommandKind Kind;
    public int PlayerId;
    public string SourceId;
    public string TargetId;
    public List<string> OptionIds;
    public List<GameCommandParameterDto> Parameters;
}

public sealed class GameCommandParameterDto
{
    public string Key;
    public string Value;
}
```

这样网络层、存档层、回放层可以共用同一套序列化格式。Netcode 传输时可以先使用 JSON 字符串承载 DTO，后续再改为 `INetworkSerializable` 降低分配。

## 验收标准

房间阶段完成标准：

- 开始页能进入单机、创建房间、加入房间三个路径。
- 首次联网前能完成 Unity Authentication 匿名登录。
- Host 创建 Lobby 后能看到 Lobby 房间码。
- Host 能通过 Relay allocation 启动 `NetworkManager.StartHost()`。
- Client 能通过 Lobby 房间码加入 Lobby。
- Client 能读取 Relay join code 并启动 `NetworkManager.StartClient()`。
- Host 和 Client 都能看到一致的玩家席位列表。
- Host 解散或断开时，Client 能回到主页并显示明确提示。

游戏阶段完成标准：

- Host 开始游戏后所有客户端进入同一对局。
- `GameState.Players` 与房间玩家列表一致。
- 本机只能替自己的 `PlayerId` 提交命令。
- 初始入场能按玩家列表完成多人落点。
- 客户端提交命令后由 Host 校验和结算。
- 所有客户端最终 `GameState` 一致。
- 断线或非法命令不会直接污染规则状态。

## 实施顺序

建议按以下顺序推进：

1. 在 Unity Package Manager 中引入 Netcode for GameObjects、Unity Transport、Authentication、Lobby、Relay。
2. 在项目中配置 Unity Gaming Services Project Id。
3. 新增 `NetworkBootstrapper`，集中初始化 Unity Services 和 `NetworkManager`。
4. 新增 `UnityRelayConnectionService`，完成 Host allocation 和 Client join allocation。
5. 新增 `UnityLobbyRoomService`，完成创建 Lobby、加入 Lobby、Lobby 心跳和房间退出。
6. 把 `StartMenuController` 的创建/加入房间入口改为官方联网栈流程。
7. 改造 `RoomMenuController`，从 Lobby / Netcode 状态刷新席位列表。
8. Host 开始游戏时写入 `GameLaunchContext`，并通知所有 Client 进入 `SampleScene`。
9. 引入 `GameCommandDto`，通过 Netcode 把 Client 命令提交给 Host。
10. Host 通过 `GameSession.Submit(GameCommand)` 结算，并广播成功命令或状态快照。
11. 补充 EditMode 测试覆盖多人入场和命令校验，补充 PlayMode 测试覆盖 Host / Client 启动流程。

## 架构约束

- `Domain` 不引用 Unity 网络包。
- `Application` 不依赖具体 Lobby、Relay 或 Netcode 实现。
- `Presentation` 只负责显示和提交命令。
- 网络层不得绕过 `GameSession.Submit(GameCommand)`。
- Host 是规则权威端，Client 不直接修改正式 `GameState`。
- Lobby 只保存房间元数据，不保存权威规则状态。
- Relay 只负责连接转发，不承载游戏规则。
- 随机事件必须可回放，不能依赖各客户端本地随机结果。
