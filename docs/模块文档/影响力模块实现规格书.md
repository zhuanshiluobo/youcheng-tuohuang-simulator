# 影响力模块 (Influence Module) 实现规格书

本文整合影响力模块的游戏规则、现有代码结构、编码规范、已实现接口与待验证清单，供开发 Agent 参照执行。

---

## 一、模块定位

影响力模块统一处理玩家影响力在地图影响力槽位上的放置、移动、移除、替换和区控计数。为部署、调度、探索、移动城市、角色牌、企业扩展等所有涉及玩家影响力操作的功能提供可复用入口。

**当前状态：** 影响力模块已完成第一轮拆分。`InfluenceService` 保留为对外门面，内部委托给放置、移动、移除和查询子模块；公开 API 保持兼容。

**当前拆分方案（来自 `docs/架构/程序模块设计.md` 第 7 节，已落地）：**

| 类型 | 职责 |
|---|---|
| `InfluenceService` | 对外统一门面，组合各子规则 |
| `InfluencePlacementRule` | 放置合法性校验 |
| `InfluenceMoveRule` | 移动合法性校验 |
| `InfluenceRemovalService` | 移除与供应堆回收 |
| `InfluenceQueryService` | 只读查询（存在性、槽位占用、区控计数） |

## 二、游戏规则完整清单

### 2.1 玩家影响力供应

- 每名玩家起始 30 个玩家影响力 → `PlayerState.InfluenceSupply = 30`
- 玩家影响力可位于供应堆、地图影响力槽位或城市样式等规则位置。
- 供应堆无可用玩家影响力时，不能放置玩家影响力或宣告城市样式。
- 地图上的玩家影响力被移除时，回到所有者供应堆（`InfluenceSupply += 1`）。
- 支付资源或拿取玩家影响力只能从自己的供应堆取用。

### 2.2 放置条件（部署）

部署是主要行动，放置 1 个玩家影响力。全部条件必须满足：

1. 目标影响力槽位为空（无任何玩家影响力）。
2. 若槽位在地块上：该地块必须已有资源点指示物（已开放已探索）。
3. 若槽位在地块上：该地块不能停靠其他玩家的移动城市（自己的移动城市可以）。
4. 若槽位在航道上：该航道不能被公路覆盖。
5. 玩家供应堆有可用玩家影响力（`InfluenceSupply > 0`）。

### 2.3 移动条件（调度）

调度是主要行动，移动 1 个自己的玩家影响力（至多 2 次）：

1. 来源玩家影响力必须存在且属于当前玩家。
2. 目标影响力槽位必须满足放置条件（除供应堆检查外，移动不消耗新玩家影响力）。
3. 若执行 2 次移动：如果第二次失败，回滚第一次移动（原子性）。

### 2.4 移除规则

- 玩家影响力必须存在。
- 移除后玩家影响力回到所有者供应堆。
- 移动城市时：移除使用航道和目标地块上的所有对手玩家影响力（自己的保留）。
- 公路放置时：移除该航道所有玩家影响力并禁止后续放置。

### 2.5 替换规则

- 替换前先校验目标玩家影响力存在、新拥有者供应和目标槽位状态。
- 校验通过后，旧玩家影响力回旧主供应堆，新玩家影响力消耗新主供应堆，并在同一槽位转移归属。
- 若新拥有者供应不足或目标槽位重新校验失败，替换失败且不修改影响力列表和双方供应。
- 文档明确指出：替换消耗新 owner 的玩家影响力，不是简单地 swap。

### 2.6 区控计数

- 统计指定区域内指定玩家的所有影响力数量。
- 若 `includeCity=true`：移动城市在所在区块视为 2 个额外影响力。
- 影响力属于某个区块的判定：
  - Location 影响力 → 看 Location 的 `RegionId`
  - Route 影响力 → 看 Route 的 `RegionId`，或 Route 两端 Location 所属区域
- 最终计分时并列最高则无人获得该区块分数。

### 2.7 阶段与命令限制

| 命令 | 允许阶段 |
|---|---|
| `DeployInfluence` | `ActionRound1`, `ActionRound2` |
| `DispatchInfluence` | `ActionRound1`, `ActionRound2` |

通用守卫条件（`MainActionCommandGuard`）：
- 阶段合法
- 当前玩家 == 命令玩家
- 无待处理选择项
- 本行动轮尚未执行主要行动

### 4.6 命令处理模式

```csharp
public sealed class DeployInfluenceCommandHandler : IGameCommandHandler {
    private readonly InfluenceService influenceService;
    private readonly RoundAdvanceService roundAdvanceService;

    // 两套构造器：完整注入 + 默认便捷
    public DeployInfluenceCommandHandler(InfluenceService influenceService)
        : this(influenceService, new RoundAdvanceService()) { }

    public DeployInfluenceCommandHandler(
        InfluenceService influenceService,
        RoundAdvanceService roundAdvanceService) {
        this.influenceService = influenceService;
        this.roundAdvanceService = roundAdvanceService;
    }

    public bool CanHandle(GameCommand command)
        => command?.Kind == GameCommandKind.DeployInfluence;

    public CommandResult Handle(GameState state, GameCommand command) {
        // 1. 通用守卫
        var guard = MainActionCommandGuard.Validate(state, command);
        if (!guard.IsValid) return CommandResult.Invalid(guard);

        // 2. 调用服务
        var result = influenceService.Place(state, command.PlayerId, command.TargetId);
        if (!result.Succeeded) return CommandResult.Invalid(result.Validation);

        // 3. 推进行动轮
        roundAdvanceService.CompleteMainAction(state, command.PlayerId);

        // 4. 返回成功
        return CommandResult.SuccessResult(
            new List<GameEvent> { /* 事件 */ },
            "部署成功"
        );
    }
}
```

### 5.2 InfluencePlacementRule

**职责：** 校验在指定槽位放置影响力的合法性。

```csharp
public sealed class InfluencePlacementRule {
    // 依赖
    private readonly IMapQueryService mapQuery;
    private readonly IInfluenceRoadCoverageQuery roadQuery;

    // 校验（不修改状态）
    public InfluenceOperationResult Validate(
        GameState state, int playerId, string slotId,
        bool requireAvailableSupply);  // true=放置, false=移动

    // 便捷方法
    public bool CanPlace(GameState state, int playerId, string slotId);
}
```

**校验清单（按顺序）：**
1. 玩家存在 → `InvalidPlayer`
2. 槽位可解析 → `InvalidSlot`
3. 槽位为空（无已有影响力） → `OccupiedSlot`
4. 若需要供应检查：`InfluenceSupply > 0` → `InsufficientSupply`
5. 若 Location 槽位：有资源指示物 → `ResourceTokenRequired`
6. 若 Location 槽位：无对手城市 → `OpponentCityPresent`
7. 若 Route 槽位：未被公路覆盖 → `RouteCoveredByRoad`

## 六、槽位 ID 格式

```
location:<locationId>:<index>   — 例: "location:A-01:0"
route:<routeId>:<index>         — 例: "route:A1:0"
```

**规则：**
- 每个地块 2 个影响力槽位 → index 范围 0-1
- 每条航道 1 或 2 个影响力槽位 → 按航道定义表中的 `影响力上限`
- 单槽位（count==1）可省略 index，由系统解析

## 九、边界情况与注意事项

1. **供应耗尽 → 无法放置但可移动：** 移动不需消耗新的玩家影响力，供应为 0 时仍可调度。
2. **"尽量执行" 原则：** 移动城市时若出发地块无可用槽位，放置失败不影响移动城市本身成功（记录 `InvalidSlot`）。
3. **替换失败不修改状态：** 当前实现已修复早期非原子失败问题。替换在新拥有者供应不足或目标槽位重新校验失败时，不应提前删除旧影响力，也不应返还或消耗任何供应。
4. **移动城市的双重计数：** 移动城市在区控中算 2 个玩家影响力，"2 个" 是恒定加成，不是乘以 2。
5. **RegionControlService 关注点：** 当前 `Evaluate` 只计数 Location 影响力，未包括 Route 影响力。`CountInRegion` 包含两者。需确认区控计分应使用哪种逻辑。
6. **槽位索引从 0 开始：** 1 号槽位 = index 0，2 号槽位 = index 1。
7. **所有影响力操作必须有失败测试：** 验证失败时不修改 GameState，成功时修改正确。
