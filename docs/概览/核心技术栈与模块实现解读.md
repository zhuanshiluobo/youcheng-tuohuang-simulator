## 0. 从零开始：读懂这份文档前需要知道什么

### 0.1 你不需要先去学完 Unity

这份文档把学习分成两层：

1. **基础层**：先知道游戏程序、Unity 和 C# 中最常见的名词是什么意思；
2. **项目层**：再看《游城拓荒模拟器》怎样使用这些概念。

第一遍阅读时，不需要记住所有类名和文件名。你只要能回答下面四个问题，就已经进入正确方向：

- 游戏现在的数据保存在哪里？
- 玩家的一次操作怎样进入规则系统？
- 谁负责判断操作是否合法？
- 判断成功后，画面怎样跟着改变？

后面的 `GameState`、`GameCommand`、Handler、Service 等英文名只是这四个问题在代码中的具体答案。

### 0.2 计算机游戏最基本的工作方式

一个游戏程序可以先粗略理解为三部分：

```text
数据 + 规则 + 画面与输入
```

- **数据**：现在是第几回合、谁有多少资源、城市在哪里、哪张牌已使用；
- **规则**：能否移动、需要支付多少资源、谁获得分数；
- **画面与输入**：把地图和按钮显示出来，接收鼠标点击，再把结果展示给玩家。

以实体桌游为例：

- 桌上的棋子、卡牌和资源是“数据”；
- 规则书是“规则”；
- 玩家拿起棋子、指出目标位置是“输入”；
- 移动棋子、扣资源、更新分数是“结果展示”。

数字游戏只是把这套过程交给计算机执行。项目的主要工作，就是把规则书中的自然语言翻译成计算机能够严格执行的条件和步骤。

#### 0.2.1 什么是技术栈

**技术栈 Technology Stack** 是一个项目实际采用的一整套技术组合。“栈”在这里不是指东西真的上下堆放，而是强调多种技术共同支撑产品。

本项目的技术栈可以先简化为：

```text
C# 编写程序
+ Unity 运行和显示游戏
+ uGUI 制作界面
+ Mirror 传输联机消息
+ Steamworks/FizzySteamworks 接入 Steam 房间和传输
+ JSON 保存或传递结构化数据
+ NUnit/Unity Test Framework 自动检查规则
+ PowerShell/Python 辅助构建、测试和素材处理
```

问“项目使用什么技术栈”，是在问“它用哪些工具和框架，分别解决什么问题”；问“项目是什么架构”，则是在问“项目自己的代码怎样划分职责和互相配合”。技术栈和架构有关联，但不是同一个概念。

### 0.3 什么是 Unity

Unity 是一个**游戏引擎**。游戏引擎可以理解为已经准备好的游戏开发工具箱，它提供：

- 打开窗口和显示画面；
- 加载图片、字体和声音；
- 接收鼠标、键盘等输入；
- 管理场景中的对象；
- 每帧更新游戏；
- 把项目生成可以运行的 `.exe`；
- 提供测试、日志和编辑器扩展能力。

如果不使用游戏引擎，开发者需要自己处理窗口、显卡绘制、输入、文件加载等大量底层工作。使用 Unity 后，项目可以把更多精力放在桌游规则和交互上。

Unity 这个词在日常讨论中可能指三种不同的东西：

| 说法 | 实际含义 |
|---|---|
| Unity 引擎 | 游戏运行时使用的基础能力 |
| Unity Editor | 开发者打开项目时看到的图形化编辑软件 |
| Unity 项目 | 当前目录中的源码、场景、图片、配置和依赖 |

本项目使用 Unity `2022.3.62f2c1`。版本号很重要，因为不同 Unity 版本支持的 API、包版本和资源格式可能不同。

### 0.4 Unity Editor 的常见区域

打开 Unity 项目后，通常会看到以下区域：

| 区域 | 可以把它理解为 | 用途 |
|---|---|---|
| Project | 项目文件浏览器 | 查看 `Assets` 中的脚本、图片、场景等资源 |
| Hierarchy | 当前场景对象目录 | 查看当前场景里有哪些 GameObject |
| Scene | 场景编辑画布 | 摆放和检查对象，不等于玩家最终看到的画面 |
| Game | 游戏预览窗口 | 查看玩家运行时真正看到的画面 |
| Inspector | 选中对象的属性面板 | 查看和修改对象挂载的组件及字段 |
| Console | 日志和错误窗口 | 查看 `Debug.Log`、警告、异常和编译错误 |

Unity 顶部的 Play 按钮会进入 **Play Mode（运行模式）**。进入后，Unity 会像真正游戏一样执行场景和脚本。退出 Play Mode 后，运行期间对普通场景对象所做的大多数临时修改不会保留。

### 0.5 什么是项目、资源和目录

Unity 项目不是一个单独文件，而是一整个目录。本项目根目录是 `F:\游城拓荒模拟器`。

最重要的目录：

| 目录 | 含义 | 是否通常手工修改 |
|---|---|---:|
| `Assets` | 项目自己的脚本、场景、图片和数据 | 是 |
| `Packages` | 项目使用的 Unity 包及版本 | 是，但应谨慎 |
| `ProjectSettings` | Unity 项目设置 | 通常通过 Editor 修改 |
| `Library` | Unity 自动生成的导入和编译缓存 | 否 |
| `Temp` | Unity 临时文件 | 否 |
| `Logs` | 测试和构建日志 | 查看为主 |
| `docs` | 项目设计、规则和开发文档 | 是 |
| `tools` | PowerShell、Python 等辅助脚本 | 是 |

Unity 中的 **Asset（资源）** 是能被项目使用的文件，例如图片、字体、场景、脚本和 JSON 数据。它不只表示美术图片。

很多 Asset 旁边有一个 `.meta` 文件。`.meta` 保存 Unity 分配的稳定 GUID 和导入配置。移动或提交资源时通常要连同 `.meta` 一起保留，否则场景中的引用可能断开。

### 0.6 什么是场景 Scene

**Scene（场景）** 可以理解为游戏中的一个页面或空间。它保存这一页中有哪些对象以及这些对象的初始设置。

本项目启用两个场景：

- `StartScene`：开始页、单机入口、建房和加入房间；
- `SampleScene`：真正的对局地图和操作界面。

从开始页进入对局时，代码调用 `SceneManager.LoadScene("SampleScene")`。这类似网页从登录页跳转到主页面，但 Unity 会卸载旧场景并加载新场景中的对象。

有些对象需要跨场景保留，例如联网运行时或启动上下文。Unity 的 `DontDestroyOnLoad` 会告诉引擎：“切换场景时不要销毁这个对象。”

### 0.7 什么是 GameObject、Component 和 Transform

Unity 场景中的基本容器叫 **GameObject（游戏对象）**。它本身更像一个空盒子，真正的能力来自挂在盒子上的 **Component（组件）**。

例如一个按钮对象可能包含：

```text
GameObject：单机开始按钮
  Transform / RectTransform：它在哪里、多大
  Image：按钮背景怎样显示
  Button：它能被点击
  Text：按钮上显示什么字
```

一个地图对象可能包含：

```text
GameObject：四人地图
  Transform：地图的位置和大小
  SpriteRenderer：把地图图片绘制出来
  MapDisplayController：项目自己编写的地图适配脚本
```

每个 GameObject 都有 `Transform`。它保存位置、旋转、缩放和父子关系。UI 对象通常使用 `RectTransform`，它额外保存矩形大小、锚点和边距。

**父子关系**表示对象的层级。移动父对象时，子对象通常会一起移动；隐藏一个面板时，它下面的按钮和文本也会一起隐藏。

### 0.8 什么是脚本和 MonoBehaviour

Unity 项目中的 `.cs` 文件是 C# 脚本。普通 C# 类可以只做数据和规则；如果一个类继承 `MonoBehaviour`，它就可以作为组件挂到 GameObject 上，并接收 Unity 的生命周期调用。

常见生命周期方法：

| 方法 | Unity 何时调用 | 本项目中的典型用途 |
|---|---|---|
| `Awake()` | 对象加载后较早调用一次 | 创建服务、注册事件、构建界面 |
| `OnEnable()` | 对象被启用时调用 | 重新刷新或绑定 |
| `Start()` | 第一帧更新前调用一次 | 依赖其他对象初始化后的启动逻辑 |
| `Update()` | 对象启用期间每一帧调用 | 处理持续输入、网络队列或定时检查 |
| `OnDestroy()` | 对象销毁前调用 | 取消事件订阅、关闭网络、释放引用 |
| `OnValidate()` | Editor 中字段变化时调用 | 编辑阶段检查或刷新配置 |

“每一帧”指游戏画面的一次更新。若游戏以每秒 60 帧运行，`Update()` 通常每秒被调用约 60 次，所以不应在里面无条件执行非常耗时的工作。

本项目的规则服务大多不是 `MonoBehaviour`。这是刻意设计：规则计算不需要依赖场景生命周期，因而更容易测试。

### 0.9 Inspector、序列化字段和引用

你会经常看到：

```csharp
[SerializeField] private string mapSceneName = "SampleScene";
```

逐部分解释：

- `private`：其他类不能随便直接访问；
- `string`：这个字段保存文字；
- `mapSceneName`：字段名；
- `= "SampleScene"`：默认值；
- `[SerializeField]`：虽然是 private，仍让 Unity 保存它并显示在 Inspector 中。

Inspector 中还可以保存对其他组件、图片或 GameObject 的引用。运行时脚本直接使用这些引用，不必每次在场景里搜索对象。

“序列化”在这里先理解为：把内存中的数据转换成可以保存、显示或传输的形式。它既用于 Inspector 保存字段，也用于联网把状态转换成 JSON；两者用途不同，但核心思想相同。

### 0.10 Prefab 是什么，本项目为什么大量运行时构造 UI

**Prefab（预制体）** 是保存好的一组 GameObject 和组件模板。比如可以先制作一个“卡牌按钮”Prefab，运行时复制多份。

本项目当前没有把所有界面都做成大量 Prefab，而是经常使用 C# 创建：

```csharp
new GameObject(...)
AddComponent<Button>()
```

这叫**运行时构造 UI**：游戏开始后，代码根据需要创建 Canvas、按钮、文本和弹窗。

优点：

- 可以快速生成规则驱动的动态界面；
- 结构能在源码和测试里直接检查；
- 不必手工维护大量相似 Prefab。

代价：

- UI 文件会很长；
- 调整布局需要修改代码；
- 对不熟悉 Unity 的开发者不如在 Scene/Prefab 中直接看起来直观。

### 0.11 Unity 2D 画面基础

本项目是 2D 项目，核心概念包括：

- **Texture2D**：图片在内存中的像素数据；
- **Sprite**：Unity 用来在 2D 世界中显示的图片资源；
- **SpriteRenderer**：把 Sprite 画在场景中的组件；
- **Camera**：决定玩家看见世界的哪一部分；
- **Orthographic Camera（正交相机）**：远近不会产生透视缩放，适合平面地图；
- **Sorting Order / Z 坐标**：决定多个 2D 图层谁盖在谁上面；
- **Collider / Hotspot**：定义可以被鼠标命中的区域。

本项目的地图底图是一个 Sprite。资源点、航道槽位和点击热点由代码按归一化坐标放到地图上。

**归一化坐标**表示把地图左下到右上统一写成 0～1：

```text
(0, 0)      地图左下
(1, 0)      地图右下
(0.5, 0.5)  地图中心
(1, 1)      地图右上
```

这样即使地图图片在屏幕上放大或缩小，代码也可以按比例计算资源点位置。

### 0.12 uGUI 和屏幕界面基础

Unity 的传统 UI 系统通常叫 **uGUI**。常见组件：

| 组件 | 作用 |
|---|---|
| `Canvas` | 所有屏幕 UI 的根容器 |
| `CanvasScaler` | 根据分辨率缩放 UI |
| `GraphicRaycaster` | 让鼠标能够命中 UI |
| `Image` | 显示背景、图标或卡牌图 |
| `Text` | 显示文字 |
| `Button` | 可点击按钮 |
| `InputField` | 文本输入框 |
| `ScrollRect` | 可滚动内容 |
| `Mask` | 裁掉容器范围外的内容 |
| `Outline` | 给文字或图形增加描边 |

`RectTransform` 的 **Anchor（锚点）** 决定 UI 相对父容器的定位方式。例如锚在右上角的设置按钮，在不同分辨率下仍会贴近右上角。

本项目虽然安装了 TextMeshPro，但当前主 UI 使用的是 uGUI 的 `Text`，并通过 `FontUtility` 管理中文字体。

### 0.13 什么是 C#

C# 是本项目编写逻辑所使用的编程语言。Unity 负责运行 C# 编译后的代码。

可以先把一段 C# 代码理解为：

```text
定义数据长什么样
+ 定义可以执行哪些操作
+ 定义在什么条件下执行
```

你不需要立即学会写代码，但需要能认出以下结构。

#### 先学会逐部分读一行代码

看下面两行：

```csharp
var session = new GameSession(state);
session.Execute(command);
```

可以逐部分读成：

| 写法 | 含义 |
|---|---|
| `var` | 让 C# 根据右侧内容推断变量类型 |
| `session` | 变量名；变量可以理解为给某个数据或对象贴的名字 |
| `=` | 把右侧结果交给左侧变量，不是数学中的“恒等” |
| `new` | 按照类的模板创建一个新对象 |
| `GameSession` | 要创建的对象类型 |
| `(state)` | 创建时传入 `state` 作为参数 |
| `;` | 这一条语句结束 |
| `session.Execute` | 用点号访问 `session` 对象的 `Execute` 方法 |
| `(command)` | 调用方法时把 `command` 交给它处理 |

代码块中的 `{` 和 `}` 表示一段内容的开始和结束；缩进用于让层级更容易看懂。`//` 后面是单行注释，是给人看的说明，不会作为游戏规则执行。

初读代码时，可以先把一行翻译成“谁，用什么方法，处理了什么”：

```text
session.Execute(command)
= 对局会话 session，用 Execute 方法，处理命令 command
```

#### 类 Class 和对象 Object

**Class（类）**是模板，**Object（对象）**是按照模板创建出的具体实例。

例如 `PlayerState` 类规定“玩家状态应该有哪些数据”；玩家 1 和玩家 2 则是两个不同的 `PlayerState` 对象。

```csharp
public sealed class PlayerState
{
    public int PlayerId;
    public int Score;
    public ResourceSet Resources = new ResourceSet();
}
```

这里表示每个玩家对象都有 ID、分数和资源。

#### 字段 Field 和属性 Property

- **字段**直接保存数据，如 `public int Score;`；
- **属性**通过 `get`/`set` 暴露数据，可能带额外控制。

本项目的 `GameState` 为了方便 Unity 序列化，主要使用公开字段；服务类经常使用只读属性保护内部状态。

#### 方法 Method

方法是一段可以被调用的操作：

```csharp
public PlayerState FindPlayer(int playerId)
{
    return Players.Find(player => player.PlayerId == playerId);
}
```

它接收 `playerId`，查找玩家，并通过 `return` 返回结果。

示例里的 `player => player.PlayerId == playerId` 叫 **Lambda 表达式**，这里可以读成：“依次拿到一个 player，找出它的 PlayerId 等于目标 playerId 的那个”。`==` 是“比较两边是否相等”，而单个 `=` 是赋值，两者含义不同。

#### 构造函数 Constructor

构造函数在 `new` 一个对象时执行：

```csharp
var session = new GameSession(state);
```

这里创建一个新的游戏会话，并把初始状态交给它。

#### 条件、循环和返回

- `if`：如果条件成立，就执行一段代码；
- `else`：否则执行另一段；
- `for` / `foreach`：重复处理一组数据；
- `switch`：根据枚举或值选择不同分支；
- `return`：结束方法并返回结果；
- `throw`：遇到不应继续的程序错误时抛出异常。

#### `null` 是什么

`null` 表示“当前没有对象”。例如没有待选事件时，`PendingCardSession` 可以是 null。

代码在访问对象前常检查 null，否则会出现 `NullReferenceException`，意思是程序试图使用一个不存在的对象。

### 0.14 常见 C# 类型

| 写法 | 含义 | 项目示例 |
|---|---|---|
| `int` | 整数 | 分数、回合、玩家 ID |
| `bool` | 真或假 | 是否就绪、是否已经移动 |
| `string` | 文字 | 卡牌 ID、提示信息 |
| `float` | 小数 | UI 尺寸、地图坐标 |
| `List<T>` | 有顺序、可增减的一组 T | 玩家列表、牌堆、目标列表 |
| `Dictionary<K,V>` | 用键快速查值 | 用地点 ID 查地点定义 |
| `HashSet<T>` | 不重复的一组 T | 已访问地点、已选槽位 |
| `enum` | 一组固定命名选项 | 游戏阶段、资源类型、命令类型 |

泛型符号 `<T>` 可以读成“里面装什么”。`List<string>` 就是“一组文字”，`Dictionary<string,int>` 就是“用文字键查整数值”。

### 0.15 接口、继承和组合

#### Interface（接口）

接口只规定“必须提供哪些能力”，不规定具体怎样实现。

例如 `IGameCommandHandler` 要求命令处理器必须有：

```text
CanHandle：能不能处理这个命令
Handle：真正处理命令
```

建设、移动、探索 Handler 都遵守这个接口，所以 `GameSession` 不必知道每个 Handler 内部细节。

#### Inheritance（继承）

`StartMenuController : MonoBehaviour` 表示开始菜单控制器继承 Unity 的 MonoBehaviour，因此能挂到 GameObject 上并收到 `Awake`、`Update` 等调用。

#### Composition（组合）

组合是让一个对象持有并使用其他对象。例如建设 Handler 持有 `BuildFacilityService`。本项目的业务逻辑主要偏向组合，而不是建立很深的继承树。

### 0.16 常见 C# 修饰词

| 词 | 零基础理解 |
|---|---|
| `public` | 其他代码可以访问 |
| `private` | 只有当前类内部可以访问 |
| `internal` | 只有同一程序集可以访问 |
| `static` | 属于类本身，不必先创建对象 |
| `sealed` | 不允许其他类继续继承它 |
| `partial` | 同一个类可以拆到多个 `.cs` 文件 |
| `readonly` | 创建后不能随意重新指向其他对象 |
| `const` | 编译时固定常量 |

`MobileCityInteractionController` 使用 `partial`，所以主控制器、角色牌交互和开发冒烟入口可以分文件维护，但编译后仍是同一个类。

### 0.17 Namespace、using 和文件路径

**Namespace（命名空间）**用于给类型分组，避免同名冲突。例如：

```csharp
namespace YC.Domain.Cards
```

表示这个类型属于“游城拓荒项目 → 领域层 → 卡牌模块”。

文件顶部的：

```csharp
using YC.Domain.State;
```

表示当前文件要使用这个命名空间中的类型。

命名空间和磁盘目录通常相似，但不是同一个概念。目录是文件放在哪里，命名空间是编译后类型属于哪个逻辑名称。

### 0.18 从源码到游戏：编译、程序集、包和依赖

#### 编译 Compile

计算机不能直接执行人类阅读的 `.cs` 源码。Unity 会先检查语法和类型，再把源码编译成可执行的中间代码。编译错误会阻止游戏进入正常运行。

#### 程序集 Assembly

程序集可以理解为“一组一起编译的 C# 代码”。Unity 中的 `.asmdef` 文件用于定义程序集边界。

为什么要分程序集：

- 明确哪一组代码可以依赖哪一组；
- 修改少量代码时减少重新编译范围；
- 阻止 Domain 不小心引用 UnityEngine；
- 让纯规则测试不必加载整个表现层。

#### 包 Package

包是一组可复用的外部功能。例如 Mirror 是联网包，Newtonsoft.Json 是 JSON 解析包。`Packages/manifest.json` 记录项目直接使用的包和版本。

Unity 的 **Package Manager（包管理器）**负责下载、识别和管理这些包。包版本会影响可用 API 和行为，因此文档会写出重要包的精确版本。

#### 库、框架、SDK、插件和 API

这些词都表示“使用别人已经完成的能力”，但侧重点不同：

| 名词 | 最容易理解的含义 | 本项目例子 |
|---|---|---|
| Library 库 | 你主动调用的一组现成功能 | Newtonsoft.Json |
| Framework 框架 | 它规定整体运行方式，并在合适时机调用你的代码 | Unity、Mirror |
| SDK 开发工具包 | 对接某个平台所需的一整套接口、类型和工具 | Steamworks.NET 对 Steamworks SDK 的 C# 封装 |
| Plugin 插件 | 安装进现有工具或引擎、为其增加能力的扩展 | FizzySteamworks 为 Mirror 增加 Steam 传输能力 |
| API 应用程序编程接口 | 一段功能允许其他代码怎样调用它的公开约定 | `SceneManager.LoadScene(...)`、Mirror 的消息注册方法 |

这些分类在实际讨论中可能有重叠。例如 Unity 既是引擎，也提供框架和大量 API。理解时重点看“它解决什么问题”，不必纠结唯一标签。

#### 依赖 Dependency

A 代码必须使用 B 才能工作，就说 A **依赖** B。例如：

```text
ExploreLocationCommandHandler 依赖 ExplorationService
ExplorationService 依赖地图查询、影响力、牌堆和资源指示物服务
```

依赖方向很重要。规则层如果依赖具体按钮和场景，就很难脱离 Unity 测试。

### 0.19 模块、层和架构分别是什么

- **模块 Module**：围绕一类功能组织的代码，如地图模块、建设模块；
- **层 Layer**：按职责高度分组的代码，如规则层、表现层；
- **架构 Architecture**：整个项目怎样划分职责、怎样通信、依赖朝哪个方向。

模块回答“这段代码处理什么功能”，层回答“它在系统中承担什么角色”。

例如建设功能会跨越多层：

```text
Presentation：显示建设牌、接收拖拽和槽位选择
Application：解析 BuildFacility 命令并编排结算
Domain：校验费用、槽位和建设规则
Data：提供牌面图片和建设牌 JSON
Tests：验证成功和失败情况
```

所以“建设模块”不是只有一个文件夹，也不是只有一个类。

### 0.20 本项目四层架构的生活化比喻

可以把一次桌游对局想象成玩家、主持人、规则裁判和场地设备：

| 项目层 | 桌游比喻 | 负责什么 | 不应该做什么 |
|---|---|---|---|
| Presentation | 玩家看到的桌面和操作手势 | 显示、点击、选择、提示 | 自己决定复杂规则 |
| Application | 主持人/流程员 | 接收动作、找到规则、推进流程 | 把所有规则硬写在自己内部 |
| Domain | 规则书和裁判 | 判断是否合法、计算结果 | 依赖按钮、图片或网络 |
| Infrastructure | 桌子、通信设备、房间系统 | 联网、身份、外部数据通道 | 改变桌游规则 |

`Data` 是规则卡表、地图图片和图标；`Tests` 是反复演练规则的检查员。

### 0.21 Controller、Presenter、Service 等名字是什么意思

这些不是 C# 关键字，而是开发者用类名表达职责的惯例。

| 后缀/名称 | 一般职责 | 本项目例子 |
|---|---|---|
| `Controller` | 接收输入、控制某个界面或流程 | `StartMenuController` |
| `Presenter` | 把状态整理成适合界面展示的形式 | `TurnActionPresenter` |
| `View` | 玩家实际看到或交互的界面 | `DispatchDecisionView` |
| `ViewModel` | 已为界面准备好的数据和可执行动作 | `ActionPanelViewModel` |
| `Service` | 一组可复用业务能力 | `InfluenceService` |
| `Handler` | 处理某一类命令 | `BuildFacilityCommandHandler` |
| `Query` | 只读取并回答问题，不改变状态 | `ResourceCollectionSelectionQuery` |
| `Validator` | 检查数据或操作是否合法 | 地图表现定义 Validator |
| `Policy` | 集中表达一组允许/禁止规则 | `CommandPhasePolicy` |
| `Adapter` | 在两种不同接口之间翻译 | `MobileCityWorkflowViewAdapter` |
| `Coordinator` | 协调多个步骤或对象 | `InteractionFlowCoordinator` |
| `Factory` | 创建一组配置正确的对象 | `GameLaunchStateFactory` |
| `Bootstrapper` | 程序启动时把服务组装起来 | `GameSessionBootstrapper` |
| `Database` | 项目内只读定义目录，不一定是真数据库服务器 | `EventCardDatabase` |
| `Catalog` | ID 到路径等简单目录 | `CardImagePathCatalog` |
| `Runtime` | 运行期间存在并管理底层系统 | `MirrorNetworkRuntime` |

名字不是绝对法律，仍要看类里面实际做什么。

### 0.22 状态 State 和状态机 State Machine

**State（状态）**就是“此刻系统是什么情况”。例如：

```text
当前第 3 回合
正在第一行动轮
当前玩家是 2
玩家 2 有 8 金券
地点 A-01 已开放
```

**State Machine（状态机）**规定系统只能在允许的状态之间转换。例如：

```text
盖放角色牌 -> 第一行动轮 -> 第二行动轮 -> 采集 -> 收尾
```

在采集阶段提交建设命令，会被 `CommandPhasePolicy` 拒绝，因为当前状态不允许这种转换。

项目把一局的主要状态集中在 `GameState`。这类似保存了一张“完整桌面快照”。

### 0.23 命令 Command 是什么

命令表示“玩家希望做什么”，不是“事情已经成功”。

例如：

```text
玩家希望把影响力部署到 location:A-01:0
```

代码先创建 `DeployInfluence` 命令，然后规则层检查：

- 现在是不是行动阶段；
- 是否轮到这个玩家；
- 玩家是否还有影响力；
- 槽位是否存在；
- 槽位是否空着；
- 地点是否已成为资源点；
- 是否有对手城市阻挡。

全部通过后，系统才真正修改 `GameState`。

这种设计能防止 UI、网络或测试代码直接把棋子塞进非法位置。

### 0.24 校验、结算、结果和异常的区别

- **校验 Validate**：检查能不能做；
- **结算 Resolve/Apply**：真正扣资源、放棋子、加分；
- **结果 Result**：把成功/失败、错误原因和产生的事件返回；
- **异常 Exception**：程序遇到不符合开发预期的错误，如传入 null 或文件损坏。

玩家操作不合法通常不应该让程序崩溃，而是返回 `ValidationResult.Failure`，再由 UI 显示“资源不足”或“不是当前玩家”。

### 0.25 什么是管线 Pipeline

**管线**不是 Unity 独有功能。它表示一份数据依次经过多个固定处理站点，前一步的输出成为后一步的输入。

可以想象工厂流水线：原料依次经过检查、加工、包装和出库。

本项目的命令管线是：

```text
收集玩家输入
-> 创建命令
-> 判断本地还是联网提交
-> Session 分发
-> Handler 解析
-> Domain 校验
-> Domain 结算
-> 写入状态和日志
-> 刷新画面
```

说“命令经过管线”，不代表项目中一定有一个名为 `Pipeline` 的类。它是在描述整体处理方式。

#### 0.25.1 Unity 中常见的四种“管线”不是同一件事

“管线”只是“分阶段处理”的通用比喻，前面加上不同限定词，就代表不同过程：

| 名称 | 处理的对象 | 用最直白的话理解 | 本项目中的情况 |
|---|---|---|---|
| 命令处理管线 | 玩家操作 | 从点击、校验到修改游戏数据 | 本项目架构的核心，后文会重点讲 |
| 渲染管线 Render Pipeline | 图形数据 | 把相机看到的精灵、文字等变成屏幕像素 | 当前使用 Unity 内置渲染管线，不是 URP/HDRP |
| 资源导入管线 Asset Import Pipeline | 图片、声音、模型等源文件 | 把外部文件转换成 Unity 能高效使用的内部资源 | 图片放入 `Assets` 后由 Unity 导入并生成 `.meta` 身份文件 |
| 构建管线 Build Pipeline | 场景、代码和资源 | 把编辑器项目打包成可运行的 Windows 游戏 | 本项目通过 Unity 构建流程和 PowerShell 工具生成 Windows x86_64 程序 |

#### 0.25.2 什么是渲染管线

**渲染**就是“算出这一帧屏幕上的每个像素应该是什么颜色”。渲染管线可以先粗略理解为：

```text
读取场景中的相机、精灵和 UI
-> 判断哪些东西需要显示
-> 按位置和前后顺序排列
-> 计算材质、颜色和透明度
-> 把结果写到屏幕
```

Unity 常见的渲染管线有：

- **Built-in Render Pipeline（内置渲染管线）**：Unity 传统默认方案；
- **URP（Universal Render Pipeline，通用渲染管线）**：可配置性更强，常用于跨平台项目；
- **HDRP（High Definition Render Pipeline，高清渲染管线）**：面向高端 3D 画面。

本项目的 `GraphicsSettings.asset` 中 `m_CustomRenderPipeline` 为空，而且包清单没有 URP/HDRP 包，因此当前使用 **Built-in Render Pipeline**。这是一项项目配置，不是 `GameState` 或命令规则的一部分。对本项目而言，地图主要由 `SpriteRenderer` 画出，菜单和面板主要由 uGUI 画出，最后都交给内置渲染管线生成屏幕画面。

#### 0.25.3 什么是资源导入管线

你复制进 `Assets` 的 PNG 图片还不是游戏最终直接读取的形式。Unity 会执行大致如下的过程：

```text
发现源文件
-> 读取导入设置
-> 转换和缓存
-> 建立资源 ID 与依赖关系
-> 在编辑器、场景和构建结果中提供资源
```

Inspector 中把图片类型设成 `Sprite (2D and UI)`，就是在告诉导入管线怎样解释这张图片。`.meta` 文件保存资源身份和导入设置，所以不能随意丢失，否则场景或脚本原来指向的图片可能断开。

#### 0.25.4 什么是构建管线

在 Unity 编辑器中点击 Play，只是在编辑器里试玩；**构建 Build** 才是制作一个不依赖编辑器也能运行的游戏程序。构建管线大致执行：

```text
选择要包含的场景
-> 编译用于目标平台的代码
-> 收集场景依赖的资源
-> 转换和压缩资源
-> 生成可执行文件与数据目录
```

本项目的构建设置包含 `StartScene` 和 `SampleScene`，目标为 Windows x86_64。PowerShell 脚本可以自动启动 Unity 的批处理构建，但真正完成编译和资源打包的仍是 Unity Build Pipeline。

### 0.26 什么是链路 Chain / Call Path

**链路**表示为了完成一个具体功能，调用依次跨过了哪些对象和模块。

例如“部署影响力链路”是：

```text
按钮
-> TurnActionPresenter
-> InfluenceActionPresenter
-> GameCommand
-> DeployInfluenceCommandHandler
-> InfluenceService
-> GameState
-> MapViewPresenter
```

管线强调“系统普遍遵守的处理阶段”，链路强调“某一个具体功能实际经过哪些类”。二者经常重叠，但观察角度不同。

### 0.27 什么是数据流 Data Flow

数据流关注“信息向哪里移动”。例如：

```text
鼠标位置 -> 地图槽位 ID -> GameCommand.TargetId
GameState -> ViewModel -> Text/Image -> 玩家看到的画面
Client 命令 -> Host -> Host 状态快照 -> Client
```

数据流图不一定表示执行时间，也不一定表示类的依赖关系。它只强调数据来源、转换和去向。

### 0.28 什么是工作流 Workflow

**工作流**是玩家完成一个目标所需的多步骤交互。

“点击结束行动”只有一步，通常不需要复杂工作流。“探索”则需要：

```text
选择探索目标
-> 选择路径
-> 选择路费接收方
-> 确认
-> 查看事件牌
-> 选择事件选项
-> 某些事件再选择影响力槽位
```

工作流需要记住“玩家已经进行到哪一步”。`ExplorationEventPresenter` 就保存探索交互的临时步骤；真正对局事实仍由 `GameState` 保存。

### 0.29 什么是生命周期 Lifecycle

生命周期表示一个对象或流程从创建到销毁经历哪些阶段。

示例：

- GameObject 生命周期：创建 → Awake → Enable → Update → Destroy；
- 房间生命周期：创建 → 玩家加入 → 身份验证 → 开局 → 断线/关闭；
- 一局游戏生命周期：入场 → 多回合 → 最终计分；
- 待选会话生命周期：打开 → 等待玩家 → 校验选择 → 结算 → 清除。

讨论“联网生命周期”时，关注的是连接何时建立、订阅事件、断开和清理，而不是某一条桌游规则。

### 0.30 什么是事实源 Single Source of Truth

**事实源**表示遇到多个副本或显示结果不一致时，哪一份数据才是最终依据。

本项目把 `GameState` 作为游戏事实源：

- UI 上的数字只是 `GameState` 的显示结果；
- 高亮只是交互提示；
- Client 在联机中不能自行宣布最终状态；
- Host 结算后的 `GameState` 才是联网权威结果。

例如 UI 显示玩家有 10 金券，但 `GameState` 中实际是 8，应该修 UI 刷新问题，而不是把状态改成 10 来迎合画面。

### 0.31 确定性、随机种子和重现

**确定性**表示相同初始状态和相同输入会得到相同结果。

洗牌需要随机，但测试和联网希望能重现，所以项目使用 **Seed（随机种子）**：给伪随机算法相同 seed，就会得到相同的牌序。

这使问题更容易复现：知道初始 seed 和命令顺序，就更容易定位“第几张牌导致错误”。不过当前完整回放系统还没有实现。

### 0.32 原子操作、事务和投影状态

**原子操作**可以理解为“要么全部成功，要么完全不发生”。

例如一次角色牌效果要求移动两个影响力：如果第一个已经移动，第二个才发现非法，就会留下半完成状态。为避免这种问题，代码可以：

1. 先复制一份临时状态；
2. 在临时状态上尝试全部步骤；
3. 全部成功后再写回真实状态；
4. 任一步失败就丢弃临时状态。

这份临时副本叫**投影状态**。它与数据库事务思想相似，但本项目主要是在内存中手工复制和提交。

### 0.33 同步、异步和事件

- **同步**：当前方法做完，调用者才继续；
- **异步**：等待网络等耗时任务时，程序可以继续处理其他事情；
- **事件 Event**：某件事发生时通知订阅者。

例如创建 Steam 房间是异步操作，因为需要等待 Steam 返回；`RoomUpdated` 是事件，房间变化时 UI 会收到通知。

C# 的 `event Action<RoomState>` 可以先读成：“允许其他对象订阅一个会携带 RoomState 的通知。”

注意：C# 事件、项目中的 `GameEvent`、桌游事件牌是三种不同概念，只是中文都叫“事件”。

### 0.34 联机最基础的概念

#### Host 和 Client

- **Host（房主）**：既运行服务器部分，也作为一个玩家参与；
- **Client（客户端）**：连接 Host，提交自己的操作并接收状态。

#### Authority（权威）

权威表示谁有资格决定最终结果。本项目是 **Host authoritative（Host 权威）**：

- Client 可以请求“我要建设”；
- Host 检查这个 Client 是否对应正确玩家；
- Host 使用正式规则结算；
- Host 把结果发回所有人。

#### Snapshot（快照）

快照是某一时刻完整状态的副本。本项目当前每个成功联网命令都会携带完整 `GameState` 快照。

#### Sequence（序号）

Host 给成功命令编号 1、2、3……。Client 若收到 8 后直接收到 10，就知道 9 丢失了，应请求重新同步，而不能假装一切正常。

#### Lobby 和 Transport

- **Lobby**：等待房间，管理成员、席位、邀请和房间元数据；
- **Transport**：真正负责在网络上传输 Mirror 消息的底层通道；
- **SteamID**：Steam 账号的唯一数字身份；
- **P2P/Relay**：Steam 帮助玩家之间建立或中继网络通信的方式。

进入 Lobby 不等于游戏网络已经连接，所以项目分别记录“已在房间”“传输已连接”“身份已验证”。

### 0.35 JSON、DTO 和序列化

**JSON**是一种文字数据格式，例如：

```json
{
  "playerId": 1,
  "score": 12
}
```

它方便保存到文件或通过网络传输。

**DTO（Data Transfer Object，数据传输对象）**是专门为传输准备的简单数据结构。领域对象可能包含字典或复杂行为，不适合直接交给 Unity `JsonUtility`，所以 `GameCommandDto` 会把命令转换成更容易序列化的结构。

DTO 不负责规则，只负责安全、稳定地搬运数据。

### 0.36 一次单机启动到底发生了什么

从点击“单机开始”到看到对局，大致顺序是：

1. Unity 加载 `StartScene`；
2. `StartMenuController.Awake()` 运行并用代码创建开始菜单；
3. 玩家点击“单机开始”；
4. `StartGame()` 创建一个本地玩家席位；
5. `GameLaunchContext` 保存“本地模式、玩家 1”等跨场景信息；
6. Unity 加载 `SampleScene`；
7. `MobileCityInteractionController.Awake()` 开始组装对局；
8. `GameSessionBootstrapper.Build()` 创建地图、初始状态、领域服务和 Handler；
9. Map/UI Presenter 创建热点、按钮、牌区和状态显示；
10. UI 从 `GameState` 执行第一次刷新。

这里的“Bootstrap（引导/启动组装）”不是游戏规则。它只是把运行所需对象正确连接起来。

### 0.37 一次“部署影响力”的完整初学者链路

假设玩家要把一个影响力放到 A-01 的第一个槽位：

| 步骤 | 发生的事 | 为什么需要 |
|---:|---|---|
| 1 | 行动面板显示“部署”按钮 | 给玩家入口 |
| 2 | 玩家点击部署 | 表达操作意图 |
| 3 | `InfluenceActionPresenter` 进入部署选择状态 | 记住现在应选择目标 |
| 4 | 地图合法槽位被高亮 | 帮助玩家选择 |
| 5 | 玩家点击 A-01 槽位 | 获得稳定槽位 ID |
| 6 | Presenter 创建 `DeployInfluence` 命令 | 把 UI 操作翻译成规则输入 |
| 7 | `CommandSubmissionController` 判断是单机 | 决定直接提交而不是发网络 |
| 8 | `GameSession` 找到部署 Handler | 把命令交给正确模块 |
| 9 | Handler 检查阶段和当前玩家 | 防止越权和错阶段 |
| 10 | `InfluenceService` 检查槽位和供应 | 执行领域规则 |
| 11 | 成功后 `GameState.Map.Influences` 增加记录 | 真正改变事实源 |
| 12 | 玩家供应中的影响力减 1 | 完成资源结算 |
| 13 | 主要行动标记为已完成 | 推进回合规则 |
| 14 | UI 从状态刷新 | 在地图上画出新影响力 |

即使第 4 步 UI 错误地高亮了非法位置，第 10 步仍会拒绝命令。这叫“表现层提示 + 领域层最终校验”。

### 0.38 为什么探索链路比部署复杂

部署只需要选择一个槽位；探索需要跨越多个有玩家选择权的步骤：

```text
地点 -> 路径 -> 路费接收者 -> 事件牌 -> 事件选项 -> 可能的影响力槽位
```

如果一次性弹出一个巨大表单，玩家难以理解，代码也难维护。因此项目用工作流把它拆成多步，并用 `PendingCardSessionState` 把“事件牌已经抽出但还没选完”的事实保存进 `GameState`。

这也解释了为什么待选状态非常重要：联机时 Client 可以在事件弹窗打开后收到刷新或短暂重连，系统仍知道正在处理哪张牌、哪个玩家和哪个目标地点。

### 0.39 一次联网命令与单机有什么不同

UI 到 `GameCommand` 的前半段相同。区别从提交开始：

```text
单机：命令 -> 本地 GameSession -> 本地状态刷新

联机 Client：命令 -> Mirror 发给 Host
             -> Host 检查连接身份
             -> Host GameSession 结算
             -> Host 广播序号 + 完整状态
             -> Client 替换本地状态并刷新 UI
```

因此规则层不需要知道玩家是否通过 Steam 联机。它只接收已经确定发起者的命令和当前状态。

## 1. 先建立一个整体认识

> **零基础衔接提示**：这一章会开始使用项目中的真实类名。先读中文含义，再把英文类名当作代码里的“地址标签”，不需要立刻背诵。如果忘记“状态机、命令、管线、链路”等词，可回看第 0.22～0.30 节。

这是一个把实体桌游《游城拓荒：铸基者》的规则数字化的 Unity 2D 项目。它的核心目标不是复刻桌游美术，而是把规则变成一套：

- 能**确定性运行**的**状态机**：相同初始数据和相同操作，会得到相同结果；程序明确知道当前处于哪个游戏阶段；
- 能通过**命令校验**的**规则引擎**：玩家先提交“我想做什么”，规则代码判断是否允许，再执行结算；
- 能在单机和 **Host 权威联机**中复用的结算核心：单机和联机共用同一套规则，联机时由主机作最终决定；
- 能用 **EditMode 测试**与**自动跑局**持续验证的系统：不必手工点击完整一局，也能让程序自动检查规则是否被改坏。

理解本项目最重要的一句话是：

> **`GameState`（整局数据）是一局游戏的事实源；玩家只提交 `GameCommand`（操作申请），命令处理器调用领域服务（规则代码）进行校验和结算，UI（画面与交互）和联网层都围绕这条链路工作。**

最常见的一次操作如下：

```text
玩家点击 UI / 地图
  -> 表现层 Presentation 收集目标、路径、支付方式等参数
  -> 生成 GameCommand（把“玩家想做什么”装进一个数据对象）
  -> CommandSubmissionController（提交控制器）决定在本机处理，还是发给 Host 主机
  -> GameSession（对局会话）查找能够处理该命令的 Handler（命令处理器）
  -> Handler 调用 Domain Service（领域规则服务）检查合法性并执行结算
  -> 成功后更新 GameState（整局数据）、追加日志、返回 GameEvent（本次操作产生的事件）
  -> UI 重新读取最新 GameState，刷新数字、棋子、按钮和提示
```

这条从“点击”到“刷新画面”的连续过程，就是一条**功能链路**；其中“收集输入、建命令、校验、结算、刷新”这些固定阶段合起来，也可以称为**命令处理管线**。

联机并没有复制一套规则。Client（加入游戏的客户端）只把命令发给 Host（主持游戏的主机），Host 仍执行同一个 `GameSession`，然后把确认序号和完整状态快照广播给所有 Client。换句话说，客户端负责“申请”，主机负责“裁决并公布结果”。

## 4. 核心运行时对象

### 4.1 `GameState`：唯一游戏事实源

文件：`Assets/YC/Domain/State/GameState.cs`

`GameState` 使用可序列化的公开字段，主要包含：

- 对局信息：`GameId`、当前阶段、回合、最大回合数；
- 回合控制：起始玩家、当前玩家、行动轮；
- `Players`：资源、分数、影响力供应、城市位置、手牌、建设和样式；
- `Map`：开放地点、道路、影响力、设施和资源指示物；
- `Decks`：三色事件牌堆、设施牌堆、公开供应和城市样式供应；
- 三类待处理状态：通用旧待选、通用抽卡会话、角色牌待选；
- 延迟到收尾的角色效果；
- 最终计分明细和对局日志。

实现选择是“可变状态对象”，不是不可变对象或事件溯源。它简单、适合 Unity 序列化和全量快照，但正确性依赖所有写操作都走 Handler/Service，并由测试约束。

### 4.2 `GameCommand`：所有操作的统一输入

文件：`Assets/YC/Domain/Commands/GameCommand.cs`

命令通用字段包括：

- `CommandId`：幂等追踪和日志标识；
- `Kind`：命令类型；
- `PlayerId`：发起玩家；
- `SourceId`、`TargetId`、`OptionIds`：常用来源、目标和选项；
- `Parameters`：各命令扩展参数。

例如探索会把 `routeIds`、`pathLocationIds`、事件选项、影响力槽位和路费接收方编码进参数；建设会传设施 ID、城市面板槽位和支付方式。

### 4.3 DTO 为什么把字典变成列表

`GameCommandDto` 把 `Dictionary<string,string>` 转为 `List<GameCommandParameterDto>`，因为 Unity `JsonUtility` 不原生序列化字典。确认消息包含：

- 连续的 `Sequence`；
- 原始命令 DTO；
- Host 结算后的完整 `GameState`。

### 4.4 `GameSession`：轻量命令总线

`GameSession` 维护 Handler 列表。提交命令时：

1. 若存在待选择项，先阻止普通命令穿透；
2. 顺序寻找 `CanHandle` 为真的处理器；
3. 调用处理器修改当前状态；
4. 成功且有日志文案时追加 `GameLogEntry`；
5. 没有处理器时返回 `UnknownCommand`。

多个 Handler 都能处理 `ResolvePendingChoice`，所以 Session 允许某个 Handler 返回“这不是我的待选”后继续尝试下一个。这是一种简单的责任链实现。

### 4.5 `GameEvent` 不是事件溯源日志

Handler 返回的 `GameEvent` 用于描述“发生了什么”，便于 UI 和日志展示；真正权威的数据仍是 `GameState`。目前系统不能仅靠事件流重建整局，因此不要把它理解成完整事件溯源或已经完成的回放系统。

## 5. 阶段与回合模块

核心文件：

- `Domain/Rules/GameEnums.cs`
- `Domain/Rules/CommandPhasePolicy.cs`
- `Domain/Rules/RoundAdvanceService.cs`
- `Application/Setup/SetupCommandHandler.cs`
- `Application/Gameplay/EndActionCommandHandler.cs`

阶段顺序为：

```text
Setup
-> Entrance
-> CharacterCover
-> ActionRound1
-> ActionRound2
-> ResourceCollection
-> Cleanup
-> 下一回合 CharacterCover 或 FinalScoring
-> GameOver（枚举和通用 PhaseFlow 中存在）
```

源码中还保留 `RoundStart` 和通用 `PhaseFlow`，但实际主流程主要由 Setup、角色盖放和 `RoundAdvanceService` 直接推进。阅读运行逻辑时应以 Handler 和 `RoundAdvanceService` 为准。

实现核心：

- `CommandPhasePolicy` 给每种命令定义允许阶段；
- `MainActionCommandGuard` 校验当前玩家、行动阶段、是否已做主要行动；
- `QuickActionCommandGuard` 允许主要行动前后的快速行动窗口；
- 每个玩家用 `ActedMainActionThisTurn` 标记当前行动轮完成情况；
- 第二行动轮全部结束后进入资源采集；
- 全员采集后进入 Cleanup；
- Cleanup 先结算延迟角色效果，再回收角色牌、决定下回合起始玩家；
- 第 8 回合后进入最终计分。

## 6. 地图与路线模块

核心目录：`Assets/YC/Domain/Maps`

### 6.1 规则地图

`GameMapDefinition` 把地图表示为图：

- `MapLocationDefinition`：地点、区块、资源类型、红区、槽位数；
- `MapRouteDefinition`：航道 ID、覆盖地点、区块、影响力槽位和基础费用；
- `MapRegionDefinition`：区块包含的地点、航道和计分值。

四人地图当前录入 22 个地点、22 条航道和 8 个区块。三人地图只有一个小型测试 placeholder。

### 6.2 查询与寻路

`MapQueryService` 在构造时建立地点、航道、区块字典和邻接表。航道可能覆盖两个以上地点，因此同一航道覆盖的地点彼此视为可邻接。

`MapPathSearchService` 提供三类能力：

- BFS 查找最少步数路径；
- DFS 枚举步数上限内的简单路径；
- 按“航道是否可通过”的谓词计算可达路径。

探索不能总是简单采用唯一最短路，因为不同航道上的影响力会改变路费接收方。表现层会列出有意义的候选路径供玩家选择。

### 6.3 路费

`RouteTollService` 是实际探索和采集共用的航道路费规则：

- 每个需付费的航道组支付 2 金券；
- 自己在该航道/共享区有影响力则免付；
- 道路覆盖航道时免付；
- 对手有影响力时钱付给指定或默认对手，否则付供应堆；
- 同一共享支付键只付一次；
- 指定接收方必须确实拥有对应影响力。

`TravelCostService` 还保留路径基础费用汇总和移动城市的 3 源石碎片基础费。

### 6.4 红区

`RedZoneAccessRule` 根据人数和回合判断红区是否开放：四人第 4 回合、三人第 5 回合、二人规则第 6 回合。

## 7. 地图表现模块

核心目录：`Assets/YC/Presentation/Maps` 与 `Presentation/MapViewPresenter.cs`

规则地图只存拓扑，不存图片坐标。表现层另外维护 0～1 的归一化坐标：

- `FourPlayerResourcePointDisplayDefinitions`：资源点和地点影响力槽位；
- `FourPlayerRouteDisplayDefinitions`：航道折线和航道影响力槽位；
- `FourPlayerScoreTrackDisplayDefinition`：计分轨位置；
- Validator：检查每个规则地点/航道都有表现定义、坐标不越界、槽位数一致。

`MapViewPresenter` 的实现方式是：

1. 根据底图 `SpriteRenderer.bounds` 把归一化坐标换算成世界坐标；
2. 运行时创建地点热点、航道、影响力槽、资源标记和城市对象；
3. 从 `GameState` 刷新 Sprite、颜色、可见性和位置；
4. 工作流只下发语义高亮，如“移动目标”“调度来源”“采集候选”。

`MapDisplayController` 用正交相机自动适配地图宽高。地图图片只是显示层，规则永远读取结构化地图定义。

## 8. 影响力模块

核心目录：`Assets/YC/Domain/Influence`

### 8.1 稳定槽位 ID

影响力槽统一编码为：

```text
location:<locationId>:<index>
route:<routeId>:<index>
```

`InfluenceSlotReference` 负责解析、规范化和兼容只有一个槽位时的简写，避免 UI 坐标成为规则 ID。

### 8.2 放置规则

`InfluencePlacementRule` 校验：

- 玩家存在且供应中有标记；
- 目标槽位合法且未占用；
- 地点必须已有资源指示物；
- 对手移动城市所在地点不能放置；
- 道路覆盖的航道槽位不能放置。

### 8.3 调度、移除和查询

`InfluenceService` 是统一写入口，支持：

- 单个放置和移动；
- 多标记原子放置/移动；
- 失败时不留下半完成状态；
- 移除后将标记返还玩家供应；
- 查找槽位上的标记。

`InfluenceQueryService` 负责只读统计，包括按玩家列出、按区块计数，以及把区块内的移动城市计为 2 点影响力。`RegionControlService` 直接复用这个统计。

应用层的 `DeployInfluenceCommandHandler` 和 `DispatchInfluenceCommandHandler` 决定它们是主要行动，并在成功后标记主要行动已完成。

## 9. 移动城市模块

核心目录：`Assets/YC/Domain/Movement`

`CityMovementService` 处理正常移动、角色牌移动和设施提供的免费移动。典型校验包括：

- 当前阶段和当前玩家是否合法；
- 本回合是否已经移动；
- 目标是否允许停靠、是否被其他城市占用；
- 起点和终点是否由一条合法航道连接；
- 红区是否开放；
- 是否能支付正常移动基础费用；
- 目标地点是否需要触发移动事件。

正常移动使用 `MoveCityCommandHandler`。服务把“移动本身”和“抽事件/待选”组合起来，必要时通过 `MoveCityEventCardScenario` 打开通用抽卡会话。设施或角色牌可以调用专用入口跳过某些正常成本，但仍复用地点、占用和事件规则。

## 10. 通用抽卡与事件牌模块

核心目录：`Assets/YC/Domain/Cards`

### 10.1 事件牌数据

`EventCardDatabase` 当前以 C# 静态数据定义：

- 6 张绿色；
- 10 张黄色；
- 6 张红色；
- 合计 22 张事件牌。

每张牌包含叙事文本、资源点类型/数量、选项描述、即时资源奖励和结构化延后效果。结构化效果当前支持得分、给对手资源、付费放影响力等。

### 10.2 确定性牌堆

`CardPoolService` 用 Fisher–Yates 洗牌，`EventDeckService` 从固定 seed 初始化三色牌堆。联网时 seed 来自房间 ID 的稳定哈希；对同一房间，Host 和初始化状态具有可复查的牌序基础。

### 10.3 通用卡牌流程

`CardFlowService` 把“抽牌并选择”统一成：

```text
ResolvePoolId
-> Peek 并预校验
-> Draw
-> OnCardRevealed
-> 写入 PendingCardSessionState
-> 玩家提交选项
-> ValidateOption
-> ApplyOption
-> 清除待选会话
```

差异通过 `IEventCardScenario` 注入。目前至少有：

- 入场事件；
- 探索事件；
- 移动城市事件。

`PendingCardSessionState.ContextData` 保存跨两次命令所需的上下文，如目标地点、路径或来源命令。`CardFlowStateAdapter` 优先读取新会话，同时为旧 `PendingChoiceState` 提供兼容视图。

## 11. 探索模块

核心目录：`Assets/YC/Domain/Exploration` 与 `ExploreLocationCommandHandler`

探索是项目中最复杂的复合主要行动之一：

1. 选择未探索地点；
2. 选择从移动城市到目标的路线；
3. 计算航道路费及接收方；
4. 检查红区和资源；
5. 支付路费；
6. 放置资源指示物并打开地点；
7. 按地点颜色抽事件牌；
8. 玩家选择事件选项；
9. 结算资源、得分、对手奖励或影响力放置；
10. 标记主要行动完成。

Handler 支持两种提交方式：

- 不带事件选项：先抽牌并创建待选会话；
- 已明确带事件选项：在自动跑局或已知预览场景中一次结算。

领域服务负责最终校验，表现层的费用估算和目标高亮只用于帮助玩家，不能替代领域校验。

## 12. 建设与设施效果模块

核心目录：`Assets/YC/Domain/Facilities`

### 12.1 建设牌数据来源

`FacilityCardDatabase` 优先读取：

`Assets/StreamingAssets/YC/Data/building_cards_manifest.json`

清单包含 41 张正式建设牌、储备牌、费用、颜色、分数、唯一性、关键词和 `effectId`。加载器使用 Newtonsoft `JObject`，并保留内置 fallback 定义，避免清单不可用时核心测试完全失效。

这不是数据库服务器，而是“静态 JSON 清单 + 运行时只读目录”。当前加载实现通过多个桌面路径探测后 `File.ReadAllText`，适合现阶段 Windows 构建；若以后移植到 Android/WebGL，应改成平台兼容的 StreamingAssets 读取方案。

### 12.2 建设结算

`BuildFacilityService` 的顺序明确为：

```text
校验供应、唯一性、3×4 城市面板槽位和支付方式
-> 支付资源或金券
-> 添加设施与位置
-> 增加牌面分
-> 结算入场效果
-> 只补充被取走的公开供应槽
```

支付支持 `resources`、`gold` 和 `auto`。`FacilityBuildCostService` 是查询和正式结算共享的费用真源，防止 UI 显示费用与实际扣费不一致。

### 12.3 设施效果

设施效果采用 `effectId` 分派：

- 确定性奖励立即结算；
- 联邦理事处记录本回合最后建造者，收尾时改变下回合起始玩家；
- 需要选择的效果写入 `PendingCardSessionState`；
- `ResolveFacilityEffectCommandHandler` 再按待选类型执行额外建设、延伸枢纽、出售资源、免费移动、五资源分配、影响力替换/部署、移除后调度或探索等逻辑。

`FacilityEntryEffectAvailabilityService` 先查询某些效果是否至少有一个合法目标，避免打开无法完成的弹窗。`FacilityInfluenceEffectService` 封装“先移除再尽可能替换”等特殊原子/尽力执行规则。

### 12.4 表现层建设草稿

`BuildFacilitySelectionController` 是纯 C# 草稿状态机：选牌、拖拽、落槽、支付、确认、返回和取消。正式状态只在确认命令成功后改变；拖拽阶段不会直接改 `GameState`。

## 13. 角色牌模块

核心文件：

- `Domain/Cards/CharacterCardDatabase.cs`
- `Domain/Cards/CharacterCardService.cs`
- `Domain/Cards/CharacterCardOptionQueryService.cs`
- `Application/Gameplay/CoverCharacterCardCommandHandler.cs`
- `Application/Gameplay/UseCharacterCardCommandHandler.cs`

当前运行时实现五张标准角色牌：雷蛇、极境、德克萨斯、坎诺特、锡人。每张实体牌为每个玩家生成独立拥有者 ID，避免不同玩家的同名牌混淆。

### 13.1 生命周期

```text
每回合 CharacterCover 阶段从手牌盖放 1 张
-> 行动阶段选择策略、计谋或允许时两者
-> 已使用牌进入弃牌/效果流程
-> 未使用盖牌在 Cleanup 回手
-> 手牌耗尽时回收弃牌
```

盖放事件不会暴露实际牌 ID，避免公开日志泄露隐藏信息。

### 13.2 效果实现

`CharacterCardService` 统一处理资源、设施供应、地图影响力、城市移动、待选和延迟效果。复杂多步效果先在投影状态中完整校验，全部成功后一次提交回真实状态，从而避免“第一步成功、第二步失败”留下半结算。

只有规则明确要求“尽可能执行”的分支才允许部分完成，例如替换受城市阻挡时可以只移除对手标记。

`CharacterCardOptionQueryService` 是只读合法目标查询：它枚举可放置槽位、对手影响力、可移动组合、可袭击地点、设施供应和锡人购买摘要。UI 用查询生成选项，领域服务在提交时再次校验。

角色待选单独使用 `PendingCharacterEffectState`，支持：

- 锡人弃牌逐张选择；
- 雷蛇收尾移除己方影响力；
- 起始玩家是否继续发动角色牌另一半效果；
- 第二效果的后续地图/非地图参数选择。

## 14. 城市样式模块

核心目录：`Assets/YC/Domain/CityStyles`

### 14.1 数据与匹配

`CityStyleDatabase` 静态定义 6 张城市样式，包括分数、等级、宣告次数、奖励、特殊行动 ID 和颜色图案。

`CityStylePatternMatcher`：

- 从玩家 3×4 城市面板提取未被历史宣告占用的设施；
- 按所需数量搜索组合；
- 在 0°、90°、180°、270° 四个方向匹配颜色图案；
- 不支持镜像；
- 可自动找组合，也可严格校验 UI 明确选择的槽位；
- 返回使用的设施 ID、槽位和匹配旋转角度。

已用于宣告的槽位记录在 `CityStyleDeclarationState`，后续不能重复消费。表现层把这些槽位渲染为已旋转/已使用状态，而规则上依赖的是“槽位已被声明占用”的记录。

### 14.2 宣告结算

`DeclareCityStyleService` 校验玩家、次数、影响力供应和图案后：

- 从供应扣 1 个影响力作为样式标记；
- 增加样式分；
- 发放即时资源奖励；
- 记录使用设施和槽位；
- 根据等级创建 1 次或 2 次特殊行动使用次数。

`DeclareCityStyleCommandHandler` 要求 UI 明确传入所选槽位，防止网络命令让 Host 自行选一组与玩家意图不同的组合。

### 14.3 当前缺口

样式宣告、计分、奖励和特殊行动次数记录已经完成，但 `UseSpecialAction` 没有注册命令处理器，5 种样式特殊行动的实际规则与 UI 仍未闭环。

## 15. 资源采集模块

核心目录：`Assets/YC/Domain/Harvest`

资源采集阶段允许玩家选择多个资源点。`ResourceCollectionService` 负责：

## 16. 最终计分模块

核心目录：`Assets/YC/Domain/Scoring`

`FinalScoringService` 在 `FinalScoring` 阶段一次结算并写入结构化明细：

```text
总分 = 基础分 + 区控分 + 剩余资源分 + 设施分 + 城市样式分
```

资源换分：

- 1 至纯源石 = 1 分；
- 6 异铁 = 1 分；
- 8 源石碎片 = 1 分；
- 9 源岩 = 1 分。

区控由 `RegionControlService` 计算：地图影响力每个 1 点，移动城市在所在区块额外计 2 点；最高者得分，并列最高时无人得分。

平局顺序：总分、剩余金券、剩余至纯源石；仍相同则共同胜利。

服务具有幂等保护：若 `FinalScoring.IsResolved` 已为真，会返回已有结果，避免重复加分。

## 17. Application 层模块

### 17.1 Setup

`SetupCommandHandler` 处理起始玩家、初始城市和入场事件：

- 初始化计分轨标记；
- 按席位顺序选择初始地点；
- 给每个玩家放置核心指挥塔；
- 没有资源指示物的地点触发入场事件；
- 全员完成后发放不同顺位的初始金券并进入角色盖放。

### 17.2 Gameplay Handlers

每个 Handler 主要承担三件事：

1. 解析通用命令中的具体参数；
2. 调用领域服务；
3. 把领域结果转换为 `CommandResult`、`GameEvent` 和日志。

当前注册的主要 Handler 覆盖：入场、盖角色牌、使用角色牌、部署、调度、探索、移动、建设、设施待选、宣告样式、采集和结束行动。

### 17.3 查询服务

Application/Domain 中还存在面向 UI 的只读查询，如建设选项、角色选项、采集选择。设计原则是“UI 可提前知道哪些目标合法，但正式提交仍由领域服务重验”。

### 17.4 Host 权威分发

`AuthoritativeCommandDispatcher`：

- 保存网络连接到玩家 ID 的映射；
- 拒绝 Client 代替其他玩家提交命令；
- Host 成功结算后分配严格递增确认序号；
- Client 只接受连续序号；
- 序号断档时要求重新同步初始/完整状态；
- Client 未完成初始快照前不能应用确认命令。

### 17.5 自动跑局

`LocalhostAutoplayRunner` 直接复用正式 Session 和 Handler，使用固定玩家、seed 和策略跑到第 8 回合结算。它覆盖入场、事件、移动、调度、建设/部署、设施待选、采集、路费接收和最终计分，用于发现跨模块死锁，而不只是验证单个函数。

## 18. Presentation 层模块

### 18.1 总控制器与适配器

`MobileCityInteractionController` 是对局场景组合控制器，主要保留：

- Unity 生命周期；
- 序列化场景引用；
- 创建 Session、服务、Presenter 和弹窗；
- 转发地图点击；

它不应直接写规则。`MobileCityGameplayAdapter` 向纯 C# 工作流暴露当前状态、当前本地玩家和提交命令能力；`MobileCityWorkflowViewAdapter` 把纯接口转换成 Unity 高亮、弹窗、提示和刷新调用。

### 18.2 工作流状态机

`YC.Presentation.Workflows` 不依赖 Unity，核心包括：

- `InteractionFlowCoordinator`：同一时间只允许一个主动工作流；

- `ExplorationEventPresenter`：目标、路径、路费、事件选项和事件影响力目标；

- `BuildFacilitySelectionController`：建设拖放草稿；
- `CharacterMapInteractionCoordinator`：角色牌多步地图目标；
- 多个小型 SelectionController：只维护选择状态，不接触 GameObject。

`WorkflowHighlight` 不直接指定颜色，而是传“目标类型 + 语义”。Unity 适配器再决定具体视觉样式。

### 18.3 行动面板

`ActionPanelController` 根据 `ActionPanelViewModel` 显示：

- 快速行动：移动城市、角色策略/计谋、宣告样式；

- 特殊行动占位；
- 完成行动和状态提示。

面板以及许多弹窗由 C# 在运行时创建 uGUI 对象，不依赖大量预制体。

### 18.4 信息、牌区与弹窗

- `ExpandableInfoPanel`：玩家概览、资源、城市、行动和角色手牌/弃牌；
- `BuildInfoPanel`：建设供应、玩家 3×4 城市面板和牌图；
- `EventChoiceDialog`：探索/入场事件、路径和支付选择；

## 19. 联机基础设施模块

### 19.1 三种启动模式

| 模式 | 房间/身份 | Mirror Transport | 规则执行位置 |
|---|---|---|---|
| 单机 | 无 | 不启动 | 本地 Session |
| Steam Host/Client | Steam Lobby + SteamID | FizzySteamworks | Host Session |
| 本地多实例 | 自建 TCP 房间 + 随机身份凭据 | Telepathy | Host Session |

### 19.2 房间抽象

`IOnlineRoomService` 统一建房、加房、开始、邀请、房间更新和错误事件。`OnlineRoomServiceProvider` 根据本地测试开关选择 `SteamRoomService` 或 `LocalMirrorRoomService`。

`RoomState` 保存 Host、本地玩家、目标人数、是否开始和稳定席位。每个 `PlayerSeat` 分别记录：

- `LobbyMemberPresent`；
- `TransportConnected`；
- `IdentityVerified`；
- `GameStateSynchronized`；
- `IsReady`。

### 19.3 Steam 房间

`SteamRoomService` 使用 Steam Matchmaking Lobby：

- `gameKey=yc_nomad_city` 过滤其他 AppID 480 项目；
- `protocolVersion=2` 做协议兼容门禁；
- Host 固定占 1 号席位，其余 SteamID 稳定分配；
- Lobby metadata 发布席位和 Host 验证的就绪状态；
- 开局时先关闭继续加入，再把房间状态改为 started；失败会回滚可加入状态。

`MirrorNetworkRuntime` 在正式模式中创建 `NetworkManager + FizzySteamworks`，用 Host SteamID 作为连接地址。

### 19.4 身份与开局门禁

`WaitingRoomConnectionAuthority` 和 `SteamIdentityBindingRegistry` 保证：

- 连接必须对应当前 Lobby 中的唯一身份；
- 一个身份不能绑定多条连接；
- Client 声称的玩家 ID 必须与 Host 计算出的席位一致；
- 断线时立即撤销绑定和就绪状态；
- 所有目标席位、传输和身份都合法后 Host 才能开始。

进入对局后，`MirrorCommandTransport` 会再次依据连接绑定校验命令所有者，不能只依赖等待房间 UI。

### 19.5 本地多实例房间

`NetworkRoomService` 用 TCP `7780-7799` 做房间信令，Telepathy 默认用 TCP `7777` 传游戏消息。Host 为每条房间信令连接签发随机身份票据，Client 把票据呈递给 Mirror；Host 验证后才绑定模拟身份和稳定席位。

这样可以防止本地 Client 只修改裸 `PlayerId` 冒充其他玩家。信令断开会撤销票据；Mirror 单独重连可在同一信令会话内恢复席位。

### 19.6 命令和快照同步

`MirrorCommandTransport` 定义提交、接受、拒绝、初始状态请求、初始状态和应用确认消息：

```text
Client GameCommand
-> SubmitCommandMessage
-> Host 身份检查
-> AuthoritativeCommandDispatcher
-> Host GameSession.Submit
-> AcceptedCommandMessage(sequence + command + full state)
-> Client 检查连续序号并 ReplaceState
```

优点是实现简单、断档后易重同步；代价是每个成功命令都发送完整状态，数据量随对局增长，并且当前快照包含所有玩家状态，尚未做按玩家裁剪的隐藏信息同步。

### 19.7 当前联机边界

- 没有 Host 迁移；Host 离开即结束房间。
- 没有专用服务器。
- 自动化测试不能替代多 Steam 账号、真实 NAT、P2P/Relay 和连接抖动验收。

## 23. 关键设计取舍与风险

### 23.1 优点

- 规则层无 Unity 依赖，测试速度快；
- 单机/联机只维护一套规则；
- 地图拓扑与表现坐标解耦；
- 待选状态显式进入 `GameState`，可跨网络和 UI 刷新；
- 多步复杂效果使用投影或原子操作，减少半结算；
- UI 合法查询和领域最终校验双层保护；
- Host 同时校验房间身份和命令身份。

### 23.2 需要警惕的点

- `GameState` 公开可变，新增代码若绕过 Handler 会破坏不变量；
- 多种待选状态并存，兼容层增加了分派复杂度；
- `ResolvePendingChoice` 由多个 Handler 共同竞争，新增处理器要遵守“不是自己的待选应允许继续分派”的约定；
- `PhaseFlow` 与实际 Handler 推进并存，未来应避免两套阶段真源漂移；
- 部分 UI 类体积仍大，特别是探索 Presenter 和大型运行时面板；
- 全量状态快照简单但不节省带宽，也不能真正保护隐藏信息；
- 运行时 `File.ReadAllText` 的 StreamingAssets 方案偏桌面平台；
- 事件牌和城市样式仍硬编码在 C#，规则数据扩充会提高代码变更频率；
- 文档很多，历史记录可能滞后，判断能力是否完成时必须看 Bootstrap 是否注册 Handler、是否有状态字段、是否有测试和实际 UI 入口。

## 24. 推荐阅读顺序

如果希望真正掌握项目，建议按以下顺序阅读源码：

1. `Domain/State/GameState.cs`：知道系统保存了什么；
2. `Domain/Commands/GameCommand.cs` 与 `GameEnums.cs`：知道玩家能提交什么；
3. `Application/Sessions/GameSession.cs`：理解命令如何分发；
4. `Presentation/GameSessionBootstrapper.cs`：看到整套服务如何组装；
5. `RoundAdvanceService.cs`：理解阶段推进；
6. 选择一条简单链路，如部署影响力，读 UI Presenter → Handler → Domain Service；
7. 再读探索或建设，理解路径、支付和待选会话；
8. 读 `AuthoritativeCommandDispatcher` 与 `MirrorCommandTransport`，理解联机只是命令入口和状态同步；
9. 最后读对应测试，确认规则边界和失败路径。

最适合作为第一条完整追踪链的是“部署影响力”：

```text
ActionPanelController
-> TurnActionPresenter.BeginDeployAction
-> InfluenceActionPresenter
-> GameCommand(DeployInfluence)
-> CommandSubmissionController
-> DeployInfluenceCommandHandler
-> InfluenceService / InfluencePlacementRule
-> GameState.Map.Influences
-> MapViewPresenter.RefreshInfluenceDisplay
```

掌握这条链后，再看探索、建设和联机，会容易很多。
