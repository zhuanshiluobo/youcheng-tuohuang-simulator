# GitHub 进度管理草案

本文件用于在远端仓库创建前先固化项目管理结构。创建 GitHub 仓库后，可将下列条目逐项转为 milestones 与 issues。

## Milestones

### M0 - 规则核心地基

目标：建立纯 C# 规则核心的基础目录、程序集边界、基础类型、`GameState`、命令/事件/校验结果契约和最小测试框架。

### M1 - 地图与费用规则

目标：把三人和四人地图转为结构化图模型，完成邻接、路径、路费、区控相关查询。

### M2 - 阶段状态机与命令流水线

目标：实现 `Setup -> Entrance -> RoundStart -> CharacterCover -> ActionRound1 -> ActionRound2 -> ResourceCollection -> Cleanup -> FinalScoring -> GameOver` 的固定流程，以及统一命令提交、校验、结算和日志。

### M3 - MVP 主要行动闭环

目标：实现入场、部署、调度、探索、城市移动、建设、采集、收尾、最终计分，让一局基础版可从开局跑到结算。

### M4 - 卡牌与效果系统

目标：接入角色牌、事件牌、设施牌、城市样式、快速行动窗口和通用效果执行器。

### M5 - Debug UI、回放与验收

目标：提供最小可用热座 Debug UI、日志面板、回放能力、golden case 和规则回归测试。

## 首批 Issues

### 1. 建立 Unity 程序集与目录边界

- 创建 `Assets/YC/Domain`、`Application`、`Infrastructure`、`Presentation`、`Data`、`Tests`。
- 增加 Assembly Definition，确保 `Domain` 不依赖 `UnityEngine`。
- 定义命名规范和模块依赖方向。

验收标准：
- Unity 可正常刷新工程。
- `Domain` 程序集可独立编译。
- 目录依赖符合 README 架构原则。

### 2. 定义基础类型与 `GameState`

- 定义资源类型、玩家颜色、阶段、行动轮次、地图元素类型、卡牌类型、错误码。
- 定义 `GameState`、`PlayerState`、`BoardState`、`DeckState`、`PendingChoice`。
- 保证状态对象可序列化。

验收标准：
- 能创建 3 人或 4 人初始状态。
- JSON 序列化与反序列化后关键字段保持一致。
- 资源和影响力数量不出现非法负数。

### 3. 建立命令、事件与校验结果契约

- 定义 `IGameCommand`、`ValidationResult`、`CommandResult`、`GameEvent`。
- 定义非法命令不修改状态的约束。
- 建立命令日志结构。

验收标准：
- 至少有一个示例命令可以走完整 submit 流程。
- 非法命令返回明确原因。
- 合法命令生成可读日志。

### 4. 录入三人和四人地图图模型

- 定义 `MapDefinition`、`ResourceNodeDefinition`、`RouteDefinition`、`RegionDefinition`。
- 手工录入三人图和四人图的节点、航道、区块。
- 地图图片只作为表现层底图，不参与规则判断。

验收标准：
- 能查询任意资源点相邻点。
- 能判断两个资源点之间是否存在航道。
- 能列出资源点所属区块。

### 5. 实现路径搜索与路费计算

- 实现探索、采集、城市移动所需路径枚举。
- 实现航道影响力相关支付对象选择。
- 实现采集阶段同一航道只支付一次路费的规则。

验收标准：
- 路径和费用计算有成功/失败单元测试。
- 对手影响力支付对象可追踪。
- 采集阶段不能使用本阶段刚获得的金券支付路费。

### 6. 实现阶段状态机

- 实现基础版固定阶段流。
- 支持 8 回合后进入最终计分。
- 每回合包含两轮玩家行动。

验收标准：
- 状态机只暴露当前阶段允许命令。
- 起始玩家按规则传递。
- 阶段推进可被日志和测试验证。

### 7. 实现五个主要行动

- 部署、调度、探索、城市移动、建设。
- 每个行动拆分 validator 和 resolver。
- 每个行动记录费用、资源、影响力和事件变化。

验收标准：
- 每个主要行动至少有 1 个成功测试和 1 个失败测试。
- 非法行动不修改 `GameState`。
- 日志能解释关键结算。

### 8. 实现采集、收尾与最终计分

- 采集资源、收尾效果、城市样式标记复位、回合推进。
- 区控、剩余资源、设施、城市样式、平局判定。

验收标准：
- 一局 8 回合可以进入 `GameOver`。
- 最终分数输出明细。
- 平局依次比较剩余金券和剩余至纯源石，仍相同则共同胜利。

### 9. 建立日志、回放与 Debug 对局驱动

- 实现 `GameSession.Submit(command)` 主入口。
- 记录命令、事件、费用、得分来源。
- 支持按命令序列重放对局。

验收标准：
- 同一命令序列重放得到一致最终状态。
- Debug 驱动能跑通最小对局片段。
- 日志可供 UI 展示。

### 10. 最小热座 UI

- 地图底图、玩家资源面板、行动面板、费用预览、非法原因提示、日志面板。
- UI 不直接写 `GameState`，只提交命令。

验收标准：
- 3 到 4 人可在本地热座操作。
- 关键操作确认前显示费用和影响。
- 非法操作显示具体原因。

## 多 Agent 分工建议

- 主控 Agent：维护目录、契约、依赖边界、集成节奏和验收标准。
- 地图 Agent：地图数据、路径搜索、路费、区控。
- 状态机 Agent：阶段流、命令系统、校验/结算骨架。
- 核心玩法 Agent：入场、五个主要行动、采集、收尾、计分。
- 卡牌 Agent：角色、事件、设施、城市样式与效果系统。
- UI/工具 Agent：`GameSession`、日志、回放、Debug UI、最终桌面 UI。
