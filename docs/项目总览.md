# 游城拓荒 2D Unity 模拟器项目总览

本文是项目设计资料的总入口。原有目标、MVP、架构、技术路线、模块拆分、数据、测试和扩展计划中的重复内容已集中到本文；各专题文档只保留差异化补充。

## 1. 项目定位

《游城拓荒：铸基者》2D Unity 模拟器优先服务于基础版规则模拟。当前目标不是完整复刻实体桌游美术，而是把规则转化为可运行、可验证、可扩展的数字规则系统。

当前阶段面向本地 PC 热座，先支持 3 到 4 人基础版游戏。后续再扩展正式桌面 UI、AI、联网、企业扩展版和更完整的视听表现。

## 3. MVP 范围

MVP 必须能用占位界面或 Debug 工具跑通一局基础版 3 到 4 人热座游戏，并输出可复查的结算明细。

必须包含：

- 开局入场。
- 基础版三人/四人地图图模型。
- 8 回合固定状态机。
- 每回合角色牌盖放、两轮玩家行动、采集、收尾。
- 部署、调度、探索、城市移动、建设。
- 快速行动、角色牌、城市样式的最小接入点。
- 资源采集、最终计分和平局判定。
- 命令、事件、日志、基础回放。
- EditMode 单元测试和关键流程测试。

暂缓内容：

- 完整动画、音效、高完成度牌面。
- AI、联机、企业扩展版。
- 完整新手引导。
- 地图热点编辑器和卡牌收藏浏览器。

## 4. 分层架构

```text
Presentation / Unity UI
  -> Application / GameSession
    -> Domain / Rule Engine
Application -> Infrastructure
Domain / Infrastructure -> Data
```

当前 Unity 工程使用下列目录：

```text
Assets/YC/
  Domain/
    Commands/
    Economy/
    Effects/
    Events/
    Facilities/
    Harvest/
    Maps/
    Rules/
    Scoring/
    State/
  Application/
    Gameplay/
    Logging/
    Sessions/
    Setup/
  Infrastructure/
    Replay/
  Presentation/
  Data/
    Covers/
    Maps/
  Editor/
  Tests/EditMode/
```

分层职责：

- `Domain`：纯 C# 规则核心，不引用 `UnityEngine`。
- `Application`：一局游戏生命周期、命令提交、日志、回放、存档协调。
- `Presentation`：Unity 显示与交互，只读取状态并提交命令。
- `Infrastructure`：存档、回放序列化、数据加载、Debug 工具。
- `Data`：地图、卡牌、效果、计分、图标和图片引用。
- `Tests`：规则单元测试、状态机测试、命令测试、回放测试。

## 5. 核心规则流程

基础版固定阶段：

```text
Setup
-> Entrance
-> RoundStart
-> CharacterCover
-> ActionRound1
-> ActionRound2
-> ResourceCollection
-> Cleanup
-> RoundStart 或 FinalScoring
-> GameOver
```

阶段要点：

- `Setup`：创建玩家、选择地图、准备牌堆与供应区。
- `Entrance`：决定起始玩家、选择初始资源点、放置移动城市、结算入场事件。
- `RoundStart`：设置本回合起始玩家并重置回合状态。
- `CharacterCover`：每名玩家盖放 1 张角色牌。
- `ActionRound1/2`：每轮从起始玩家开始，每名玩家执行快速行动窗口、1 个主要行动、快速行动窗口。
- `ResourceCollection`：玩家选择可采集资源点并支付连接路费。
- `Cleanup`：结算收尾效果、复位标记、传递起始玩家、推进回合。
- `FinalScoring`：区控、剩余资源、设施、城市样式和平局判定。

## 6. 命令流水线

所有玩家操作都必须通过命令系统：

```text
UI / Debug / AI
-> GameSession.Submit(command)
-> Validate
-> Resolve
-> Mutate GameState
-> Emit GameEvent
-> Append Log
-> Refresh Presentation
```

约束：

- 非法命令返回明确原因，不修改 `GameState`。
- 合法命令只通过 handler/resolver 修改状态。
- `PendingChoice` 必须写入 `GameState`，直到玩家提交选择结果。
- UI、AI、联网都不能绕过命令校验。

必备命令：

- 选择起始玩家、选择初始资源点、结算入场事件。
- 盖放角色牌。
- 部署、调度、探索、城市移动、建设。
- 使用角色牌、宣告城市样式、使用特殊行动。
- 采集资源、处理待选择项、结束行动。

## 7. 地图、路径与费用

地图必须是结构化图模型，图片只作为表现层底图。

结构化数据：

- 资源点：id、颜色、区块、资源槽、影响力槽、事件槽、是否可停靠城市。
- 航道：id、起点、终点、影响力槽、费用属性。
- 区块：id、颜色或区域类型、包含资源点、计分值。
- 地图面：三人地图、四人地图和适用玩家数。

服务边界：

- `IMapQueryService`：相邻点、航道、区块、停靠点查询。
- `MapPathSearchService`：最短路径和有限步数内简单路径枚举。
- `TravelCostService`：路径费用与城市移动基础费用入口。
- 后续补 `RegionControlService`：区控统计、移动城市按 2 影响力计入、区块给分。

当前地图定义仍是 placeholder，真实节点、航道、区块和费用需要从地图图面与规则书手工录入。

## 8. 数据与素材路线

数据优先级：

1. 地图规则数据：节点、航道、区块、初始可选点、槽位、停靠点。
2. 基础资源与图标映射：金券、源岩、源石、异铁、至纯源石、VP、行动图标。
3. 卡牌定义：角色、事件、设施、城市样式。
4. 效果定义：触发器、条件、费用、操作。

命名规范：

- 规则 id 使用英文稳定 id，例如 `map_four_players`、`facility_core_command_tower`。
- 中文名放入 `displayName` 或等价字段。
- 图片文件可保留中文名，但规则数据引用稳定 id。
- 地图节点建议使用区域加序号，例如 `B-01`。
- 航道建议使用两端节点组合，例如 `B-01_B-02`。

## 9. 测试与验收

测试分层：

- `Domain` 单元测试：资源、影响力、地图查询、路径、费用、行动校验、效果、区控、计分。
- `Application` 流程测试：`GameSession`、命令流水线、阶段推进、入场、回合、采集、GameOver。
- 回放测试：固定 seed 和命令序列得到固定最终状态。
- 随机模拟测试：随机合法命令序列不产生非法资源、影响力丢失或状态机卡死。

MVP 完成定义：

- 可创建 3 到 4 人基础版游戏。
- 可从开局入场推进到最终计分。
- 五个主要行动可用。
- 快速行动和效果系统有最小可用接入。
- 采集、收尾、计分可测试。
- 操作日志完整。
- 至少一条 golden case 可重放。
- 核心规则测试通过。

## 10. 多 Agent 开发顺序

推荐按波次推进：

1. 第 0 波：主控契约，目录、程序集、基础类型、`GameState`、命令、事件、返回结果。
2. 第 1 波：地图规则基础与状态机/命令流水线并行。
3. 第 2 波：开局入场、五个主要行动、采集、收尾、计分。
4. 第 3 波：`GameSession`、日志、回放、Debug 驱动。
5. 第 4 波：卡牌与效果系统。
6. 第 5 波：正式 UI。

并行约束：

- 每个 worker 必须有明确写入范围。
- 地图、状态机、核心玩法、卡牌、UI 的写入目录要分开。
- 新增规则至少配 1 个成功测试和 1 个失败测试。
- 不回滚他人改动，不批量删除文件。

## 13. 后续扩展

不进入 MVP 阻塞链路，但保留结构空间：

- 完整桌面 UI：地图热点、玩家面板、行动面板、费用预览、日志面板。
