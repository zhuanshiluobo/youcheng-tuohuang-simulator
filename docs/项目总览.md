# 游城拓荒 2D Unity 模拟器项目总览

本文是项目设计资料的主入口和人工维护的事实源。若与旧工作记录或临时方案文档冲突，以本文和最新工作记录为准。

## 1. 项目定位

《游城拓荒：铸基者》2D Unity 模拟器优先服务于基础版规则模拟。当前目标不是完整复刻实体桌游美术，而是把规则转化为可运行、可验证、可扩展的数字规则系统。

当前阶段仍以本地 PC 热座和基础版规则闭环为主，先支持 3 到 4 人基础版游戏。同时项目已有 Unity 官方联网栈、Host 权威命令传输和快照同步 MVP 原型；联网继续作为扩展验证路径，不阻塞基础规则闭环。

## 3. 当前闭环状态

- 建设已经落地：`BuildFacilityCommandHandler` 与 `BuildFacilityService` 已接通设施供应校验、唯一设施限制、城市面板槽位、资源/金券支付、建成奖励与得分；`BuildFacilitySelectionController` 与 `EventChoiceDialog.ShowBuildFacilityOptions(...)` 已接入表现层弹窗。
- 采集已经落地：`CollectResourceCommandHandler` 与 `ResourceCollectionService` 已接通显式 `routeIds`、共享航道路费、接收方指定和采集阶段推进。
- 收尾推进已经落地：第 2 行动轮结束后进入 `ResourceCollection`，全部玩家采集完成后进入 `Cleanup`，再推进到下一回合或 `FinalScoring`。
- 最终计分已经落地基础闭环：`FinalScoringService` 当前结算 `BaseScore + RegionScore + ResourceScore + FacilityScore + CityStyleScore`，并按剩余金券、剩余至纯源石处理平局；设施分会从已建设施牌面分拆出，城市样式分按正式宣告记录结算。
- 城市样式宣告已形成最小闭环：`DeclareCityStyleService` 与 `CityStylePatternMatcher` 会校验样式存在、未重复宣告、影响力供应、设施类型和城市面板槽位条件，`DeclareCityStyleCommandHandler` 写回 `GameState.DeclaredCityStyleIds` 与宣告使用槽位；`宣告样式` UI 可展示可宣告样式、不可宣告原因并提交命令。
- 仍是占位的按钮与区域：`使用角色牌`、`特殊行动` 当前只提示“暂未实现”；`GameSettingsMenuController` 的设置菜单主体区域已承载规则书入口，更多音量、画面等设置项仍待扩展。
- 字体开发态诊断入口已接入：`FontUtility` 现在除了被动 30 秒巡检外，还支持手动执行一次字体健康检查并输出托管字体、关联 `Text`、材质与纹理状态快照；开发者可通过 Editor 菜单或命令行参数主动触发，并可模拟一次托管字体重建路径。
- 自动跑局当前覆盖：固定四席位、固定初始点、入场默认选项、建设或部署主行动、当前城市资源点采集、收尾推进与最终计分；不覆盖探索、城市移动、调度、特殊行动或付费扩路采集。

- 两轮玩家行动、采集阶段、回合推进与最终计分基础结算。
- 部署、调度、探索、移动城市、建设。
- EditMode 单元测试与关键流程测试。

当前仍阻塞 MVP 完整闭环的部分：

- `使用角色牌`、`特殊行动`。

## 5. 核心规则流程

基础版固定阶段：

```text
Setup
-> Entrance
-> RoundStart
-> CharacterCover
-> ActionRound1
-> ActionRound2
-> ResourceCollection
-> Cleanup
-> RoundStart 或 FinalScoring
-> GameOver
```

阶段要点：

- `Setup`：创建玩家、选择地图、准备牌堆与供应区。
- `Entrance`：决定起始玩家、选择初始地块、放置移动城市、处理入场默认选项。
- `RoundStart`：设置本回合起始玩家并重置回合状态。
- `CharacterCover`：每名玩家盖放 1 张角色牌。
- `ActionRound1/2`：每轮从起始玩家开始，每名玩家执行快速行动窗口、1 个主要行动、快速行动窗口。
- `ResourceCollection`：玩家选择可采集资源点并支付连接路费。
- `Cleanup`：当前已负责阶段推进；独立收尾效果仍待扩展。
- `FinalScoring`：当前结算基础分、区控分、资源分、设施分、城市样式分与平局判定。

## 6. 分层架构

```text
Presentation / Unity UI
  -> Application / GameSession
    -> Domain / Rule Engine
Application -> Infrastructure
Domain / Infrastructure -> Data
```

当前 Unity 工程主要目录：

```text
Assets/YC/
  Domain/
    Commands/
    Economy/
    Effects/
    Events/
    Facilities/
    Harvest/
    Maps/
    Rules/
    Scoring/
    State/
  Application/
    Gameplay/
    Logging/
    Sessions/
    Setup/
  Infrastructure/
    Replay/
  Presentation/
  Data/
  Editor/
  Tests/EditMode/
```

分层职责：

- `Domain`：纯 C# 规则核心，不引用 `UnityEngine`。
- `Application`：一局游戏生命周期、命令提交、阶段推进、日志与联机协调。
- `Presentation`：Unity 显示与交互，只读取状态并提交命令。
- `Infrastructure`：房间、快照同步、回放与后续存档扩展。
- `Data`：地图、卡牌、图标和图片引用。
- `Tests`：规则单元测试、状态机测试、命令测试与流程测试。

## 9. 测试与验收口径

统一使用仓库脚本运行 Unity EditMode 测试：

```powershell
powershell -ExecutionPolicy Bypass -File .\tools\Run-EditModeTests.ps1
```

常用过滤示例：
```powershell
powershell -ExecutionPolicy Bypass -File .\tools\Run-EditModeTests.ps1 `
  -TestFilter "YC.Tests.EditMode.LocalhostAutoplayRunnerTests"
```

字体自检最小回归：
```powershell
powershell -ExecutionPolicy Bypass -File .\tools\Run-FontHealthCheckValidation.ps1
```
当前环境限制：同一个 Unity 项目仍不能同时被多个 Editor 或 batchmode 实例打开；脚本会提示，但不会自动结束已有进程。

UI 诊断日志：

- 流程文档：`docs/UI诊断日志流程.md`
- 运行时录入：`YC.Presentation.UiDiagnosticLog.Record(...)`
- Editor 导出：`YC / Dev / UI Diagnostics / Export Snapshot`
- Editor 读取：`YC / Dev / UI Diagnostics / Read Latest Snapshot`
- 日志目录：`Application.persistentDataPath/YCDiagnostics`

UI 渲染类问题后续修改前，应先按该流程采集一次结构化日志，再根据日志修改。
