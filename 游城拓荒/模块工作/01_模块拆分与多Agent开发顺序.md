# 模块拆分与多 Agent 开发顺序

## 1. 文档目标

本文档用于把《游城拓荒：铸基者》2D Unity 模拟器的开发模块进一步工程化整理，明确：

- 项目需要哪些核心模块。
- 模块之间的依赖关系。
- 单人推进时的开发优先级。
- 多 Agent 并行开发时的推荐分工与顺序。

本文件是 `yc_plan_docs` 中总体目标、MVP、架构、数据和测试计划的补充工作文档，供后续实施、分工和追踪使用。

## 2. 模块总览

建议按六层结构拆分模块。

### 2.1 规则基础层

- `基础类型模块`：资源类型、玩家颜色、阶段枚举、地图元素类型、卡牌类型、错误码。
- `GameState 模块`：整局状态、玩家状态、地图状态、牌堆状态、设施状态、待选择状态。
- `规则事件模块`：命令结算后产生的事件结构。
- `序列化模块`：状态、命令、事件和回放数据的编码与恢复。

### 2.2 地图与数学规则层

- `地图数据模块`：三人图、四人图、资源点、航道、区块、停靠点等结构化定义。
- `地图查询模块`：相邻查询、航道查询、区块归属、合法停靠点查询。
- `路径搜索模块`：探索、采集、城市移动所需路径枚举。
- `路费计算模块`：探索路费、采集路费、支付对象选择、重复支付规则。
- `区控计算模块`：区块控制、影响力统计、城市按 2 影响力计入等规则。

### 2.3 回合与命令层

- `阶段状态机模块`：`Setup -> Entrance -> RoundStart -> CharacterCover -> ActionRound1 -> ActionRound2 -> ResourceCollection -> Cleanup -> FinalScoring -> GameOver`。
- `命令定义模块`：统一表示玩家操作。
- `命令校验模块`：判断命令是否合法并返回明确原因。
- `命令结算模块`：合法命令修改状态、生成事件、记录结果。
- `待选择项模块`：处理中途支付对象、路径、效果分支等选择。

### 2.4 玩法子系统层

- `开局入场模块`
- `角色盖放模块`
- `主要行动模块`：部署、调度、探索、城市移动、建设。
- `快速行动模块`
- `抽卡/弃牌/补牌模块`
- `事件结算模块`
- `设施建设模块`
- `城市样式模块`
- `资源采集模块`
- `最终计分模块`

### 2.5 应用编排层

- `GameSession 模块`：整局游戏运行入口。
- `日志模块`：命令、事件、费用、得分来源记录。
- `回放模块`：按命令序列重放对局。
- `存档模块`：保存和恢复对局状态。
- `合法命令枚举模块`：为 UI、AI、Debug 提供可执行操作集合。
- `Debug 对局驱动模块`：在正式 UI 完成前用于跑通整局。

### 2.6 表现层

- `地图显示模块`
- `玩家面板模块`
- `行动面板模块`
- `费用预览模块`
- `非法原因提示模块`
- `日志与回放界面模块`

## 3. 核心依赖关系

推荐按下面这条主依赖链理解项目结构：

`基础类型 / GameState`
-> `地图服务`
-> `命令与状态机`
-> `核心行动`
-> `采集与计分`
-> `日志回放`
-> `卡牌效果`
-> `正式 UI`

其中必须优先稳定的底层接口有：

- `GameState`
- `IGameCommand`
- `ValidationResult`
- `CommandResult`
- `GameEvent`
- `PendingChoice`
- 地图节点、航道、区块 id 命名规则
- 卡牌与效果数据结构

如果这些接口没有先统一，多人并行开发时会出现大量返工。

## 4. 单线开发优先级

如果按一条主线顺序推进，建议开发顺序如下：

1. `基础类型 + GameState + 序列化`
2. `地图数据 + 地图查询 + 路径搜索 + 路费计算`
3. `阶段状态机 + 命令接口 + 校验/结算骨架`
4. `开局入场 + 五个主要行动`
5. `资源采集 + 收尾 + 最终计分`
6. `抽卡/角色/事件/设施/城市样式 + 效果系统`
7. `GameSession + 日志 + 回放 + Debug 对局工具`
8. `正式 UI`

这个顺序的目标是：在正式 UI 尚未完成前，也能先把一整局基础版规则跑通。

## 5. 多 Agent 推荐分工

建议使用 `1 个主控 Agent + 5 个功能 Agent`。

### Agent 0：主控与集成

职责：

- 定义目录结构、程序集边界和命名规范。
- 定义统一核心接口和基础数据结构。
- 管理合并节奏、冲突处理和回归检查。
- 维护开发顺序、依赖清单和验收口径。

最重要的工作不是写最多代码，而是先把所有 Agent 共用的契约定住。

### Agent 1：地图与规则基础

职责：

- 建立三人图、四人图结构化地图数据。
- 提供节点、航道、区块、停靠点等查询能力。
- 实现路径搜索、路费计算、区控服务。

依赖：

- 依赖 Agent 0 已定义基础类型和地图数据接口。

### Agent 2：状态机与命令流水线

职责：

- 实现阶段状态机。
- 定义命令接口、校验器、resolver 骨架。
- 实现非法原因结构与待选择项结构。

依赖：

- 依赖 Agent 0 已定义 `GameState`、`IGameCommand`、`GameEvent` 等基础契约。

### Agent 3：核心玩法

职责：

- 实现开局入场。
- 实现部署、调度、探索、城市移动、建设。
- 实现采集、收尾、最终计分。

依赖：

- 依赖 Agent 1 的地图与费用服务。
- 依赖 Agent 2 的命令与状态机骨架。

### Agent 4：卡牌与效果

职责：

- 实现抽卡、弃牌、补牌。
- 实现角色牌、事件牌、设施牌、城市样式牌。
- 实现通用效果系统和必要的特殊规则处理器。

依赖：

- 依赖 Agent 2 的命令系统。
- 依赖 Agent 3 的基础玩法入口和触发时机。

### Agent 5：应用、工具与 UI

职责：

- 实现 `GameSession`、日志、回放、存档。
- 搭建 Debug 对局驱动与最小可用界面。
- 在后期接手正式地图交互和玩家界面。

依赖：

- 前期依赖 Agent 0 的接口定义即可启动框架工作。
- 中后期依赖 Agent 2、Agent 3、Agent 4 的规则能力逐步接入。

## 6. 多 Agent 开发波次

建议按波次推进，而不是让所有 Agent 同时无序开工。

### 第 0 波：主控 Agent 先行

目标：

- 建立项目目录与程序集边界。
- 定义统一核心接口。
- 输出命名规范、数据结构和协作约束。

交付物：

- 基础类型草案。
- `GameState` 结构草案。
- 命令、事件、待选择项、返回结果结构草案。
- 模块依赖表。

### 第 1 波：Agent 1 与 Agent 2 并行

目标：

- 完成地图图模型与服务层基础。
- 完成状态机与命令流水线骨架。

交付物：

- 可加载的三人图与四人图结构数据。
- 地图查询接口。
- 状态机基础实现。
- 命令校验与结算骨架。

### 第 2 波：Agent 3 启动

目标：

- 把基础版核心行动和入场流程做通。
- 建立从开局到收尾的核心规则闭环。

交付物：

- 五个主要行动可用。
- 入场流程可用。
- 采集、收尾、最终计分可用。

### 第 3 波：Agent 5 启动整局驱动

目标：

- 把整局驱动、日志、回放和最小调试入口接起来。

交付物：

- `GameSession.Submit(command)` 主入口。
- 日志记录。
- 回放基础能力。
- Debug 操作工具或最简操作面板。

### 第 4 波：Agent 4 深入接卡牌与效果

目标：

- 在闭环规则基础上，把角色牌、事件牌、设施牌、城市样式和快速行动补齐。

交付物：

- 通用效果执行器。
- 基础牌堆流程。
- 最小可用卡牌规则集。

### 第 5 波：Agent 5 转向正式 UI

目标：

- 在规则稳定后补地图交互、玩家面板、行动面板、费用预览和日志界面。

交付物：

- 可玩桌面界面。
- 费用和非法原因可视化。
- 回放与日志界面。

## 7. 多 Agent 协作约束

为了降低并行开发的冲突，建议统一以下规则：

- 所有规则状态只能通过命令结算修改。
- Presentation 不直接写 `GameState`。
- 所有随机数必须来自统一 seed 或统一随机服务。
- 所有新增规则必须至少配 1 个成功测试和 1 个失败测试。
- 地图与卡牌规则尽量数据化，特殊规则单独挂 resolver 或 handler。
- 日志结构保持稳定，便于回放、调试和后续 AI 接入。

## 8. 精简版人员配置建议

如果可用 Agent 数量不足，可以收缩为 `3 Agent` 模式：

- `Agent A`：基础类型、地图、路径、费用、区控。
- `Agent B`：状态机、命令系统、核心行动、采集、计分。
- `Agent C`：日志、回放、Debug UI、卡牌效果接入。

此时仍建议保留一个“主控角色”，负责接口收口和集成验收。

## 9. 当前建议结论

当前阶段最适合优先启动的不是 UI，而是以下三块：

1. `基础状态与接口定义`
2. `地图与费用规则`
3. `状态机与命令流水线`

这三块一旦稳定，后续核心行动、卡牌效果、日志回放和正式 UI 都会顺很多。
