# 企业家逐效果页面流程

**状态：实装方案，尚未实施。更新日期：2026年10月19日。**

五位企业家的逐效果页面流程统一在本文件维护，覆盖艾格尼丝、蒂亚戈、保罗、马丁、第五号的5张能力牌、40个回合抉择面，以及马丁提示卡和三色设施。每条效果说明来源、入口、页面步骤、回答者、提交后的状态和完成边界。卡面文字及组合式仍以[卡面效果与Effect式](卡面效果与Effect式.md)为索引，组件图片见[素材清单](素材清单.md)。

以下是页面行为与内容编排规格，不表示已实现的API或界面。`FundInvestment`、图纸交换、分层查询及终局修正等名称中的规格伪式不能直接当作Lua函数调用。文末分别列出现有Lua能组合的部分、必须补充的通用内核接口和待裁定规则。

## 共用页面与执行约束

五位均沿用[总方案的U01—U17通用页面合同](实装准备与待确认事项.md#页面逐项合同)。房间开启、入场能力牌选人、完整牌组详情、局内能力牌加四回合牌位、未抉择查看全部候选、DIY同回合多选项和正式抉择流程，不按企业家各建一套。U06先保存选面并启用持续规则，再调度独立立即条目；同一条内部按原顺序推进，两个“立即”各有独立节点和完成收据。

| 页面 | 本文件中的用途 |
| --- | --- |
| U04／U05／U07 | 卡牌查看、局内企业家牌列、来源说明与真实库存数量；只读查看不发动能力 |

| U12／U13／U14 | 既有地图操作、企业升级／直接选特效、干员特派 |
| U15／U16／U17 | 收尾顺序与待答义务、终局正式请求与分项、日志与恢复 |

通用完成规则：自动加资源／分数只更新既有数值与日志；没有选择就不造确认页。图标影响力操作沿用内核默认，只有卡面明确写己方、非帮派、资源点等才增加限制。普通效果空集合按既定规则完成，不能因此跳过同条后续兄弟Effect；条件左侧则必须实际完成要求的支付或移除数量，不能把空集合完成当作条件已支付。必选Choice不因某分支空目标而删除该分支；空目标交给所选原语处理。

所有正式请求均保留来源实例／能力／回合、Effect节点、决策玩家和版本；页面关闭、查看卡面及重连不改变规则进度。以下每行完成后均更新U17，涉及资源、标记、牌区或行动次数时同步更新U07、U05及对应入口。全体玩家收尾及响应结束后才复位使用轨道。

**标记返回规则（10月19日用户明确）**：没有写“放回游戏盒”的标记移除／支付，返回该标记所属玩家的玩家供应区；指令、普通声望及第五号能力牌上用于兑换的3枚本人玩家标记均返本人供应。明确回盒的D07快速行动3枚声望永久离开本局。按真实物品转移记录目的区，能力区支付不伪造一次地图影响力离场；地图离场另有合法收容响应时仍先按通用去向流程处理。本规则不把金券等资源支付改成物品区域转移。

**获得指令的Lua封装与数量分支（10月18日最终修订）**：所有取得指令的来源调用同一内容层函数，函数只构造Effect，不直接改资源或物品位置，也不新增内核专用`GainCommand`类型。每次调用读取A01对应的当前有效选择；“第三回合前/后”是官方流程结果，不能替代有效规则查询。按用户最新要求，撤销免费逐枚Choice及付费逐枚条件串，统一为以下结构。名称是规格记法，不是现成Lua API：

```text
未启用加价：
  GainCommand(n) → 一个可放弃的Choice（取得n指令 / … / 取得1指令）
已启用加价且n>1：
  GainCommand(n) → 一个可放弃的Choice（Condition(付2n券,取得n指令) / … / Condition(付2券,取得1指令)）
已启用加价且n=1：
  GainCommand(1) → Condition（付2券,取得1指令）

3B立即② → [可放弃Choice(付8券取4 / 付6券取3 / 付4券取2 / 付2券取1), UpgradeEnterprise(通用企业候选,levels=2)]
Choice等待期间点击“结束行动” → 放弃当前选择，本次取得0枚；没有“不获得指令”效果行
```

免费取得只创建一个可放弃的数量Choice。例如1A/1B立即2指令只列“取得2枚/取得1枚”；选k后固定移入k枚，点击“结束行动”则放弃当前请求，本次不取得。“不获得指令”不是Effect，不声明为0选项、`decline`候选或空效果分支。加价后的多枚取得也只创建一个可放弃Choice，各数量对应自己的条件式；只创建并执行所选条件，不按序执行所有数量，也不在选择k枚后继续询问剩余n−k枚。3B的Choice属于立即②内部，企业升级位于Choice及其全部条件分支之外；放弃选择或放弃所选付款条件均结束本次取得并继续升级，不自动重开数量选择，不结束整轮行动或整个结算窗口。立即①与立即②仍分别记录进度，不合并为一条卡面立即效果。

数量候选按真实供应与通用合法性合同生成和更新，不要求先具备最大n枚或2n金券才能选择较小数量。选定k后，在真正付款前校验足额2k金券及可转移的k枚不同的本人玩家标记；必要的供应/支付依赖沿用等待合同。不能付一部分费用、只移入一部分却记为取得k枚，也不能付款后静默改成较小数量；状态变化导致选项失效时按正式请求校验和刷新处理。所选条件右侧固定转移k枚，不再弹数量或接受确认，不递归调用封装。记录原效果/事件、来源、所选分支及k、支付和转移收据；恢复只继续同一选择的未完步骤，不重复支付、重新选量或发放。免费分支同样复验并一次转移实际所选k枚。

当前Lua已支持`Effect.Choice({options=…,minSelections=0,maxSelections=1,interactionType="effect.choice.execute"})`；执行器由`minSelections=0`生成`AllowDecline=true`的正式请求。`Choice.branches`简写仍拒绝同时声明`minSelections/maxSelections`，不能直接拿它实现上述可放弃Choice，也不能凭空添加`allowDecline`字段。实施采用已有的`options`加结果续接：通过`Effect.WithContext`保存阶段和来源，在本能力内容声明绑定的完成处理器中读取所选`gain_k`，免费时返回固定转移k枚的Effect，加价时返回对应`Condition`；放弃产生空选择结果，处理器返回空效果列表，结束本次取得。若使用`resultContext`，读取结果的`value`，不能把整个结果对象当所选ID。该续接归属当前Choice，完成后才继续同条原效果的后续步骤；不得把3B升级只挂在选中数量的回调路径上。

上述放弃能力无需新增内核或指令姐专用页面。现有[LoadCardMarkers](../../Assets/YC/Domain/Effects/ContentPrimitiveEffectExecutor.cs)仍走数量输入，且载体限角色牌，不能用它代替本次明确要求的Choice候选列表，也不能在付款后再次询问数量。真实物品转移的通用卡载体授权、固定所选数量取得及当次供应校验仍待补齐；这些缺口与Choice是否可放弃分开记录。

共用Lua函数优先与相关处理入口放在同一脚本中，由内容声明绑定入口，避免各张牌复制加价实现。若内容组织确需跨脚本复用，应由冻结内容装配提供显式、可校验的共享源码依赖，并纳入内容版本/哈希；当前宿主禁止`require/loadfile/dofile`，不能把普通`require`写成已支持的实现路径，也不为此开放任意文件加载。

旁路窗口承载现有通用Effect选择与条件支付请求，不新增指令姐专用页面。窗口和响应保留源事件、来源能力、回答玩家及完成收据，重连恢复同一次待决定/待支付响应。原操作是否等待由实际依赖决定：不再一律要求该旁路回答完成才能继续所有原操作；涉及未决响应的必要依赖仍须等待，全体收尾完成与复位也不能漏掉未结清响应。本项只指定3A离场响应的联机路由，不将所有取得指令、其他企业家响应或本地流程一律改成旁路。

当前[旁路响应合同](../../Assets/YC/Domain/Effects/DeferredEventResponseContracts.cs)及[调度实现](../../Assets/YC/Domain/Effects/DeferredResponseScheduling.cs)主要承载离场物品去向，并要求真实保管物品；3A是从玩家供应取得指令，不是收容本次离场的同一枚标记，不能伪造去向/保管关系来接入。实施需核对并补齐通用可选事件响应的旁路合同及自身/他人触发路由，UI仍由正式窗口和Effect请求驱动；不能仅因已有旁路去向机制就宣称3A已接通。

### 5A事件响应与5B通用收尾接入

5A订阅现有`CityMoveCompleted`，不在城市移动按钮、界面刷新或移动内核里直接奖励。当前[CityMoveEffectExecutor](../../Assets/YC/Domain/Effects/CityMoveEffectExecutor.cs)在移动子效果完成后发布事件，含移动玩家、起点、终点及稳定事件ID，并等待响应子效果；[EventCardLuaCatalog](../../Assets/YC/Infrastructure/Lua/EventCardLuaCatalog.cs)已有同事件订阅。5A处理器校验事件玩家为本人、5A来源仍有效，返回“取得2碎片、移动1影响力”的原效果树，以事件＋来源能力防重。两次成功城市移动对应两个事件；预览、取消、未完成移动及普通影响力移动不触发。与事件牌等响应按通用事件顺序调度，不擅自新增“全部事件牌完成后才触发”的时点。

5B用卡牌能力的收尾声明接入既有结算目录：声明来源、`cleanup_order`、每收尾一次、availability和展示元数据，Lua提供`Condition(支付2指令,可放弃Choice(未用战术))`。没有可用战术时，不注入本次结算选项；已有候选变空时通过同一通用资格合同撤去可执行入口并拒绝陈旧提交，不保留一个空的5B选项。战术可用性看启用来源、合法调用资格及未用轨道；不能因为战术内部条件付不起或不想执行，就把该战术排除。

条件左侧支付成功不强制右侧选择：付2指令后仍可在战术Choice用“结束行动”放弃，已付指令不退，不调用任何战术，也不移动任何战术使用标记。选定战术后提交其稳定行动身份给通用行动内核；内核复验并自动移动该战术的共享使用标记，再执行内容。5B的“每收尾一次”由本次收尾条目的受理/结算记录控制，受理后按该条进度执行或放弃，不因放弃右侧或战术条件而重新注入；这是收尾阶段次数，与被调用战术的轨道状态分开。企业家Lua不增加手工消费轨道节点。被调用战术保留自身条件，不另付快速入口2指令、不发特殊入口10金券；内部条件不执行仍算调用了战术。

### PayResource合计资源模式与复合动力迁移（10月19日用户确定）

**统一扩展现有支付资源Effect。** `PayResource`增加“指定资源集合中合计n个”的资源类型选项；Lua只声明资源集合、合计数量及同笔固定费用，由内核生成合法配比、校验并将交互引导到复合动力系统现有的组合付款UI。撤销前版“公开独立组合付款构造器、由D09 Lua枚举完整配比”的方案。内核可复用既有组合付款执行器作为内部实现，但内容入口始终是`Effect.PayResource`。

当前依据：[复合动力系统内容](../../Assets/StreamingAssets/Content/core/city_style/city_style_composite_power_system.json)声明“1碎片及源岩／异铁合计3个”；[样式执行器](../../Assets/YC/Domain/Effects/CityStyleSpecialActionEffectExecutor.cs)专门枚举配比，再交给[ResourcePaymentChoiceEffectExecutor](../../Assets/YC/Domain/Effects/ResourcePaymentChoiceEffectExecutor.cs)。后者支持一般`ResourceSet`候选并复用`ResourceEffectExecutor.ExecutePayment`整笔提交。[现有付款接线](../../Assets/YC/Presentation/SpecialActionInteractionUiCoordinator.cs)通过`ShowPaymentDraft`呈现资源数量行，[SettlementHost](../../Assets/YC/Domain/Effects/SettlementHost.cs)提供`paymentOptions/paymentDraft`及草稿受理。这些是复用基础，新增模式目前尚未实装。

以下字段为拟定扩展合同，示例不是当前可运行Lua；最终接入须同时更新宿主字段、参数归一化、内核校验与内容版本：

| 字段 | 合计资源模式的语义 |
| --- | --- |
| `resourceType = "total"` | 选择“合计资源”支付模式；这是支付选项，不在玩家资源库存中新增名为total的资源，也不扩展为GainResource可取得的资源 |
| `allowedResourceTypes` | 非空、无重复的真实资源类型集合，例如源岩／碎片／异铁，或源岩／异铁；未列资源不能用于该合计部分 |
| `amount = n` | 合计部分必须支付的准确数量，整数且在统一数量上限内；不是每种各n个，也不是至多n个。没有合计部分时使用原固定费用写法 |
| `cost` | 同一笔的固定费用，可省略。最终费用＝固定费用＋玩家选定的合计配比；固定费用不计入n。若固定费用和可选集合包含同类资源，按数量相加，不能重复抵算 |
| `player`、来源及支付规则 | 沿用现有本人支付身份、内容来源、条件上下文和替代支付规则；`allowSubstitution`等既有配置必须传递到实际付款，不能因内部转接丢失 |

```lua
-- 拟定写法：基金投资的金券和三类合计费用属于同一笔。
Effect.PayResource({
    player = ctx.playerId,
    resourceType = "total",
    allowedResourceTypes = { "Originium", "OriginiumShard", "Iron" },
    amount = n,
    cost = { GoldVoucher = gold }
})

-- 拟定写法：复合动力系统，固定1碎片，另付源岩／异铁合计3个。
Effect.PayResource({
    player = ctx.playerId,
    resourceType = "total",
    allowedResourceTypes = { "Originium", "Iron" },
    amount = 3,
    cost = { OriginiumShard = 1 }
})
```

**内核与页面流程**：正式执行PayResource时，读取冻结的资源集合、n及固定费用，生成满足合计要求的费用候选并按现有通用可支付性过滤，直接路由到既有组合付款页。页面按付款投影展示资源数量与固定费用，草稿必须匹配正式候选；最终确认足额支付整笔费用，放弃不付款，费用不足不能进入条件右式。U10／U11分别指该页的付款确认与数量分配职责，不要求额外弹两个确认窗口；也不先用普通Choice选择配比。普通单资源／固定cost付款仍走原合同。

例如基金n=2时，内核可生成三种同类各2、三种两类各1的六个配比，并将固定金券加入每项；这不是Lua生成六个效果选项。原始费用、所选配比和最终支付记录归属同一笔PayResource；即使内部使用子节点，也必须传递同一来源、条件和付款身份，正确将付款成功／放弃／失败反馈给父节点，不能把子节点结束误作条件支付成功。恢复读取已有草稿、选定组合和支付收据，不重新定价或再次扣费。替代支付按整笔实际费用结算，候选与报价不能只看客户端资源；规则禁用替代时须在候选及正式提交两处遵守。

[Lua宿主](../../Assets/YC/Infrastructure/Lua/MoonSharpLuaRuntimeHost.cs)当前`PayResource`未允许`allowedResourceTypes`，而`cost`分支会先进入固定组合校验；[资源执行器](../../Assets/YC/Domain/Effects/ResourceEffectExecutor.cs)也将带cost的节点按固定费用解析。实施须先识别并校验新模式，保留旧单资源和固定cost解析合同，避免只支付cost而漏掉合计部分。还须接好规则条件与付款页的可放弃语义、正式提示、费用预览和请求恢复；不得新增企业家ID或城市样式ID的付款UI分支。

**复合动力系统后续迁移顺序**：先完成通用PayResource模式及付款页接入，再改写复合动力的内容声明／Lua，将上述同一个PayResource放在条件左式，右式沿用既有免费城市移动及移动完成后读取`traversedRouteSlots`放置影响力的流程。迁移时撤掉该样式由`FlexibleOriginiumAndIronCost`及固定费用额外生成付款条件的旧运行路径，预览与激活资格也改用同一通用费用声明，不能保留旧检查与新支付各算一份。更新对应内容合同／硬编码校验及版本；旧存档按原版本恢复或明确迁移，不把进行中的旧节点直接解释为新付款。

现有[复合动力Lua](../../Assets/StreamingAssets/Content/core/lua/city_styles/composite_power_system.lua)只负责移动与其完成续接。加入条件／支付后，完成处理器须按来源节点和阶段区分支付、条件与城市移动结果，只有实际移动结果可提供经过航道；不能将新增付款完成事件误作移动完成。行动入口的授权与使用标记仍归通用行动内核，支付内容迁移不改变卡面费用、移动和放置资格，也不重复消费行动。最后让D09的投资函数使用同一PayResource模式，仅提交动态金券、三类集合与n。

验收覆盖原固定支付不回归、合计1／2／3的不同配比、固定费与合计资源同类相加、资源不足／放弃、陈旧草稿、允许／禁止替代、付款前后恢复及只扣一次。复合动力迁移前后应具有相同合法配比、费用与后续移动／放置结果；基金验证3B＋5A合计2资源及金券整笔提交。源码核查不等于已运行验收；本次仅修订方案。

### 任意次收尾兑换与结算按钮（已确定方案，待实装）

目标是兑换一次后回到U15，让玩家可继续兑换，也可先做基金投资或其他收尾效果再回来；第五号T09的任意次兑换同样适用。不能只在一个兑换段里自动循环或连续弹付款窗口，那样无法自由穿插其他收尾条目。

当前[SettlementEntryService](../../Assets/YC/Domain/Effects/SettlementEntryService.cs)每项`MaxUses=1`，受理后增加`AcceptedUseCount`，完成即标为`resolved`；重复提交同一选项按已有受理处理，恢复校验也只允许一次。[SettlementLuaHost](../../Assets/YC/Infrastructure/Lua/SettlementLuaHost.cs)的Offer同样限制一次，且普通Offer不能直接注册到收尾窗口。普通`EffectCompleted`续接挂在原Effect／续接作用域内，不会自动成为外层收尾窗口的新按钮；收尾登记及恢复还要求正式来源和触发收据。这些是待补的通用合同，不表示现成Lua已经能够反复启用同一按钮。

**10月19日用户确认采用可重复来源入口。** 通用层在本次收尾窗口内保留同一来源入口，每次点击创建一次独立兑换执行记录；完成后释放当前执行并返回U15，按最新库存刷新该入口。Lua声明重复资格并生成一次兑换正文，不负责完成后给外层窗口重新挂自己，也不自动进入下一次兑换。

来源入口身份关联本次收尾窗口、玩家、来源实例和能力；每次执行另有递增序号、请求身份、费用及结果收据。已受理请求的重复提交或重连沿用同次执行，不能因为入口仍在就多扣一次费用；下一次主动点击才产生新记录。执行中同一入口不可再次受理，其他收尾条目的穿插发生在本次兑换完成后。单次收尾条目继续维持原合同，不能一并恢复可用。

暂时不足时禁用入口，其他效果补足后恢复可用；放弃本次付款只结束本次执行并返回U15，不自动再弹，来源资格仍在时可以稍后主动重试。玩家按通用规则结束收尾时，可重复入口本身不构成未履行义务；仍须等当前兑换和必做义务完成，关闭窗口后不再受理。不能清空历史使用记录、递归触发`PlayerCleanupStarted`或伪造外层节点ID。此为L09已定实现方向，尚未实装；D01／D02与T09共用，不新增企业家专用UI。

### 替换内核的阶段与供应重查

此为通用影响力替换改动，适用于普通标记、帮派和其他合法主体。替换仍是一个有稳定身份的操作，企业家Lua继续调用替换原语，不自行拆成失去关联的Remove＋Place。

| 阶段 | 目标合同与页面 |
| --- | --- |
| 选择目标 | U12按替换目标规则选影响力，保存原位置及操作身份；不要求替换开始时供应已经有替入物 |
| 移除与响应 | 真实移除所选实例，生成带替换原因的离场事实；结算必须在后续放置前完成的响应。保罗在这里通过U12补放非帮派，多萝西／T09通过U22决定原标记去向；仍沿用各自权限、旁路及依赖合同 |
| 去向提交 | 将离场实例实际返还其供应或存入选定合法载体。未决去向不能被当作可用供应；后续放置确实依赖它时必须等待，不能把“将要返还”直接计入库存 |
| 重新查询并放置 | 到本阶段重新查询供应、所有者、类型限制和原目标格合法性，再走通用放置交互。若原帮派已回供应，它与其他合法供应一样参加候选，不预留给本次替换、不强制选它；被收容则不在供应中。真正无可放实例时按替入未发生处理 |
| 完成替换 | 记录实际结果为完整替换或仅移除，并保留相关子步骤和实例收据。最终结果通知不能再次执行已在移除阶段结算的补放／收容／指令响应；按同一离场身份去重。页面、日志与恢复均沿用该操作的事实 |

源码核对：`ExecutePlace`本身已经从当前状态查供应；问题并非单纯“缓存未刷新”。`ExecuteItemDeparture(replace=true)`当前在`Depart`后立即创建放置子节点，直到`placing_replacement`结束才发离场事件，再到`awaiting_destination`调用返供应。原物仍在暂存区时，实时查询也看不到它。因此L03须调整离场响应／去向与放置的先后，同时保留恢复和去重。现有成功替换只发`InfluenceReplaced`、不发`InfluenceRemoved`是当前事实；实施新阶段合同还需同步调整事件及订阅，不能只追加一个Removed后让两种通知各触发一次。

### 城市设施格子区域的源码核查与讨论方案（10月19日）

子区域结构继续以“城市设施格→顶层设施1张＋被覆盖设施子区（有序多张）”为讨论基础，子区属于固定格而非顶牌。顶牌沿现有主区展示；叠建时旧顶牌移入该格下层，新牌进入顶层。**10月19日用户确定建设查询采用下文的前置集合补充接口**：M13 Lua查询真实下层实例，补入本次已建设施集合，供唯一性和颜色判定使用。宣告等仍按规则只取顶层；详情查看层序、转移后顶牌变化、终局按格计数、存档和既有绑定按L05／已确认J-Q10补齐；覆盖仅改变位置，绑定及实例状态保持，宣告旋转状态随卡不随格。不要把补充集合直接写回旧地图展示列表：宣告页同格后写覆盖，城市／建设页取首项，递归摊平后结果可能不同。子区具体模板及层序编码仍待落实，已确定的集合补充方向不再列为待裁定问题。

### 建设页设施供应格的叠放显示（10月19日用户确定）

**当前尚未适配**：[FacilityBuildDialogView](../../Assets/YC/Presentation/FacilityBuildDialogView.cs)的公共供应分支按6个固定槽遍历，每槽通过`visibleItems.Items.Find`只取一个直接在槽内的实例，并只创建一份卡视图；它没有读取全层或计算叠放偏移。[FacilitySupplySlot预制体](../../Assets/YC/Presentation/Prefabs/Gameplay/Dialogs/FacilitySupplySlot.prefab)目前是控制子项尺寸的布局容器，[FacilityEffectCardView](../../Assets/YC/Presentation/FacilityEffectCardView.cs)按单张卡底框测量占位，没有多层包围范围。[区域模板](../../Assets/YC/Domain/Items/ZoneTemplateRegistry.cs)的供应槽仍为无序且容量1。因此只增加区域下层或向现有容器多放几张图，不等于已经实现本次叠放显示。本次结论来自源码与预制体文本核查，未运行实景验收。

供应格仍代表同一个真实供应槽，展示该槽按权威层序从顶到下的全部可见设施牌。顶牌为基准，最靠近顶牌的被盖牌编号n=1，其后n=2、3……；第n张被盖牌相对顶牌**上移125n个设施牌面贴图像素**，横向不偏移，各层保留相同牌面尺寸与比例。不是第n张相对前一张再上移125n，也不能把n=1当成顶牌。

| 牌在堆叠中的位置 | 相对顶牌的向上偏移（牌面贴图像素） |
| --- | --- |
| 顶牌 | 0 |
| 被盖住的第1张 | 125 |
| 被盖住的第2张 | 250 |
| 被盖住的第3张 | 375 |

125以单张设施牌面贴图区域为像素基准，按牌面实际渲染比例换算到UI局部坐标，随卡牌缩放同步变化；例如局部显示牌高为h、对应单张牌面贴图高为H时，偏移为`125*n*h/H`。使用图集时H取单张牌的裁片区域，不取整张图集高度，也不将125直接写成固定屏幕像素。步长作为明确的可序列化布局参数，值按本次用户要求为125，不通过运行时代码反复覆盖用户编辑的资产配置。

层内按最深层先绘制、顶牌最后绘制，使每张被盖牌露出自己的顶部名称条；显示整张原牌面并通过叠放遮挡，不另外复制名称文本、重画卡面或拉伸标题。槽内布局须支持重叠定位，现有单张卡的布局占位不能把各层重新排成普通纵向列表。格子的测量及滚动内容范围须包含上方伸出的所有名称条，并检查遮罩、相邻行及页面标题／按钮的遮挡；6个供应槽的身份和顺序保持，不将下层增加为独立供应格。

展示层序与选牌资格分开：全部可见层均可展示，不能只绘制合法建设候选；建设及其他按顶牌选择的操作仍只提交当前合法顶牌实例，下层露出名称不使其成为候选。查看下层沿只读详情合同，不提交选牌，也不能让名称条的点击穿透而误选顶牌或相邻槽。上插、下插、交换、取顶揭露及海德整批刷新后，从正式层序重算n和位置；不按实例ID、颜色或UI对象顺序猜顶牌，不累加旧偏移。恢复和页面重开读取同一层序。此显示规则适用于建设页的设施供应格，不自动套用到城市设施格或普通候选卡牌列表；揭露／补槽与单张／全层转移按下文已确认J-Q04实施。

本项作为L05及U20／U21的界面适配要求实施，沿用当前实际预制体的卡面与整体样式；本次只修订方案，未修改或重建界面资产。验收需覆盖单层、2／3／更多层、不同槽不同层数、上插及下插后层序、取顶后的重新编号、全层刷新、页面缩放和滚动边界，以及下层名称可读且不可作为建设候选。偏移与层序可做功能校验，名称露出、遮挡和可读性仍须在正常流程的实际建设页确认。

### 供应取顶、补槽与两条独立效果（用户已确认，J-Q04关闭）

供应A盖B时，取走A后直接露出B，B成为新的合法顶牌；只要槽内还有任何下层牌，就不从设施牌堆补牌。整槽为空才在原操作的补槽环节补牌；成对交换等完整转移不因中途暂时移出顶牌而插入一次补槽。牌堆不足沿现有补槽合同处理，不复制实例。普通选择并移动1张供应设施只移动所选顶牌及其自身状态，不带走整槽；明确整批刷新的海德4级仍处理所有层。

M09快速行动的上插与移牌堆底是同级独立Effect。上插完成后，第二个Effect重新查询当时合法的供应顶牌，允许选择刚放上去的图纸牌；也可选其他合法顶牌，不继承上插的颜色或图纸库存过滤。若把刚放上的A移至牌堆底，原B直接露出且不补牌；上插因无合法配对直接完成，仍执行第二个Effect。第二个Effect完成自己的转移及必要补槽后，后续查询再读取更新后的供应。

覆盖、取顶、揭露与补槽各保存真实实例、槽位、层序和操作收据；恢复不得再取下一张、重复补槽或重复移牌堆底。J-Q04规则已确定，剩余为L05的区域、转移、展示与恢复实现。

### 覆盖、提顶与卡牌自身宣告状态（用户已确认，J-Q10关闭）

被覆盖设施仍在城市面板中，只改变所在层；其绑定关系、已有状态和已注册能力保持，不因盖住或露出而额外注销、暂停、重注册或复位。按位置限制的操作仍依法只查询顶层：下层不能用于新的城市样式宣告，不能作为建设附属能源设施时选择的旧设施，不能作为城市化区域统计中的核心塔相邻设施，也不能作为M11回盒目标。已有样式关系及宣告历史不会因覆盖消失，保持绑定不等于绕过这些选取范围。

**本次规则书截图补充的候选边界**：建设城市化区域时，被覆盖旧设施不参与与核心塔十字相邻的设施计数；宣告城市样式、建设附属能源设施时，均不得选择被覆盖旧设施。这里“附属能源”限制的是实际选择目标，不能只改邻接计数而仍把下层牌列入选项。相关页面只提供符合原规则的当前顶牌，正式候选查询与提交复验使用同一层级限制；查看下层详情不授予选择资格。建设前补充的全层“已建设施集合”仅供相应的唯一性、颜色和计数查询，不能直接充当上述操作的目标池。等待期间目标被覆盖时，按通用候选刷新拒绝陈旧提交；7A提顶后重新查询候选，宣告仍同时检查该牌自身旋转状态，附属能源选择仍检查其原有条件。

“是否已经用于宣告”属于设施卡实例自身的旋转／宣告状态，不是设施格永久用过的标记。覆盖和提顶都保留同一实例及其旋转状态；M11回盒顶牌后，重新露出的牌未宣告／未旋转时可参与合法宣告，已宣告／已旋转则不能因为重新露出而重用。上层曾宣告不把状态传给下层；下层曾宣告也不把状态传给新建上层。提顶不重新建设、不触发入场、不重新计分；真正回盒的顶牌及其绑定退出沿正常退出合同处理，不连带退出留在该格的下层牌及其绑定。

当前[正式宣告执行器](../../Assets/YC/Domain/Effects/CityStyleDeclarationEffectExecutor.cs)保存`UsedFacilityIds`，[样式匹配器](../../Assets/YC/Domain/CityStyles/CityStylePatternMatcher.cs)在物品实例路径按该实例集合排除已用设施；这可作为现有宣告事实的接入依据。实施须让通用卡牌状态、宣告记录和旋转展示保持同一份权威事实，不另存会与历史漂移的“格已宣告”状态，也不将样式图案匹配的`RotationDegrees`误作设施牌的使用旋转。当前[宣告页](../../Assets/YC/Presentation/Workflows/CityStyleInteraction.cs)与[城市面板](../../Assets/YC/Presentation/BuildInfoPanel.cs)仍有按`UsedCityBoardSlotIndexes`／格号投影使用状态的路径，必须改为当前顶牌实例的状态投影；设施详情查看下层时也读取该牌自身状态。查询、合法候选、显示、提交复验及存档恢复须一致，不能仅改匹配器后宣称提顶宣告已接通。

**联机投影与一致性校验也须同步**：[GameStateView](../../Assets/YC/Domain/State/GameStateView.cs)仍将历史`UsedCityBoardSlotIndexes`并集生成`CityStyleUsedSlotIndexes`，`HasConsistentCityStyleDeclarations`也要求两者一致。不能只改页面或本地匹配器：为当前设施实例的宣告／旋转状态提供正式可见投影，将当前顶牌显示状态与历史宣告记录分开。历史格号继续保留为原宣告证据，不为显示而改写历史；必要时由当前格中实例与已宣告实例集合求出展示格。序列化、客户端验证、恢复与旧档兼容同步维护该合同，避免本地可宣告但远端仍显示已用或一致性检查失败。

**覆盖转移与真实离场必须分开（本轮源码核查）**：[ItemTransferService.Apply](../../Assets/YC/Domain/Items/ItemTransferService.cs)目前只要设施目标区不再是`core.zone.city_facility_cell`，就把该设施的活动角色绑定设为无效。因此直接移动旧牌到新下层子区会违反已经确认的绑定保留规则。通用转移须识别“同一玩家城市面板内，主区与合法被覆盖设施子区之间的层级移动”，保持控制者、既有绑定及状态；实际离开城市面板或控制关系变化仍沿原有退出合同，不把所有非主区目的地一律放行。已绑定状态保留与能否新建绑定分别遵从各自规则，不因此开放对子区任意新绑定。

同一区别也适用于提顶：把旧顶牌压入同格下层是叠建的一部分，不能误判为回盒／离场后立即把它又提回。覆盖旧牌与新牌落位作为同次分层变更保持一致；真正取走顶牌离开该格且不属于该覆盖步骤时，才按相应退出流程提顶。M11实际回盒所选牌时，保留原退出及所选牌绑定处理，下层牌的绑定不会连带清除；提顶本身不补建、重入场或重注册。存档与恢复保留这一操作身份，不能只凭“主区暂空”推断操作类型。

### 多核心塔数量与逐塔邻接求和（用户已确认）

M02／M03／M04读取实际结算玩家城市面板上的全部核心指挥塔实例，包含被覆盖的塔；图纸、玩家供应或回盒中的塔不计。每个实例只计一次，同格有多层也不丢失真实塔数。本人入场与对手入场分别读取各自城市面板。

基础蓝色城市化区域按每座核心塔分别统计四向相邻格中的合法顶层设施，然后将各塔的数量相加：`相邻计数 = Σ每座核心塔的相邻设施数`，金券为该计数的4倍。核心塔集合同样包含仍在城市面板上的被覆盖塔，以该塔所在设施格确定位置；相邻格只计顶层，不枚举被覆盖的相邻设施。同一顶层设施若同时邻接两座核心塔，应分别贡献1次，不能在所有核心塔之间按设施ID去重。n座塔最多累计4n次相邻计数；边界、空格及原本的合法性限制照常适用。

通用Lua投影需提供每座实际核心塔的位置及邻接集合，或等价的逐塔计数／来源明细。当前[基础城市化脚本](../../Assets/StreamingAssets/Content/core/lua/facilities/gain_gold_per_core_adjacent_facility.lua)只按每个实例的布尔`adjacentToCore`累加，无法表达同一设施对多座塔的重复贡献；实施改为逐塔查询并求和，不能只把固定第7格的布尔判断扩成“邻接任意核心塔”。全层塔数、顶层邻接对象及每塔贡献分别保存或可重建，供双方入场、日志与恢复使用，不给马丁增加计数选择页面。

### 建设前补充已建设施集合（用户确定方向）

建设前暴露纯集合事件／查询接口，输入本次建设上下文和基础已建设施实例集合，允许有效内容来源补充一个实例集合。M13处理器读取本人城市设施格下的真实被覆盖牌并返回它们，内核合并后供本次建设使用。它补充的是**判定依据中的已建设施**，不把下层牌加到“待建设卡牌候选”中，也不移动或复制这些牌。事件名、候选种类和字段名在此为待设计合同，不宣称已经存在新Lua API。

现有[LuaEffectEventDispatcher](../../Assets/YC/Infrastructure/Lua/LuaEffectEventDispatcher.cs)已支持`CandidateSetBuilding`的纯集合补丁，[CandidateSetResolver](../../Assets/YC/Domain/Interactions/CandidateSetResolver.cs)已有按来源排序、合法范围校验与实例去重，可以沿用这一机制。当前[FacilityBuildCandidateQuery](../../Assets/YC/Domain/Facilities/FacilityBuildCandidateQuery.cs)的`facility.build.card`是“选择哪张牌建设”，**不能一概表述成事件总在唯一性和费用筛选之后**；实际分两条路径：

| 路径 | 当前顺序及可露希尔存牌的校验 |
| --- | --- |
| 普通建设及正常建设页面流程 | `RequireBuildable`默认false，先从公共来源和有效角色牌下设施生成来源池，经事件补充最终候选，再由[BuildFacilityOptionQueryService](../../Assets/YC/Application/Gameplay/BuildFacilityOptionQueryService.cs)逐张查询唯一性、合法槽位和支付资格。普通入口使用`ValidateFacility`，Effect建设页面也显式判断唯一性；补进来源列表不等于已经可建 |
| 要求只列可建设牌的选择流程 | `RequireBuildable=true`时，公共牌与活动角色牌下设施一并经过唯一性、空格和费用筛选，通过后才进入`CandidatePoolIds`；事件只能在该池内补充。不是只检查公共供应，再让Lua随意加存牌 |

[可露希尔计谋脚本](../../Assets/StreamingAssets/Content/core/lua/characters/operator.closure.tactic.lua)先将`candidatePoolIds`建立为允许集合，仅把本人`orders`区且已在池内的实例交给`Candidate.Add`；公共补丁解析器还会拒绝池外ID。正式建设仍经[BuildFacilityService](../../Assets/YC/Domain/Facilities/BuildFacilityService.cs)的唯一性、支付与落位校验，陈旧候选不能绕过实际状态。因此本次建设前已建集合补充要接在**各路径首次消费已建事实的位置之前**：普通路径的逐张合法性／报价查询，以及`RequireBuildable=true`路径的池内预筛选都使用它。该补充集合用途与原“待建卡牌候选”不同，不能混入原候选输出；不是因为原事件漏查可露希尔的唯一性才增加此接口。

| 环节 | 实装合同 |
| --- | --- |
| 输入与返回 | 输入执行玩家、当前状态版本、建设来源／请求身份、基础已建实例集合；处理器返回补充实例ID集合及来源。查询可没有正在执行的Effect节点，不要求预览为了查集合先创建效果 |
| M13查询 | 经只读物品／区域投影读取本人城市格的被覆盖设施实例，保留城市格及层次来源；不按卡名制造设施，也不把图纸、公共供应或他人城市设施视作本人已建 |
| 合并与授权 | 按真实实例ID并集合并，相同实例只计一次；同名不同实例不按定义ID误合并。校验实例存在、设施类型、本人城市归属及声明来源资格；该补充入口只增加合法已建事实，不删基础事实，不修改物品位置 |
| 建设判定 | 默认集合加补充集合后，统一交给唯一设施判定、已建颜色统计及依赖这些事实的费用计算。下层参与已建统计不意味着它参与顶层邻接、空格或叠建分数比较；这些仍使用各自的顶层／位置查询 |
| 预览与正式提交 | 建设候选、建设页报价、正常建设和Effect内建设、付款前复验使用同一集合查询；`ReadOnlyQuery`缓存包含集合结果并随状态版本失效。不能只在正式付款前补一次，导致页面提前误判不能建或报价不一致 |
| 范围与恢复 | 纯查询不发资源、不收费、不激活入场效果；正式提交保存适用来源及集合依据，恢复沿用已提交费用和落位收据。新查询按当前状态重算，旧版本请求复验；不把查询结果存成另一套永久已建库存 |

这个接口解决建设时下层牌参与唯一性／颜色查询的问题。马丁3B终局按格数牌、层次详情、供应整层转移等不处于建设前，仍通过同一下层实例读取能力按各自范围查询，不能为了取牌数伪发建设事件。现有正常建设路径中直接读取`BuiltFacilityIds`的分支也须统一接入补充结果，不能仅改带`ReadOnlyQuery`的路径。区域模板、真实移动、卡上／区域只读投影和企业家来源授权仍是通用前置。

### M13叠建的候选与入场前子效果（10月19日最小改动建议）

**用户最新明确：落位后event的分发与响应挂接放在原入场Effect挂接之前。** 顺序为“完成落位与原建设计分→分发落位后event并挂上响应子Effect→挂原入场子Effect→按同级顺序结算”。事件响应只需完成装配，不需要先执行完移除才挂入场。方案据此收敛为：**扩展现有选格候选，在同一次建设落位后、设施入场子效果之前执行必做移除**。替换上一版“落位前另开可放弃条件并取得授权”的建议；M13不增加建设准备插入窗口，也不再发起指定设施的第二次Build。接口及接线仍待实装，本节描述方案，不声称现有Lua已经可以注入该节点。

**实际父子关系与时点**：[FacilityBuildEffectExecutor.ExecuteEntity](../../Assets/YC/Domain/Effects/FacilityEntryEffectExecutor.cs)落位后加建设分、消费适用的主行动次数，并以`AddChild(FacilityEntryEffectSpecFactory.Activate(...))`挂入场子效果。按用户最新明确，**移除与原入场在同一轮装配中直接挂成同级有序子Effect，移除在前、入场在后**；前者及必要响应结清后才执行后者，不需要等移除完成再创建入场节点，也不把入场放在移除的完成回调或子树中。上一版要求分阶段挂入场的建议撤销。

**同级调度源码核查**：[EffectStepResult.AddChildren／AppendChildEffects](../../Assets/YC/Domain/Effects/EffectKernel.cs)按列表顺序保存子节点；[EffectRuntimeState.IsChildSchedulingEligible](../../Assets/YC/Domain/State/EffectRuntimeState.cs)要求普通前序节点进入调度终态，`ActivateNextChild`据此逐项启用。子效果、普通事件响应及完成续接形成的未决blocker会阻止前序节点结束，所以已挂入树不等于开始执行。此处使用普通有序子节点，不使用`AddIndependentChildren`。必要旁路依赖沿既有依赖合同处理，不能把全部无关旁路都改成强制等待。现有[有序兄弟恢复测试](../../Assets/YC/Tests/EditMode/ExpansionRules/BlockedEffectResumeTests.cs)及[默认顺序测试](../../Assets/YC/Tests/EditMode/ExpansionRules/IndependentEffectGroupTests.cs)已有对应断言；本次只核对源码，未运行测试。

**事件装配的具体缺口**：当前`ApplyStepResult`先追加`ChildEffects`，再分发`Events`，事件响应通常追加到同一所属节点的末尾。因此不能仅写`AddEvent(入场前事件)`再写`AddChild(入场)`，就认定实际列表是移除在前。本次通用建设接线须在同一装配过程中**先分发落位后event**，正式登记其响应子式及分发收据，**再挂原入场子式**，保存到同一Build的有序子列表；这是装配顺序，不是等待移除结算后才挂入场。保留事件来源、权限、稳定身份和防重，不在企业家Lua里直接修改运行树，也不为M13全局倒置所有已有事件和子节点的处理顺序。具体接线合同待实施，现成的顺序调度无需为此另造一套。

上一版以“落位后移除可能使用入场新获得的影响力”为由排除此接法不准确：**只要移除先于入场子树，该问题就不存在**。不过此时新旧设施已经分层落位、建设分已经入账，移除触发的响应会看到这个状态；它与“移除成功后才落位”在时点上有区别。本建议按最新讨论采用前者，并把叠建选择后的移除作为必须履行的效果，不能在已经取得建设结果后再选择放弃支付。

**UI复用依据**：[FacilityBuildPlacementUiCoordinator](../../Assets/YC/Presentation/FacilityBuildPlacementUiCoordinator.cs)把正式候选格传给建设页；[FacilityBuildDialogView](../../Assets/YC/Presentation/FacilityBuildDialogView.cs)按合法格列表高亮与控制点击，没有在显示层另行禁止已占格。旧顶牌仍显示在格内，可复用原格按钮和确认入口；移除使用U12默认影响力选择。候选来源、分数及额外移除说明由内容／请求提供，必要时只补通用动态说明接线，不新增M13页面、固定按钮或覆盖预制体。实际显示仍须验收。

| 环节 | 最小接入及页面合同 |
| --- | --- |
| 槽位候选 | 复用`CandidateSetBuilding`纯补丁机制，补建设槽位候选种类；输入待建真实实例／定义、玩家、来源、各格当前顶牌和状态版本，默认合法空格。有效M13来源可加入新分数严格更高且有可实际移除己方影响力的旧格；不得加入池外或他人城市格。新候选种类及字段待定义，不把现有交互ID直接当作已实现的候选合同 |
| 统一资格 | 正常、图纸、核心塔／枢纽、嵌套及免费建设的预筛选、页面报价、付款前复验、正式选格与落位提交共用查询，替换“必须有空格”的硬限制。`RequireBuildable=true`不能先清空满板牌池。来源、唯一性及原建设费用继续校验；纯查询不移动物品、不支付影响力 |

| 执行与失败 | 选格前可以选择普通空格；正式确认叠建后，移除不可任意放弃，必须核验实际移除1枚。付款准备响应导致无合法方案时，提交付款前拒绝并刷新；已付款待放置时继续按原建设状态复验。若提交后意外失去移除目标，保留建设、分层、计分和待移除记录，按通用故障／恢复处理，不能将空目标完成冒充履约后继续入场。现有顺序调度把`Completed`和`Failed`均视为普通终态；顺序不是成功条件，不能返回普通`Failed`就以为后位必被阻止。必做义务失效须在通用资格／故障合同中处理，`Faulted`不会解锁后位，不为此把入场移回移除的结果续接。该处理是实施验收项，不宣称当前已具备完整协议 |
| 恢复 | 保存建设身份、叠建事实、事件分发收据、同级子节点身份及顺序、移除与入场进度；恢复读取已挂节点，不重新装配入场或重复付款、补供应、移除、计分。移除及必要响应未结清时，后位入场保持已挂但不可执行；移除最后1枚成功后不再要求仍有另一枚 |

这条接法省去新建设插入窗口、可放弃条件返回选格的分支及落位前条件授权传递。内核仍须补槽位候选、企业家有效来源、前置响应与入场的有序装配接线和真实分层转移；不是只靠Lua调整现有入场脚本顺序即可完成。现有`FacilityEntryEffectExecutor`要求设施有入场能力并已落位，因此不能仅订阅其内部激活事件，否则没有入场效果的设施会漏掉移除。

“补充已建设施集合”仍独立负责下层参与唯一性／颜色／费用的事实查询。待建牌候选、目的地格候选与已建事实是不同集合；M13对手入场仍在本人全部入场效果完成后选择对手，不因这次新增的入场前移除提前触发。

**建设图纸颜色匹配的候选过滤（用户明确，覆盖全部相关选择）**：M05／1A交换、M06／1B下插、M09／5A上插，以及DIY声明同类颜色匹配的操作，共用按真实实例构造的配对候选。先查询本人M13图纸区中本次合法可转移的牌，再过滤公共供应顶牌：必须同时满足非彩色、本次来源／转移资格，以及图纸中至少存在1张同色可用实例，才作为本次供应选牌候选。颜色按有效内容定义／规则读取，不按图片、卡名或初始配方推断库存；供应下层、已离开图纸或本次不可转移的牌均不能充数。例如图纸已无红牌，所有红色供应牌都不进入这次候选；不让玩家选完红牌才发现无牌可配。如有按颜色分组或直接选择颜色的选项，同样只提供存在合法配对的颜色，不新增一层颜色选择页面。

**M01付款页面衔接（核查补充）**：建设页选定设施及资源付款方式后，创建本次付款准备，再从付款前结算目录选择M01、进入替代分配、返回原付款确认；展示实际所需的剩余资源与新增金券，最终提交才整笔扣除。M01分配页面只允许从尚需支付的源岩／碎片／异铁中选1个，已无可替代基础资源时不提供新的替代份额；放弃本来源则不替代。异客入口独立，仍按其自己的合法库存及至多2份分配。不能要求先付得起未替代的全部资源才允许进入替代准备；结构合法性、替代入口资格和最终支付能力分开校验，普通建设与Effect建设均需覆盖。已有[付款准备服务](../../Assets/YC/Domain/Effects/ResourcePaymentPreparationService.cs)及[页面工作流](../../Assets/YC/Presentation/Workflows/ActionPaymentPreparation.cs)可复用，不新增M01专用付款页面。

替代尚未提交时，取消本次建设付款准备按既有合同清理草稿并回到选牌；重新选设施或支付方式须重建对应报价，不沿用上一张牌的替代份额。已发生的独立结算效果遵从自身收据，不能随草稿一并回滚；M01的替代分配本身不得提前扣券。等待及恢复复用同一准备身份、来源与分配记录，最终付款前复验持牌资格、资源与金券，不能重复扣款。两个来源可先后进入各自的分配交互；返回同一付款准备后分别展示并保留各来源的分配、M01所需1金券和异客标记费用。修改／撤销一个来源只改变它的草稿，不清空另一来源；重新分配需复验合计上限。M01已分配1份时同一来源的再次操作只可编辑这1份，不能再追加1份；每次建设的额度绑定建设与付款身份，重开窗口、恢复或重复提交不重置，独立的下一次建设才重新获得该额度。
