# 架构落地计划

## 1. 总体方向

当前 Unity 项目 `F:\游城拓荒模拟器` 仍接近空工程，因此架构落地应从目录、程序集和纯 C# 规则核心开始，而不是先搭 UI 场景。目标是让规则层、应用层、表现层、数据层和基础设施边界在第一轮开发中就清楚。

## 2. Unity 项目结构

建议后续在 Unity 项目中形成以下结构：

```text
Assets/
  Scripts/
    Domain/
    Application/
    Presentation/
    Infrastructure/
    Tests/
  Data/
    Maps/

  Art/
    Board/
    Cards/
    Tokens/
    UI/
  Scenes/
    Bootstrap.unity
    Game.unity
    Debug.unity
```

## 3. 程序集拆分

### Domain

职责：纯规则核心，不依赖 `UnityEngine`。

包含：

- `GameState`
- `PlayerState`
- `BoardState`
- `GamePhase`
- `IGameCommand`
- `CommandValidator`
- `CommandResolver`
- `GameEvent`
- `PendingChoice`
- 路径、费用、区控、计分服务

完成标准：Domain 可以被 Unity Test Framework 在 EditMode 下直接测试，不需要加载场景。

### Application

职责：组织一局游戏的生命周期。

包含：

- `GameSession`
- 新游戏创建。
- 数据库加载。
- 命令提交入口。
- 规则事件派发。
- 日志、存档、回放协调。

完成标准：UI、Debug 工具、未来 AI 都通过同一个 `GameSession.Submit(command)` 入口操作游戏。

### Presentation

职责：Unity 表现和交互。

包含：

- 地图视图。
- 卡牌视图。
- 玩家资源面板。
- 行动选择面板。
- 结算预览面板。
- 日志与回放面板。

完成标准：Presentation 不直接修改 `GameState`，只读取视图模型并提交命令。

### Infrastructure

职责：非玩法核心能力。

包含：

- JSON 或 ScriptableObject 加载。
- 存档读写。
- 回放序列化。
- 资源包加载。
- Debug 工具。

完成标准：基础设施替换不影响 Domain 规则测试。

### Data

职责：静态规则定义和资产引用。

包含：

- 地图定义。
- 资源点、航道、区块定义。
- 角色牌、事件牌、设施牌、城市样式牌定义。
- 效果定义。
- 计分定义。
- 图片和图标引用。

完成标准：地图和卡牌数据不硬编码在 UI 组件里。

### Tests

职责：规则正确性和回归保障。

包含：

- 单元测试。
- 状态机测试。
- 命令结算测试。
- 回放测试。
- 随机合法命令模拟。

完成标准：每个新增规则能力至少有一个成功场景和一个失败场景测试。

## 4. 命令流水线

所有玩家操作走同一条路径：

1. UI、Debug 工具或 AI 创建命令。
2. `GameSession` 接收命令。
3. `CommandValidator` 校验当前阶段、行动权、资源、路径、目标、槽位和特殊限制。
4. 校验失败时返回明确错误，不修改状态。
5. 校验成功后由 `CommandResolver` 修改状态。
6. resolver 生成 `GameEvent`。
7. `GameSession` 记录命令与事件日志。
8. Presentation 根据新状态刷新显示和播放动画。

## 5. 服务边界

### BoardGraphService

提供地图图查询：相邻节点、航道、区块、影响力槽和城市停靠点。

### RouteCostService

提供路径枚举和费用计算：探索路费、采集路费、航道支付对象和采集阶段已付航道记录。

### RegionControlService

提供区控计算：影响力统计、移动城市计 2 影响力、控制者判断、并列处理和区块分数。

### EffectService

提供效果执行：根据触发点、条件、费用和操作列表执行角色牌、事件、设施和城市样式效果。

### ScoringService

提供最终计分：区块控制、剩余资源、设施、城市样式、平局判定和分数明细。

## 6. 实施顺序

1. 建立 Domain 基础类型和枚举。
2. 建立地图、玩家、资源、影响力和阶段状态。
3. 建立 `GameSession` 与命令流水线。
4. 接入地图图服务和路费服务。
5. 实现 Setup 到 Cleanup 的状态机。
6. 实现主要行动和采集。
7. 接入轻量效果系统。
8. 实现最终计分。
9. 补充日志、回放和测试。
10. 再开始完整 Presentation UI。

## 7. 不做的事

- 不把规则写在按钮点击事件里。
- 不让 Unity 场景对象成为规则状态来源。
- 不为了短期演示跳过命令校验和日志。
- 不在 MVP 中引入联网同步和企业扩展版复杂度。
