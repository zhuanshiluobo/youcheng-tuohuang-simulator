# 主界面边框补丁 v3.5

## 这次解决什么

本补丁将主界面外框、底栏框与结算槽框改为更细、更低对比的完整边线，并提供更高分辨率的原生重绘资源。底栏底图另行清理，避免只换边框后仍露出旧图中的白色角线。

新框以 1.25 个逻辑单位的主线和 0.65 个逻辑单位的弱内线构成；角部仅提高亮度，不另叠粗块。参考坐标中从外缘到最内侧边线的整体占宽约 4.825 个逻辑单位，大片中心区域保持透明。

按钮、文字、地图、城市板与模块内容的布局继续由原 UI 控制，原有模块边框和按钮素材继续保留。

## 诊断依据

已检查用户截图与旧版素材生成源码，能确认以下事实：

- 旧 `outer-frame` 的 PNG 为 1024×576；若直接整张拉伸到 1920×1080，像素和边线会一起放大。旧资源即便带 SVG 外壳，内部边框仍取样自位图，并非可无限放大的纯向量线条。
- 旧 `bottom-frame` 原本已是 1920×96，但源图包含 9 px 宽侧边和 6 px 角部描边。因此，单纯提高分辨率不能解决边线本身过粗的问题。
- 旧 `bottom-bar` 底图左下包含白色角线残留。底图与新框叠加时仍可能形成重复边线，因此本次连同底图一起替换。
- 截图左右下角出现粗重的亮色转角，底边存在多条平行线与装饰挤在一起的情况。

可能参与问题的还有整图拉伸、切片参数、导入像素密度、UI 缩放和多层边框重叠。用户引擎的源代码与导入设置未提供，不能仅凭截图断言是哪一项配置出错。旧演示渲染器曾主动缩小目标切片边距；仅照搬其源图而未复现目标边距，也可能产生不同的视觉厚度。

本补丁提供可直接检查的新素材与明确的源／目标尺寸约定，实际游戏中的最终结果仍需在接入后确认。

## 分层与替换映射

| 既有资源 ID | 本次作用 | 中心透明度 |
| --- | --- | --- |
| `outer-frame` | 主界面外框，替换旧外框 | 完全透明 |
| `bottom-frame` | 底栏外框，替换旧底栏框 | 完全透明 |
| `chain-slot-frame` | 结算槽框，替换旧槽框 | 完全透明 |
| `bottom-bar` | 指向新 `bottom-bar-clean` 底图 | 完全不透明 |

保留上述 ID 有利于沿用已有资源引用。文件的实际位置、各分辨率路径与切片值以素材清单和 `integration/catalog-overrides.json` 为准；安装到既有素材目录后，新文件集中在 `frame-assets-v3.5/`。

独立资源清单为 `assets/frame-assets.json`。整图命名为 `assets/{名称}.svg`、`assets/{名称}.png` 和 `assets/{名称}@2x.png`；其中底栏底图名称为 `bottom-bar-clean`，其余三个名称与资源 ID 相同。

`integration/catalog-overrides.json` 是安装用的 2× 映射：其 `path` 指向 `@2x.png`，`viewBox` 使用该 PNG 的实际像素尺寸，`slices` 分别为主框 `[48,48,48,48]`、底栏和结算槽 `[24,24,24,24]`；`targetSlices` 则仍为主框 `[24,24,24,24]`、底栏和结算槽 `[12,12,12,12]`。不要将独立资源清单的 1× 默认尺寸与安装清单的 2× 图像混用。

建议按所属容器分层：背景 → 对应填充底图 → 对应透明边框 → 文字、图标与按钮。主界面外框只放一份；底栏和结算槽分别放自己的框。旧框必须移除或禁用，不要让新框覆盖旧框充当“修补层”。

底栏尽量位于主界面外框的内侧，避免将底栏外框和主外框对齐到同一条线。如果实际项目要求贴边，需在布局或遮罩中明确谁负责那条共享边，不应依靠加深描边掩盖接缝。

## 尺寸与九宫格参数

所有数组顺序均为 `[左, 上, 右, 下]`。

| 素材 | 1× PNG / SVG 逻辑尺寸 | 2× PNG 像素尺寸 | 1× 源切片 / 目标逻辑切片 | 2× 源切片 |
| --- | --- | --- | --- | --- |
| 主界面外框 | 1920×1080 | 3840×2160 | `[24,24,24,24]` | `[48,48,48,48]` |
| 底栏边框 | 1920×96 | 3840×192 | `[12,12,12,12]` | `[24,24,24,24]` |
| 结算槽边框 | 1024×64 | 2048×128 | `[12,12,12,12]` | `[24,24,24,24]` |
| 干净底栏底图 | 1920×96 | 3840×192 | 不需要保护边角 | 不需要保护边角 |

切片边距是需要保护的角区宽度，不是实际描边厚度。例如 `[24,24,24,24]` 表示保留 24 个逻辑单位的角区，不表示边线宽 24。

2× 图用于增加采样密度：源图切片以像素计，需乘以 2；输出到 UI 的角区仍保持原来的逻辑尺寸。不要将 `48` 源像素直接当成 `48` 个逻辑单位，也不要让引擎把 2× 图按两倍物理尺寸绘制。

以 2× 主界面外框绘制到 1920×1080 的逻辑 UI 为例，参数语义如下；这是引擎无关的配置示意，字段须对应到项目使用的组件：

```json
{
  "assetId": "outer-frame",
  "sourceSizePixels": [3840, 2160],
  "sourceSlicesPixels": [48, 48, 48, 48],
  "sourcePixelRatio": 2,
  "destinationRectLogical": [0, 0, 1920, 1080],
  "destinationSlicesLogical": [24, 24, 24, 24],
  "drawCenter": false
}
```

九宫格规则：四角保持目标逻辑尺寸；上、下边只在水平方向伸展；左、右边只在垂直方向伸展；透明中心不填充。不能将整张外框当普通图片非等比拉伸，否则边线厚度仍可能随目标宽高改变。参考代码见 `integration/nine_slice.mjs`。

调用参考函数时，将资源清单的 `viewBox` 传给 `sourceSize`，`slices` 传给 `sourceBorders`，`targetSlices` 传给 `targetBorders`，目标布局矩形传给 `targetRect`。此函数只计算切片几何；实际绘制由项目负责。旧演示中自动将边距缩小到固定 `target` 的 `nine()` 不会自动读取新增字段，需要显式适配后再使用新清单。

底栏底图独立铺满容器；它没有需要保护的描边或角部，因此无需和透明边框共用切片参数。结算槽原有底图仍可使用。

新 `bottom-bar` 的 `targetSlices` 为 `[0,0,0,0]`，`drawCenter` 为 `true`；应按普通图片铺满容器，不走透明边框的九宫格分支。

## 八片拆分版本

不支持九宫格的 UI 系统可使用四角与四边共八张贴图。它与整张边框表达同一外观，不是额外叠加的装饰。

目录为 `assets/parts/{边框名称}/`，文件名称包括 `top-left`、`top`、`top-right`、`left`、`right`、`bottom-left`、`bottom`、`bottom-right`；每片均有 SVG、PNG 和 `@2x.png`。

- 四个角固定在容器四角，保留逻辑尺寸。
- 上、下边放在两角之间，只调整宽度；左、右边放在两角之间，只调整高度。
- 2× 拆片同样按 2 像素对应 1 逻辑单位导入。
- 中心继续由独立底图和内容承担。

避免角与边之间产生小数坐标缝隙；在最终像素映射中保持接缝连续。不要同时启用九宫格整图和八片版本。

## 接入检查

在补丁根目录运行 `python tools/install_assets.py "完整主界面目录"` 会安装资源并合并目标 `asset-manifest.json` 的四个相关条目；运行 `python tools/install_assets.py "游戏素材目录" --assets-only` 则仅复制资源，供引擎手动导入。脚本会备份将被覆盖的文件，不修改项目源码或业务逻辑。

安装后仍需把上述源／目标切片约定接入实际渲染组件；如果组件忽略 `targetSlices`，仅换素材或合并清单并不能保证正确显示。

使用 1× 图时保持 1 像素对应 1 个基础逻辑单位；使用 2× 图时保持 2 像素对应 1 个基础逻辑单位，再由统一 UI 缩放处理全局比例。高 DPI 屏幕和引擎画布缩放可能继续改变最终物理像素数，因此须区分素材像素、UI 逻辑单位和屏幕像素。

检查四项即可：资源引用是否全部指向新版；底栏底图是否也已更换；旧边框是否仍在叠加；2× 导入密度与目标切片是否匹配。然后在实际运行窗口查看两个下角、底部中线和结算槽四角，确认没有错位、变粗或接缝。

本包预览来自已提供的主界面演示场景；新旧对比使用相同场景与布局，以便比较素材变化。未修改用户上传的运行截图，也未访问或改写用户的游戏项目。
